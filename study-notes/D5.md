# D5. Configure Pod admission and scheduling (limits, node affinity, etc.)

## 이 항목에서 공부할 것
- [ ] Deployment에 `k set resources`로 requests/limits를 넣고, `limits`만 쓰면 requests가 같은 값이 되어 Guaranteed가 됨을 `qosClass`로 확인한다
- [ ] LimitRange(`default`, `defaultRequest`, `min`, `max`)를 만들고, 기본값이 주입되는 것과 `max` 초과 Pod가 거부되는 것을 확인한다
- [ ] ResourceQuota(`requests.cpu`, `limits.memory`, `pods`)를 만들고, Deployment가 quota 때문에 일부만 뜨는 이유를 `k describe rs`/`k describe quota`로 찾는다
- [ ] 노드에 라벨(`k label node`)을 붙여 `nodeSelector`로 고정하고, taint(`k taint nodes`)에 맞는 `tolerations`를 Pod에 넣는다 (컨트롤 플레인 taint 포함)
- [ ] `nodeAffinity` required/preferred(weight), `podAntiAffinity`(topologyKey `kubernetes.io/hostname`)를 YAML로 쓴다
- [ ] `topologySpreadConstraints`를 쓰고, 컨트롤 플레인 taint 때문에 Pending이 되는 경우 `nodeTaintsPolicy: Honor`로 고친다
- [ ] PriorityClass를 만들고(`value`, `preemptionPolicy: Never`) Deployment에 `priorityClassName`으로 붙인다. "기존 최고 값보다 1 작게" 요구도 풀 수 있다
- [ ] Pending Pod의 `FailedScheduling` 이벤트 문장을 읽고 원인(taint/selector/Insufficient cpu/anti-affinity/spread)을 구분한다

## 개념 설명

### requests / limits 와 QoS
- 무엇: 컨테이너마다 `resources.requests`(스케줄러가 노드에 자리를 잡는 기준량)와 `resources.limits`(실행 중 넘을 수 없는 상한). CPU는 `100m`(=0.1코어), 메모리는 `64Mi`.
- 왜: 스케줄러는 **requests의 합**이 노드 `allocatable`을 넘지 않게 배치한다. limits는 실제 사용을 막는다(CPU는 느려지고 메모리는 초과 시 종료).
- 규칙 (직접 확인): `limits`만 쓰면 `requests`가 limits와 같은 값으로 채워진다. 그 결과 cpu/memory 모두 requests=limits면 `qosClass: Guaranteed`, requests만 있으면 `Burstable`, 둘 다 없으면 `BestEffort`.
- `k run`에는 `--requests/--limits`가 없다 (kubectl v1.34.1에서 `unknown flag`). Deployment는 `k set resources deploy <d> --requests=cpu=100m,memory=64Mi --limits=cpu=200m,memory=128Mi`, 단독 Pod는 YAML.
- 노드 용량 보기: `k describe node <n>`의 `Allocatable`(스케줄 가능한 총량)과 `Allocated resources`(이미 requests로 잡힌 양). q11처럼 "allocatable을 replicas로 나누라"는 문제는 이 두 값으로 계산한다.

### LimitRange
- 무엇: **네임스페이스 안 각 컨테이너/Pod의 requests/limits에 기본값과 허용 범위**를 정하는 객체. Pod 생성(admission) 시점에만 적용되고 이미 실행 중인 Pod는 건드리지 않는다 (문서).
- 핵심 필드: `limits[].type: Container`, `default`(기본 limits), `defaultRequest`(기본 requests), `min`, `max`, `maxLimitRequestRatio`.
- 직접 확인: LimitRange 이후 만든 Pod는 자원 설정이 없어도 requests 100m/64Mi, limits 200m/128Mi가 주입되고(`Burstable`, annotation `kubernetes.io/limit-ranger`), `max`(cpu 500m)를 넘는 limits의 Pod는 `maximum cpu usage per Container is 500m, but limit is 1`로 거부된다.
- 관계: Deployment가 거부되는 경우 Deployment 자체는 만들어지지만 **ReplicaSet이 Pod를 못 만든다** (`FailedCreate`). 아래 "자주 틀리는 점" 참고.

### ResourceQuota
- 무엇: **네임스페이스 전체의 합계 상한**. `requests.cpu`, `limits.memory`, `pods`, `count/deployments.apps` 등.
- 왜: 한 팀이 클러스터를 다 쓰지 못하게 하려고.
- 규칙 (직접 확인): quota에 `requests.cpu`/`limits.*`가 들어 있으면 그 네임스페이스에서 만드는 Pod는 해당 값을 **반드시 지정**해야 한다 (`must specify limits.cpu ...`). LimitRange의 기본값을 같이 두면 이 오류를 피할 수 있다.
- 초과하면: 새 Pod 생성이 `exceeded quota: rq, requested: requests.cpu=200m, used: requests.cpu=400m, limited: requests.cpu=500m`로 거부된다. 확인은 `k describe quota`(Used / Hard).

### Pod Security Admission (참고)
- 네임스페이스 라벨 `pod-security.kubernetes.io/enforce=baseline|restricted|privileged`로 위험한 Pod 설정을 admission에서 막는다. 직접 확인: `baseline`을 걸자 `privileged: true` Pod가 `violates PodSecurity "baseline:latest"`로 거부됐다. 이 하위 역량의 공식 문구("Pod admission")에 포함되는지는 확정할 수 없어 부수 항목으로만 둔다 (미확인).

### nodeSelector 와 노드 라벨
- 무엇: Pod가 **특정 라벨이 있는 노드에만** 가게 하는 가장 단순한 방법. `spec.nodeSelector: {disk: ssd}`.
- 노드에 라벨 달기: `k label node k8s-worker disk=ssd` (지우기 `disk-`). 기본 라벨 `kubernetes.io/hostname`, 컨트롤 플레인의 `node-role.kubernetes.io/control-plane`(값은 빈 문자열)을 바로 쓸 수 있다.
- `nodeSelector`와 `nodeAffinity`를 같이 쓰면 **둘 다** 만족해야 한다 (문서).
- `spec.nodeName`을 직접 쓰면 스케줄러를 건너뛴다. 직접 확인: `NoSchedule` taint가 있는 컨트롤 플레인에 `nodeName`으로 지정한 Pod가 그대로 Running이 됐다. 시험에서는 금지 조건이 있는 경우가 많다.

### Node affinity
- 무엇: nodeSelector의 확장판. `requiredDuringSchedulingIgnoredDuringExecution`(반드시), `preferredDuringSchedulingIgnoredDuringExecution`(가능하면, `weight` 1~100).
- 문법: `nodeSelectorTerms[].matchExpressions[]`에 `key`, `operator`(`In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`), `values`. terms는 OR, 한 term 안의 expressions는 AND (문서).
- 이름이 길어 보이지만 뜻은 "스케줄링할 때만 본다(IgnoredDuringExecution): 이미 뜬 Pod는 라벨이 바뀌어도 쫓겨나지 않는다".

### Pod affinity / anti-affinity
- 무엇: **다른 Pod가 어디에 있느냐**를 기준으로 배치. affinity는 같은 곳에 모이게, anti-affinity는 흩어지게.
- 핵심 필드: `labelSelector`(상대 Pod), `topologyKey`(같은 곳의 기준 라벨; 노드 단위면 `kubernetes.io/hostname`), 선택적으로 `namespaces`/`namespaceSelector`.
- 직접 확인: replicas 3, required anti-affinity(hostname)인 Deployment는 워커 2대에 1개씩 뜨고 세 번째는 Pending: `1 node(s) had untolerated taint {...control-plane}, 2 node(s) didn't match pod anti-affinity rules`.

### Taints 와 Tolerations
- taint는 **노드가 "이 조건을 참아 주는 Pod만 와라"** 하는 표시, toleration은 Pod가 "참아 줄게요"라는 선언. 비유: 노드는 "금연실" 팻말, Pod의 toleration은 "저는 괜찮습니다" 확인서. 단, toleration은 그 노드에 **가도 된다**는 허가이지 **가라**는 명령이 아니다 (가게 하려면 nodeSelector/affinity 추가).
- 형식 `key=value:effect`. effect는 `NoSchedule`(새 Pod 금지), `PreferNoSchedule`(되도록 피함), `NoExecute`(이미 있던 Pod도 쫓아냄; `tolerationSeconds`로 유예).
- 추가/삭제: `k taint nodes <n> team=blue:NoSchedule`, 지울 때는 끝에 `-`: `k taint nodes <n> team=blue:NoSchedule-`.
- toleration 문법: `{key, operator: Equal|Exists, value, effect}`. `Exists`는 value를 쓰지 않는다 (문서).
- 이 클러스터의 컨트롤 플레인에는 `node-role.kubernetes.io/control-plane:NoSchedule`이 있다. 이 taint가 있는 노드에서 일하려면 toleration이 필수다.

### Topology spread constraints
- 무엇: Pod를 노드/존 같은 **도메인에 고르게** 분산. `maxSkew`(도메인 간 개수 차이 허용치), `topologyKey`, `whenUnsatisfiable`(`DoNotSchedule` 또는 `ScheduleAnyway`), `labelSelector`.
- 함정 (직접 확인): 기본은 `nodeTaintsPolicy: Ignore`라서 **toleration이 없어 못 가는 컨트롤 플레인도 도메인에 센다.** replicas 4, maxSkew 1, hostname 키로 쓰면 2개만 뜨고 2개는 Pending(`2 node(s) didn't match pod topology spread constraints`). `nodeTaintsPolicy: Honor`를 `whenUnsatisfiable` 옆에 추가하면 워커 2대에 2개씩 뜬다 (q68의 핵심).

### PriorityClass 와 preemption
- 무엇: Pod의 **우선순위 숫자**. 클러스터 자원이 부족할 때 높은 우선순위 Pod가 낮은 Pod를 밀어내고(preemption) 먼저 스케줄된다. Pod는 `spec.priorityClassName`으로 클래스를 지정하고, 서버가 `spec.priority` 숫자를 채운다.
- 핵심 필드: `value`(사용자 정의 최대 1,000,000,000: 직접 확인, 그보다 크면 `maximum allowed value of a user defined priority is 1000000000`), `globalDefault`(클러스터에 하나만, 지정 안 된 Pod의 기본), `preemptionPolicy: PreemptLowerPriority`(기본) 또는 `Never`, `description`.
- 없는 클래스 이름을 쓰면 Pod 자체가 거부된다 (`no PriorityClass with name ... was found`, 확인함). 클래스를 먼저 만든다.
- 기본으로 `system-cluster-critical`(2000000000), `system-node-critical`(2000001000)이 있다. "사용자 정의 최고값"을 셀 때는 이 둘을 뺀다.

## 예시

**상황 1: Deployment `app`에 requests/limits를 넣고 QoS를 본다.**
```bash
k create deploy app --image=busybox:1.37 -- sleep 3600
k set resources deploy app --limits=cpu=200m,memory=100Mi          # requests는 자동으로 같은 값
k get pod -l app=app -o jsonpath='{.items[0].spec.containers[0].resources}{" "}{.items[0].status.qosClass}{"\n"}'
k set resources deploy app --requests=cpu=50m --limits=cpu=200m,memory=100Mi
```
기대 결과: `{"limits":{"cpu":"200m","memory":"100Mi"},"requests":{"cpu":"200m","memory":"100Mi"}} Guaranteed`. 마지막 명령 뒤 `requests`는 `{"cpu":"50m"}`만 남는다 (memory request 없음 -> Burstable).

**상황 2: 네임스페이스에 LimitRange, 그리고 초과 Pod 거부.**
```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr
spec:
  limits:
  - type: Container
    default:        {cpu: 200m, memory: 128Mi}
    defaultRequest: {cpu: 100m, memory: 64Mi}
    min:            {cpu: 50m,  memory: 32Mi}
    max:            {cpu: 500m, memory: 256Mi}
```
```bash
k apply -f lr.yaml; k run plain --image=busybox:1.37 --restart=Never -- sleep 3600
k get pod plain -o jsonpath='{.spec.containers[0].resources}{"\n"}'     # 기본값이 주입됨
k describe limitrange lr
```
`limits: {cpu: "1", memory: 512Mi}`인 Pod는 `forbidden: [maximum cpu usage per Container is 500m, but limit is 1, maximum memory usage per Container is 256Mi, but limit is 512Mi]`.

**상황 3: ResourceQuota를 만들고 Deployment가 일부만 뜨는 것을 해석한다.**
```bash
k create quota rq --hard=pods=4,requests.cpu=500m,requests.memory=512Mi,limits.cpu=1,limits.memory=1Gi
k create deploy qd --image=busybox:1.37 --replicas=3 -- sleep 3600
k set resources deploy qd --requests=cpu=200m,memory=64Mi --limits=cpu=250m,memory=128Mi
k get deploy qd; k describe quota rq; k describe rs -l app=qd | grep "exceeded quota"
```
기대 결과: `qd 2/3`, Used `requests.cpu 400m / 500m`, 이벤트 `exceeded quota: rq, requested: requests.cpu=200m, used: requests.cpu=400m, limited: requests.cpu=500m`. 해결은 Deployment의 requests를 줄이거나(예: 150m -> 3x150=450m) replicas를 줄이는 것 (문제가 허용하는 쪽).

**상황 4: 노드 라벨 + nodeSelector, 컨트롤 플레인 전용 배치(라벨 + toleration).**
```bash
k label node k8s-worker disk=ssd
k create deploy fast --image=busybox:1.37 -- sleep 3600
k patch deploy fast --type=merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"disk":"ssd"}}}}}'
k create deploy cp-mon --image=busybox:1.37 -- sleep 3600
k patch deploy cp-mon --type=merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"node-role.kubernetes.io/control-plane":""},"tolerations":[{"key":"node-role.kubernetes.io/control-plane","operator":"Exists","effect":"NoSchedule"}]}}}}'
k get pod -o wide
```
기대 결과: `fast`는 `k8s-worker`, `cp-mon`은 `k8s-control-plane`에서 Running. toleration 없이 컨트롤 플레인 `nodeSelector`만 주면 Pending: `1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match Pod's node affinity/selector`. 라벨은 끝나면 `k label node k8s-worker disk-`.

**상황 5: taint 추가 형식 확인(노드를 바꾸지 않고).**
```bash
k taint nodes k8s-worker2 team=blue:NoSchedule --dry-run=server -o yaml | grep -A4 taints
k get nodes -o custom-columns=N:.metadata.name,T:.spec.taints          # 실제로는 안 바뀜
k describe nodes | grep -E '^Name:|^Taints:'                           # NoSchedule taint가 있는 노드 찾기
```
`--dry-run=server`여도 `node/k8s-worker2 tainted`라고 출력하지만 노드는 바뀌지 않는다 (확인함). 실제 적용은 `--dry-run` 없이, 제거는 값 뒤에 `-`.

**상황 6: nodeAffinity(required + preferred) 와 podAntiAffinity.**
```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - {key: tier, operator: In, values: ["app"]}
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - {key: zone, operator: In, values: ["a"]}
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: {app: web-tier}
        topologyKey: kubernetes.io/hostname
```
이 블록은 Pod 템플릿의 `spec` 아래(Deployment면 `spec.template.spec`)에 넣는다. 위 블록을 Deployment에 넣어 `k apply --dry-run=server`로 필드 이름을 검증했다. 라벨 키만 바꾼 같은 구조로 실제 배치도 확인했다: required nodeAffinity는 라벨이 있는 노드에만, anti-affinity replicas 3은 2개 Running + 1개 Pending. (`tier`, `zone` 라벨은 이 랩 노드에 없으므로 그대로 적용하면 Pending이다. q13이 라벨을 붙여 준다.)

**상황 7: topologySpreadConstraints (컨트롤 플레인 taint 함정 포함).**
```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    nodeTaintsPolicy: Honor       # 이 줄이 없으면 replicas 4 중 2개가 Pending
    labelSelector:
      matchLabels: {app: spread}
```
```bash
k get pods -l app=spread -o wide --no-headers | awk '{print $7}' | sort | uniq -c    # 워커마다 2개
```
Pod 템플릿 안에 있어야 하고 `labelSelector`가 Pod 라벨과 일치해야 한다. 이미 만든 Deployment를 수정하면 롤링 업데이트 중 옛 Pod가 같이 계산돼 분포가 어긋나 보일 수 있다 (직접 겪음; 확인은 Terminating이 사라진 뒤).

**상황 8: PriorityClass 만들기, "기존 최고값 -1", Deployment에 연결.**
```bash
k get pc -o custom-columns=NAME:.metadata.name,VALUE:.value --no-headers | grep -v '^system-' | sort -k2 -n | tail -1   # 사용자 정의 최고값
k create priorityclass business-critical --value=<최고값-1> --description="Business critical workloads"
k create priorityclass batch-low --value=100 --preemption-policy=Never --description="no preempt"
k patch deploy checkout --type=merge -p '{"spec":{"template":{"spec":{"priorityClassName":"business-critical"}}}}'
k get pc; k get pod -l app=checkout -o jsonpath='{.items[0].spec.priority}{"\n"}'
```
기대 결과: `k get pc`의 PREEMPTIONPOLICY가 `Never`로 표시된다. `--global-default=true`를 주면 `globalDefault: true`로 만들어진다 (`--dry-run=server`로 확인). 값이 10억을 넘으면 거부.

## 자주 틀리는 점
- 증상: Deployment가 `2/3`, ReplicaSet은 만들어졌는데 Pod가 안 생김 -> `k describe rs`/`k get events`에 `FailedCreate ... forbidden: maximum cpu usage per Container is 500m` 또는 `exceeded quota` -> LimitRange `max` 또는 ResourceQuota 초과 -> Deployment의 requests/limits를 범위 안으로 (확인함).
- 증상: `k apply`한 Pod가 `failed quota: rq: must specify limits.cpu ...`로 거부 -> 네임스페이스에 requests/limits 기준 quota가 있음 -> Pod에 requests와 limits를 모두 쓴다 (확인함).
- 증상: Pod `Pending`, `0/3 nodes ... 2 Insufficient cpu` -> requests 합이 allocatable보다 큼 -> requests를 줄이거나 replicas/다른 Pod를 조정. 먼저 `k describe node | grep -A6 "Allocated resources"` (확인함, 메시지는 `1 node(s) had untolerated taint {...}, 2 Insufficient cpu`).
- 증상: `Pending` + `node(s) didn't match Pod's node affinity/selector` -> nodeSelector/affinity 라벨 오타이거나 노드에 라벨이 없다 -> `k get nodes --show-labels`로 대조, 라벨은 `k label node`로 (확인함).
- 증상: `Pending` + `untolerated taint {node-role.kubernetes.io/control-plane: }` -> toleration 누락. toleration의 `effect`/`key`가 taint와 정확히 맞아야 한다.
- 증상: toleration을 넣었는데 원하는 노드로 가지 않는다 -> toleration은 "가도 됨"일 뿐 -> `nodeSelector`/`nodeAffinity`도 함께 넣는다 (q12, q13 요구에서 둘 다 필요).
- 증상: `topologySpreadConstraints`로 replicas 일부가 Pending (`didn't match pod topology spread constraints`) -> 컨트롤 플레인 같은 tainted 노드가 도메인에 세어짐 -> `nodeTaintsPolicy: Honor` (확인함: 4개 중 2개 Pending -> 2/2 분산).
- 증상: `podAntiAffinity` Deployment의 마지막 replica가 Pending -> 노드 수보다 replicas가 많음 (`didn't match pod anti-affinity rules`) -> required를 preferred로 바꾸거나 replicas를 노드 수 이하로 (확인함).
- 증상: `k create priorityclass --value=...`가 거부 -> 사용자 정의 값은 10억 이하 (확인함). "기존 최고 -1"은 `system-` 클래스를 빼고 센다.
- 증상: Pod 생성이 `no PriorityClass with name ... was found` -> 클래스를 먼저 만든다. PriorityClass는 네임스페이스가 없는 클러스터 객체라 `-n`이 필요 없고, 연습 후에는 직접 지운다.
- 증상: `k taint ... --dry-run=server` 출력에 `tainted`가 보여 실제 적용된 줄 앎 -> 노드는 안 바뀐다 (`spec.taints`로 확인함).
- 시뮬레이터 차이: 클러스터는 v1.34.0 (시험 v1.37). 스케줄러 메시지 문구가 버전에 따라 조금 다를 수 있다 (v1.37 문구는 확인하지 못했다) (미확인). 이 랩의 `k8s-worker2` Pod는 노드 간 통신이 불안정해 (D4 노트의 "시뮬레이터 차이" 참고) 스케줄링 자체는 정상이지만 서비스 호출 검증은 `k8s-worker` 기준으로 한다.

## 빠르게 푸는 순서
1. (30초) 컨텍스트/네임스페이스, "하지 말라" 조건(nodeName 금지, taint 변경 금지, 이름 유지)을 읽는다.
2. (30초) 현황 파악: `k get nodes --show-labels`, `k describe nodes | grep -E '^Name:|^Taints:'`, `k get pc`, 필요하면 `k describe node <n> | grep -A8 Allocatable`.
3. (1분) 자원 문제면 `k set resources`로 시작, 단독 Pod/LimitRange/quota는 문서 YAML 복사. 노드 라벨은 `k label node`.
4. (2분) 배치 규칙은 `k create deploy --dry-run=client -o yaml`로 뼈대를 만들고, 문서의 affinity/toleration/topologySpread 블록을 `spec.template.spec` 아래에 붙인다. 들여쓰기를 한 단계 더 확인.
5. (30초) `k apply -f x.yaml --dry-run=server` 후 `k apply`, `k rollout status deploy <d>`.
6. (1분) `k get pod -o wide`로 올라간 노드/상태 확인. Pending이 있으면 `k describe pod`의 `FailedScheduling` 한 줄을 읽고 원인별로 고친다 (taint/selector/Insufficient/anti-affinity/spread).
7. (30초) 사용한 임시 라벨/PriorityClass가 문제에서 요구한 것인지 대조하고, 요구하지 않은 변경(taint 변경 등)이 없는지 확인. (총 5~6분 목표)
