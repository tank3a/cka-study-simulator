# C1. Understand connectivity between Pods

## 이 항목에서 공부할 것
- [ ] `k get pods -o wide`로 Pod IP와 노드를 읽고, 같은 노드/다른 노드의 Pod에 `wget <PodIP>:<port>`로 직접 접속해 본다
- [ ] 쿠버네티스 네트워크 모델 규칙(Pod마다 고유 IP, NAT 없이 모든 Pod끼리 통신, 노드의 에이전트는 그 노드의 모든 Pod에 접근)을 말한다
- [ ] 한 Pod 안의 컨테이너끼리 `127.0.0.1`로 통신하는 것을 `k exec -c`로 확인한다
- [ ] 노드의 podCIDR(`k get node -o jsonpath='{.spec.podCIDR}'`), 클러스터 Pod 대역, Service 대역(`--service-cluster-ip-range`)을 찾는다
- [ ] 노드의 CNI 설정 파일 이름(`/etc/cni/net.d`)과 CNI 바이너리 위치(`/opt/cni/bin`), CoreDNS Service의 ClusterIP(`kube-dns`)를 찾아 파일에 쓴다
- [ ] 한 Pod만 Service 이름을 못 풀 때 `/etc/resolv.conf`를 정상 Pod과 비교해 `dnsPolicy`/`dnsConfig` 문제를 찾고 Pod을 다시 만든다
- [ ] `hostNetwork: true` Pod의 IP가 노드 IP이고 DNS도 달라진다는 것을 안다
- [ ] Pod IP가 해당 노드의 podCIDR 밖이면 CNI 설정 문제를 의심한다

## 개념 설명

### 쿠버네티스 네트워크 모델 (Pod 대 Pod)
- 무엇인가: 모든 Pod은 클러스터 전체에서 유일한 자기 IP를 갖고, 같은 노드든 다른 노드든 NAT 없이 서로 그 IP로 직접 통신할 수 있다는 약속이다. Pod을 "각자 전용 전화번호를 가진 작은 가상 서버"로 보면 된다. 한 Pod 안의 컨테이너들은 같은 네트워크 네임스페이스를 공유해서 `localhost`로 서로 통신한다 (문서 `The Kubernetes network model`).
- 왜 필요한가: 포트 매핑이나 컨테이너 링크 없이 앱을 VM처럼 배치하고 서로 찾게 하려고. 그 위에 Service(안정된 주소), NetworkPolicy(제한)가 쌓인다.
- 핵심 동작 (이 랩에서 확인함): (1) 같은 노드와 다른 노드(worker -> control-plane)의 Pod IP로 `wget`이 성공했다. (2) 서버 로그에 찍힌 출처 IP가 클라이언트 Pod IP 그대로였다 (`10.244.1.79 ... "GET /"`): NAT가 없다. (3) Pod IP로 `ping`도 된다. (4) 노드에서 Pod IP로 `curl` 200. (5) 같은 Pod의 `sidecar` 컨테이너에서 `127.0.0.1`로 `web` 컨테이너(nginx)가 응답. (6) 다른 네임스페이스의 Pod에도 IP로 닿는다 (NetworkPolicy가 없으면 네임스페이스는 네트워크 경계가 아니다, C2에서 확인함).
- 관계: Pod IP는 Pod이 재생성되면 바뀌므로 앱은 Service 이름(C3, A5)으로 접속한다. 정책이 없으면 모든 통신이 열려 있고(default allow), 막는 것은 NetworkPolicy(C2)다.

### CNI와 IP 대역 (누가 무엇을 나눠 주나)
- 역할 분담: Pod 네트워크 세팅은 컨테이너 런타임(CRI)이 하고, 실제 구현은 CNI 플러그인(이 랩은 kindnet)이 한다. 문서 `Kubernetes IP address ranges`: Pod IP는 네트워크 플러그인이, Service IP는 kube-apiserver가, 노드 IP는 kubelet/cloud-controller-manager가 할당한다. 세 대역은 서로 겹치면 안 된다.
- 이 랩의 값 (모두 확인함): Pod 대역 `10.244.0.0/16` (kubeadm-config `podSubnet`, controller-manager `--cluster-cidr`), 노드별 podCIDR는 control-plane `10.244.0.0/24`, worker `10.244.1.0/24`, worker2 `10.244.2.0/24`. Service 대역 `10.96.0.0/16` (`serviceSubnet`, apiserver/controller-manager `--service-cluster-ip-range`). CoreDNS Service `kube-dns`는 `10.96.0.10`.
- 노드의 CNI 파일: 설정은 `/etc/cni/net.d/`(이 랩 worker는 `10-kindnet.conflist`, 안에 `"subnet": "10.244.1.0/24"`), 플러그인 바이너리는 `/opt/cni/bin/` (이 랩 `host-local`, `loopback`, `portmap`, `ptp`). 시험의 CNI(Calico/Cilium 등)는 파일 이름이 다르다. 개념(설정 디렉터리, 노드별 대역)은 같다.
- 확인 못 한 것: CNI가 없을 때 노드가 `NotReady`가 되는 증상은 이 랩에서 재현하지 않았다 **(미확인)**. 문서 `Network Plugins`는 컨테이너 런타임이 CNI 플러그인을 로드해야 한다고만 적는다.

### Pod의 DNS 설정 (dnsPolicy, dnsConfig)
- `dnsPolicy` 기본값은 `ClusterFirst`다 (`Default`는 기본값이 아니다, 문서 `Pod's DNS Policy`). `ClusterFirst` Pod의 `/etc/resolv.conf`는 `nameserver 10.96.0.10`, `search <ns>.svc.cluster.local svc.cluster.local cluster.local`, `options ndots:5` (확인함).
- `dnsPolicy: None`이면 `dnsConfig`만 쓴다. 잘못된 nameserver를 넣으면 `resolv.conf`가 `nameserver 192.0.2.53` 한 줄뿐이 되고 `wget: bad address 'backend'`가 난다 (확인함, q36 Part 1).
- `hostNetwork: true` Pod은 IP가 노드 IP(이 랩 `172.18.0.2`)다 (확인함). DNS는 `ClusterFirst`를 그대로 두면 노드의 resolv.conf(`nameserver 192.168.65.254`, 이 랩의 Docker Desktop DNS)를 쓴다 (확인함). 클러스터 Service 이름을 풀려면 `dnsPolicy: ClusterFirstWithHostNet`이 필요하다고 문서에 나온다.
- Pod의 `dnsPolicy`/`dnsConfig`는 만든 뒤 수정이 안 된다. `patch`하면 `pod updates may not change fields other than spec.containers[*].image,...`로 거부된다 (확인함). 지우고 다시 만든다.

## 예시

### 예시 1. Pod 간 직접 통신 확인 (같은 노드, 다른 노드)
상황: "Pod `client`에서 `web-a`와 다른 노드의 `web-cp`에 IP로 접속되는지 확인하라."
```bash
k -n net-lab get pods -o wide                     # IP, NODE 열
A=$(k -n net-lab get pod web-a -o jsonpath='{.status.podIP}')
C=$(k -n net-lab get pod web-cp -o jsonpath='{.status.podIP}')
k -n net-lab exec client -- wget -qO- -T3 http://$A | head -3
k -n net-lab exec client -- wget -qO- -T3 http://$C | head -3
k -n net-lab exec client -- ping -c1 -W2 $A
```
기대: 두 `wget` 모두 `<!DOCTYPE html>`, `ping`은 `1 packets received, 0% packet loss` (확인함). 서버 쪽 `k logs web-a`에 출처가 `client`의 Pod IP로 찍힌다. 이미지에 `curl`이 없으면 `wget`(busybox)을 쓴다.

### 예시 2. 한 Pod 안의 컨테이너끼리는 localhost
```bash
k -n net-lab exec two-ctr -c sidecar -- wget -qO- -T3 http://127.0.0.1 | head -2
```
기대: nginx 페이지 (`two-ctr`의 `web` 컨테이너가 응답, 확인함). 컨테이너 이름은 `k get pod two-ctr -o jsonpath='{.spec.containers[*].name}'`로 본다.

### 예시 3. 대역과 CNI 정보 찾기 (q36 Part 2, q26 형태)
상황: "노드 `k8s-worker`의 podCIDR, CNI 설정 파일 이름, CoreDNS Service IP를 파일에 쓰라."
```bash
k get node k8s-worker -o jsonpath='{.spec.podCIDR}' > /home/candidate/podcidr-node1.txt
k -n kube-system get svc kube-dns -o jsonpath='{.spec.clusterIP}' > /home/candidate/dns-ip.txt
ssh k8s-node1 sudo ls /etc/cni/net.d                      # 파일 이름을 눈으로 확인한 뒤
echo 10-kindnet.conflist > /home/candidate/cni-conf.txt   # 확인한 이름을 그대로
cat /home/candidate/podcidr-node1.txt /home/candidate/dns-ip.txt /home/candidate/cni-conf.txt
```
기대: `10.244.1.0/24`, `10.96.0.10`, `10-kindnet.conflist` (이 랩에서 jsonpath 두 개와, `ssh` 대신 호스트의 `docker exec k8s-worker ls /etc/cni/net.d`로 파일 이름을 확인함). 클러스터 전체 대역은:
```bash
k get nodes -o custom-columns='NAME:.metadata.name,PODCIDR:.spec.podCIDR'
k -n kube-system get cm kubeadm-config -o jsonpath='{.data.ClusterConfiguration}' | grep -E 'podSubnet|serviceSubnet'
# control-plane 노드에서: grep -hE 'cluster-cidr|service-cluster-ip-range' /etc/kubernetes/manifests/kube-*.yaml
```
기대: `podSubnet: 10.244.0.0/16`, `serviceSubnet: 10.96.0.0/16` (확인함). kubeadm으로 만든 클러스터가 아니면 `kubeadm-config`가 없으므로 매니페스트 grep을 쓴다.

### 예시 4. 한 Pod만 DNS가 안 될 때 (q36 Part 1 형태)
상황: "`broken-client`만 `http://backend`를 못 푼다. 같은 네임스페이스 `healthy-client`는 된다. 하드코딩한 DNS 주소는 쓰지 말라."
```bash
k -n net-debug exec broken-client -- cat /etc/resolv.conf       # nameserver 192.0.2.53 뿐
k -n net-debug exec healthy-client -- cat /etc/resolv.conf      # nameserver 10.96.0.10 + search 줄
k -n net-debug get pod broken-client -o yaml > bc.yaml
# bc.yaml 에서 dnsConfig 블록을 지우고 dnsPolicy: None -> ClusterFirst 로 고친다 (vim)
k replace --force -f bc.yaml                                    # 삭제 후 재생성
k -n net-debug exec broken-client -- wget -qO- -T3 http://backend
```
기대: 수정 후 `resolv.conf`가 정상 Pod과 같아지고 `wget`이 응답한다. 이 랩에서 `k replace --force -f`는 `pod "broken-client" deleted ... pod/broken-client replaced`로 동작했고 `resourceVersion`, `uid` 같은 서버 필드가 남은 YAML도 받아들였다 (확인함). 더 빠른 방법은 이름과 이미지, 명령이 같게 `k delete pod broken-client --now; k run broken-client --image=busybox:1.37 --command -- sleep 86400` (확인함). 문제가 "이름/이미지/명령 유지"를 요구하면 이 값을 그대로 쓴다.

### 예시 5. hostNetwork Pod 확인
```bash
k -n net-lab get pod hostnet -o wide              # IP 열이 노드 IP (172.18.0.2)
k -n net-lab exec hostnet -- cat /etc/resolv.conf # 노드의 nameserver, 클러스터 DNS 아님
```
기대: IP가 `172.18.0.2`, resolv.conf에 `nameserver 192.168.65.254` (확인함). 클러스터 이름을 풀게 하려면 spec에 `hostNetwork: true`와 `dnsPolicy: ClusterFirstWithHostNet`을 같이 쓴다 (문서 예제 기준, 이 랩에서는 시험하지 않았다 **(미확인)**).

## 자주 틀리는 점
- Pod IP로는 되는데 이름으로는 안 된다 -> Pod 네트워크가 아니라 DNS/Service 문제 -> A5. 반대로 Service 이름은 되는데 직접 Pod IP가 안 되면 NetworkPolicy나 CNI를 본다.
- 한 Pod만 `bad address` -> 그 Pod의 `dnsPolicy: None` + 잘못된 `dnsConfig` 등 (확인함) -> `resolv.conf`를 정상 Pod과 비교 -> 수정 불가이므로 재생성 (`k replace --force`).
- `hostNetwork` Pod에서 서비스 이름이 안 풀린다 -> `ClusterFirst`가 노드 DNS로 떨어진다 (확인함) -> `ClusterFirstWithHostNet`.
- `ping <PodIP>`는 되지만 `ping <ClusterIP>`는 안 된다 -> ClusterIP는 TCP/UDP만 규칙이 있다 (A5에서 확인함) -> `wget`/`nc`로 시험.
- 대상 Pod 이미지에 `curl`이 없어 시험을 못 한다 -> 시험은 `curl`/`wget`이 있는 쪽 Pod에서 한다. 이 랩의 테스트 Pod은 `busybox:1.37`이고 `wget -qO- -T3 http://ip:port`로 확인했다. 어떤 이미지에 `curl`이 있는지는 이미지마다 다르다 **(미확인)**.
- 노드 podCIDR를 `k describe node`에서 찾느라 느리다 -> `k get node <n> -o jsonpath='{.spec.podCIDR}'`가 한 줄이다 (확인함).
- Pod IP가 해당 노드의 podCIDR 밖이다 -> CNI 설정(`/etc/cni/net.d`의 `subnet`)이 노드 객체의 podCIDR와 어긋났다 -> 노드의 CNI 파일과 `k get node -o jsonpath` 비교. 이 랩에서 실제로 관찰한 사례를 아래에 적는다.
- 시뮬레이터 차이: (1) 이 랩은 v1.34.0이고 문서는 v1.37이다. (2) CNI는 kindnet이라 파일 이름이 `10-kindnet.conflist`다. 시험은 다를 수 있다 (q36 해설과 같음). (3) 한때 `k8s-worker2`의 CNI 설정 대역이 노드 podCIDR와 어긋나 그 노드 Pod의 DNS/노드 간 통신이 실패한 적이 있다(랩 고장, 시험과 무관, 수정됨). 같은 증상이 다시 나오면 `kubectl --context k8s -n kube-system delete pod -l app=kindnet --field-selector spec.nodeName=k8s-worker2`로 kindnet을 재생성하거나 `bin/sim doctor`로 점검한다.

## 빠르게 푸는 순서
1. context와 namespace, 질문이 "값 찾기"인지 "고장 고치기"인지 확인한다 (0.5분).
2. 값 찾기: podCIDR는 `k get node <n> -o jsonpath='{.spec.podCIDR}'`, DNS IP는 `k -n kube-system get svc kube-dns -o jsonpath='{.spec.clusterIP}'`, CNI 파일은 `ssh <node>` 후 `sudo ls /etc/cni/net.d`로 확인한 이름을 그대로 쓴다 (2분).
3. 쓰기 전에 파일 요구 형식(값 한 줄, 경로가 아닌 파일 이름)을 문제에서 다시 읽는다. `cat`으로 결과를 확인한다 (0.5분).
4. 고장 고치기: 증상 Pod과 정상 Pod의 `cat /etc/resolv.conf`를 비교한다 (1분).
5. 수정 불가 필드이므로 `k get pod -o yaml > x.yaml` -> 편집 -> `k replace --force -f x.yaml`, 또는 같은 이름 조건을 지켜 `k delete` 후 `k run` (1.5분).
6. `k exec <pod> -- wget -qO- -T3 http://<svc>`로 해결 확인 (0.5분).
7. 마지막으로 `exit`로 base 노드로 돌아왔는지, 파일이 요구한 위치(`/home/candidate/...`)인지 확인한다 (0.5분). 전체 목표 약 6분.
