# B2. Prepare underlying infrastructure for installing a Kubernetes cluster

## 이 항목에서 공부할 것
- [ ] 노드가 사전 조건(OS, CPU/RAM, 고유 hostname/MAC/product_uuid, 열려야 할 포트)을 만족하는지 명령으로 확인한다
- [ ] swap을 지금 끄고(`swapoff -a`) 재부팅 후에도 꺼지게 `/etc/fstab`의 swap 줄을 주석 처리한다
- [ ] `net.ipv4.ip_forward = 1`을 `/etc/sysctl.d/*.conf`에 쓰고 `sysctl --system`으로 적용한다 (문제가 요구하면 `overlay`/`br_netfilter` 모듈 등록 포함)
- [ ] containerd의 `SystemdCgroup = true`와 kubelet의 `cgroupDriver: systemd`가 일치하는지 확인하고 고친 뒤 containerd를 재시작한다
- [ ] pkgs.k8s.io apt 저장소를 추가하고 `kubelet kubeadm kubectl`을 설치한 뒤 `apt-mark hold` 한다
- [ ] `systemctl enable --now kubelet`, `kubeadm version -o short`, `kubelet --version`으로 설치를 확인한다
- [ ] 공식 문서에서 위 각 단계의 명령 블록 위치를 바로 찾는다 (설치 페이지, 컨테이너 런타임 페이지)

## 개념 설명

### 노드 사전 조건 (kubeadm 설치 페이지 "Before you begin")
- 무엇: `kubeadm init/join` 전에 각 노드가 갖춰야 할 기본 조건이다. 문서 기준: 2 GB 이상 RAM, 컨트롤 플레인은 2 CPU 이상, 노드 간 전체 네트워크 연결, 노드마다 고유한 hostname/MAC/product_uuid, 필요한 포트 개방.
- 왜: 값이 겹치면 Kubernetes가 노드를 구분하지 못해 설치가 실패할 수 있다고 문서가 설명한다 (특히 복제한 VM).
- 확인 명령: `hostname`, `ip link`, `sudo cat /sys/class/dmi/id/product_uuid`, `nc 127.0.0.1 6443 -zv -w 2`.
- 포트 (Ports and Protocols 페이지): 컨트롤 플레인 6443(API), 2379-2380(etcd), 10250(kubelet), 10259(scheduler), 10257(controller-manager). 워커 10250, 10256(kube-proxy), 30000-32767(NodePort).

### swap
- 무엇: 디스크를 메모리처럼 쓰는 영역. kubelet은 기본값으로 swap이 있으면 시작에 실패한다 (문서 "Swap configuration"). 허용하려면 kubelet 설정에 `failSwapOn: false`.
- 끄는 법: 즉시는 `sudo swapoff -a`. 재부팅 후에도 꺼지려면 `/etc/fstab` 등 설정 파일에서 swap을 비활성화한다 (문서는 `systemd.swap`도 언급).
- 비유: swap은 책상이 좁을 때 서랍에 서류를 넣는 것. kubelet은 "서랍에 넣으면 자원 계산이 틀어진다"며 기본적으로 거부한다.

### 커널 설정 (IPv4 forwarding, 모듈)
- 무엇: Pod 트래픽이 노드의 네트워크 인터페이스 사이를 지나가려면 IPv4 forwarding이 켜져 있어야 한다. 현재 문서(컨테이너 런타임 페이지)는 `net.ipv4.ip_forward = 1`을 `/etc/sysctl.d/k8s.conf`에 쓰고 `sudo sysctl --system`으로 적용한 뒤 `sysctl net.ipv4.ip_forward`로 확인하라고 한다.
- 핵심: 파일에 써 두면 재부팅 후에도 유지되고, `sysctl --system`을 해야 지금 바로 적용된다. `sysctl -w`만 쓰면 재부팅 때 사라진다.
- `overlay`, `br_netfilter` 모듈과 `net.bridge.bridge-nf-call-iptables` 항목은 현재 v1.37 문서 페이지(컨테이너 런타임, kubeadm 설치, 클러스터 생성)에서 검색되지 않았다 (세 페이지 HTML에서 grep 0건). 문제가 요구하면 `/etc/modules-load.d/k8s.conf`에 모듈 이름을 한 줄씩 쓰는 방식을 쓴다 (q72 해설 기준).

### 컨테이너 런타임(CRI)과 cgroup driver
- 무엇: kubelet이 Pod를 실제로 실행시킬 때 부르는 런타임(여기서는 containerd). 소켓 기본값은 `/run/containerd/containerd.sock`.
- 왜: kubelet과 런타임이 같은 cgroup driver를 써야 한다 (문서: "critical"). systemd가 init인 리눅스, 특히 cgroup v2에서는 `systemd` driver를 쓰라고 한다.
- 핵심 설정 두 곳이 서로 맞아야 한다.
  - kubelet: `KubeletConfiguration`의 `cgroupDriver: systemd` (노드에서는 `/var/lib/kubelet/config.yaml`).
  - containerd: `/etc/containerd/config.toml`의 runc `options` 아래 `SystemdCgroup = true`. 바꾼 뒤에는 `sudo systemctl restart containerd`.
- containerd 버전에 따라 테이블 이름이 다르다: 1.x는 `[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]`, 2.x는 `[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.runc.options]`.
- v1.37 문서에는 `KubeletCgroupDriverFromCRI` 기능 게이트가 켜져 있고 런타임이 `RuntimeConfig` CRI RPC를 지원하면 kubelet이 driver를 런타임에서 자동 감지하고 kubelet 설정의 `cgroupDriver`는 무시한다는 설명이 있다 (오래된 containerd 1.y는 이 RPC가 없다고 한다). 문제가 "맞춰라"고 하면 직접 맞춘다.

### kubeadm / kubelet / kubectl 패키지와 버전 고정
- kubeadm: 클러스터를 만드는 도구. kubelet: 노드 에이전트(서비스로 상시 실행). kubectl: 클라이언트. kubeadm은 kubelet/kubectl을 설치·관리해 주지 않으므로 직접 맞춰 설치한다 (문서).
- 패키지 저장소는 마이너 버전마다 따로 있다 (`pkgs.k8s.io/core:/stable:/v1.37/deb/`). 구 저장소 `apt.kubernetes.io`는 동결되어 쓰면 안 된다.
- 설치 후 `apt-mark hold kubelet kubeadm kubectl`로 일반 `apt upgrade`에 딸려 올라가지 않게 고정한다. 업그레이드(B4)할 때는 `unhold` -> 설치 -> `hold` 순서다.
- 설치 직후 kubelet은 `kubeadm init/join`이 설정을 줄 때까지 몇 초마다 재시작을 반복하는데, 문서는 이 crashloop가 정상이라고 한다.

## 예시

**상황 1: 노드가 설치 조건을 만족하는지 읽기만 해서 확인한다 (해당 노드에 ssh해서).**
```bash
uname -r; . /etc/os-release; echo $PRETTY_NAME       # 6.10.14-linuxkit / Debian GNU/Linux 12 (bookworm)
nproc; free -m | sed -n 2p                            # CPU 수, 메모리(MB)
hostname; ip -br link | head -3
sudo cat /sys/class/dmi/id/product_uuid               # 실제 VM에서 사용
nc 127.0.0.1 6443 -zv -w 2                            # 컨트롤 플레인에서: Connection to 127.0.0.1 6443 port [tcp/*] succeeded!
ss -ltnp | grep -E ':(6443|2379|2380|10250|10257|10259) '   # 컨트롤 플레인이 실제로 듣는 포트
```
시뮬레이터에서는 `product_uuid` 파일이 없다 (`No such file or directory`). 나머지는 위 주석과 같이 나왔다.

**상황 2: swap을 끄고 재부팅 후에도 꺼지게 한다.** (미확인: 이 랩에서는 노드를 변경하지 않아 `swapoff`/`fstab` 편집은 실행하지 않았다. 파일 편집 로직은 임시 컨테이너의 샘플 fstab으로 확인했다.)
```bash
sudo swapoff -a
sudo sed -i '/ swap / s/^/#/' /etc/fstab      # swap 줄을 주석 처리
grep swap /etc/fstab                          # 줄 앞에 #가 붙어야 함
swapon --show                                 # 아무것도 안 나와야 함
free -m | grep -i swap                        # Swap: 0 0 0
```

**상황 3: ip_forward를 영구 설정하고 즉시 적용한다 (문서 블록 그대로).** (미확인: 위와 같은 이유로 파일 쓰기/적용은 실행하지 않음. 확인 명령은 실행함.)
```bash
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.ipv4.ip_forward = 1
EOF
sudo sysctl --system
sysctl net.ipv4.ip_forward        # net.ipv4.ip_forward = 1
```
문제가 `overlay`/`br_netfilter` 모듈 부팅 로드를 요구하는 경우:
```bash
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
lsmod | grep -E 'overlay|br_netfilter'      # 실제 VM에서 확인 (이 랩 컨테이너는 lsmod가 비어 있음)
```

**상황 4: containerd와 kubelet의 cgroup driver가 맞는지 확인하고, 다르면 containerd를 고친다.**
```bash
grep -n SystemdCgroup /etc/containerd/config.toml     # SystemdCgroup = true
grep cgroupDriver /var/lib/kubelet/config.yaml        # cgroupDriver: systemd
containerd config dump | grep -n SystemdCgroup        # 실제로 적용된 값
stat -fc %T /sys/fs/cgroup/                           # cgroup2fs 이면 cgroup v2
```
위 출력은 시뮬레이터 워커에서 그대로 나왔다 (config.toml에 두 줄, `cgroup2fs`). 줄이 없거나 `false`이면:
```bash
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
grep SystemdCgroup /etc/containerd/config.toml        # 결과가 없으면 sed가 아무것도 못 바꾼 것
sudo systemctl restart containerd
```
`containerd config default`(2.1.3, version = 3)에는 `SystemdCgroup` 줄 자체가 없다 (grep 0건 확인). 이 경우 sed는 아무것도 바꾸지 못하므로 runc `options` 줄 바로 아래에 직접 넣는다 (줄이 이미 있으면 중복 키가 되므로 위 `grep`으로 먼저 확인):
```bash
sudo sed -i "/runtimes.runc.options\]/a\            SystemdCgroup = true" /etc/containerd/config.toml
containerd config dump | grep -n SystemdCgroup        # 파싱되어 SystemdCgroup = true 가 나와야 함
```
(이 sed는 기본 설정 사본을 임시 파일에 적용해 `containerd -c <file> config dump`가 `SystemdCgroup = true`를 출력하는 것까지 확인했다. 실제 `/etc/containerd/config.toml` 수정과 재시작은 하지 않았다.)

**상황 5: Debian 계열 노드에 kubeadm/kubelet/kubectl을 설치한다 (문서의 Debian 탭).** (미확인: 시뮬레이터 노드는 kind 이미지라 apt로 설치하지 않아 실행하지 않았다. 아래는 문서 v1.37 블록의 형태다.)
```bash
sudo apt-get update
sudo apt-get install -y apt-transport-https ca-certificates curl gpg
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.37/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.37/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
sudo systemctl enable --now kubelet
```
확인:
```bash
kubeadm version -o short        # v1.34.0 (시뮬레이터) / 시험에서는 설치한 버전
kubelet --version               # Kubernetes v1.34.0
apt-mark showhold               # kubeadm kubectl kubelet (시험 노드). 시뮬레이터 kind 노드는 비어 있음
systemctl is-enabled kubelet    # enabled
```
시뮬레이터 차이: kind 노드는 containerd와 kubelet이 이미지에 들어 있고 dpkg 패키지가 아니다(`dpkg -l`에 kubeadm/kubelet 없음). swap은 Docker VM 것이 `swapon --show`에 보이고(kind 노드의 kubelet 설정은 `failSwapOn: false`) 모듈은 호스트 커널 것이라 `lsmod`가 비어 있다. 즉 "swap 때문에 kubelet이 안 뜬다"는 현상은 여기서 재현되지 않는다.

## 자주 틀리는 점
- 증상: 설치 후 kubelet이 `activating (auto-restart)`를 반복한다 -> 원인: `kubeadm init/join` 전에는 정상이다 (문서: crashloop is expected) -> 당황하지 말고 다음 단계로 간다. 단, `kubeadm init` 이후에도 반복되면 `journalctl -u kubelet`에서 swap/cgroup 오류를 본다.
- 증상: swap이 켜진 노드에서 kubelet이 시작하지 않는다 -> 원인: 기본 동작이 swap 감지 시 실패 -> `swapoff -a`와 `/etc/fstab` 수정, 또는 `failSwapOn: false`.
- 증상: 재부팅 후 swap/ip_forward가 되돌아간다 -> 원인: `swapoff -a`나 `sysctl -w`만 하고 파일에 영구 설정을 안 했다 -> `/etc/fstab` 주석, `/etc/sysctl.d/*.conf` 작성.
- 증상: sysctl 파일을 썼는데 값이 그대로다 -> 원인: `sysctl --system`을 안 했다 -> 실행하고 `sysctl net.ipv4.ip_forward`로 확인.
- 증상: `sed`로 `SystemdCgroup`을 바꿨다는데 `grep`에 아무것도 없다 -> 원인: containerd 2.x 기본 설정에는 그 줄이 없다 (`false`가 아니라 줄 자체가 없음) -> runc `options` 테이블 아래에 줄을 추가한다.
- 증상: config.toml을 고쳤는데 효과가 없다 -> 원인: containerd를 재시작하지 않았다 -> `sudo systemctl restart containerd` (문서 명시).
- 증상: kubelet은 `systemd`인데 containerd는 기본값 -> 원인: 두 곳의 cgroup driver가 다름 (문서: 반드시 같아야 함) -> 둘을 맞추고 containerd를 재시작한다. 이미 클러스터에 조인한 노드의 driver를 바꾸는 일은 기존 Pod에서 오류를 낼 수 있다고 문서가 경고하므로 설치 전에 맞춘다.
- 증상: `apt-cache madison kubeadm`에 원하는 버전이 보이지 않는다 -> 원인: 저장소 URL의 마이너 버전이 다르다 (문서: 마이너마다 별도 저장소, 기대한 버전이 안 보이면 저장소 확인) -> `/etc/apt/sources.list.d/kubernetes.list`의 `v1.xx`를 요구 버전에 맞추고 `apt-get update`.
- 증상: `curl ... | gpg --dearmor -o /etc/apt/keyrings/...`가 디렉터리 오류로 실패 -> 원인: 오래된 배포판(Debian 12/Ubuntu 22.04 이전)은 `/etc/apt/keyrings`가 없다 (문서 노트) -> `sudo mkdir -p -m 755 /etc/apt/keyrings`를 먼저.
- 참고: 후기에서 이 하위 항목의 구체적 출제는 확인되지 않았다(study-guide 3절의 미확인). 문서의 명령을 찾아 복사하는 능력이 핵심이다.

## 빠르게 푸는 순서
1. 문제가 요구하는 것을 목록으로 적는다 (swap, ip_forward, 모듈, cgroup driver, 패키지, hold). 어느 노드(`ssh <node>`)인지 확인하고 `sudo -i`. (30초)
2. 현재 상태를 먼저 읽는다: `swapon --show`, `sysctl net.ipv4.ip_forward`, `grep SystemdCgroup /etc/containerd/config.toml`, `grep cgroupDriver /var/lib/kubelet/config.yaml`. (1분)
3. swap: `swapoff -a` 후 `/etc/fstab` swap 줄 주석. (1분)
4. 커널: 문서 블록을 복사해 `/etc/sysctl.d/`에 쓰고 `sysctl --system`. 모듈을 요구하면 `/etc/modules-load.d/`. (1분)
5. 런타임: 문서의 containerd 블록으로 `SystemdCgroup = true`를 맞추고 `systemctl restart containerd`. 변경하지 말라는 다른 설정이 있는지 확인 (`diff`로 변경 줄만 바뀌었나 본다). (1~2분)
6. 패키지: install-kubeadm 페이지의 Debian 탭 블록을 순서대로 붙여 넣는다. 마지막에 `apt-mark hold`, `systemctl enable --now kubelet`. (2분)
7. 확인: `kubeadm version -o short`, `kubelet --version`, `apt-mark showhold`, `systemctl is-enabled kubelet`. 결과를 파일로 저장하라는 요구가 있으면 경로를 지킨다. (30초)
8. `exit`로 base 호스트로 돌아온다. 총 목표 5~7분.
