# E3. Manage persistent volumes and persistent volume claims

## 이 항목에서 공부할 것
- [ ] hostPath PV YAML(capacity, accessModes, storageClassName, reclaimPolicy, hostPath)을 문서에서 복사해 만든다
- [ ] PVC YAML을 만들고 `k get pv,pvc`의 STATUS / VOLUME / CLAIM 열로 Bound 여부를 읽는다
- [ ] Deployment 또는 Pod에 PVC를 `claimName`으로 연결해 `mountPath`에 마운트한다
- [ ] Pending PVC를 PV와 나란히 비교(class, accessModes, size, volumeMode, selector)해서 원인을 찾고 고친다 (PVC는 지우고 다시 만든다)
- [ ] `storageClassName` 미지정과 `""`의 차이를 설명하고 "클래스 없는 PV"에 바인딩한다
- [ ] `selector.matchLabels` 또는 `volumeName`으로 특정 PV에 PVC를 붙인다
- [ ] Retain PV가 `Released`가 된 뒤 `claimRef`를 비워 `Available`로 되돌린다
- [ ] 같은 namespace의 Pod만 PVC를 쓸 수 있다는 것(PVC는 namespace 리소스, PV는 클러스터 리소스)을 지킨다

## 개념 설명

### PersistentVolume (PV)
- 무엇인가: 클러스터 범위(namespace 없음)에 있는 "이미 준비된 저장소 한 덩어리". 관리자가 미리 만들거나 provisioner가 자동으로 만든다. 창고에 쌓인 상자 하나.
- 핵심 필드: `capacity.storage`, `accessModes`, `persistentVolumeReclaimPolicy`, `storageClassName`(클래스 이름표), `volumeMode`, 저장소 종류(`hostPath`, `nfs`, `local`, `csi` 등), 그리고 바인딩 후 자동으로 채워지는 `claimRef`.
- 상태(phase): `Available`(아직 임자 없음) -> `Bound`(PVC와 연결) -> `Released`(PVC는 지워졌지만 정리 안 됨, Retain일 때) / `Failed`(자동 회수 실패).

### PersistentVolumeClaim (PVC)
- 무엇인가: namespace 안에서 "이 정도 크기, 이 접근 방식의 저장소가 필요하다"고 적은 주문서. Pod은 PV를 직접 쓰지 않고 PVC를 쓴다.
- 핵심 필드: `accessModes`, `resources.requests.storage`, `storageClassName`, `volumeMode`, 선택적으로 `selector`(PV 라벨로 고르기), `volumeName`(PV 이름으로 지정).
- 관계: PVC가 PV 하나와 1:1로 묶인다 (`claimRef`와 `volumeName`으로 서로 가리킴). 한 번 묶이면 다른 PVC는 그 PV를 못 쓴다.
- 확장은 `spec.resources.requests.storage`만 가능하고 그 외 `spec`은 만든 뒤 수정 불가 (확인함: `spec is immutable after creation except resources.requests and volumeAttributesClassName for bound claims`).

### 바인딩 규칙 (PVC가 어떤 PV와 붙는가)
컨트롤러가 아래를 모두 만족하는 `Available` PV를 찾는다 (정적 PV 기준). 하나라도 어긋나면 PVC는 Pending이다.
1. 클래스: PVC의 `storageClassName`과 PV의 `storageClassName`이 같다. PV에 클래스가 없으면 PVC도 `""`여야 한다.
2. 접근 방식: PV의 `accessModes`가 PVC의 요청 모드를 포함한다.
3. 크기: PV 용량 >= PVC 요청. 붙은 뒤 PVC의 CAPACITY 열은 PV의 용량으로 보인다 (확인함: 3Gi 요청 -> 5Gi 표시).
4. `volumeMode`가 같다 (미지정 = Filesystem).
5. `selector`가 있으면 PV 라벨이 일치한다. `volumeName`이 있으면 그 PV만 후보가 된다.
- `storageClassName`을 PVC에서 아예 안 쓰면 default 클래스 이름이 자동으로 채워진다 (확인함). 그래서 "클래스 없는 PV"에 붙이려면 `storageClassName: ""`를 명시해야 한다.
- 클래스 이름이 가리키는 StorageClass 객체가 없어도, 이름이 같은 정적 PV가 있고 나머지 조건이 맞으면 바인딩된다 (확인함: 클래스 `manual` / `shared-slow`는 객체가 없었지만 Bound). 반대로 조건이 안 맞을 때도 Events에는 똑같이 `storageclass ... not found`가 찍혀서 헷갈린다 (아래 예시 2).
- 클래스가 `WaitForFirstConsumer`(예: `standard`)인 PVC는 Pod이 쓰기 전까지 정적 PV에도 안 붙는다. 클래스 객체가 없는 경우(`manual` 등)는 Pod 없이도 바로 Bound다 (확인함. `Immediate` 클래스도 같은 동작이 문서상 기대되지만 정적 PV로는 따로 확인하지 않았다). study-guide의 "PV/PVC는 Pod이 사용해야 Bound"는 클래스의 binding mode에 따라 다르다는 뜻이다.

### Pod에서 PVC 쓰기
- `volumes[].persistentVolumeClaim.claimName`에 PVC 이름, 컨테이너 `volumeMounts`에 같은 `name`과 `mountPath`. Pod은 PVC와 같은 namespace에 있어야 한다.
- 문서 정의상 RWO는 "노드 하나"에서만 mount 가능하다 (같은 노드의 Pod 여러 개는 가능). replica가 여러 개인 Deployment가 RWO PVC 하나를 쓰는 경우의 실제 배치 동작은 이번에 확인하지 않았다.

### Reclaim 이후의 PV 수명
- `Retain`이면 PVC 삭제 후 PV는 `Released`, `claimRef`가 남아서 새 PVC가 안 붙는다. `claimRef`를 `null`로 patch하면 `Available`이 된다 (E2에서 정책을 바꾸는 법).
- `Delete`는 PV까지 지운다. hostPath PV는 `/tmp` 밖 경로면 삭제 실패로 `Failed`가 된다 (E2 참고).
- 사용 중인 PVC를 지우면 `kubernetes.io/pvc-protection` finalizer 때문에 Pod이 사라질 때까지 `Terminating`으로 남고, Pod이 지워진 뒤에야 사라지며 Retain PV는 `Released`가 된다 (확인함).

## 예시

### 예시 1. 정적 PV + PVC + Deployment (q01 형태)
상황: "PV `pv-data`(1Gi, RWO, `manual`, Retain, hostPath `/mnt/data-app`), PVC `pvc-data`(500Mi), Deployment `data-app`이 `/usr/share/nginx/html`에 마운트".
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-data
spec:
  capacity:
    storage: 1Gi
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/data-app
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-data
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 500Mi
```
```bash
k apply -f pv-pvc.yaml
k get pv,pvc
# 기대: pv-data 1Gi RWO Retain Bound <ns>/pvc-data manual
#       pvc-data Bound pv-data 1Gi RWO manual     (Pod 없이도 Bound, CAPACITY 는 PV 의 1Gi)
k create deploy data-app --image=nginx:1.27 --dry-run=client -o yaml > app.yaml
# containers[0] 아래에 volumeMounts, template.spec 아래에 volumes 추가 (E1 예시 2와 같은 모양)
```
```yaml
        volumeMounts:
        - {name: html, mountPath: /usr/share/nginx/html}
      volumes:
      - name: html
        persistentVolumeClaim:
          claimName: pvc-data
```
`type`을 안 쓴 hostPath는 노드에 경로가 없어도 Pod 시작 때 디렉터리가 만들어진다 (확인함). 문제가 "경로가 이미 있다"고 하면 그대로 두면 된다.

### 예시 2. Pending PVC 원인 찾기 (q06 형태)
상황: "`ledger-pvc`가 Pending, PV `pv-ledger`는 수정 금지".
```bash
k describe pvc ledger-pvc | tail -5            # Events 확인 (그러나 원인을 정확히 말해 주지 않음)
k get pv pv-ledger -o custom-columns=CLASS:.spec.storageClassName,MODES:.spec.accessModes,SIZE:.spec.capacity.storage,VMODE:.spec.volumeMode
k get pvc ledger-pvc -o custom-columns=CLASS:.spec.storageClassName,MODES:.spec.accessModes,SIZE:.spec.resources.requests.storage,VMODE:.spec.volumeMode
# 두 줄을 나란히 보고 다른 칸을 모두 찾는다
```
Events가 `storageclass.storage.k8s.io "shared-slow" not found`로 나와도 그것이 진짜 원인이 아닌 경우가 많다 (확인함: 접근 모드, 크기, volumeMode만 틀려도 같은 메시지가 찍혔다). 비교 표가 기준이다.
```bash
k get pvc ledger-pvc -o yaml > pvc.yaml     # 백업 후 spec 의 틀린 칸 수정
k delete pvc ledger-pvc                      # spec 은 수정 불가이므로 지우고 다시 만든다
k apply -f pvc.yaml                          # status / uid / resourceVersion 같은 서버 필드는 지우고 apply
k get pvc,pv
# 기대: ledger-pvc Bound, pv-ledger Bound
```

### 예시 3. 클래스 없는 PV에 selector로 붙이기 (q03 형태)
상황: "클래스 없이 `tier=reports` 라벨 PV를 ROX 2Gi로 claim".
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: reports-pvc
spec:
  accessModes: [ReadOnlyMany]
  storageClassName: ""
  resources:
    requests:
      storage: 2Gi
  selector:
    matchLabels:
      tier: reports
```
```bash
k apply -f reports-pvc.yaml && k get pvc reports-pvc
# 기대: Bound, STORAGECLASS 열이 빈칸
```
같은 PVC에서 `storageClassName` 줄만 빼면 `k get pvc -o jsonpath='{.spec.storageClassName}'`이 `standard`로 채워지고 Pending에 머문다 (확인함). `volumeName: <pv이름>`으로 이름을 직접 지정해도 된다 (class는 여전히 같아야 함).

### 예시 4. Released PV 되살려 재사용
상황: "Retain PV가 `Released`라서 새 PVC가 안 붙는다".
```bash
k get pv                                                # STATUS Released, CLAIM 열에 옛 PVC
k patch pv pv-data -p '{"spec":{"claimRef":null}}'
k get pv pv-data
# 기대: STATUS Available, CLAIM 비어 있음
```
옛 데이터는 그대로 남아 있다. 특정 PVC만 붙게 하고 싶으면 `claimRef`에 name/namespace를 직접 넣는 방법도 있다 (문서 `Reserving a PersistentVolume`).

## 자주 틀리는 점
- PVC Pending이고 Events가 `storageclass ... not found` -> 그 메시지는 "클래스 객체가 없다"는 사실일 뿐 진짜 불일치 원인(accessModes, 크기, volumeMode, selector)을 가리지 않는다 -> PV와 PVC를 `-o custom-columns`로 나란히 비교하고, 다른 칸을 전부 고친다 (q06).
- PVC의 `accessModes`를 patch하니 `spec is immutable after creation except resources.requests ...` -> PVC spec은 불변 (확인함) -> `k delete pvc` 후 수정한 YAML로 다시 apply. 사용 중인 PVC를 지울 때는 Pod부터 정리해야 한다.
- 클래스 없는 PV를 쓰려는데 PVC가 `standard`로 채워져 Pending -> `storageClassName`을 안 썼음 -> `storageClassName: ""`를 명시 (확인함).
- PV를 `volumeName`으로 지정했는데 안 붙음 -> PV의 클래스 / 용량 / 모드가 PVC와 다르면 pre-bind해도 확인이 걸린다 (문서: control plane still checks storage class, access modes, size) -> 값을 맞춘다.
- PV는 `Available`인데 PVC가 계속 Pending -> PV 라벨이 `selector`와 다름, 또는 PV 크기가 요청보다 작음 -> `k get pv --show-labels`로 라벨, `k get pv`로 크기 확인.
- `Released` PV가 다시 안 붙음 -> `claimRef`가 남음 -> `{"spec":{"claimRef":null}}` patch (확인함).
- Pod이 `Pending`이고 Events에 `FailedScheduling ... persistentvolumeclaim "x" not found` (확인함) -> PVC가 다른 namespace에 있거나 이름 오타 -> `k get pvc -A`. PVC와 Pod은 같은 namespace여야 한다.
- 정적 PVC가 Pod 없이 `Pending`(Events `waiting for first consumer`) -> PVC 클래스가 `WaitForFirstConsumer`인 `standard`로 채워진 경우 -> 클래스 지정을 확인. 정상이면 Pod을 붙인다.
- PV `Delete` + hostPath 조합 -> PV `Failed` (E2 참고). 정적 PV는 `Retain`으로 둔다.
- 시뮬레이터 차이: 이 클러스터는 v1.34.0(시험 v1.37). hostPath 경로는 kind 노드 컨테이너 안이다. 동적 PV(local-path)는 `/var/local-path-provisioner/pvc-<uid>_<ns>_<pvc>` 아래에 만들어진다. PVC 확장은 API 값만 바뀐다.

## 빠르게 푸는 순서
1. context / namespace, 그리고 "PV 수정 금지", "Pod 삭제 금지" 같은 제약을 확인한다 (0.5분).
2. `k get pv,pvc,sc`로 현재 상태를 한 번에 본다 (0.5분).
3. 정적 구성이면 tutorials 페이지(`Ctrl+F` `task-pv-volume`)에서 PV, PVC YAML을 복사해 이름/크기/클래스/경로/모드를 고치고 한 파일로 apply (2분).
4. Pending이면 PV와 PVC를 `-o custom-columns`로 나란히 놓고 다른 칸을 모두 찾는다. PVC는 delete 후 재생성 (2분).
5. Deployment는 `k create deploy --dry-run=client -o yaml`로 뼈대를 만들고 `volumes` / `volumeMounts`를 넣어 apply (1.5분).
6. `k get pv,pvc,pod`로 Bound / Running 확인, 필요하면 `k exec ... -- ls <mountPath>`로 마운트 확인 (0.5분).
7. 정책이나 라벨 요구가 있으면 `k get pv -o custom-columns=...`로 마지막에 다시 확인 (0.5분). 전체 목표 6~7분.
