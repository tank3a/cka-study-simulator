# A2. Troubleshoot cluster components

## 이 항목에서 공부할 것
- [ ] `k get pods -n kube-system`으로 컨트롤 플레인 구성요소(apiserver, etcd, scheduler, controller-manager)의 상태를 보고, 이름이 `<구성요소>-<노드이름>`(mirror Pod)임을 안다
- [ ] 증상(Pod가 Pending인데 이벤트가 없다 / 모든 `k` 명령이 연결 거부 / Deployment가 Pod를 못 만든다)에서 고장난 구성요소를 추정한다
- [ ] 컨트롤 플레인 노드에 `ssh` + `sudo -i`로 들어가 `ls /etc/kubernetes/manifests`, `crictl ps -a`, `crictl logs <id>`로 죽은 컨테이너의 마지막 로그를 읽는다 (API 서버가 죽어도 된다)
- [ ] 매니페스트의 오타 유형(플래그 철자, 인증서/kubeconfig 경로, 이미지 태그, probe 포트)을 찾아 고치고, kubelet이 static Pod를 다시 만드는 것을 확인한다
- [ ] 백업은 `/etc/kubernetes/manifests` **밖**에 두고, mirror Pod를 `k delete`로 고치려 하지 않는다
- [ ] `/livez`, `/readyz`, 스케줄러 10259, controller-manager 10257, etcd `endpoint health`로 상태를 직접 확인한다
- [ ] 고친 뒤 `k get pods -n kube-system`, 증상이 있던 워크로드가 정상이 되는지 확인하고 `exit`로 base 복귀한다

## 개념 설명

### 컨트롤 플레인 구성요소 지도 (kubeadm 클러스터)
| 구성요소 | 하는 일 | 이 랩 포트 / 상태 확인 | 고장 나면 보이는 것 |
|---|---|---|---|
| kube-apiserver | 모든 요청의 관문. etcd와 통신 | 6443 / `/livez`, `/readyz` | `k`가 연결 거부 |
| etcd | 클러스터 상태 저장소 | 2379(클라이언트), 2380(peer), 2381(`/readyz`) | apiserver가 불안정/기동 실패 |
| kube-scheduler | Pending Pod를 노드에 배정 | 10259 / `/livez` | 새 Pod가 Pending, 이벤트 없음 |
| kube-controller-manager | Deployment->ReplicaSet->Pod 등 컨트롤러 실행 | 10257 / `/healthz` | Deployment를 만들어도 ReplicaSet/Pod가 안 생김 |
| kubelet | 노드에서 위 네 개(static Pod)와 일반 Pod를 실행 | 10248 `/healthz` | A1 참고 |
| kube-proxy, CoreDNS, CNI | DaemonSet/Deployment로 도는 애드온 | `k -n kube-system get ds,deploy` | Service/DNS 문제 (A5, C6) |
- 비유: apiserver는 관공서 접수 창구, etcd는 서류 보관소, scheduler는 배정 담당, controller-manager는 "서류대로 현실을 맞추는" 현장 반장. 접수 창구가 닫히면 아무도 서류를 못 내지만, 이미 일하던 Pod(kubelet 소관)는 계속 돈다 (문서: apiserver가 죽어도 기존 Pod는 계속 동작).
- 이 랩 포트와 경로는 모두 `/etc/kubernetes/manifests/*.yaml`에서 확인했다 (스케줄러 `containerPort: 10259 name: probe-port`, controller-manager 10257, apiserver 6443, etcd metrics 2381).

### Static Pod 와 mirror Pod
- 무엇: API 서버가 아니라 **kubelet이 노드의 디렉터리(`staticPodPath`, 보통 `/etc/kubernetes/manifests`)에서 직접 읽어** 띄우는 Pod. kubeadm은 컨트롤 플레인 네 개를 이 방식으로 띄운다.
- 왜 중요한가: 파일을 고치면 kubelet이 감지해서 Pod를 다시 만든다. 이것이 컨트롤 플레인 수리의 유일한 경로다. 이 랩에서 `fileCheckFrequency`는 20s, `syncFrequency`는 1m (`configz`에서 확인).
- mirror Pod: kubelet이 API 서버에 만들어 두는 **읽기 전용 그림자**. 이름은 `<pod이름>-<노드이름>`(예: `kube-scheduler-k8s-control-plane`), `ownerReferences[0].kind=Node`, annotation `kubernetes.io/config.source=file` (확인함). `k delete pod`로 지워도 kubelet이 static Pod를 지우지 않는다 (문서).
- **함정 (문서의 Caution)**: kubelet은 점(.)으로 시작하지 않는 **모든 파일**을 읽는다. 확장자 필터가 없어서 `cp kube-apiserver.yaml kube-apiserver.yaml.bak`을 같은 디렉터리에 두면 둘 다 Pod 정의로 읽혀 옛 설정이 적용될 수 있다. 백업은 `/tmp` 같은 다른 곳에.
- 관계: etcd 복원(B4)도 이 매니페스트를 고쳐 `data-dir`을 바꾼다.

### 증상으로 고장 난 구성요소 찾기
아래는 시뮬레이터 해설(q39, q40, q103, q104, q107, q108)과 문서에서 정리한 것이고, 컨트롤 플레인을 실제로 고장내 재현하지는 않았다 (미확인). 로그 문구는 아래 "자주 틀리는 점"의 샌드박스 재현을 쓴다.

| 증상 | 의심 | 먼저 볼 것 |
|---|---|---|
| `The connection to the server ... was refused` | apiserver 또는 etcd | 노드에서 `crictl ps -a \| grep -E 'apiserver\|etcd'` |
| 새 Pod가 Pending, `k describe pod`의 Events가 **아예 비어 있음** | scheduler 정지 | `k -n kube-system get pods`, scheduler 로그 |
| Pending인데 Events에 `0/3 nodes are available ...` | scheduler는 정상. 자원/taint/라벨 문제 | D5 |
| `k create deploy` 후 Deployment만 있고 ReplicaSet/Pod가 없음 | controller-manager 정지 또는 컨트롤러 비활성(`--controllers=`) | controller-manager 로그와 `--controllers` 플래그 |
| 컨트롤 플레인 Pod가 `Running`인데 `RESTARTS`가 계속 증가 | probe 포트/경로가 실제와 불일치 또는 크래시 | `k describe pod`의 Events, `crictl logs` |
| `ImagePullBackOff` (컨트롤 플레인 Pod) | 이미지 태그 오타 | `k describe pod`의 `Failed to pull image ... not found`, 같은 노드의 다른 매니페스트와 태그 비교 |

### 진단 도구 우선순위
1. `kubectl`이 되면: `k -n kube-system get pods -o wide`, `k -n kube-system describe pod <p>`, `k -n kube-system logs <p>`(`--previous`).
2. `kubectl`이 안 되면(노드에서): `crictl ps -a`(종료된 것 포함, `ATTEMPT` 열이 재시작 횟수), `crictl logs <id>`, `crictl logs --tail=20 <id>`.
3. 로그 파일 직접: `/var/log/pods/kube-system_<pod>_<uid>/<container>/<N>.log`. 확인함: 이 랩에서 `0.log`, `1.log`가 재시작별로 있다. 문서의 `/var/log/kube-apiserver.log` 경로는 kubeadm(컨테이너) 환경에는 없다 (이 랩의 `/var/log`에 `.log`는 `alternatives.log`, `dpkg.log`뿐).
4. kubelet 로그: `journalctl -u kubelet -n 50 --no-pager` (static Pod가 아예 안 뜰 때 매니페스트 파싱 오류가 여기 나온다).
5. 상태 엔드포인트: `curl -sk https://127.0.0.1:6443/livez`(apiserver), `.../readyz?verbose`, `https://127.0.0.1:10259/livez`(scheduler), `https://127.0.0.1:10257/healthz`(controller-manager), `curl -s http://127.0.0.1:2381/readyz`(etcd). 모두 `ok` (확인함).

## 예시
(노드 안 명령은 컨트롤 플레인 노드에서 `ssh` -> `sudo -i`. 이 노트는 컨트롤 플레인을 고장내지 않았다. "읽기 전용 점검"은 실제 실행으로 확인했고, "수리 절차"는 해설과 문서 기준이다.)

**상황 1: 컨트롤 플레인 현황을 한 번에 본다 (읽기 전용, 실행 확인).**
```bash
k -n kube-system get pods -o wide | grep -E 'etcd|apiserver|scheduler|controller'
k get --raw='/readyz?verbose' | tail -3          # ... readyz check passed
k get cs                                          # 'v1 ComponentStatus is deprecated' 경고가 나오지만 Healthy 3줄
k -n kube-system get lease kube-scheduler kube-controller-manager -o custom-columns=NAME:.metadata.name,HOLDER:.spec.holderIdentity
```
기대 결과: 네 Pod `1/1 Running`, `readyz check passed`, 리더 Lease의 HOLDER가 `k8s-control-plane_<uuid>`.

**상황 2: 노드에서 컨테이너와 static Pod 매니페스트를 본다 (읽기 전용, 실행 확인).**
```bash
ssh k8s-cp; sudo -i                                # 시험: ssh <컨트롤 플레인 노드>
ls /etc/kubernetes/manifests                       # etcd.yaml kube-apiserver.yaml kube-controller-manager.yaml kube-scheduler.yaml
crictl ps -a --name kube-scheduler                 # 이전 Exited 컨테이너(ATTEMPT 0)와 현재 Running(ATTEMPT 1)
crictl logs --tail=3 $(crictl ps --name kube-scheduler -q)
ls /var/log/pods/kube-system_kube-scheduler-*/kube-scheduler/      # 0.log 1.log
grep -E '^\s+- --' /etc/kubernetes/manifests/kube-scheduler.yaml
```
기대 결과 (이 랩): scheduler 플래그는 `--authentication-kubeconfig`, `--authorization-kubeconfig`, `--bind-address=127.0.0.1`, `--kubeconfig=/etc/kubernetes/scheduler.conf`, `--leader-elect=true`. 이 경로들이 `ls /etc/kubernetes/*.conf`에 실제 있어야 한다.

**상황 3: 상태 엔드포인트와 etcd 건강 확인 (읽기 전용, 실행 확인).**
```bash
curl -sk https://127.0.0.1:6443/livez; echo; curl -sk https://127.0.0.1:10259/livez; echo; curl -sk https://127.0.0.1:10257/healthz; echo
etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key endpoint health
kubeadm certs check-expiration | head -8
```
기대 결과: `ok` 세 줄, `https://127.0.0.1:2379 is healthy: successfully committed proposal: took = ...`, 인증서 만료일 표 (이 랩은 약 363일 남음). etcd 3.6의 `etcdctl`은 `ETCDCTL_API=3`을 붙이면 `unrecognized environment variable` 경고만 낸다. 인증서 경로(`/etc/kubernetes/pki/etcd/*`)는 etcd 매니페스트의 `--cert-file`, `--key-file`, `--trusted-ca-file`에서 가져온다.

**상황 4: static Pod 매니페스트 문법 검증 (실행 확인).** 매니페스트는 평범한 Pod 정의라서 API 서버로 사전 검증할 수 있다.
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: audit-agent
  namespace: default      # q41은 static-demo. 네임스페이스가 먼저 존재해야 mirror Pod가 보인다
spec:
  containers:
  - name: agent
    image: busybox:1.37
    command: ["sleep", "3600"]
```
```bash
k apply -f audit-agent.yaml --dry-run=server      # pod/audit-agent created (server dry run): 필드 이름이 맞다는 뜻
# 노드에서: 파일을 /etc/kubernetes/manifests/ 에 둔다. 미러 Pod 이름은 audit-agent-<노드이름>
k -n default get pod audit-agent-k8s-worker       # <pod이름>-<노드이름> (q41 해설 기준) (미확인)
```
`--dry-run=server`는 static Pod로서의 동작(디렉터리 위치)을 검증하지는 않는다. 디렉터리 위치는 `grep staticPodPath /var/lib/kubelet/config.yaml`로 확인한다.

**상황 5: 구성요소가 죽었을 때의 수리 절차 (q40, q39 해설 기준) (미확인).**
```bash
# kubectl이 되는 경우
k -n kube-system describe pod kube-scheduler-<노드>      # Events: Failed to pull image ... not found 이면 이미지 태그
# kubectl이 안 되는 경우 (apiserver 다운)
crictl ps -a | grep -E 'apiserver|etcd'                  # Exited/CrashLoop 컨테이너 id
crictl logs <id> 2>&1 | tail -20                         # 마지막 오류 한 줄이 원인
vim /etc/kubernetes/manifests/kube-apiserver.yaml        # 오타 수정 (백업은 /tmp/에)
watch crictl ps                                           # kubelet이 다시 만들 때까지 대기 (약 20초 + 기동 시간)
curl -sk https://127.0.0.1:6443/livez                     # ok 이면 복구
```
이미지 태그는 같은 디렉터리의 다른 매니페스트(예: apiserver)와 같은 버전이어야 한다 (`grep image: /etc/kubernetes/manifests/kube-*.yaml`). 수정 후에도 크래시면 `crictl logs`로 **두 번째 오류**를 찾는다 (q40: 이미지 태그 -> kubeconfig 경로 순서로 오류가 둘).

## 자주 틀리는 점
아래 "로그 문구"는 **컨트롤 플레인 이미지(v1.34.0)를 잘못된 플래그로 샌드박스 Pod(`nodeName: k8s-control-plane`, 내 네임스페이스)에서 직접 실행해 얻은 실제 출력**이다. 실제 static Pod가 같은 오타로 죽을 때도 `crictl logs`에 같은 문장이 나온다.
- 증상: 컨테이너가 바로 `Error`, `crictl logs` 끝에 `Error: unknown flag: --leader-elec` (앞에는 긴 `Usage:` 도움말이 붙는다) -> 플래그 철자 오타 (scheduler, controller-manager 모두 확인함) -> 로그는 `| tail -3`으로 끝만 읽고 매니페스트의 `- --플래그`를 고친다.
- 증상: scheduler 로그에 `"command failed" err="stat /etc/kubernetes/scheduler-conf.yaml: no such file or directory"` -> `--kubeconfig` 경로 오타 (확인함) -> `ls /etc/kubernetes/*.conf`와 대조 (`scheduler.conf`).
- 증상: apiserver 로그에 `F... Error creating leases: error creating storage factory: open /etc/kubernetes/pki/etcd/ca.crt.typo: no such file or directory` -> `--etcd-cafile` 경로 오타 (확인함) -> `ls /etc/kubernetes/pki/etcd/`와 대조. `--etcd-certfile`, `--etcd-keyfile`도 같은 방식.
- 증상: apiserver 로그에 `"command failed" err="authorization-mode \"RBCA\" is not a valid mode"` -> `--authorization-mode` 값 오타 (확인함, 정상 값은 `Node,RBAC`).
- 증상: apiserver 로그에 `failed to parse service-account-issuer-key-file: open ...: no such file or directory` -> `--service-account-signing-key-file`/`--service-account-key-file` 경로 오타 (확인함).
- 증상: `ImagePullBackOff`, `manifest for registry.k8s.io/kube-scheduler:v1.34.99 not found` 류 -> 이미지 태그 오타 -> 다른 컴포넌트와 같은 버전으로 (q40 해설 기준) (미확인).
- 증상: static Pod를 `k delete pod`로 지우거나 `k edit pod`로 고쳤는데 그대로다 -> mirror Pod는 읽기 전용 그림자, 삭제해도 kubelet이 static Pod를 지우지 않는다 (문서) -> 노드의 매니페스트 파일을 고친다.
- 증상: 백업 파일 때문에 고친 설정이 적용 안 됨/이상한 Pod가 뜸 -> `kube-apiserver.yaml.bak`을 manifests 디렉터리에 둠 (문서 Caution) -> 백업은 디렉터리 밖(`/tmp`)으로 옮긴다.
- 증상: 매니페스트가 이전 컨테이너를 그대로 쓰는 것처럼 보임 -> kubelet이 파일 변경을 감지하는 주기(이 랩 `fileCheckFrequency: 20s`)를 아직 안 기다림 -> 약 20초 + 기동 시간, `crictl ps`로 `CREATED`가 새로워졌는지 본다.
- 증상: 컨테이너는 `Running`인데 `RESTARTS`가 계속 증가 -> livenessProbe/startupProbe가 실제 포트와 불일치(예: 매니페스트의 `probe-port` 정의 포트와 플래그가 다름) 또는 앱 크래시 -> `k describe pod`에서 `Liveness probe failed`, probe 포트가 `containerPort`와 같은지 대조 (q108 해설 기준) (미확인).
- 증상: 컨트롤 플레인 노드가 아닌 곳에서 `/etc/kubernetes/manifests`를 찾음 -> 워커의 같은 디렉터리는 비어 있다(이 랩 `k8s-worker` 확인함) -> `ssh`한 노드가 컨트롤 플레인인지 `hostname`으로 확인.
- 증상: 고친 뒤 `exit`를 안 하고 다음 문제로 -> 노드에 남은 채로 `kubectl`을 쳐서 다른 컨텍스트/호스트 혼동 -> `exit`로 base 복귀.
- 시뮬레이터 차이: 클러스터 v1.34.0 (시험 v1.37)이고 노드가 Docker 컨테이너다. q39/q107은 apiserver를 직접 죽이므로 해당 노드의 kubectl이 끊긴다. `ek8s` 클러스터에서 연습하며, q103/q104/q107/q108은 한 번에 하나씩만 한다 (INDEX.md 충돌 3번).

## 빠르게 푸는 순서
1. (30초) `k -n kube-system get pods`: 비정상 Pod 이름(`-<노드>` 꼬리)이 어느 구성요소인지 본다. `k`가 안 되면 곧바로 4번으로.
2. (30초) 증상표로 구성요소 추정 (Pending+이벤트 없음 = scheduler, RS/Pod 안 생김 = controller-manager, 연결 거부 = apiserver/etcd).
3. (30초) `k -n kube-system describe pod <p>`: Events에 이미지 오류/Probe 실패가 있으면 그것이 원인 후보.
4. (30초) `ssh <컨트롤 플레인>` -> `sudo -i` -> `crictl ps -a | grep <구성요소>` -> `crictl logs <id> | tail -20`. 마지막 `E`/`F` 줄이 원인.
5. (1~2분) `/etc/kubernetes/manifests/<구성요소>.yaml`에서 해당 플래그/경로/이미지를 실제 파일과 대조(`ls`, `grep image:`)해 수정. 백업은 `/tmp`.
6. (1분) `watch crictl ps` 또는 `k -n kube-system get pods -w`로 재생성 대기. 크래시가 남으면 `crictl logs`로 **다음 오류**를 다시 읽는다.
7. (30초) `curl -sk https://127.0.0.1:<포트>/livez`(또는 `k get cs`), 증상이 있던 워크로드(Pending Pod 등) 정상화 확인 후 `exit`. (총 5~7분 목표)

## 연습 문제
- **오늘 풀 문제** (study-guide.md 5절 Day 2):
  - `q40` — kube-scheduler broken (image tag + kubeconfig path), pods Pending: 이미지 태그와 kubeconfig 경로 두 오류를 매니페스트에서 고친다.
  - `q41` — Static pod manifest in wrong dir + bad image: 매니페스트가 `manifest/`(s 없음)에 있고 이미지도 틀린 static Pod를 살린다.
- **추가 연습** (COVERAGE.md의 A2 개념 기준):
  - `q39` — kube-apiserver down (etcd CA path, secure-port) (hard, 가중치 8): API 서버가 죽은 상태에서 `crictl`로 복구. q37, q40과 같은 세트 금지.
  - `q107` — kube-apiserver crash: bad authorization-mode, missing tls key path (hard).
  - `q108` — Pending Pods: scheduler flag typo, then secure-port vs probe port.
  - `q103` — No ReplicaSet created, kube-controller-manager crash (flag typo + sa key path).
  - `q104` — RS and Job make no Pods, `--controllers=*,-replicaset,-job` (Running but inert): Pod는 Running인데 동작이 없는 경우.
  - `q18` — Restore etcd from a snapshot (destructive, cluster-soft): static Pod 매니페스트 편집이 포함되지만 주 개념은 B4. 마지막에 단독 실행.
- 주의: q103, q104, q107, q108은 서로 배타적이고 q37, q39, q40과도 충돌한다 (한 번에 컨트롤 플레인 결함 하나, 사이에 cluster-soft 초기화).
