# C6. Understand and use CoreDNS

## 이 항목에서 공부할 것
- [ ] 클러스터 DNS의 구성(Service `kube-dns`, Deployment `coredns`, 라벨 `k8s-app=kube-dns`, ConfigMap `coredns`)을 `k -n kube-system get ...`으로 찾는다
- [ ] Service / Pod / headless Pod의 DNS 이름 규칙을 쓰고 `nslookup`으로 확인한다
- [ ] Pod의 `/etc/resolv.conf`(search, nameserver, `ndots:5`)를 읽고 `dnsPolicy` 4가지(ClusterFirst, Default, None, ClusterFirstWithHostNet)의 차이를 설명한다
- [ ] `dnsPolicy: None` + `dnsConfig`로 Pod의 DNS를 직접 지정한다
- [ ] CoreDNS ConfigMap(Corefile)에 stub domain(별도 서버 블록 + `forward`)과 `rewrite name exact`를 추가한다
- [ ] 변경이 적용됐는지 확인하는 법(reload 대기 vs `rollout restart`, 로그의 `Reloading complete`)을 안다
- [ ] DNS 장애를 3단계(Pod resolv.conf → kube-dns Service/EndpointSlice → CoreDNS 로그/ConfigMap)로 진단한다
- [ ] 문서의 Corefile 예제를 복사할 때 현재 CoreDNS가 거부하는 지시어(`upstream`)를 걸러낸다

## 개념 설명

### 클러스터 DNS와 CoreDNS
모든 Pod는 자기 `/etc/resolv.conf`에 적힌 DNS 서버로 이름을 묻습니다. 그 서버가 CoreDNS입니다(전화번호부 안내원). kubelet이 Pod를 만들 때 CoreDNS Service의 IP를 resolv.conf에 넣어 줍니다.
- Service 이름은 구현이 CoreDNS여도 호환성 때문에 `kube-dns`입니다(문서 Note, 검증: `k -n kube-system get svc kube-dns` → 10.96.0.10, 53/UDP,53/TCP,9153/TCP).
- CoreDNS는 `kube-system`의 Deployment `coredns`(Pod 2개, 라벨 `k8s-app=kube-dns`, 검증)이고 설정은 ConfigMap `coredns`의 `Corefile` 키입니다. Pod에 `/etc/coredns`로 마운트됩니다.
- 쿠버네티스 이름(`cluster.local` 영역)은 `kubernetes` 플러그인이 Service/EndpointSlice를 보고 답하고, 나머지는 `forward`로 노드의 `/etc/resolv.conf`가 가리키는 상위 DNS에 넘깁니다.

### Service와 Pod의 DNS 레코드
| 대상 | 이름 | 답 |
|---|---|---|
| ClusterIP Service | `<svc>.<ns>.svc.cluster.local` | Service ClusterIP (A) |
| headless Service (`clusterIP: None`) | 위와 같은 이름 | Ready Pod IP들 (A 여러 개) |
| headless의 Pod (`hostname`+`subdomain` 필드가 있을 때) | `<hostname>.<svc>.<ns>.svc.cluster.local` | 그 Pod IP |
| Pod | `<IP의 점을 -로>.<ns>.pod.cluster.local` (예: `10-244-1-62.lab.pod.cluster.local`) | Pod IP |
| 이름 있는 포트 | `_http._tcp.<svc>.<ns>.svc.cluster.local` (SRV) | `0 100 80 <svc>...` |
| ExternalName Service | 위와 같은 이름 | CNAME |
위 레코드들은 모두 실제 클러스터에서 `nslookup`으로 확인했습니다. ClusterIP를 거꾸로 묻는 PTR(`nslookup 10.96.x.x`)도 Service 이름을 돌려줍니다.

### Pod의 resolv.conf, ndots, dnsPolicy
기본 Pod의 resolv.conf(검증):
```
search lab.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
```
`ndots:5`는 점이 5개 미만인 이름은 먼저 search 목록을 붙여 시도한다는 뜻입니다. 그래서 같은 네임스페이스의 `web`이 `web.lab.svc.cluster.local`로 풀립니다. 끝에 점을 찍은 FQDN(`web.lab.svc.cluster.local.`)은 search를 건너뜁니다.
- `ClusterFirst`(기본): 클러스터 DNS를 먼저 사용, 클러스터 도메인이 아닌 이름은 상위로 forward.
- `Default`: 노드의 resolv.conf를 상속(이름이 Default지만 기본값이 아님). 검증: 이 클러스터에서는 resolv.conf가 `nameserver 192.168.65.254`, `options ndots:0`이 되고, 이때 `backend.lab.svc.cluster.local`은 Service IP가 아니라 상위 DNS가 돌려준 엉뚱한 주소로 풀렸습니다(환경에 따라 NXDOMAIN일 수 있음). 클러스터 이름은 Service IP로 풀려야 정상입니다.
- `None`: 모든 설정을 `dnsConfig`(`nameservers`, `searches`, `options`)로 직접 지정. 이때 `nameservers`는 1개 이상 필수.
- `ClusterFirstWithHostNet`: `hostNetwork: true` Pod가 클러스터 DNS를 쓰려면 반드시 이 값. `hostNetwork: true`에 dnsPolicy를 안 쓰면 노드 DNS를 씁니다(검증).

### Corefile과 플러그인
기본 Corefile은 하나의 서버 블록 `.:53 { ... }`이고 지시어(플러그인) 순서대로 일합니다.
- `errors`, `log`(질의를 로그에 남김, 기본에는 없음), `health`, `ready`, `prometheus :9153`
- `kubernetes cluster.local in-addr.arpa ip6.arpa { pods insecure; fallthrough in-addr.arpa ip6.arpa; ttl 30 }`: 클러스터 이름
- `forward . /etc/resolv.conf`: 그 외 이름을 상위 DNS로
- `cache 30`, `loop`, `reload`(Corefile 변경을 자동 감지), `loadbalance`
- 영역(zone)마다 서버 블록을 따로 둡니다. 특정 도메인만 다른 DNS로 보내려면 `.:53 { }` **바깥에** `corp.internal:53 { errors; cache 30; forward . <DNS IP> }` 블록을 추가합니다(stub domain).
- `rewrite name exact A B`: 질의 이름 A를 B로 바꿔서 처리합니다. 답에서는 이름이 원래 A로 돌아옵니다.

### 변경 반영
ConfigMap을 고치면 Pod 안 파일이 갱신되고(수십 초) `reload`가 약 30초 주기로 감지합니다. 이 클러스터에서 측정한 총 소요는 약 100초였고 문서도 "allow two minutes"라고 합니다. 바로 반영하려면 `k -n kube-system rollout restart deploy coredns`.

## 예시
상황 1: 클러스터 DNS 현황을 읽기 전용으로 확인한다.
```bash
k -n kube-system get deploy,svc -l k8s-app=kube-dns
k -n kube-system get endpointslice -l kubernetes.io/service-name=kube-dns
k -n kube-system get cm coredns -o jsonpath='{.data.Corefile}'
k -n kube-system get cm coredns -o yaml > coredns-backup.yaml        # 수정 전 백업
```
기대 결과: `deployment.apps/coredns  2/2`, `service/kube-dns  ClusterIP  10.96.0.10  53/UDP,53/TCP,9153/TCP`, EndpointSlice의 ENDPOINTS에 CoreDNS Pod IP 2개. 이 클러스터의 Corefile은 기본형에 `forward . /etc/resolv.conf { max_concurrent 1000 }`, `cache 30 { disable success cluster.local ... }`가 더해진 형태입니다.

상황 2: 테스트 Pod에서 이름을 풀어 본다 (네임스페이스 `lab`, Service `backend`는 예시).
```bash
k -n lab run dnsutils --image=busybox:1.37 --command -- sleep 86400
k -n lab exec dnsutils -- cat /etc/resolv.conf
k -n lab exec dnsutils -- nslookup backend.lab.svc.cluster.local
k -n lab exec dnsutils -- nslookup -type=SRV _http._tcp.backend.lab.svc.cluster.local
k -n lab exec dnsutils -- nslookup backend.lab.svc.cluster.local 10.96.0.10      # DNS 서버를 직접 지정
k -n lab exec dnsutils -- wget -qO- -T3 http://backend.lab                         # libc 해석기는 search를 적용
```
기대 결과: `Name: backend.lab.svc.cluster.local  Address: 10.96.205.200`. 문서의 테스트 Pod(`admin/dns/dnsutils.yaml`)는 이미지 `registry.k8s.io/e2e-test-images/agnhost:2.39`입니다. busybox 1.37의 `nslookup`은 주의점이 있습니다(아래 "자주 틀리는 점").

상황 3: stub domain + rewrite (q35 형태). `corp.internal` 영역은 Service `corp-dns`(ClusterIP는 `k -n dns-lab get svc corp-dns -o jsonpath='{.spec.clusterIP}'`)로 보내고, `old-db.example.org`는 `db.dns-lab.svc.cluster.local`로 바꿔 답한다.
```bash
k -n kube-system edit cm coredns
```
```
.:53 {
    errors
    health {
       lameduck 5s
    }
    ready
    rewrite name exact old-db.example.org db.dns-lab.svc.cluster.local
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {
       max_concurrent 1000
    }
    cache 30
    loop
    reload
    loadbalance
}
corp.internal:53 {
    errors
    cache 30
    forward . 10.96.240.68
}
```
(`10.96.240.68`은 예시 IP이므로 반드시 실제 ClusterIP로.)
```bash
k -n kube-system rollout restart deploy coredns
k -n kube-system rollout status deploy coredns
k -n kube-system logs -l k8s-app=kube-dns --tail=20           # [INFO] plugin/reload ... Running configuration, 에러 없는지
k -n dns-lab exec dnsclient -- nslookup app.corp.internal
k -n dns-lab exec dnsclient -- nslookup old-db.example.org
```
검증 방법과 한계: kube-system의 CoreDNS는 공용이라 직접 수정하지 않았습니다. 대신 같은 이미지(`coredns:v1.12.1`)를 별도 네임스페이스에서 띄워 (a) 위 Corefile 전체가 파싱 오류 없이 시작되는지(kubernetes 플러그인은 RBAC가 없어 API 대기 상태), (b) `kubernetes` 줄을 `forward . <kube-dns IP>`로 바꾼 복사본에서 `corp.internal` 질의가 stub 서버의 `10.1.2.3`으로, `old-db.example.org`가 `db` Service의 ClusterIP로 답하는지 확인했습니다. 실제 kube-system에 적용한 결과는 이 노트에서 직접 확인하지 않았습니다(미확인).

상황 4: Pod가 이름을 못 풀 때, 개별 Pod의 DNS를 직접 지정 / 고친다 (q36 형태).
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: dns-example
spec:
  containers:
  - name: test
    image: busybox:1.37
    command: ["sleep", "86400"]
  dnsPolicy: "None"
  dnsConfig:
    nameservers: ["192.0.2.53"]
    searches: ["my.search.local"]
    options:
    - {name: ndots, value: "2"}
```
```bash
k exec dns-example -- cat /etc/resolv.conf     # search my.search.local / nameserver 192.0.2.53 / options ndots:2
```
`dnsPolicy`와 `dnsConfig`는 Pod 생성 후 수정할 수 없으므로 `k get pod X -o yaml`로 뽑아 고친 뒤 `k delete pod X` → `k apply`로 재생성합니다(q36 해설). 비교 대상으로 정상 Pod의 resolv.conf를 같이 보세요.

상황 5: 질의가 CoreDNS에 오는지 보려면 `log`를 Corefile에 한 줄 추가한다.
```bash
k -n kube-system edit cm coredns        # .:53 { 안, errors 다음 줄에  log  한 줄만 추가
k -n kube-system rollout restart deploy coredns
k -n kube-system logs -l k8s-app=kube-dns -f --tail=5
```
**시뮬레이터 차이**: CNI는 kindnet이고 서버는 v1.34.0입니다. 한때 `k8s-worker2`의 CNI 설정 대역이 노드 podCIDR와 어긋나 그 노드 Pod의 DNS/노드 간 통신이 실패한 적이 있다(랩 고장, 시험과 무관, 수정됨). 같은 증상이 다시 나오면 `kubectl --context k8s -n kube-system delete pod -l app=kindnet --field-selector spec.nodeName=k8s-worker2`로 kindnet을 재생성하거나 `bin/sim doctor`로 점검한다. 또 q46은 클러스터 DNS를 의도적으로 깨뜨리므로 단독으로 실행해야 합니다.

## 공식 문서에서 찾는 법
| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| Service/Pod DNS 이름 형식 | `dns for services and pods` | https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/ | `A/AAAA records` | YAML 없음. `<service-name>.<namespace>.svc.<cluster-domain>` 형식 확인 |
| Pod dnsPolicy 4가지, hostNetwork | 같은 페이지 | 같은 페이지 | `Pod's DNS Policy` | 맨 아래 `ClusterFirstWithHostNet` busybox YAML |
| Pod dnsConfig(nameservers, searches, options) | 같은 페이지 | 같은 페이지 | `Pod's DNS Config` | `service/networking/custom-dns.yaml` (dnsPolicy "None" + dnsConfig) |
| 기본 Corefile, 플러그인 설명 | `customizing dns service` | https://kubernetes.io/docs/tasks/administer-cluster/dns-custom-nameservers/ | `CoreDNS ConfigMap options` | 기본 ConfigMap YAML (`Corefile: |` 블록) |
| stub domain / 상위 DNS 지정 | 같은 페이지 | 같은 페이지 | `consul.local:53` | `consul.local:53 { errors; cache 30; forward . 10.150.0.1 }` 블록과 그 아래 최종 ConfigMap YAML |
| rewrite 플러그인 문법 | `coredns rewrite` | 위 4개 DNS 페이지(dns-custom-nameservers, dns-debugging-resolution, dns-pod-service, coredns)에는 `rewrite`가 없음을 확인함. 허용 사이트의 다른 페이지에 있는지는 (미확인) | 해당 없음 | 없음. `rewrite name exact 원래이름 새이름` 형태를 외워 둘 것 |
| DNS 점검 순서와 테스트 Pod | `debugging dns resolution` | https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/ | `dnsutils` | `admin/dns/dnsutils.yaml` (agnhost 이미지 Pod) |
| CoreDNS Pod 로그, Service, EndpointSlice 확인 명령 | 같은 페이지 | 같은 페이지 | `Check for errors in the DNS pod`, `Is DNS service up?`, `Are DNS endpoints exposed?` | `kubectl logs --namespace=kube-system -l k8s-app=kube-dns`, `kubectl get endpointslice -l kubernetes.io/service-name=kube-dns --namespace=kube-system` |
| 질의 로그 켜기 | 같은 페이지 | 같은 페이지 | `Are DNS queries being received/processed?` | 설명은 참고만. 예제 Corefile 전체를 복사하면 안 됨(아래 함정) |
| CoreDNS 개요 | `using coredns for service discovery` | https://kubernetes.io/docs/tasks/administer-cluster/coredns/ | `About CoreDNS` | 설명만 있고 복사할 YAML 없음 |

## 자주 틀리는 점
- 증상: `nslookup backend.lab`(또는 `kubernetes.default`)이 NXDOMAIN, 단일 이름 `nslookup backend`는 성공해도 NXDOMAIN 줄이 섞여 나오고 종료 코드 1 → 원인: busybox 1.37 nslookup은 점이 있는 이름에 search 도메인을 붙이지 않고, 단일 이름은 여러 search 후보를 차례로 시도하며 실패 줄을 출력함(검증: 같은 이름을 `wget http://backend.lab`으로 접속하면 성공) → 고침: 테스트는 FQDN `<svc>.<ns>.svc.cluster.local`로. 진짜 장애와 구분하려면 `wget`/`curl`도 써 보기. 다른 이미지(dnsutils/agnhost)에서의 동작은 (미확인).
- 증상: `log`를 켜려고 문서 `Are DNS queries being received/processed?`의 Corefile을 통째로 붙였더니 CoreDNS가 안 뜸, 로그에 `plugin/kubernetes: ... Error during parsing: unknown property 'upstream'` → 원인: 그 예제 Corefile의 `kubernetes` 블록에 옛 지시어 `upstream`이 남아 있음(검증: CoreDNS v1.12.1에서 재현) → 고침: 예제 전체를 복사하지 말고 기존 Corefile에 `log` 한 줄만 추가.
- 증상: ConfigMap을 고쳤는데 한참 동안 변화가 없음 → 원인: 파일 갱신과 reload 주기(측정 약 100초) → 고침: `k -n kube-system rollout restart deploy coredns`.
- 증상: Corefile에 오타(예: `forward`를 `forwrd`)를 냈는데 DNS는 계속 옛 설정으로 동작 → 원인: reload가 파싱에 실패하면 옛 설정을 유지하고 로그에만 `[ERROR] Restart failed: ... Unknown directive 'forwrd'`를 남김(검증). 이 상태에서 `rollout restart`하면 새 Pod는 `Error/CrashLoopBackOff`이고 옛 Pod는 롤링 업데이트 때문에 남아 있음(검증) → 고침: `k -n kube-system logs <pod>`의 `Error during parsing`이 가리키는 줄 번호의 오타 수정.
- 증상: `Unknown directive 'corp.internal:53'` → 원인: stub 영역 서버 블록을 `.:53 { }` 안에 넣음(검증) → 고침: `.:53`의 닫는 `}` 뒤에 별도 블록으로.
- 증상: Pod에서 모든 이름이 timeout → 원인: `dnsPolicy: None`에 잘못된 nameserver(검증: 192.0.2.53은 timeout) 또는 CoreDNS Pod/Endpoint 없음 → 고침: 1) Pod resolv.conf 2) `k -n kube-system get pods,svc -l k8s-app=kube-dns`, `k -n kube-system get endpointslice -l kubernetes.io/service-name=kube-dns` 3) CoreDNS 로그/ConfigMap 순서로.
- 증상: Pod는 외부 이름만 안 풀리거나 클러스터 이름만 안 풀림 → 원인: q46 해설 기준으로 Corefile의 `kubernetes cluster.lcl ...`(클러스터 도메인 오타)는 `svc.cluster.local` 질의를 NXDOMAIN으로, `forward . 10.255.255.1`은 외부 질의를 timeout으로 만듭니다. 이 노트에서 직접 재현하지는 않았습니다(미확인).
- 증상: CoreDNS Pod가 Running인데 해석이 안 됨 → 원인: Pod 상태와 설정 정상 여부는 별개(q46 해설) → ConfigMap과 로그를 반드시 확인.
- 증상: hostNetwork Pod에서 클러스터 이름이 안 풀림 → 원인: dnsPolicy 미지정이면 노드 DNS 사용(검증) → `ClusterFirstWithHostNet`.
- 증상: 명령이 엉뚱한 곳에 적용됨 → 원인: CoreDNS ConfigMap은 `kube-system`에 있음. `-n kube-system`을 빼먹으면 `NotFound` → 항상 `-n kube-system`. 수정 전 `coredns-backup.yaml` 백업.

2. (1분) 장애면 `k exec <client> -- cat /etc/resolv.conf` → `k -n kube-system get pods,svc -l k8s-app=kube-dns` 와 `k -n kube-system get endpointslice -l kubernetes.io/service-name=kube-dns` → `k -n kube-system logs -l k8s-app=kube-dns --tail=30` 순서로 본다.
3. (30초) `k -n kube-system get cm coredns -o yaml > coredns-backup.yaml` 백업.
4. (2분) `k -n kube-system edit cm coredns`. stub domain은 문서 `consul.local:53` 블록을 `.:53`의 닫는 `}` 뒤에 붙이고 도메인/IP만 수정. rewrite는 `.:53` 안에 `rewrite name exact A B` 한 줄.
5. (30초) `k -n kube-system rollout restart deploy coredns && k -n kube-system rollout status deploy coredns`.
6. (30초) `k -n kube-system logs -l k8s-app=kube-dns --tail=20`에서 `Error during parsing`이 없는지 확인.
7. (1분) 테스트 Pod에서 `nslookup <FQDN>`으로 새 결과 확인. 출력 파일을 요구하면 `| tee 경로`로 exec 바깥에서 저장(q46).
