# A3. Monitor cluster and application resource usage

## 이 항목에서 공부할 것
- [ ] `k top node`로 노드별 CPU/메모리 사용량과 사용률(%)을 읽고, `--sort-by`로 가장 바쁜 노드를 찾는다
- [ ] `k top pod -n <ns> --sort-by=cpu`와 `--sort-by=memory`로 가장 많이 쓰는 Pod 이름 하나만 뽑아 파일에 쓴다 (`--no-headers | head -1 | awk '{print $1}'`)
- [ ] `k top pod <pod> --containers`로 멀티 컨테이너 Pod의 컨테이너별 사용량을 본다
- [ ] `-A`, `-l <label>`, `--sum`으로 범위를 바꾸거나 합계를 낸다
- [ ] 가장 많이 쓰는 Pod의 소유 Deployment를 찾아 `k set resources`로 CPU limit을 건다 (request가 limit보다 크면 거부된다는 것도 안다)
- [ ] `k top`이 실패하면 APIService -> metrics-server Pod -> Service/EndpointSlice -> 로그 순서로 원인을 좁힌다
- [ ] "사용량(`top`)"과 "요청/한도(`requests`/`limits`, `describe node`의 Allocated resources)"를 구분해서 읽는다
- [ ] 공식 문서에서 `kubectl top pod` 예제와 Metrics API 설명(`resource metrics pipeline`)의 위치를 바로 찾는다

## 개념 설명

### Metrics API와 metrics-server (resource metrics pipeline)
- 무엇인가: 노드와 Pod의 CPU/메모리 "현재 사용량"을 API로 주는 통로. 데이터는 각 노드 kubelet(cAdvisor)에서 나오고, 클러스터 애드온인 metrics-server가 모아서 `metrics.k8s.io` API로 내놓는다. 아파트 계량기(kubelet) 숫자를 관리사무소(metrics-server)가 모아 게시판(API)에 붙여 두는 모양이다.
- 왜 필요한가: `kubectl top`과 HPA/VPA가 모두 이 API만 읽는다. 이게 죽으면 `top`도 HPA(D3)도 같이 멈춘다.
- 핵심 동작: 경로는 `kubelet -> metrics-server -> APIService(v1beta1.metrics.k8s.io) -> kube-apiserver -> kubectl top`. APIService는 `kube-system/metrics-server` Service를 가리킨다. 이 랩의 metrics-server는 `--metric-resolution=15s`라서 값이 약 15초 단위로 갱신된다 (Deployment args에서 확인함).
- 관계: 새로 만든 Pod은 첫 수집 전까지 `error: metrics not available yet`이 나온다 (확인함, 생성 직후). 약 30초 뒤에는 값이 나왔다.
- 이 파이프라인은 모니터링 도구가 아니다. 과거 기록도 없고 CPU/메모리 두 가지뿐이다. 그래서 "지금 누가 많이 쓰나"만 답한다.

### kubectl top (node / pod)
- 무엇인가: Metrics API를 사람이 읽기 좋게 표로 보여 주는 명령. `k top node`, `k top pod`.
- 읽는 법: CPU는 millicore (`1000m` = 코어 1개), 메모리는 working set(`Mi`). 노드의 `CPU(%)`, `MEMORY(%)`는 그 노드 allocatable 대비 비율이다 (확인함: allocatable cpu 10, 사용 1021m -> 10%).
- 핵심 옵션: `-A`(전체 네임스페이스), `-n`, `-l 라벨`, `--containers`(컨테이너별 줄), `--sort-by=cpu|memory`(내림차순, 가장 큰 것이 첫 줄), `--no-headers`, `--sum`(맨 아래 합계 줄). `--sort-by`에 다른 값을 쓰면 `error: --sort-by accepts only cpu or memory` (확인함).
- `--field-selector spec.nodeName=...`은 top에서 안 된다 (`"spec.nodeName" is not a known field selector`, 확인함). 노드별 Pod 목록은 `k get pods -A -o wide --field-selector spec.nodeName=<node>`로 먼저 뽑는다.

### 사용량(usage) vs 요청(requests) vs 한도(limits)
- `requests`는 스케줄러가 자리를 잡을 때 쓰는 숫자, `limits`는 실행 중 상한이다. CPU 한도를 넘으면 느려지고(throttle), 메모리 한도를 넘으면 죽는다(OOMKilled, A4).
- `top`은 이 둘이 아니라 "지금 실제로 쓰는 양"이다. 그래서 `top`이 한가해도 requests 합이 allocatable을 넘으면 새 Pod은 Pending이다. 노드의 requests 합계는 `k describe node <n>`의 `Allocated resources`에서 본다.
- 관계: limit을 걸면 `top`에 찍히는 CPU가 그 값 근처에서 멈춘다 (확인함: limit 150m 설정 후 `150m`, 걸기 전 `1000m`).

## 예시

### 예시 1. 노드와 Pod 사용량 훑기
상황: "클러스터가 느리다. 어느 노드/Pod이 바쁜지 확인하라."
```bash
k top node
k top node --sort-by=memory
k -n top-lab top pod
k -n top-lab top pod --sort-by=cpu
k top pod -A --sort-by=cpu | head -5
```
확인: 기대 (이 랩에서 실제로 본 형태)
```
NAME          CPU(cores)   CPU(%)   MEMORY(bytes)   MEMORY(%)
k8s-worker2   1021m        10%      390Mi           4%
NAME                     CPU(cores)   MEMORY(bytes)
burner-65cb5b7c87-vfmhs  1000m        1Mi
```
`-A`를 쓰면 첫 열에 `NAMESPACE`가 생기므로 `awk '{print $1}'`이 아니라 `$2`가 Pod 이름이다.

### 예시 2. 가장 많이 쓰는 Pod 이름을 파일에 (q50 형태)
상황: "ns `top-lab`에서 CPU 최대 Pod, 메모리 최대 Pod 이름만 각각 파일에, 노드 표는 통째로 파일에."
```bash
mkdir -p /home/candidate/q50
k -n top-lab top pod --sort-by=cpu --no-headers | head -1 | awk '{print $1}' > /home/candidate/q50/top-cpu-pod.txt
k -n top-lab top pod --sort-by=memory --no-headers | head -1 | awk '{print $1}' > /home/candidate/q50/top-mem-pod.txt
k top node > /home/candidate/q50/nodes.txt
cat /home/candidate/q50/*.txt
```
`--no-headers`를 빼면 `NAME` 헤더가 첫 줄이라 파일에 `NAME`이 들어간다. 명령이 실패하면 파일은 비어 있고 오류는 터미널에만 나오므로 항상 `cat`으로 확인한다. (이 랩에서 같은 파이프로 CPU 최대 = `burner-...`, 메모리 최대 = `memhog`가 나옴을 확인함.)

### 예시 3. 컨테이너별 사용량 + 소유 Deployment에 CPU limit 걸기
상황: "CPU를 가장 많이 쓰는 Pod의 Deployment에 CPU limit 150m을 걸어라. 삭제/replicas 변경 금지."
```bash
k -n top-lab top pod --containers                       # 컨테이너별 줄 (멀티 컨테이너면 -c 후보 확인)
P=$(k -n top-lab top pod --sort-by=cpu --no-headers | head -1 | awk '{print $1}')
k -n top-lab get pod $P -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}{"\n"}'
# 기대: ReplicaSet/burner-c545fcf66   -> Deployment 이름은 burner (뒤의 해시를 뗀다)
k -n top-lab set resources deploy/burner --limits=cpu=150m
k -n top-lab rollout status deploy/burner
k -n top-lab get deploy burner -o jsonpath='{.spec.template.spec.containers[0].resources}{"\n"}'
# 기대: {"limits":{"cpu":"150m"},"requests":{"cpu":"50m","memory":"16Mi"}}
```
약 30초 뒤 `k -n top-lab top pod`를 다시 치면 새 Pod이 `150m` 근처로 내려온다. 롤아웃 직후에는 옛 Pod(1000m)이 잠깐 같이 보일 수 있다 (확인함).
limit이 기존 request보다 작으면 거부된다: `must be less than or equal to cpu limit of 20m` (limit 20m 시도로 확인함). 그때는 `--requests=cpu=10m --limits=cpu=20m`처럼 같이 줄인다.

### 예시 4. top이 안 될 때 진단 순서 (읽기 전용 명령)
상황: `k top nodes`가 `Metrics API not available`류 오류를 낸다 (q105, q106 형태).
```bash
k get apiservice v1beta1.metrics.k8s.io                       # AVAILABLE 열이 True 인가
k get apiservice v1beta1.metrics.k8s.io -o jsonpath='{.status.conditions[0]}{"\n"}'   # reason / message
k -n kube-system get pods -l k8s-app=metrics-server           # Ready 1/1 인가
k -n kube-system get endpointslices -l kubernetes.io/service-name=metrics-server       # 엔드포인트가 있는가
k -n kube-system logs deploy/metrics-server --tail=20         # x509, connection refused 같은 원인
k -n kube-system get svc metrics-server -o jsonpath='{.spec.ports}{"\n"}'              # targetPort 가 컨테이너 포트와 맞는가
```
정상일 때 기대: `AVAILABLE True`, condition `"reason":"Passed","message":"all checks passed"`, Pod `1/1`, EndpointSlice의 PORTS `10250`, Service `targetPort":"https"` (모두 확인함). 이 클러스터는 정상이라 실패 화면은 재현하지 않았다.
원인 판별 (q105/q106 해설 기준, 실패 상태는 공유 클러스터라 직접 만들지 않음 **(미확인)**): `MissingEndpoints`면 Pod 미준비/selector, `FailedDiscoveryCheck`+connection refused면 Service `targetPort` 불일치, 로그에 `x509: cannot validate certificate`면 metrics-server에 `--kubelet-insecure-tls` 인자 누락.

### 예시 5. 사용량이 아니라 요청/한도를 보고 싶을 때
상황: "Pod이 Pending인데 노드는 한가해 보인다."
```bash
k describe node k8s-worker2 | sed -n '/Allocated resources/,/Events/p'
k -n top-lab get pods -o custom-columns='NAME:.metadata.name,CPU_REQ:.spec.containers[*].resources.requests.cpu,CPU_LIM:.spec.containers[*].resources.limits.cpu,MEM_REQ:.spec.containers[*].resources.requests.memory'
```
기대: `Allocated resources`에 `cpu 160m (1%)  100m (1%)` 같은 requests/limits 합계 표, 두 번째 명령은 Pod별 요청/한도 표 (둘 다 확인함). Pending의 이유는 `k describe pod`의 Events (`Insufficient cpu` 등, D5/A4)에서 확인한다.

## 자주 틀리는 점
- `error: metrics not available yet` -> Pod이 방금 만들어져 아직 수집 전 -> 30~60초 뒤 다시 친다 (확인함). 몇 분 뒤에도 같으면 예시 4의 진단 순서로 간다.
- `k top pod`가 `No resources found in default namespace.` -> 네임스페이스를 안 줬다 -> `-n <ns>` 또는 `-A` (확인함). 문제의 namespace를 매번 확인한다.
- 파일 첫 줄에 `NAME`이 들어갔다 -> `--no-headers`를 빼먹었다 -> 위 예시 2의 파이프로 다시 쓴다. `-A`를 쓰면 이름은 `$1`이 아니라 `$2`다.
- "요청을 가장 많이 한 Pod"을 물었는데 `top`을 봤다 -> `top`은 사용량이다 -> `custom-columns`로 requests를 뽑는다 (예시 5).
- `set resources`가 `must be less than or equal to cpu limit` 오류 -> 기존 request가 새 limit보다 크다 (확인함) -> request도 같이 낮춘다.
- limit을 걸었는데 `top`에서 옛 Pod 값이 보인다 -> Deployment가 롤아웃되며 옛 Pod이 Terminating인 동안 같이 나온다 (확인함) -> `rollout status` 후 30초 기다린다.
- `top node`의 CPU%가 낮은데 Pod이 Pending -> 사용률이 아니라 requests 합이 문제 -> `describe node`의 Allocated resources.
- 시뮬레이터 차이: (1) 이 클러스터는 v1.34.0이고 시험 문서는 v1.37이다. 문서의 Metrics API 예제는 `metrics.k8s.io/v1`(문서에 "Stable since Kubernetes v1.37")인데 이 랩은 `metrics.k8s.io/v1beta1`만 제공한다 (`k get --raw /apis/metrics.k8s.io/v1/nodes`가 `NotFound`, 확인함). (2) 이 랩의 metrics-server는 `--kubelet-insecure-tls`로 돈다 (`simulator/docs/KNOWN_LIMITS.md`). 실제 시험 환경의 인자는 **(미확인)**. (3) 이 랩에는 `k8s-worker2` 노드의 Pod 네트워크가 깨져 있다 (C1 참고). `top`과는 무관하지만 그 노드의 Pod에서 다른 노드로 요청이 안 나간다.

## 빠르게 푸는 순서
1. 문제 첫 줄의 `kubectl config use-context ...`와 namespace, 저장할 파일 경로를 확인한다 (0.5분).
2. `k top node`, `k -n <ns> top pod --sort-by=cpu`를 쳐서 값이 나오는지 본다. `metrics not available yet`이면 30초 기다리며 다음 단계를 읽는다 (1분).
3. 이름만 필요하면 `--no-headers | head -1 | awk '{print $1}' > 파일`로 저장하고 `cat`으로 확인한다. cpu와 memory 두 번 따로 한다 (1분).
4. 표 통째로 필요하면 `k top node > 파일`처럼 리다이렉트만 한다. 가공하지 않는다 (0.5분).
5. 한도를 걸라고 하면 Pod의 `ownerReferences`로 Deployment 이름을 찾고 `k set resources deploy/<name> --limits=cpu=150m` (1분).
6. `k rollout status`, `k get deploy -o jsonpath='{...resources}'`로 값이 들어갔는지 확인한다 (0.5분).
7. `top`이 계속 실패하면 예시 4의 순서로 apiservice -> Pod -> endpointslice -> 로그를 본다 (2분). 전체 목표 약 5분.
