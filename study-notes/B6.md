# B6. Use Helm and Kustomize to install cluster components

## 이 항목에서 공부할 것
- [ ] `helm repo add` + `helm repo update` 후 `helm search repo <repo>/<chart> --versions`로 모든 CHART/APP VERSION을 보고 요구한 버전을 고른다
- [ ] `helm show values <repo>/<chart> --version X`로 값 이름을 찾는다 (CRD 설치 여부 같은 스위치 포함)
- [ ] `helm install <rel> <repo>/<chart> --version X -n <ns> --create-namespace -f values.yaml --set k=v --wait`로 설치한다 (`--set`이 `-f`보다 우선)
- [ ] `helm upgrade`로 값 하나만 바꾸되 기존 값을 잃지 않는다 (`--reuse-values` 또는 `--reset-then-reuse-values`)
- [ ] `helm history`로 revision을 확인하고 `helm rollback <rel> <revision>`으로 명시한 revision으로 되돌린다
- [ ] `helm template`으로 클러스터에 아무것도 만들지 않고 YAML을 파일로 저장한다 (`-n`, `-f`, `--set`, `--skip-tests`)
- [ ] `helm list -A`, `helm get values/manifest`, `helm uninstall`로 릴리스를 조회·정리한다 (네임스페이스 `-n`을 잊지 않는다)
- [ ] `kustomization.yaml` overlay를 작성해 `k kustomize`로 미리 보고 `k apply -k`로 배포한다 (namespace, namePrefix, labels, images, generator, patches)

## 개념 설명

### Helm: chart / repository / release / revision
- 무엇: chart는 "쿠버네티스 YAML 템플릿 묶음 + 기본값(values.yaml)", repository는 chart를 모아 둔 웹 주소(`index.yaml`), release는 chart를 클러스터에 설치한 **인스턴스**(이름 붙은 설치본), revision은 release의 변경 이력 번호다.
- 왜: 같은 chart를 이름만 바꿔 여러 번 설치하고, 값만 바꿔 업그레이드·롤백하기 위해 쓴다. cert-manager, nginx-gateway-fabric, Argo CD 같은 클러스터 컴포넌트가 chart로 배포된다.
- 핵심 동작: 설치·업그레이드·롤백은 모두 revision을 **하나 더 만든다** (되돌려도 번호는 줄지 않는다). release 이력은 해당 네임스페이스의 Secret `sh.helm.release.v1.<이름>.v<revision>`으로 저장된다. 그래서 release는 네임스페이스에 속하고, `-n`을 빼면 default 네임스페이스만 본다.
- 두 가지 버전을 구분한다: `CHART VERSION`(chart 자체 버전, `--version`이 고르는 값)과 `APP VERSION`(chart가 배포하는 앱 버전). "앱 1.4를 설치하라"면 `--versions`로 모든 행을 보고 APP VERSION이 1.4인 행의 CHART VERSION을 쓴다.
- 비유: chart는 레시피, values는 주문서, release는 "오늘 만든 요리", revision은 그 요리를 고친 횟수.

### values와 우선순위
- 낮음 -> 높음: chart 기본값(`values.yaml`) < `-f file` (여러 번이면 뒤가 우선) < `--set`. 확인은 `helm get values <rel>`(사용자가 준 값만) / `-a`(계산된 전체).
- `--set` 문법: `a.b=c`(중첩), `list[0].key=v`(배열), 키 안의 점은 `\.` (예: `nodeSelector.kubernetes\.io/os=linux`), 숫자처럼 보이는 문자열은 `--set-string`.
- **없는 키를 쓰면 에러 없이 무시된다** (`replicacount=5`는 대소문자가 달라 무시되어 replicas가 그대로 1). 쓴 뒤 `helm get values`나 `helm template | grep`으로 반영을 확인한다.
- `helm upgrade`는 기본적으로 **이전 revision의 `--set`/`-f` 값을 가져오지 않는다**. 값을 다시 안 주면 chart 기본값으로 돌아간다. `--reuse-values`는 이전 값을 그대로 쓰고 새 `--set`만 덮는다. `--reset-then-reuse-values`는 chart의 (새 버전) 기본값에 이전 값을 얹는다.

### install / upgrade / rollback
- `helm install <릴리스> <chart>`: 새 release 생성. 이름이 이미 있으면 `cannot re-use a name that is still in use`. 로컬 디렉터리/`.tgz`/URL도 chart로 쓸 수 있다.
- `helm upgrade <릴리스> <chart>`: revision +1. `--install`을 붙이면 없을 때 설치한다.
- `helm rollback <릴리스> <revision>`: 해당 revision의 내용으로 **새 revision**을 만든다 (DESCRIPTION이 `Rollback to N`). revision을 생략하면 "현재 바로 앞 번호"로 돌아가는데, 이미 한 번 rollback한 뒤라면 그 앞 번호가 방금 버린 **망가진 revision**이다 (rev 4가 "Rollback to 2"일 때 번호 없이 rollback하면 망가진 rev 3으로 돌아가는 것을 확인했다). 항상 번호를 명시한다.
- `--wait`는 Pod가 Ready가 될 때까지 기다리고 `--timeout`(기본 5분)이 지나면 revision을 `failed`로 기록한다. `--wait` 없이 업그레이드하면 이미지가 틀려도 명령은 `deployed`로 끝난다 (Pod만 `ErrImagePull`).
- `--create-namespace`는 네임스페이스가 없을 때 만든다. 없이 쓰면 `namespaces "x" not found`.

### helm template (렌더링만)
- 무엇: chart + values를 로컬에서 YAML로 렌더링해 출력만 한다. 클러스터에 release도 오브젝트도 만들지 않는다 (`KUBECONFIG=/dev/null`에서도 렌더링되는 것을 확인했다).
- 주의: 테스트 훅 Pod(`helm.sh/hook: test`)도 같이 렌더링된다. 빼려면 `--skip-tests`. `-n`을 주면 `.Release.Namespace`에 반영되고, `kubectl apply`용으로 쓸 때는 `apply -n`도 맞춘다.
- `helm install --dry-run`은 비슷하지만 release 이름/NOTES/hook까지 보여 주며 `--dry-run=server`면 서버 검증도 한다 (해도 release는 만들어지지 않는다).

### Kustomize: base / overlay / kustomization.yaml
- 무엇: 템플릿 없이 "원본 YAML(base) 위에 변경을 선언(overlay)"하는 방식. `kustomization.yaml`이 있는 디렉터리가 빌드 단위다. kubectl에 내장되어 있다 (`k kustomize <dir>` 미리보기, `k apply -k <dir>` 적용).
- 구조: `base/`(deployment.yaml, service.yaml, kustomization.yaml)와 `overlays/prod/kustomization.yaml`(`resources: [../../base]` + 변경). base는 overlay를 모르고, overlay가 base를 참조한다.
- 자주 쓰는 필드:

| 필드 | 효과 |
|---|---|
| `namespace` | 모든 리소스의 namespace를 설정 (네임스페이스를 만들어 주지는 않는다) |
| `namePrefix` / `nameSuffix` | 모든 리소스 이름 앞/뒤에 붙임 (Service/ConfigMap/Secret 참조는 자동 갱신, 아래 주의) |
| `labels: [{pairs: {k: v}, includeSelectors: true}]` | 라벨 추가. `includeSelectors: true`면 selector까지 바꾼다 |
| `images: [{name, newName, newTag}]` | 이미지 이름/태그 치환 (패치 불필요) |
| `replicas: [{name, count}]` | Deployment 등의 replicas 설정 |
| `configMapGenerator` / `secretGenerator` | literals/files/envs에서 생성. 이름 뒤에 내용 해시가 붙고 참조는 자동 치환 |
| `generatorOptions.disableNameSuffixHash` 또는 generator별 `options` | 해시 접미사 제거 |
| `patches` | `path:` 파일 또는 인라인 `patch:`. strategic merge(YAML) 또는 JSON6902(`- op: replace`)는 `target:`과 함께 |

- 이름 참조 자동 갱신은 **kustomization이 관리하는 리소스에 대해서만** 일어난다. 생성기도 없고 base에도 없는 ConfigMap 이름(`envFrom`)은 `namePrefix`가 붙어도 그대로 남는다.
- deprecated: `bases:`(-> `resources:`), `commonLabels:`(-> `labels:`), `patchesStrategicMerge:`(-> `patches:`). 빌드는 되지만 `# Warning: 'bases' is deprecated`가 출력된다.

### Helm과 Kustomize를 언제 쓰나
- chart가 주어지고 "값만 바꿔 설치"하면 Helm. 이미 YAML이 있고 "환경별로 조금씩 바꿔 배포"하면 Kustomize. 시험 문제는 문장에서 도구가 드러난다 ("repository", "release", "chart" vs "overlay", "kustomization").

## 예시

**상황 1: 저장소를 추가하고 chart의 모든 버전을 본 뒤, 0.1.0 버전을 값 파일 + replica 덮어쓰기로 설치한다. (저장소 `http://exam-assets/charts`, chart `webapp`)**
```bash
helm repo add cka-charts http://exam-assets/charts
helm repo update
helm search repo cka-charts/webapp --versions        # CHART VERSION 0.2.0, 0.1.0 모두 보임 (--versions 없으면 최신 하나)
cat > web-values.yaml <<'EOF'
replicaCount: 1
podLabels:
  team: blue
EOF
helm install web cka-charts/webapp --version 0.1.0 -n demo --create-namespace \
  -f web-values.yaml --set replicaCount=2 --wait
```
확인:
```bash
helm list -n demo                    # web  demo  1  deployed  webapp-0.1.0  1.27
helm get values web -n demo          # USER-SUPPLIED VALUES: podLabels.team: blue, replicaCount: 2  (--set이 파일을 이김)
k -n demo get deploy,pods            # 2/2 Ready
```

**상황 2: 업그레이드가 망가졌다. 이력을 보고 정상 revision으로 되돌린 뒤 값을 유지한 채 이미지 태그를 바꾼다.**
```bash
helm upgrade web cka-charts/webapp --version 0.2.0 -n demo --reuse-values --set image.tag=1.26 --wait      # revision 2 (정상)
helm upgrade web cka-charts/webapp --version 0.2.0 -n demo --reuse-values --set image.tag=9.99.99-nope      # revision 3 (깨짐, 명령은 성공)
k -n demo get pods                                  # 새 Pod 하나가 ErrImagePull, 기존 2개는 Running
helm history web -n demo                            # 1 superseded / 2 superseded / 3 deployed
helm get values web -n demo --revision 2            # 되돌릴 revision의 값 확인
helm rollback web 2 -n demo --wait                  # "Rollback was a success!"
```
확인:
```bash
helm history web -n demo | tail -2                  # 4  deployed  ... Rollback to 2  (번호는 4: 되돌려도 증가)
k -n demo get pods                                  # 2/2 Running, 깨진 Pod 사라짐
```
`--reuse-values` 없이 `helm upgrade ... --set image.tag=1.26`만 하면 `replicaCount`와 `podLabels`가 chart 기본값(replicas 1, 라벨 없음)으로 돌아간다. 하나만 바꿀 때는 `--reuse-values`를 습관으로.

**상황 3: 설치하지 않고 렌더링만 해서 파일로 저장하고, 그 YAML이 서버에서 유효한지 본다.**
```bash
helm template preview cka-charts/webapp --version 0.2.0 -n demo -f web-values.yaml --set replicaCount=3 --skip-tests > preview.yaml
grep -E '^kind:|replicas:' preview.yaml             # ServiceAccount, Service, Deployment, replicas: 3
k -n demo apply --dry-run=server -f preview.yaml    # ... created (server dry run), 실제로는 만들어지지 않음
helm list -n demo -q                                # preview 릴리스가 없다
```

**상황 4: chart의 CRD 설치 스위치를 켜서 렌더링한다 (이름은 chart마다 다르다).**
```bash
helm show values cka-charts/cert-manager | grep -n -i -A3 '^crds:'       # crds.enabled: false
helm template cm cka-charts/cert-manager -n cert-manager --set crds.enabled=true --skip-tests | grep -c '^kind: CustomResourceDefinition'   # 6 (기본값이면 0)
```
(Argo CD chart의 CRD 스위치 이름은 확인하지 못했다. 미확인. `helm show values ... | grep -i crd`로 찾는다. 위 렌더링만 실행했고 cert-manager 설치는 클러스터 공유 CRD를 건드려 하지 않았다.)

**상황 5: base 위에 prod overlay를 만들어 배포한다 (namespace `demo`, prefix, 라벨, 이미지 태그, replicas, ConfigMap 생성, 메모리 패치).**
```bash
cat > overlays/prod/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base
namespace: demo
namePrefix: prod-
labels:
- pairs:
    env: prod
  includeSelectors: true
replicas:
- name: api
  count: 2
images:
- name: nginx
  newTag: 1.27-alpine
configMapGenerator:
- name: api-config
  literals:
  - LOG_LEVEL=warn
patches:
- target:
    kind: Deployment
    name: api
  patch: |-
    - op: replace
      path: /spec/template/spec/containers/0/resources/limits/memory
      value: 128Mi
EOF
k create ns demo
k kustomize overlays/prod        # 미리보기
k apply -k overlays/prod
```
확인 (base의 Deployment `api`는 `envFrom.configMapRef.name: api-config`, `image: nginx:1.26`, memory limit 64Mi):
```bash
k kustomize overlays/prod | grep -E 'name: prod-|replicas|image:|memory|namespace'   # prod-api, prod-api-config-<해시>, replicas: 2, nginx:1.27-alpine, 128Mi
k -n demo get deploy,svc,cm -l env=prod                # prod-api 2/2, prod-api, prod-api-config-<해시>
k diff -k overlays/prod; echo $?                       # 변경 없으면 출력 없이 0
k delete -k overlays/prod                              # 지울 때도 -k
```
`envFrom`의 이름이 `prod-api-config-<해시>`로 자동 치환되는 것이 핵심이다. 패치의 `target.name`은 prefix가 붙기 전 원래 이름(`api`)을 쓴다. 이 overlay는 `notes-b6` 네임스페이스에서 실제로 apply하고 `delete -k`까지 확인했다 (예시의 `demo`로 바꿔 써도 같다).

**상황 6: 동료가 만든 overlay가 deprecated 필드와 경로 오타를 갖고 있다. 고치고, Secret을 해시 없이 만든다.**
```bash
# overlays/dev/replicas-patch.yaml : apiVersion apps/v1, kind Deployment, metadata.name api, spec.replicas 3
cat overlays/dev/kustomization.yaml        # 고치기 전
#   bases: [../../bsae]   namespace: demo   namePrefix: dev-   commonLabels: {env: dev}   patchesStrategicMerge: [replicas-patch.yaml]
k kustomize overlays/dev                   # '# Warning: 'bases' is deprecated...' 3줄 + 경로 오류
cat > overlays/dev/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base
namespace: demo
namePrefix: dev-
labels:
- pairs:
    env: dev
  includeSelectors: true
patches:
- path: replicas-patch.yaml
secretGenerator:
- name: db-creds
  literals:
  - password=s3cr3t
  options:
    disableNameSuffixHash: true
EOF
k kustomize overlays/dev | grep -E 'Warning|password|name: dev-|replicas'
```
기대 결과: 경고 없음, `password: czNjcjN0`(s3cr3t의 base64), Secret 이름 `dev-db-creds`(해시 없음), `name: dev-api`, `replicas: 3`. `bases:`/`commonLabels:`/`patchesStrategicMerge:`가 각각 `resources:`/`labels:`/`patches:`로 바뀐 것이 핵심이다. `k apply -k overlays/dev`는 `demo` 네임스페이스가 없으면 `namespaces "demo" not found`로 실패한다 (그 오류도 확인했다).

시뮬레이터 차이: 시뮬레이터의 `helm`은 exam-term에 v3.18.6, 호스트에는 v4.0.1이 있고 시험의 Helm 버전은 알 수 없다(미확인). helm.sh 문서 페이지는 Helm 4 기준(`Version: 4.3.1`)으로 보인다. Helm 4는 `--atomic`이 `--rollback-on-failure`로 바뀌고 `--wait`가 값을 받는 등 플래그가 달라진다. `--create-namespace`, `--reuse-values`, `--reset-then-reuse-values`, `--dry-run=server`는 두 버전의 `--help`에 모두 있다 (v3.18.6에서는 실제로 실행해 확인). 모르면 터미널에서 `helm install --help`. 저장소 URL은 시험에서는 문제에 주어지고 시뮬레이터는 `http://exam-assets/charts`다 (chart: webapp 0.1.0/0.2.0, podinfo, cert-manager, cka-web, cka-notes, nginx-gateway-fabric).

## 공식 문서에서 찾는 법
허용 사이트만 쓴다. 검색 결과 순위는 직접 확인하지 못했다(미확인). 안 나오면 URL 경로를 주소창에 직접 쓴다. **`helm install`의 `--version`, `--create-namespace`, `--reuse-values`, `helm template`, `--skip-tests`는 using_helm 페이지에 설명이 없다.** 그 페이지가 "플래그 전체는 `helm <command> --help`"라고 안내하므로 터미널 `--help`를 쓴다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| 저장소 추가/목록 | `helm repo add` | https://helm.sh/docs/intro/using_helm/ | `Working with Repositories` | `helm repo add dev https://example.com/dev-charts` |
| chart 검색 | `helm search repo` | 위와 같음 | `Finding Charts` | `helm search repo brigade` (`--versions`는 `helm search repo --help`) |
| 설치 기본형, 릴리스 이름 | `helm install` | 위와 같음 | `Installing a Package` | `helm install happy-panda bitnami/wordpress` |
| 기본값 확인 | 위와 같음 | 위와 같음 | `Customizing the Chart Before Installing` | `helm show values bitnami/wordpress` |
| 값 파일 / `--set` 규칙 | 위와 같음 | 위와 같음 | `Format and Limitations of --set` | `helm install -f values.yaml ...`, 배열/이스케이프 예제 |
| 로컬 chart, URL 설치 | 위와 같음 | 위와 같음 | `More Installation Methods` | `helm install foo path/to/foo` |
| upgrade / rollback / history | `helm rollback` | 위와 같음 | `Upgrading a Release, and Recovering on Failure` | `helm upgrade -f panda.yaml ...`, `helm get values`, `helm rollback happy-panda 1` |
| `--wait`, `--timeout` | 위와 같음 | 위와 같음 | `Helpful Options for Install/Upgrade/Rollback` | (옵션 설명) |
| 삭제, `--keep-history` | `helm uninstall` | 위와 같음 | `Uninstalling a Release` | `helm uninstall happy-panda` |
| helm 클라이언트 설치 | `installing helm` | https://helm.sh/docs/intro/install/ | `From Apt`, `From Script` | 해당 설치 블록 |
| 생성기(ConfigMap/Secret) | `kustomize` | https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/ | `configMapGenerator`, `secretGenerator`, `generatorOptions` | `cat <<EOF >./kustomization.yaml` 블록 |
| namespace/prefix/labels | 위와 같음 | 위와 같음 | `Setting cross-cutting fields` | `namespace: my-namespace`, `namePrefix: dev-`, `labels:` 블록 |
| 패치 (strategic merge / JSON6902), images | 위와 같음 | 위와 같음 | `increase_replicas.yaml`, `Json6902`, `newTag` | `patches: - path: ...`, `- target:` + `op: replace`, `images: newTag:` |
| base/overlay 구조 | 위와 같음 | 위와 같음 | `Bases and Overlays` | `resources: - ../../base` overlay 블록 |
| apply/get/diff/delete `-k` | 위와 같음 | 위와 같음 | `How to apply/view/delete objects using Kustomize` | `kubectl apply -k ./`, `kubectl diff -k ./`, `kubectl delete -k ./` |

kustomization 페이지의 `Kustomize Feature List` 표에는 `replicas`가 없다 (`replicas:` 필드는 실제로 동작함을 확인했다). 문서에서 replicas를 바꾸려면 같은 페이지의 `increase_replicas.yaml` 패치 예제를 쓴다.

## 자주 틀리는 점
- 증상: 업그레이드 뒤 설정이 사라졌다 (replicas, 라벨이 기본값) -> 원인: `helm upgrade`에 `--reuse-values`를 안 줬다 -> `helm get values --revision N`으로 이전 값을 보고 `--reuse-values`(또는 `-f`로 값 파일을 다시) 준다.
- 증상: `helm list`가 비어 있다 / `helm get values web`가 `release: not found` -> 원인: `-n <ns>`를 빼서 default 네임스페이스만 봤다 -> `-n` 또는 `helm list -A`.
- 증상: 최신 버전이 설치됐다 -> 원인: `--version`을 생략했다 (`search repo`는 `--versions` 없이는 최신 한 행만 보인다) -> `--versions`로 확인 후 `--version`을 명시.
- 증상: `INSTALLATION FAILED: create: failed to create: namespaces "x" not found` -> `--create-namespace` 추가. `cannot re-use a name that is still in use` -> 이미 있는 이름이다. `helm list -A`로 확인하고 `upgrade --install`이나 다른 이름을 쓴다.
- 증상: `chart "webapp" matching 9.9.9 not found in ... index (try 'helm repo update')` -> 버전 오타이거나 `helm repo update`를 안 했다. `repo notesrepo not found` -> 저장소 이름이 다르다 (`helm repo list`).
- 증상: `--set` 했는데 반영이 안 됐다 -> 원인: 키 철자/대소문자가 달라 조용히 무시됐다 -> `helm show values`로 정확한 키를 복사하고 `helm get values`로 확인.
- 증상: `helm rollback web`(번호 없음)을 했더니 또 깨진 상태 -> 원인: 번호를 생략하면 현재 바로 앞 번호로 가는데, 이미 rollback한 뒤라면 그 번호가 버린 revision이다 -> `helm history` 후 정상 revision 번호를 명시한다.
- 증상: 업그레이드가 `Error: UPGRADE FAILED: context deadline exceeded`로 끝나고 revision이 `failed` -> 원인: `--wait`가 시간 안에 Ready를 못 봤다 (이미지 오타 등). 이미 반영된 Pod는 남아 있다 -> 원인을 고치고 다시 upgrade 하거나 `helm rollback <정상 revision>`. (실제로 `failed` revision 뒤에 rollback이 성공하는 것을 확인했다.)
- 증상: `helm template` 결과에 `kind: Pod`(test)가 섞여 있다 -> `--skip-tests`. 결과 파일 경로와 이름을 문제가 시킨 대로 정확히 쓴다 (`> /path/out.yaml`).
- 증상: `--wait`를 Ctrl+C로 끊은 뒤 재설치가 안 된다 -> 원인: release가 `pending-install`/`failed`로 남았다 -> `helm uninstall <이름> -n <ns>` 후 다시 설치 (프로세스를 종료했을 때 `failed`로 바뀌고 uninstall이 되는 것을 확인했다).
- 증상(Kustomize): `accumulating resources ... no such file or directory` -> 경로 오타 (`../bsae`) 또는 해당 디렉터리에 `kustomization.yaml`이 없다 (`unable to find one of 'kustomization.yaml'...`).
- 증상(Kustomize): 패치가 적용되지 않았는데 에러도 없다 -> 원인: `target`의 kind/name이 일치하지 않아 조용히 무시된다 (replicas가 그대로 1) -> `k kustomize | grep`으로 결과 값을 눈으로 확인. JSON6902의 `path`가 없는 인덱스면 `doc is missing path` 에러.
- 증상(Kustomize): `namespaces "x" not found` -> `namespace:`는 네임스페이스를 만들지 않는다 -> `k create ns x`를 먼저.
- 증상(Kustomize): 다시 apply 했더니 `spec.selector ... field is immutable` -> 원인: `labels`에 `includeSelectors: true`를 추가해 Deployment selector가 바뀌었다 (기존 Deployment는 selector 변경 불가) -> 지우고 다시 만들거나 `includeSelectors`를 빼서 라벨만 붙인다.
- 증상(Kustomize): 생성된 ConfigMap이 `k get cm api-config`로 안 보인다 -> 원인: 이름 뒤에 `-<해시>`(와 prefix)가 붙는다 -> `k get cm`로 전체를 보거나 `disableNameSuffixHash: true`. 내용을 바꾸고 다시 apply하면 새 해시의 ConfigMap이 생기고 옛것은 남는다.
- 증상(Kustomize): `bases`/`commonLabels` 경고 -> 에러는 아니지만 문제가 "경고 없이 빌드"를 요구할 수 있다 -> `resources`/`labels`로 교체.

## 빠르게 푸는 순서
1. 문제에서 도구(Helm/Kustomize), 컨텍스트, 네임스페이스, 릴리스/chart 이름, 출력 파일 경로, 금지 조건("재설치 금지", "kubectl apply 금지")을 적는다. (30초)
2. Helm이면 `helm repo add` -> `helm repo update` -> `helm search repo <repo>/<chart> --versions`. 버전·APP VERSION 요구가 있으면 여기서 고른다. (1분)
3. 값 이름은 `helm show values <repo>/<chart> --version X`에서 찾고(필요하면 파일로 저장), 모르는 플래그는 `helm install --help`. (1분)
4. `helm install/upgrade/rollback`에 `-n`, `--version`, `-f`, `--set`을 모두 명시하고 `--wait`를 붙인다. upgrade는 값 유지를 먼저 생각(`--reuse-values`). (1~2분)
5. 확인: `helm list -n <ns>`, `helm history`, `helm get values`, `k -n <ns> get pods`. `helm template` 문제는 출력 파일에 `kind:`와 요구 값(`replicas`, 이미지)이 있는지 `grep`. (1분)
6. Kustomize이면 문서의 `Bases and Overlays`/`Setting cross-cutting fields` 블록을 복사해 `kustomization.yaml`을 쓴다. `k kustomize <dir>`로 미리 보고 이름·값·경고를 확인한 뒤 `k apply -k <dir>`. (2~3분)
7. 마지막에 `k get ... -n <ns>`로 결과가 의도한 이름(prefix/해시 포함)인지 본다. 총 목표 6~8분.
