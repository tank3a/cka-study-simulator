# B4. Manage the lifecycle of Kubernetes clusters

## 이 항목에서 공부할 것
- [ ] etcd static Pod 매니페스트에서 endpoint와 인증서 경로를 찾아 `etcdctl snapshot save`로 백업하고 `etcdutl snapshot status`로 검증한다
- [ ] 인자(`$1`)로 경로를 받는 etcd 백업 스크립트를 쓰고, 인자가 없거나 저장이 실패하면 오류로 종료되게 한다
- [ ] `etcdutl snapshot restore`로 복원하고(새 data-dir + `etcd.yaml`의 hostPath 수정, 또는 매니페스트를 치우고 같은 경로에 복원) 클러스터가 돌아오기를 `crictl ps`로 기다린다
- [ ] `kubeadm certs check-expiration`으로 만료일을 보고, 인증서 하나만 `kubeadm certs renew <name>` 한 뒤 static Pod를 재시작한다
- [ ] `kubectl drain --ignore-daemonsets --delete-emptydir-data`(필요하면 `--force`)와 `cordon/uncordon`을 상황에 맞게 쓴다
- [ ] 컨트롤 플레인(`upgrade plan` -> `upgrade apply`)과 워커(`upgrade node`)의 업그레이드 순서를 틀리지 않고 쓴다
- [ ] 업그레이드 가능한 버전을 `kubeadm upgrade plan`/`apt-cache madison kubeadm`으로 찾고, 마이너 버전은 하나씩만 올린다
- [ ] 문서에서 위 각 명령 블록의 위치를 바로 찾는다

## 개념 설명

### etcd와 snapshot (etcdctl과 etcdutl)
- 무엇: etcd는 클러스터의 모든 오브젝트를 저장하는 DB다. kubeadm 클러스터에서는 컨트롤 플레인 노드의 static Pod로 돈다. snapshot은 그 전체 상태를 한 파일로 떠 두는 백업이다.
- 두 도구: `etcdctl`은 네트워크로 etcd에 붙는 클라이언트(백업 `save`, `member list`, `endpoint status/health`). `etcdutl`은 파일을 직접 다루는 도구(`snapshot status`, `snapshot restore`) (문서 "Understanding etcdctl and etcdutl").
- etcd 3.6에서는 `etcdctl snapshot`에 `save`만 남았다. 시뮬레이터의 etcdctl 3.6.4에서 `snapshot` 하위 명령은 `save` 하나뿐이고 `snapshot restore --data-dir`는 `unknown flag: --data-dir` 오류가 났다. 검증·복원은 `etcdutl`. (시험 호스트의 etcd 도구 버전과 설치 여부는 미확인)
- 접속에 필요한 값은 etcd 매니페스트에 있다: `--listen-client-urls`(endpoint), `--trusted-ca-file`(`--cacert`), `--cert-file`(`--cert`), `--key-file`(`--key`). 전부 `/etc/kubernetes/pki/etcd/` 아래다.
- `ETCDCTL_API=3`은 3.6에서 필요 없고 붙이면 `unrecognized environment variable` 경고 로그가 한 줄 나올 뿐 동작은 한다.

### etcd 복원
- 복원은 snapshot에서 새 데이터 디렉터리(`<dir>/member/snap/db`, `<dir>/member/wal/`)를 만드는 일이다. 그다음 etcd가 그 디렉터리를 쓰게 해야 한다. 방법은 두 가지다.
  - A. 새 경로로 복원 후 `/etc/kubernetes/manifests/etcd.yaml`의 `volumes`에서 `name: etcd-data`의 `hostPath.path`만 새 경로로 바꾼다. 컨테이너 안의 `--data-dir` 플래그와 `volumeMounts`는 그대로 둔다 (문서와 q18 해설).
  - B. 같은 경로에 복원: 먼저 etcd를 멈추고(매니페스트를 manifests 밖으로 이동), 옛 디렉터리를 치우고(`mv /var/lib/etcd /var/lib/etcd.old`), 같은 경로로 복원하고, 매니페스트를 되돌린다 (q80 해설, 문서의 "같은 폴더면 지우고 etcd 프로세스를 멈춘 뒤 복원").
- 문서 Caution: API server가 돌고 있으면 etcd를 복원하지 말고, API server를 멈추고 -> 복원 -> 다시 시작하라고 한다. etcd가 내려가면 `kubectl`도 응답하지 않으므로 `crictl ps`로 상태를 본다.

### kubeadm 인증서
- kubeadm이 만든 인증서는 기본 1년 유효(CA는 10년)다. `kubeadm certs check-expiration`이 `/etc/kubernetes/pki`의 인증서와 `admin.conf`/`controller-manager.conf`/`scheduler.conf`에 박힌 인증서 만료일을 보여준다. `kubelet.conf`는 자동 갱신(회전)되는 인증서를 쓰므로 목록에 없다 (문서).
- `kubeadm upgrade`가 컨트롤 플레인을 업그레이드할 때 관리하는 인증서를 자동 갱신한다 (`--certificate-renewal=false`로 끔).
- 수동 갱신: `kubeadm certs renew <이름>` 또는 `renew all`. 파일만 바뀌므로 컨트롤 플레인 static Pod를 재시작해야 새 인증서를 읽는다 (문서: 동적 재로딩이 모든 컴포넌트에서 지원되지 않음). 재시작은 매니페스트를 `/etc/kubernetes/manifests/` 밖으로 옮겼다가 20초 정도 기다린 뒤 되돌린다 (문서의 `fileCheckFrequency`).

### 노드 유지보수: cordon / drain / uncordon
- `cordon`: 새 Pod 스케줄만 막는다. `drain`: cordon + 기존 Pod 퇴출(eviction, PDB 존중). `uncordon`: 다시 스케줄 허용. drain 후에는 반드시 uncordon해야 한다 (문서).
- 플래그 (`kubectl drain` 참조 페이지): `--ignore-daemonsets`(DaemonSet Pod 무시), `--delete-emptydir-data`(emptyDir 사용 Pod 허용), `--force`(컨트롤러 없는 Pod도 진행), `--dry-run=server`, `--grace-period`, `--disable-eviction`(PDB 우회, 주의).
- 컨트롤러가 없는 Pod는 `--force`로 지우면 다시 안 생긴다. 컨트롤러가 있는 Pod는 다른 노드에서 다시 생긴다.

### kubeadm 업그레이드
- 컨트롤 플레인: kubeadm 패키지 업그레이드 -> `kubeadm upgrade plan` -> `kubeadm upgrade apply v1.xx.y` -> drain -> kubelet/kubectl 패키지 -> `systemctl daemon-reload && systemctl restart kubelet` -> uncordon.
- 워커 노드(그리고 추가 컨트롤 플레인): `kubeadm upgrade apply`가 아니라 `kubeadm upgrade node`.
- 마이너 버전은 건너뛸 수 없다 (문서: 1.36.x -> 1.37.x 또는 1.37.x -> 1.37.y). kubelet은 API server보다 새로우면 안 된다 (kubeadm 설치 문서의 skew 설명).
- 패키지는 `apt-mark hold`로 고정되어 있으므로 문서는 `unhold` -> 설치 -> `hold` 순서를 쓴다. 저장소 URL의 마이너 버전(`v1.37`)이 목표 버전과 맞아야 한다.
- 문서의 드레인 위치와 문제의 지시가 다를 수 있다: 문서는 컨트롤 플레인에서 `apply` 후 drain 하고 kubelet을 올린다. "업그레이드 전에 drain"이라고 쓴 문제는 q19처럼 먼저 drain한다. 어느 쪽이든 kubelet을 올리고 재시작하기 전에 drain이 끝나 있어야 한다.

## 예시

**상황 1: etcd 스냅샷을 `/opt/cka/etcd-backup.db`에 저장하고 검증하고 멤버 수를 기록한다.** (컨트롤 플레인 노드에서 `sudo -i`)
```bash
grep -E -- '--(listen-client-urls|cert-file|key-file|trusted-ca-file)=' /etc/kubernetes/manifests/etcd.yaml
mkdir -p /opt/cka
etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/cka/etcd-backup.db
etcdutl snapshot status /opt/cka/etcd-backup.db -w table
etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key \
  member list | wc -l > /opt/cka/etcd-members.txt
```
확인 (시뮬레이터에서 `/tmp`에 저장하는 같은 명령으로 실제 실행): grep은 `--cert-file=.../server.crt`, `--key-file=.../server.key`, `--listen-client-urls=https://127.0.0.1:2379,...`, `--trusted-ca-file=.../ca.crt` 4줄을 보여준다. `save`는 `Snapshot saved at ...`를 출력한다. `status -w table`은 `HASH | REVISION | TOTAL KEYS | TOTAL SIZE | VERSION` 열의 표를 출력한다. `member list`는 이 클러스터에서 1줄(멤버 1개)이다. endpoint 상태는 `etcdctl ... endpoint health`가 `https://127.0.0.1:2379 is healthy: successfully committed proposal`을 출력한다.

**상황 2: 인자로 경로를 받는 백업 스크립트를 만들고, 상태를 JSON과 표로 저장한다.**
```bash
cat > /opt/cka/etcd-backup.sh <<'EOF'
#!/bin/bash
set -euo pipefail
OUT=${1:?usage: $0 <snapshot-file>}
etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save "$OUT"
etcdutl snapshot status "$OUT" >/dev/null
EOF
chmod +x /opt/cka/etcd-backup.sh
mkdir -p /opt/cka/backups && /opt/cka/etcd-backup.sh /opt/cka/backups/etcd-snap.db
etcdutl snapshot status /opt/cka/backups/etcd-snap.db -w json > /opt/cka/etcd-snap-status.json
etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key endpoint status -w table > /opt/cka/etcd-endpoint-status.txt
```
확인 (스크립트 내용을 `bash <file>`로 실제 실행): 인자 없이 실행하면 `usage: ... <snapshot-file>` 메시지와 종료 코드 1, 존재하지 않는 디렉터리를 주면 `could not open ... no such file or directory`와 종료 코드 5, 정상 경로면 `Server version 3.6.0`을 마지막에 출력하고 종료 코드 0. JSON은 `{"hash":...,"revision":...,"totalKey":...,"totalSize":...,"version":"3.6.0"}` 한 줄이다. `endpoint status` 표에는 `IS LEADER` 열이 있다.

**상황 3: 스냅샷을 새 디렉터리로 복원하고 etcd가 그것을 쓰게 한다 (방법 A).** (미확인: `restore` 명령 자체는 임시 디렉터리로 실행해 `member/snap/db`, `member/wal/`이 생기는 것까지 확인했다. 매니페스트 수정 후 etcd/API server가 되살아나는 과정은 클러스터를 바꾸므로 실행하지 않았다.)
```bash
etcdutl snapshot restore /opt/cka/etcd-snapshot-prev.db --data-dir /var/lib/etcd-restore
vim /etc/kubernetes/manifests/etcd.yaml      # volumes: - name: etcd-data 의 hostPath.path 를 /var/lib/etcd-restore 로
watch crictl ps                              # etcd, kube-apiserver 컨테이너가 다시 Running 될 때까지
k get deploy -A                              # 복원 시점의 오브젝트만 남아 있는지 확인
```
문서의 형태 `etcdutl --data-dir <dir> snapshot restore snapshot.db`도 같게 동작했다. 기존 `/var/lib/etcd`는 지우지 않는다(문제의 제약). etcd.yaml에서 바꿀 곳은 확인한 매니페스트 기준 `volumes:` 아래 `- hostPath: path: /var/lib/etcd ... name: etcd-data` 한 곳이다.

**상황 4: 같은 경로에 복원한다 (방법 B, 매니페스트 수정 없음).** (미확인: 클러스터를 바꾸므로 실행하지 않음. q80 해설과 문서 문장 기준.)
```bash
mv /etc/kubernetes/manifests/etcd.yaml /opt/cka/etcd.yaml.disabled
watch crictl ps | grep etcd                  # etcd 컨테이너가 사라질 때까지
mv /var/lib/etcd /var/lib/etcd.old
etcdutl snapshot restore /opt/cka/etcd-pre-incident.db --data-dir /var/lib/etcd
mv /opt/cka/etcd.yaml.disabled /etc/kubernetes/manifests/etcd.yaml
crictl ps | grep -E 'etcd|apiserver'
```
복원했는데 `k get deploy`에 지워진 것이 남아 보이면 kube-apiserver static Pod를 같은 방식(매니페스트를 치웠다가 되돌림)으로 재시작해 본다 (q18/q80 해설의 경험담, 미확인).

**상황 5: 인증서 만료일을 보고, `apiserver-kubelet-client` 하나만 갱신하고 API server를 재시작한다.**
```bash
kubeadm certs check-expiration > /opt/cka/cert-expiry.txt
openssl x509 -in /etc/kubernetes/pki/ca.crt -noout -enddate > /opt/cka/ca-notafter.txt
kubeadm certs renew apiserver-kubelet-client                       # (미확인: 파일을 바꾸므로 실행하지 않음)
mv /etc/kubernetes/manifests/kube-apiserver.yaml /root/                          # 매니페스트를 잠깐 치운다
until ! crictl ps | grep -q kube-apiserver; do sleep 3; done                     # 컨테이너가 사라질 때까지 (문서: 약 20초)
mv /root/kube-apiserver.yaml /etc/kubernetes/manifests/
crictl ps | grep kube-apiserver ; k get --raw=/readyz
```
확인 (`check-expiration`과 `openssl`은 실제 실행): 표에 `CERTIFICATE | EXPIRES | RESIDUAL TIME | CERTIFICATE AUTHORITY | EXTERNALLY MANAGED` 열로 `admin.conf`, `apiserver`, `apiserver-etcd-client`, `apiserver-kubelet-client`, `controller-manager.conf`, `etcd-healthcheck-client`, `etcd-peer`, `etcd-server`, `front-proxy-client`, `scheduler.conf`, `super-admin.conf`가 나오고 아래에 CA 3개(`ca`, `etcd-ca`, `front-proxy-ca`)가 따로 나온다. `openssl ... -enddate`는 `notAfter=Oct 15 05:04:34 2036 GMT` 형태다. 갱신 후 같은 표에서 해당 줄의 만료일이 늘었는지 본다. 재시작은 디렉터리를 바꾸지 않고 매니페스트 파일만 잠깐 치웠다 되돌리는 것이다.

**상황 6: 노드를 유지보수하려고 비운다 (플래그가 하나씩 필요한 이유 확인).**
```bash
k get nodes
k drain k8s-worker --dry-run=server                                              # 먼저 모의 실행
k drain k8s-worker --ignore-daemonsets --delete-emptydir-data --force
k get nodes                                                                      # Ready,SchedulingDisabled
k uncordon k8s-worker                                                            # 작업이 끝나면
```
확인 (`--dry-run=server`로 실제 실행, 노드 상태는 바뀌지 않음을 `k get nodes`로 확인): 플래그 없이는 `cannot delete DaemonSet-managed Pods (use --ignore-daemonsets to ignore)`와 emptyDir Pod 및 컨트롤러 없는 Pod에 대한 오류가 함께 나온다. `--ignore-daemonsets`를 붙이면 `cannot delete Pods with local storage (use --delete-emptydir-data to override)`와 `cannot delete Pods that declare no controller (use --force to override)`만 남고, `--delete-emptydir-data`까지 붙이면 `--force` 오류만 남고, 셋 다 붙이면 `evicting pod ... (server dry run)` 줄들과 `node/k8s-worker drained (server dry run)`로 끝난다. 모의 실행 결과는 다른 사용자의 Pod까지 포함한 노드 전체 기준이다. 실제 퇴출과 `SchedulingDisabled` 표시는 이 랩에서 실행하지 않았다(미확인, q78 해설에 `Ready,SchedulingDisabled`로 적혀 있음).

**상황 7: 업그레이드 가능한 버전을 확인하고 컨트롤 플레인/워커 절차를 정리한다.**
```bash
kubeadm upgrade plan                                   # 읽기 전용
apt-cache madison kubeadm | head                       # 설치 가능한 패치 버전
# 컨트롤 플레인 (미확인: 클러스터를 바꾸므로 실행하지 않음, 문서 v1.37 블록의 형태)
sudo apt-mark unhold kubeadm && sudo apt-get update && sudo apt-get install -y kubeadm='1.37.x-*' && sudo apt-mark hold kubeadm
kubeadm version -o short
sudo kubeadm upgrade plan
sudo kubeadm upgrade apply v1.37.x
k drain <control-plane-node> --ignore-daemonsets
sudo apt-mark unhold kubelet kubectl && sudo apt-get update && sudo apt-get install -y kubelet='1.37.x-*' kubectl='1.37.x-*' && sudo apt-mark hold kubelet kubectl
sudo systemctl daemon-reload && sudo systemctl restart kubelet
k uncordon <control-plane-node>
# 워커 (워커 노드에서; drain/uncordon은 컨트롤 플레인에서)
sudo apt-mark unhold kubeadm kubectl && sudo apt-get update && sudo apt-get install -y kubeadm='1.37.x-*' kubectl='1.37.x-*' && sudo apt-mark hold kubeadm kubectl
sudo kubeadm upgrade node
k drain <worker> --ignore-daemonsets                   # 컨트롤 플레인에서
# 그다음 워커에서: kubelet 설치 -> daemon-reload -> restart kubelet, 컨트롤 플레인에서 k uncordon <worker>
k get nodes                                            # 모두 Ready, VERSION 갱신
```
확인 (`kubeadm upgrade plan`은 실제 실행): 시뮬레이터에서 `Cluster version: 1.34.0`, 표에 `kube-apiserver ... v1.34.0 -> v1.34.12`, etcd `3.6.4-0`이 나오고, 마지막에 `kubeadm upgrade apply v1.34.12` 명령과 "먼저 kubeadm을 v1.34.12로 올려야 한다"는 안내가 나왔다. 워커 순서는 `upgrade-linux-nodes` 문서 기준이며 kubectl도 같이 올린다.

시뮬레이터 차이: kind 노드에서는 `kubeadm upgrade apply`와 apt 설치가 정상 동작하지 않을 수 있다 (KNOWN_LIMITS: q19는 best effort, 미테스트). etcd 복원은 임시 디렉터리 복원까지만 확인했고, 인증서 갱신/재시작도 실행하지 않았다. 서버는 v1.34.0이고 시험은 v1.37이다. 노드 컨테이너의 `/tmp`는 `noexec` tmpfs라서 거기 둔 스크립트는 `bash 파일`로 실행해야 한다 (시험 호스트에서는 해당 없음, 미확인).

## 자주 틀리는 점
- 증상: `etcdctl snapshot status`/`restore`가 도움말만 출력하거나 `unknown flag: --data-dir` -> 원인: etcd 3.6의 etcdctl에는 `snapshot save`만 있다 -> `etcdutl snapshot status/restore`를 쓴다.
- 증상: `snapshot save`가 인증서 오류/타임아웃 -> 원인: `--cacert/--cert/--key`가 비었거나 endpoint가 틀렸다 -> `etcd.yaml`의 `--trusted-ca-file`, `--cert-file`, `--key-file`, `--listen-client-urls` 값을 그대로 쓴다. 인증서 이름이 비슷한 `--peer-cert-file`과 헷갈리지 않는다.
- 증상: 복원했는데 etcd가 이전 데이터로 뜬다 -> 원인: `etcd.yaml`의 hostPath를 바꾸지 않았거나(방법 A), 같은 경로 복원인데 etcd를 먼저 멈추지 않았다(방법 B) -> 각 방법의 순서를 지킨다. `--data-dir` 플래그와 hostPath를 둘 다 바꾸면 마운트가 어긋나 etcd가 안 뜰 수 있다 (q18 해설).
- 증상: 복원 후 한동안 `kubectl`이 응답하지 않는다 -> 원인: etcd/API server가 재시작 중이다 -> `watch crictl ps`로 etcd와 kube-apiserver가 Running이 될 때까지 기다린다. 기다리는 동안 매니페스트를 또 건드리지 않는다.
- 증상: 인증서를 renew했는데 API server가 옛 인증서를 쓴다 -> 원인: static Pod를 재시작하지 않았다 (문서: 재시작 필요) -> 매니페스트를 치웠다 되돌린다. `kubectl`로 지우는 방식은 static Pod에 통하지 않는다 (문서).
- 증상: 요구하지 않은 인증서까지 갱신했다 -> 원인: `kubeadm certs renew all`을 썼다 -> 이름을 지정해 하나만 갱신한다 (`kubeadm certs renew --help`의 하위 명령 목록).
- 증상: drain이 `cannot delete DaemonSet-managed Pods ...`로 멈춘다 -> 원인: `--ignore-daemonsets` 누락 -> 추가. emptyDir 오류면 `--delete-emptydir-data`, 컨트롤러 없는 Pod 오류면 `--force`. 실패한 줄의 괄호 안에 필요한 플래그가 적혀 있다.
- 증상: drain 후 Pod가 Pending (q78 해설) -> 원인: 다른 워커가 cordon된 채여서 갈 곳이 없다 -> 먼저 `k get nodes`로 `SchedulingDisabled` 노드를 확인하고 `uncordon`.
- 증상: drain이 오래 멈춘다 -> 원인: PodDisruptionBudget이 퇴출을 막는다 (문서: drain은 PDB를 존중) -> PDB 설정을 확인한다 (D4 q59). `--disable-eviction`은 PDB를 우회하므로 문제가 허용할 때만.
- 증상: 업그레이드 후 노드가 계속 `SchedulingDisabled` -> 원인: `uncordon`을 잊었다 -> 마지막에 `k get nodes`로 확인.
- 증상: 워커에서 `kubeadm upgrade apply`를 쳤다 -> 원인: 워커는 `kubeadm upgrade node` -> 컨트롤 플레인만 `apply`.
- 증상: 마이너 버전을 두 단계 올리려 한다 -> 원인: 건너뛰기는 지원되지 않는다 (문서) -> 한 마이너씩. 문제의 "newest v1.xx patch"는 `kubeadm upgrade plan`이 알려주는 버전이다.

## 빠르게 푸는 순서
1. 문제의 호스트와 컨텍스트를 확인하고 `ssh <node>` -> `sudo -i`. 끝나면 `exit`로 base까지 돌아온다. 금지 조건("etcd를 재시작하지 말 것", "인증서를 갱신하지 말 것")을 먼저 적는다. (30초)
2. etcd 백업: `etcd.yaml`에서 4개 값을 grep -> `snapshot save` -> `etcdutl snapshot status`. 결과 파일 경로를 요구대로 쓴다. (2~3분)
3. etcd 복원: `etcdutl snapshot restore`를 요구된 `--data-dir`로 실행 -> 요구에 맞게 hostPath 수정 또는 매니페스트 이동 -> `watch crictl ps`로 복구 대기 -> `k get`으로 확인. 복원은 단독으로, 마지막에 푼다. (5~8분)
4. 인증서: `check-expiration`을 파일로 저장, 요구한 하나만 `renew`, manifests에서 파일을 치웠다 되돌려 재시작, `readyz` 확인. (3~4분)
5. drain 문제: 노드 상태를 먼저 `k get nodes`로 보고, `drain`에 필요한 플래그를 붙이고 결과를 본다. 요구가 "계속 unschedulable"이면 uncordon하지 않는다. (2~3분)
6. 업그레이드: `kubeadm upgrade plan`으로 목표 버전 확인 -> drain -> kubeadm 설치 -> 컨트롤 플레인은 `apply`, 워커는 `node` -> kubelet/kubectl 설치 -> daemon-reload + restart -> uncordon. 노드 하나당 5~8분이므로 시간이 모자라면 나중에 푼다. (8~12분)
7. 마지막에 `k get nodes`, `crictl ps`, 요구된 결과 파일을 `cat`으로 다시 확인한다. (1분)

## 연습 문제
오늘 풀 문제 (14일 계획 7일차):
- `q17` — Take and verify an etcd snapshot (스냅샷 저장·검증·멤버 수, etcd는 건드리지 않음)
- `q18` — Restore etcd from a snapshot (destructive, cluster-soft). 계획에 따라 마지막에, 단독으로. q17, q20, q21을 먼저 채점
- `q19` — Upgrade control plane and worker (ik8s, cluster-hard). ik8s 전용, partial fidelity, 기본 세트 제외

추가 연습:
- `q76` — Renew one kubeadm cert and restart the API server (`kubeadm certs renew` 하나만, static Pod 재시작. q39/q40과 같은 세트에 넣지 않는다)
- `q77` — upgrade plan, drain dry-run, worker runbook (실제 업그레이드 없이 계획 수립, partial fidelity)
- `q78` — Stale cordon, drain with flags, node stays cordoned (drain/cordon/uncordon, 워커 상태를 바꾸므로 worker2 스케줄이 필요한 문제와 같은 세트 금지)
- `q79` — Backup script with $1, snapshot status JSON, endpoint status (etcd 백업 스크립트. q18/q80 전에 채점)
- `q80` — Restore etcd in place, no manifest edit (방법 B. q18과 같은 세트에 넣지 않는다. q17/q75/q79를 먼저 채점)
- `q20` — Cert expiry report and worker join token (오늘 계획상 B3 문제지만 `kubeadm certs check-expiration`과 openssl 부분이 이 항목)
