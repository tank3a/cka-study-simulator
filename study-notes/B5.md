# B5. Implement and configure a highly-available control plane

## 이 항목에서 공부할 것
- [ ] 클러스터가 stacked etcd인지 external etcd인지 읽어서 판별한다 (`kubeadm-config`의 `etcd:` 블록, etcd static Pod 유무, apiserver의 `--etcd-servers`)
- [ ] `kubeadm-config` ConfigMap에서 `controlPlaneEndpoint`를 읽는다
- [ ] kube-scheduler / kube-controller-manager 리더 lease(`holderIdentity`)에서 "지금 리더인 노드 이름"만 뽑는다
- [ ] etcd 멤버 수와 리더를 `etcdctl member list` / `endpoint status`로 확인한다 (인증서 옵션 3개 포함)
- [ ] etcd 멤버 수 n에서 quorum과 허용 장애 수를 계산한다 (1대 장애를 견디는 최소 구성, 2대 장애를 견디는 최소 구성)
- [ ] 문서의 external etcd `ClusterConfiguration` 블록을 복사해 값만 바꾸고 `kubeadm config validate`로 통과시킨다
- [ ] HA 부트스트랩 순서를 말할 수 있다: 로드밸런서 -> `kubeadm init --control-plane-endpoint ... --upload-certs` -> 나머지 노드 `kubeadm join ... --control-plane --certificate-key`
- [ ] 인증서 키가 만료(2시간)됐을 때 다시 올리는 명령(`kubeadm init phase upload-certs --upload-certs`)을 문서에서 찾는다

## 개념 설명

### 컨트롤 플레인 구성요소와 "HA에서 각자 어떻게 동작하나"
- 무엇: kube-apiserver, kube-scheduler, kube-controller-manager, etcd. kubeadm 클러스터에서는 모두 control-plane 노드의 static Pod다 (`/etc/kubernetes/manifests/*.yaml`).
- 왜 HA가 필요한가: control plane 노드가 1대면 그 노드가 죽는 순간 API가 사라진다 (이미 떠 있는 Pod는 계속 돌지만 아무것도 바꿀 수 없다).
- 동작 차이가 핵심이다.
  - kube-apiserver: 노드마다 하나씩 동시에 다 일한다 (active-active). 앞에 로드밸런서를 둔다.
  - kube-scheduler, kube-controller-manager: 노드마다 하나씩 떠 있지만 **한 시점에 리더 하나만 일한다**. 리더는 `kube-system`의 Lease 오브젝트(`kube-scheduler`, `kube-controller-manager`)를 먼저 잡은 쪽이고, 나머지는 대기한다.
  - etcd: Raft 합의로 과반수(quorum)가 살아 있어야 쓰기가 된다.
- 비유: apiserver는 "창구 여러 개", scheduler/controller-manager는 "당직 책임자 1명(Lease가 당직표)", etcd는 "다수결 회의".

### Stacked etcd 토폴로지 (kubeadm 기본값)
- 무엇: control-plane 노드마다 etcd 멤버가 같이 뜬다. 각 etcd는 같은 노드의 apiserver하고만 직접 통신한다. `kubeadm init`과 `kubeadm join --control-plane`이 etcd를 자동으로 만든다.
- 장점: 노드 수가 적고(최소 3대) 설정이 단순하다. 단점: 노드 1대가 죽으면 apiserver와 etcd 멤버가 **함께** 사라진다 (문서의 "failed coupling").
- 확인 방법: `kube-system`에 `etcd-<노드>` Pod가 control-plane 노드 수만큼 있고, `kubeadm-config`의 `etcd:` 아래가 `local:`이다.

### External etcd 토폴로지
- 무엇: etcd를 별도 호스트(최소 3대)에 따로 운영하고 control-plane 노드(최소 3대)가 그 etcd에 접속한다. 호스트가 stacked의 2배 필요하다.
- 장점: control-plane 노드 장애와 etcd 장애가 분리된다. kubeadm은 etcd static Pod를 만들지 않는다.
- 핵심 설정: `ClusterConfiguration`의 `etcd.external` 아래 `endpoints`(URL 목록), `caFile`, `certFile`, `keyFile`. 이 인증서 3개를 첫 control-plane 노드에 미리 복사해 둬야 한다 (문서의 `scp` 블록).
- 확인 방법: `kube-system`에 etcd Pod가 없고, apiserver의 `--etcd-servers`가 외부 주소 목록이며, `kubeadm-config`에 `etcd.external`이 있다.

### etcd quorum (과반수) 계산
- quorum = `floor(n/2) + 1`, 허용 장애 = `n - quorum`. 짝수 멤버는 홀수 하나 아래와 허용 장애가 같아서 이득이 없다 (문서도 홀수 개를 권장).

| 멤버 n | quorum | 허용 장애 |
|---|---|---|
| 1 | 1 | 0 |
| 2 | 2 | 0 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |

- "1대 장애를 견디는 stacked 최소 control-plane 노드 수"는 3, "2대 장애를 견디는 etcd 최소 멤버 수"는 5다. 이 표는 허용 사이트 문서에 없다 (공식은 etcd FAQ에 있고 허용 목록 밖, 미확인). 공식을 외워서 계산한다. k8s 문서는 "운영에는 5-member 권장"까지만 말한다.

### 로드밸런서와 `controlPlaneEndpoint`
- 무엇: worker와 kubectl이 control-plane 노드 한 대의 IP가 아니라 **LB의 DNS:포트**로 apiserver에 접속하게 하는 주소. `kubeadm init --control-plane-endpoint "LB_DNS:PORT"` 또는 config의 `controlPlaneEndpoint`.
- 왜: 이 값은 kubeconfig와 인증서 SAN에 박힌다. 첫 노드 IP로 만들면 나중에 HA로 바꾸기 어렵다. 문서도 LB 주소와 `ControlPlaneEndpoint`가 항상 일치해야 한다고 한다.
- 단일 control-plane 클러스터도 `controlPlaneEndpoint`가 있을 수 있다 (시뮬레이터는 `k8s-control-plane:6443`). 값이 있다고 HA인 것은 아니다.

### 인증서 공유 (`--upload-certs`, certificate key)
- 새 control-plane 노드는 CA 등 공유 인증서가 필요하다. `kubeadm init --upload-certs`는 이를 암호화해 `kube-system`의 `kubeadm-certs` Secret에 올리고 복호화 키(`certificate-key`)를 출력한다. 추가 노드는 `kubeadm join ... --control-plane --certificate-key <키>`로 내려받는다.
- Secret과 키는 **2시간 후 만료**된다. 만료되면 기존 control-plane 노드에서 `sudo kubeadm init phase upload-certs --upload-certs`로 다시 올린다. 키만 새로 만들려면 `kubeadm certs certificate-key`.
- `kubeadm init`에서 `--config`와 `--certificate-key`는 같이 못 쓴다. config를 쓰면 `InitConfiguration.certificateKey`(join은 `JoinConfiguration.controlPlane.certificateKey`)에 넣는다.

## 예시

**상황 1: 현재 클러스터가 stacked인지 external인지, 엔드포인트는 무엇인지 읽기 전용으로 조사한다.**
```bash
k get nodes -l node-role.kubernetes.io/control-plane
k -n kube-system get pods -l tier=control-plane -o wide
k -n kube-system get cm kubeadm-config -o jsonpath='{.data.ClusterConfiguration}' | grep -E -A3 '^controlPlaneEndpoint|^etcd:'
k -n kube-system get pod -l component=kube-apiserver -o yaml | grep -- '--etcd-servers'
```
기대 결과 (시뮬레이터 `k8s`): control-plane 노드 1개, 그 노드에 etcd/kube-apiserver/kube-controller-manager/kube-scheduler Pod가 각 1개, `controlPlaneEndpoint: k8s-control-plane:6443`, `etcd:` 아래 `local:`, `--etcd-servers=https://127.0.0.1:2379`. -> **stacked** (etcd Pod가 있고 `etcd.local`, 서버 주소가 localhost).

**상황 2: 리더 노드, etcd 멤버 수를 파일에 `key=value`로 적는다 (q21 형식).**
```bash
k -n kube-system get lease                                   # kube-scheduler, kube-controller-manager의 HOLDER 확인
k -n kube-system get lease kube-scheduler -o jsonpath='{.spec.holderIdentity}'            # 노드이름_uuid
k -n kube-system get lease kube-scheduler -o jsonpath='{.spec.holderIdentity}' | cut -d_ -f1   # 노드 이름만

# etcdctl은 control-plane 노드(ssh)에서 쓰거나, 노드 없이 etcd Pod 안에서 exec 한다
k -n kube-system exec etcd-<control-plane-노드> -- etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key member list -w table
```
기대 결과: holder `k8s-control-plane_<uuid>` -> `k8s-control-plane`. `member list`에 `started` 멤버 1개(`IS LEARNER false`). 멤버 수만 세려면 `member list | wc -l` (출력이 `1`). `endpoint status -w table`에는 `IS LEADER`와 Raft 정보가 나온다. 답 파일은 이런 모양이다 (값은 클러스터에서 읽은 것을 쓴다).
```bash
mkdir -p ~/answers && cat > ~/answers/q21.txt <<'EOF'
topology=stacked
scheduler_leader=k8s-control-plane
control_plane_endpoint=k8s-control-plane:6443
etcd_members=1
min_cp_nodes_for_ha=3
EOF
```

**상황 3: 외부 etcd 3대 + LB를 쓰는 HA 클러스터의 `ClusterConfiguration` 파일을 만든다 (문서 블록 복사 후 값 수정).**
```bash
cat > ha-external-etcd.yaml <<'EOF'
apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
kubernetesVersion: v1.34.0
controlPlaneEndpoint: "lb.example.com:6443"
etcd:
  external:
    endpoints:
      - https://10.0.0.11:2379
      - https://10.0.0.12:2379
      - https://10.0.0.13:2379
    caFile: /etc/kubernetes/pki/etcd/ca.crt
    certFile: /etc/kubernetes/pki/apiserver-etcd-client.crt
    keyFile: /etc/kubernetes/pki/apiserver-etcd-client.key
EOF
sudo kubeadm config validate --config ha-external-etcd.yaml      # control-plane 노드에서
```
기대 결과: `ok`. 필드 이름을 틀리면 `strict decoding error: unknown field "controlPlaneEndpont"`, 없는 apiVersion이면 `unknown configuration APIs`가 나오고 종료 코드 1이다. (검증은 노드의 kubeadm에 파일을 stdin으로 넘겨 확인했다. 인증서 파일이 실제로 있는지는 `validate`가 보지 않는다.) 필드 이름이 기억나지 않으면 `kubeadm config print init-defaults`로 구조를 본다 (읽기 전용).

**상황 4: stacked HA를 새로 만든다면 명령 순서는 어떻게 되나 (문서 그대로, 시험에서는 문서 블록을 복사).**
```bash
nc -zv -w 2 <LOAD_BALANCER_IP> <PORT>                                    # LB -> 첫 노드 연결 확인 (refused는 정상, timeout이면 LB 문제)
sudo kubeadm init --control-plane-endpoint "LOAD_BALANCER_DNS:LOAD_BALANCER_PORT" --upload-certs
# 출력에 나온 control-plane용 join 명령을 나머지 control-plane 노드에서 실행:
sudo kubeadm join <LB>:6443 --token <t> --discovery-token-ca-cert-hash sha256:<h> --control-plane --certificate-key <key>
k -n kube-system rollout restart deployment coredns          # 문서 권고: CoreDNS가 첫 노드에 몰려 있으면 분산
```
(미확인: 실제 실행하지 않았다. kind 시뮬레이터는 control-plane이 1대라 `init/join`을 돌릴 수 없다. 플래그는 `kubeadm init --help`, `kubeadm join --help`에서 `--control-plane-endpoint`, `--upload-certs`, `--certificate-key`, `--control-plane`이 있는 것을 확인했다. `kubeadm certs certificate-key`는 실행해 64자 hex 키가 나오는 것을 확인했다.)

**상황 5: 클러스터가 지금 건강한지 control plane 쪽만 빠르게 본다.**
```bash
k get --raw='/readyz?verbose' | grep -E 'etcd|readyz check passed'
k get --raw='/readyz/etcd'; echo
```
기대 결과: `[+]etcd ok`, `[+]etcd-readiness ok`, `/readyz/etcd`는 `ok`.

시뮬레이터 차이: 노드 접속 별칭은 `ssh k8s-cp` (q21/q81은 `ek8s` 클러스터라 `ssh ek8s-cp`). kind 클러스터는 control-plane 1대, etcd 1멤버라 "리더 노드 = 유일한 노드"이고 HA 자체를 만들 수는 없다 (q21/q81은 읽기와 파일 작성만). 서버는 v1.34.0, 시험은 v1.37. 시험 호스트에 `etcdctl`이 있는지는 공식 자료에 없다(미확인). 없으면 위처럼 etcd Pod에 `k exec`로 쓸 수 있다. `etcdctl` 3.6은 `ETCDCTL_API=3`을 붙이면 "unrecognized environment variable" 경고만 내고 동작한다 (붙일 필요 없음).

## 공식 문서에서 찾는 법
허용 사이트만 쓴다. 검색 결과 순위는 직접 확인하지 못했다(미확인). 안 나오면 URL 경로를 주소창에 직접 쓴다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| stacked / external 차이, 최소 노드 수 | `HA topology` | https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/ha-topology/ | `Stacked etcd topology`, `External etcd topology`, `minimum of three` | (코드 블록 없음) 설명 문장 |
| LB 만들고 연결 테스트 | `creating highly available clusters kubeadm` | https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/high-availability/ | `Create load balancer for kube-apiserver` | `nc -zv -w 2 <LOAD_BALANCER_IP> <PORT>` |
| 첫 control-plane `kubeadm init` | 위와 같음 | 위와 같음 | `Steps for the first control plane node` | `sudo kubeadm init --control-plane-endpoint "LOAD_BALANCER_DNS:LOAD_BALANCER_PORT" --upload-certs` |
| 나머지 control-plane join | 위와 같음 | 위와 같음 | `Steps for the rest of the control plane nodes` | `sudo kubeadm join ... --control-plane --certificate-key ...` |
| 인증서 키 재업로드 / 새 키 생성 | 위와 같음 | 위와 같음 | `kubeadm init phase upload-certs`, `certificate-key` | `sudo kubeadm init phase upload-certs --upload-certs`, `kubeadm certs certificate-key` |
| external etcd용 config YAML | 위와 같음 | 위와 같음 | `External etcd nodes`, `Set up the first control plane node` | `kind: ClusterConfiguration` ... `etcd: external:` YAML 블록 |
| etcd 인증서 복사 | 위와 같음 | 위와 같음 | `apiserver-etcd-client.crt` | `export CONTROL_PLANE=...; scp ...` 블록 |
| 인증서 수동 배포 (`--upload-certs` 안 쓸 때) | 위와 같음 | 위와 같음 | `Manual certificate distribution` | `scp /etc/kubernetes/pki/ca.crt ...` 반복문 |
| etcd 권장 크기 (5-member), 멤버 교체 | `operating etcd clusters` | https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/ | `five-member`, `Replacing a failed etcd member` | (설명 문장) |
| Lease 기반 리더 선출 설명 | `Leases` | https://kubernetes.io/docs/concepts/architecture/leases/ (※) | `Leader election` | (코드 블록 없음) |

(※) `official.md`/`study-guide.md` 목록에 없는 kubernetes.io/docs 페이지다. 2026-10-19에 curl로 HTTP 200과 `Leader election` 절을 확인했다.
`high-availability` 페이지의 YAML은 "External etcd nodes" 아래 "Set up the first control plane node"에 한 블록(`kubeadm.k8s.io/v1beta4`)만 있다. stacked는 YAML이 아니라 `kubeadm init` 한 줄이다. quorum 계산표는 허용 사이트에 없다(위 개념 절).

## 자주 틀리는 점
- 증상: `scheduler_leader` 답이 오답 처리 -> 원인: `holderIdentity`가 `k8s-control-plane_5053b5ae-...`처럼 `노드이름_uuid`인데 통째로 썼다 -> `cut -d_ -f1`로 노드 이름만. 문제가 요구한 형식(공백 없는 `key=value`)도 같이 확인한다.
- 증상: `etcdctl member list`가 한참 뒤 `Error: context deadline exceeded` -> 원인: `--cacert/--cert/--key`가 빠졌거나 틀렸다. 경고에 `x509: certificate signed by unknown authority` 또는 `tls: certificate required`가 보이면 인증서 옵션 문제다 -> etcd 매니페스트(`/etc/kubernetes/manifests/etcd.yaml`)의 `--trusted-ca-file/--cert-file/--key-file` 경로를 그대로 쓴다.
- 증상: `kubeadm config validate`가 `unknown field "..."` -> 원인: 필드 오타 (엄격 디코딩) -> 철자 확인. `unknown configuration APIs` -> `apiVersion`이 `kubeadm.k8s.io/v1beta4`인지 확인.
- 증상: external etcd 구성을 만들었는데 `etcd.local`도 같이 남겨 둠, 혹은 `etcd.external`의 `caFile/certFile/keyFile` 대신 다른 이름을 씀 -> 문서 블록을 그대로 복사하고 `endpoints`만 고친다.
- 증상: join 때 인증서를 못 받는다 (`kubeadm-certs` 없음/키 불일치) -> 원인: `--upload-certs` 후 2시간이 지났다 -> 기존 control-plane에서 `kubeadm init phase upload-certs --upload-certs`를 다시 실행하고 새 키를 쓴다.
- 증상: `kubeadm init --config x.yaml --certificate-key ...`가 거부된다 -> 원인: `--config`와 `--certificate-key`는 같이 못 쓴다 (문서 노트) -> `InitConfiguration`에 `certificateKey:` 필드로 넣는다 (`kubeadm config validate`가 통과하는 것을 확인했다).
- 증상: "2대 장애를 견디려면 4대"라고 답함 -> 원인: quorum 계산 착오 -> n=5 (quorum 3, 허용 2). 4대는 3대와 허용 장애가 같다.
- 증상: control-plane 2대 + stacked로 "HA 구성"이라 답함 -> 1대가 죽으면 etcd 2멤버 중 1개만 남아 quorum(2)을 못 채운다 -> 최소 3대 (문서도 "minimum of three stacked control plane nodes").
- 증상: `controlPlaneEndpoint`가 있으니 HA라고 판단 -> 원인: 값은 LB 주소일 수도, 노드 이름일 수도 있다 (시뮬레이터는 노드 이름) -> `etcd` 멤버 수와 control-plane 노드 수를 같이 본다.
- 증상: 잘못된 클러스터를 조사 -> 원인: q21은 `ek8s`, 대부분 다른 문제는 `k8s`다 -> 문제 첫 줄의 `kubectl config use-context`를 그대로 실행한다.
- "읽기만 하라/변경 금지" 문제에서 `kubeadm init phase`나 `etcdctl snapshot restore`를 실행하지 않는다. 이 항목 문제는 대부분 `get`/`member list`/파일 작성이다.

## 빠르게 푸는 순서
1. 컨텍스트와 호스트(`ssh <node>`)를 메모하고, "변경 금지"와 출력 형식(`key=value`, 파일 경로)을 먼저 찾는다. (30초)
2. 토폴로지: `k -n kube-system get pods -o wide | grep etcd`로 etcd Pod 유무, `kubeadm-config`의 `etcd:`가 `local`/`external` 중 무엇인지 본다. (1분)
3. 엔드포인트: `kubeadm-config`를 `grep controlPlaneEndpoint`. (30초)
4. 리더: `k -n kube-system get lease <kube-scheduler|kube-controller-manager> -o jsonpath='{.spec.holderIdentity}' | cut -d_ -f1`. (30초)
5. etcd 멤버 수: `ssh` 후 `sudo -i`에서 `etcdctl ... member list` (인증서 경로는 etcd 매니페스트에서 복사), 또는 etcd Pod에 `k exec`. (1~2분)
6. 계산 문제(quorum, 최소 노드 수)는 `floor(n/2)+1` 공식으로 암산하고 표와 대조한다. (30초)
7. 파일 작성 문제는 `high-availability` 페이지의 `External etcd nodes` 블록을 복사해 값만 바꾸고 `kubeadm config validate`로 확인한다. (2~3분)
8. 파일 내용을 `cat`으로 다시 보고 오타·공백(`=` 주변)을 확인한다. 총 목표 5~7분.
