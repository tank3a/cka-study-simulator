# B8. Understand CRDs, install and configure operators

## 이 항목에서 공부할 것
- [ ] `k get crd`에서 **정확히 그 API 그룹**의 CRD 이름만 골라 정렬해 파일로 저장한다 (접미사 grep의 함정을 안다)
- [ ] CRD의 scope, 버전(served/storage), shortNames, 필수 필드를 `-o jsonpath`로 읽는다
- [ ] `k explain <kind>.spec.<field>` (필요하면 `--api-version`) 출력을 파일로 저장한다
- [ ] 스키마(required, minimum/maximum, enum)를 읽고 그에 맞는 CR을 만든다. 거부 메시지를 읽고 고친다
- [ ] 문서의 CRD 예제로 CRD를 직접 작성한다 (`names`, `scope`, `versions`, `schema`, `default`, `additionalPrinterColumns`, `status` 서브리소스)
- [ ] `k get <plural> -A`로 모든 네임스페이스의 CR 개수를 세어 요구한 형식(숫자 한 줄 등)으로 쓴다
- [ ] operator = CRD + 컨트롤러 Deployment + RBAC임을 알고, 번들을 설치한 뒤 최소 권한 RBAC(`/status`, `/finalizers`, `events`, `leases`)를 `auth can-i`로 검증하고 컨트롤러를 켠다
- [ ] CRD를 지우면 그 CR이 전부 사라진다는 것을 알고, "CRD를 수정/삭제하지 말 것" 조건을 지킨다

## 개념 설명

### CustomResourceDefinition (CRD)
- 무엇: API 서버에 **새 종류의 리소스**(Kind)를 등록하는 오브젝트. 등록되면 `Deployment`처럼 `kubectl get/apply/delete`, RBAC, `explain`을 그대로 쓸 수 있다. CRD 자체는 클러스터 범위(`apiextensions.k8s.io/v1`)다.
- 왜: 도구(cert-manager의 `Certificate`, Gateway API의 `HTTPRoute`)가 자기 설정을 쿠버네티스 오브젝트로 선언하게 하려는 것이다. CRD만 있으면 "저장되는 데이터 형식"만 생기고, 그것을 보고 일하는 주체는 컨트롤러(아래 operator)다.
- 핵심 필드: `metadata.name`은 반드시 `<plural>.<group>`; `spec.group`; `spec.scope`(`Namespaced`/`Cluster`); `spec.names`(`plural`, `singular`, `kind`, `shortNames`); `spec.versions[]`(`name`, `served`, `storage`, `schema.openAPIV3Schema`, `subresources`, `additionalPrinterColumns`).
- 관계: CRD가 만드는 오브젝트는 custom resource(CR)다. CRD를 삭제하면 그 종류의 CR이 **모두 삭제**된다. 비유: CRD는 "양식 틀", CR은 그 틀로 쓴 "신청서", operator는 신청서를 읽고 처리하는 "담당 직원".

### 스키마와 검증 (structural schema)
- `schema.openAPIV3Schema`가 CR의 형식을 정한다 (`apiextensions.k8s.io/v1`에서는 필수). 쓰는 키워드: `type`, `properties`, `required`(**그 객체 안의 문자열 배열**), `enum`, `minimum`/`maximum`, `pattern`, `default`, `description`.
- 서버는 형식이 틀린 CR을 거부한다 (enum 밖의 값, 범위 밖의 숫자, 필수 필드 누락). `kubectl apply`는 스키마에 없는 필드도 `strict decoding error: unknown field`로 거부한다. `--validate=false`를 주면 그 필드를 **조용히 버리고(pruning)** 만든다.
- `default`는 서버가 값을 채운다. `description`은 `k explain` 출력에 나온다 (없으면 `<empty>`).
- `x-kubernetes-preserve-unknown-fields: true`는 검증을 느슨하게 하는 옵션이다. 문제가 "스키마가 잘못된 CR을 거부해야 한다"고 하면 쓰지 않는다.

### 버전과 서브리소스
- 한 CRD에 버전이 여러 개일 수 있다. `served: true`는 API로 노출, `storage: true`는 etcd에 저장하는 버전이고 **정확히 하나**여야 한다. 버전마다 스키마가 다를 수 있어 `k explain <kind>.spec --api-version=<group>/<version>`로 본다. 저장된 버전은 `status.storedVersions`에도 있다.
- `subresources.status: {}`를 켜면 `status`는 `/status` 경로로만 바뀐다. 본체를 patch해도 `status`는 무시된다. 컨트롤러가 상태를 쓰는 통로다.
- `additionalPrinterColumns`는 `k get`의 표에 열을 추가한다 (`jsonPath: .spec.cronSpec`).

### Operator 패턴: CRD + 컨트롤러 + RBAC
- 무엇: CR(원하는 상태)을 지켜보다가 실제 리소스(Deployment, PVC, Job...)를 만들고 맞추는 **컨트롤러**를 같이 배포하는 방식. 컨트롤러는 control plane 밖에서 보통 Deployment 하나로 돈다 (문서: `Deploying operators`).
- 설치 번들(YAML 또는 Helm chart)에 보통 들어 있는 것: CRD, Namespace, ServiceAccount, 컨트롤러 Deployment, (Cluster)Role/(Cluster)RoleBinding, 가끔 webhook 설정. 예: cert-manager chart를 렌더링하면 CRD 6, Deployment 3, ClusterRole 13, ClusterRoleBinding 10, Role/RoleBinding 각 4, ValidatingWebhookConfiguration/MutatingWebhookConfiguration 각 1이 나온다 (`helm template ... --set crds.enabled=true`, 설치는 하지 않음).
- RBAC 최소 권한 패턴: CR 자원 + `자원/status` + `자원/finalizers`(서브리소스는 따로 허용해야 한다), `events`(create, patch), 그리고 컨트롤러가 여러 개 떠도 하나만 일하도록 하는 leader election용 `coordination.k8s.io`의 `leases`(보통 자기 네임스페이스의 Role).
- 컨트롤러를 켜는 것(scale 1)과 CR을 만드는 것은 별개다. CR 생성만으로는 아무 일도 일어나지 않을 수 있다 (시뮬레이터의 operator 번들은 nginx 대체물이라 reconcile이 없다).

## 예시

**상황 1: 이미 설치된 CRD를 읽기만 해서 사실을 정리한다 (시뮬레이터에는 Gateway API와 cert-manager CRD가 있다).**
```bash
k get crd | grep -E 'cert-manager|gateway.networking' | head
k get crd -o jsonpath='{range .items[?(@.spec.group=="cert-manager.io")]}{.metadata.name}{"\n"}{end}' | sort      # 그룹이 정확히 일치하는 4개
k get crd -o name | sed 's#.*/##' | grep '\.cert-manager\.io$' | sort                                              # 접미사 매칭: acme.cert-manager.io 2개가 섞여 6개
C=httproutes.gateway.networking.k8s.io
k get crd $C -o jsonpath='scope={.spec.scope} kind={.spec.names.kind} short={.spec.names.shortNames}{"\n"}'
k get crd $C -o jsonpath='{range .spec.versions[*]}{.name} served={.served} storage={.storage}{"\n"}{end}'
k get crd $C -o jsonpath='{.spec.versions[?(@.storage==true)].name}{"\n"}'
k api-resources --api-group=gateway.networking.k8s.io
k explain httproute.spec.hostnames
```
기대 결과: 그룹 일치 4개는 `certificaterequests`, `certificates`, `clusterissuers`, `issuers` (`.cert-manager.io`). `acme.cert-manager.io`의 `challenges`/`orders`는 **다른 그룹**이므로 위 `==` 필터에는 안 나온다. HTTPRoute는 `scope=Namespaced kind=HTTPRoute short=`(shortNames 없음), `v1 served=true storage=true`, `v1beta1 served=true storage=false`, 저장 버전 `v1`. `explain`은 `GROUP: gateway.networking.k8s.io ... FIELD: hostnames <[]string>` 설명을 보여 준다. 파일 저장은 `k explain ... > ~/answers/explain.txt`.

**상황 2: CRD를 직접 작성해 등록하고 CR 하나를 만든다 (문서의 CronTab 예제를 확장: 필수 필드, 범위, enum, 기본값, status, 출력 열).**
```bash
cat > crontab-crd.yaml <<'EOF'
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: crontabs.stable.example.com
spec:
  group: stable.example.com
  scope: Namespaced
  names:
    plural: crontabs
    singular: crontab
    kind: CronTab
    shortNames:
    - ct
  versions:
  - name: v1
    served: true
    storage: true
    subresources:
      status: {}
    additionalPrinterColumns:
    - name: Schedule
      type: string
      jsonPath: .spec.cronSpec
    - name: Replicas
      type: integer
      jsonPath: .spec.replicas
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            required: [cronSpec]
            properties:
              cronSpec:
                type: string
                description: Cron expression
              image:
                type: string
              replicas:
                type: integer
                minimum: 1
                maximum: 5
                default: 1
                description: Number of runs kept
              mode:
                type: string
                enum: [fast, slow]
          status:
            type: object
            properties:
              phase:
                type: string
EOF
k apply --dry-run=server -f crontab-crd.yaml && k apply -f crontab-crd.yaml
k wait --for=condition=established crd/crontabs.stable.example.com --timeout=30s
cat <<'EOF' | k apply -f -
apiVersion: stable.example.com/v1
kind: CronTab
metadata:
  name: nightly
  namespace: demo
spec:
  cronSpec: "0 2 * * *"
  image: busybox:1.37
EOF
```
확인:
```bash
k -n demo get ct                                        # NAME nightly / SCHEDULE 0 2 * * * / REPLICAS 1  (replicas는 default로 채워짐)
k -n demo get crontab nightly -o jsonpath='{.spec}{"\n"}'   # {"cronSpec":"0 2 * * *","image":"busybox:1.37","replicas":1}
k explain crontab.spec.replicas                         # DESCRIPTION: Number of runs kept
k -n demo patch crontab nightly --subresource=status --type=merge -p '{"status":{"phase":"Ready"}}'
k -n demo get crontab nightly -o jsonpath='{.status}{"\n"}'   # {"phase":"Ready"}  (--subresource 없이 patch하면 status는 무시된다)
```
(위 명령은 `notes-b8` 네임스페이스에서 실제로 실행했다. 네임스페이스 `demo`는 먼저 `k create ns demo`로 만든다.)

**상황 3: 스키마에 안 맞는 CR이 거부될 때 메시지를 읽고 고친다.**
```bash
cat <<'EOF' | k apply -f -
apiVersion: stable.example.com/v1
kind: CronTab
metadata: {name: bad, namespace: demo}
spec: {cronSpec: "* * * * *", replicas: 9, mode: medium}
EOF
```
기대 결과: `spec.mode: Unsupported value: "medium": supported values: "fast", "slow"`와 `spec.replicas: Invalid value: 9: spec.replicas in body should be less than or equal to 5`. 다른 거부 메시지: 필수 필드 누락은 `spec.cronSpec: Required value`, 스키마에 없는 필드(`colour`)는 `strict decoding error: unknown field "spec.colour"`. `--validate=false`로 만들면 `colour`는 버려지고 `{"cronSpec":"* * * * *","replicas":1}`만 저장된다 (확인함). 값을 고쳐 다시 apply 한다. 필드 제약은 `k get crd crontabs.stable.example.com -o yaml`의 `schema` 부분에서 읽는다.

**상황 4: operator 번들을 설치하고, 최소 권한 RBAC을 주고, 컨트롤러를 켠다 (CRD + ServiceAccount + replicas 0 Deployment가 든 번들 가정).**
```bash
k apply -f bundle.yaml                      # CRD, ServiceAccount crontab-operator, Deployment crontab-operator(replicas: 0, image nginx 대체)
k get crd crontabs.stable.example.com
cat <<'EOF' | k apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: crontab-operator
rules:
- apiGroups: [stable.example.com]
  resources: [crontabs, crontabs/status, crontabs/finalizers]
  verbs: [get, list, watch, update, patch]
- apiGroups: [""]
  resources: [events]
  verbs: [create, patch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: crontab-operator
roleRef: {apiGroup: rbac.authorization.k8s.io, kind: ClusterRole, name: crontab-operator}
subjects:
- {kind: ServiceAccount, name: crontab-operator, namespace: demo}
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: leader-election
  namespace: demo
rules:
- apiGroups: [coordination.k8s.io]
  resources: [leases]
  verbs: [get, list, watch, create, update, patch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: leader-election
  namespace: demo
roleRef: {apiGroup: rbac.authorization.k8s.io, kind: Role, name: leader-election}
subjects:
- {kind: ServiceAccount, name: crontab-operator, namespace: demo}
EOF
k -n demo scale deploy crontab-operator --replicas=1
k -n demo rollout status deploy crontab-operator
```
확인:
```bash
SA=system:serviceaccount:demo:crontab-operator
k -n demo auth can-i patch crontabs.stable.example.com --subresource=status --as=$SA      # yes
k -n demo auth can-i update crontabs.stable.example.com --subresource=finalizers --as=$SA # yes
k -n demo auth can-i delete crontabs.stable.example.com --as=$SA                          # no
k -n demo auth can-i create deployments.apps --as=$SA                                     # no
k -n demo auth can-i create leases.coordination.k8s.io --as=$SA                           # yes
```
`resources`에 `crontabs`만 적으면 `patch crontabs --subresource=status`가 `no`가 된다 (확인함). `k create role ... --resource=crontabs.stable.example.com/status`처럼 서브리소스를 `자원.그룹/서브리소스` 형태로 쓸 수 있다. (위 RBAC·scale 결과는 `notes-b8` 네임스페이스에서 확인했고, ClusterRole은 이름이 겹치지 않게 만들었다가 지웠다.)

**상황 5: 답 파일을 요구된 형식으로 만든다, 그리고 CRD 삭제의 영향을 본다.**
```bash
k get crontabs -A --no-headers | wc -l > ~/answers/count.txt     # 숫자 한 줄 (Linux wc는 공백 없이 "1")
k get crontabs.stable.example.com -A                              # 같은 이름의 Kind가 겹치면 전체 이름으로
k delete crd crontabs.stable.example.com                          # CR도 함께 삭제됨
k get crontabs -A                                                 # error: ... the server could not find the requested resource
```
시뮬레이터 차이: 서버는 v1.34.0이고 시험은 v1.37. 문서의 CRD 페이지는 v1.37 기준이다. 시뮬레이터의 operator 번들(q87)은 nginx 대체물이라 CR을 만들어도 reconcile이 일어나지 않는다. 시뮬레이터에는 실제 operator 컨트롤러(cert-manager의 컨트롤러 등)가 떠 있지 않고 CRD만 있다 (`cert-manager` CRD 존재, 네임스페이스는 없음). 같은 파일에 CRD와 CR을 함께 두고 한 번에 `apply`해도 성공했다 (kubectl 1.34). 시험 환경에서는 안 될 수도 있으니 실패하면 CRD가 Established 된 뒤 다시 apply (미확인).

## 공식 문서에서 찾는 법
허용 사이트만 쓴다. 검색 결과 순위는 직접 확인하지 못했다(미확인). 안 나오면 URL 경로를 주소창에 직접 쓴다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| CRD 전체 YAML 뼈대 (group, scope, names, versions) | `CustomResourceDefinition` | https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/ | `Create a CustomResourceDefinition` | 첫 번째 YAML (`crontabs.stable.example.com`) |
| CR 만들기, `kubectl get ct` | 위와 같음 | 위와 같음 | `Create custom objects` | `kind: CronTab` 블록과 `kubectl get ct -o yaml` |
| 범위/패턴 검증 (`minimum`, `maximum`, `pattern`) | 위와 같음 | 위와 같음 | `Validation` 절의 `must have a minimum value of 1` | `replicas: minimum: 1 maximum: 10` 블록 |
| 기본값 `default` | 위와 같음 | 위와 같음 | `Defaulting` | `default: "5 0 * * *"` 포함 CRD |
| `kubectl get` 추가 열 | 위와 같음 | 위와 같음 | `Additional printer columns` | `additionalPrinterColumns:` 블록 |
| `status` 서브리소스 | 위와 같음 | 위와 같음 | `Status subresource` | `subresources: status: {}` 블록 |
| 여러 버전 (`served`/`storage`) | 위와 같음 | 위와 같음 | `Serving multiple versions of a CRD` | 버전 목록 설명 |
| CRD 삭제 영향 | 위와 같음 | 위와 같음 | `Delete a CustomResourceDefinition` | `kubectl delete -f resourcedefinition.yaml` |
| CRD가 무엇이고 operator와 어떻게 다른가 | `custom resources` | https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/ | `CustomResourceDefinitions`, `Custom controllers` | (설명 문장) |
| operator 패턴 설명, 배포 방식 | `operator pattern` | https://kubernetes.io/docs/concepts/extend-kubernetes/operator/ | `Deploying operators`, `An example operator` | (설명 문장) |

CRD 페이지에는 `enum` 전용 예제가 없다 (`enum: ["low", "medium", "high"]` 한 줄이 `Transition rules` 절의 `x-kubernetes-validations` 예제 안에 있을 뿐이다). 스키마 키워드는 OpenAPI 표준이다. 헷갈리면 이 노트의 CRD를 복사해 쓰고 `k apply --dry-run=server`로 검증한다. 검증 에러 메시지는 `metadata.name: ... must be spec.names.plural+"."+spec.group`, `schema.openAPIV3Schema: Required value`, `must have exactly one version marked as storage version`처럼 무엇이 틀렸는지 알려 준다 (모두 실제로 확인함).

## 자주 틀리는 점
- 증상: "그룹 `cert-manager.io`의 CRD만" 요구했는데 `challenges.acme.cert-manager.io`가 섞였다 -> 원인: `grep '\.cert-manager\.io$'` 접미사 매칭이 하위 그룹까지 잡는다 -> `jsonpath='{range .items[?(@.spec.group=="cert-manager.io")]}...'`로 그룹 필드를 직접 비교하고 `sort`.
- 증상: `no matches for kind "CronTab" in version "stable.example.com/v2"` + `ensure CRDs are installed first` -> 원인: CRD가 없는 게 아니라 **버전 또는 Kind의 철자**(`Crontab`)가 틀렸다 -> `k api-resources --api-group=<group>`과 CRD의 `versions[].name`으로 맞춘다.
- 증상: CRD apply 직후 CR이 안 만들어진다 -> 원인: 아직 Established가 아님 -> `k wait --for=condition=established crd/<name>` 후 CR (한 파일 동시 apply는 이 환경에서 통과).
- 증상: `unknown field "spec.colour"` -> 원인: 스키마에 없는 필드(오타) -> 이름을 CRD 스키마에서 복사. `--validate=false`로 우회하면 필드가 조용히 사라지므로 쓰지 않는다.
- 증상: 값이 거부됨 (`should be less than or equal to 5`, `Unsupported value`) -> 원인: 범위/enum 제약 -> `k get crd <이름> -o yaml`의 `minimum/maximum/enum`을 읽고 허용 값에서 문제 요구에 맞는 값을 고른다 ("허용되는 가장 큰 값" 같은 문구).
- 증상: `status`를 patch했는데 반영되지 않고 `(no change)` -> 원인: `status` 서브리소스가 켜져 있는데 본체를 patch했다 -> `--subresource=status`.
- 증상: `must be spec.names.plural+"."+spec.group` -> 원인: `metadata.name`이 `crontabs.stable.example.com` 형식이 아니다 (단수형을 썼다). `schema ... Required value` -> `apiextensions.k8s.io/v1`은 `openAPIV3Schema`가 필수. `json: cannot unmarshal bool ... required of type []string` -> `required: true`를 필드 안에 썼다 (v1에서는 객체 수준 `required: [필드...]`).
- 증상: operator가 `Forbidden ... cannot patch resource "crontabs/status"` -> 원인: RBAC에 `crontabs`만 있고 `crontabs/status`가 없다 -> `resources`에 서브리소스를 따로 추가 (leader election 오류면 `leases` Role 확인, 이 오류들은 시뮬레이터 대체물에서는 재현되지 않음: 미확인).
- 증상: CR이 있는데 `k get crontabs`가 `the server doesn't have a resource type` -> 원인: CRD가 지워졌다 (CR도 함께 사라진다). "CRD를 삭제/수정하지 말 것" 조건이 있으면 `k delete crd`를 절대 하지 않는다.
- 증상: CRD 삭제 후 다시 만들어도 이전 CR이 없다 -> 원인: CRD 삭제 때 모든 CR이 삭제됨 -> 삭제 전에 `k get <plural> -A -o yaml`로 백업하거나 건드리지 않는다.
- 증상: 출력 형식 감점 -> 원인: 문제가 요구한 형식(정렬, 한 줄에 하나, 숫자만)을 안 지켰다 -> `sort`, `--no-headers`, `wc -l`로 가공하고 파일을 `cat`으로 확인.

## 빠르게 푸는 순서
1. 컨텍스트/네임스페이스, CRD 그룹 이름, 출력 파일 경로와 형식, 금지 조건("CRD 수정 금지", "와일드카드 금지")을 먼저 적는다. (30초)
2. 조사형: `k get crd`로 그룹을 확인하고 jsonpath로 scope/버전/shortNames를 읽는다. 그룹 필터는 `==`로. (1~2분)
3. 필드 문서화: `k explain <kind>.spec.<field>`를 파일로 리다이렉트 (`--api-version` 필요하면 추가). (30초)
4. CR 생성: CRD 스키마의 `required`/`minimum`/`maximum`/`enum`을 읽고 YAML을 쓴 뒤 `k apply`. 거부되면 메시지 그대로 고친다. (2분)
5. CRD 작성형: `Create a CustomResourceDefinition` 블록을 복사해 이름(`<plural>.<group>`), names, 스키마, `default`, 서브리소스, 출력 열을 추가하고 `k apply --dry-run=server` -> 적용 -> `k wait --for=condition=established`. (3~4분)
6. operator 설치형: `k apply -f bundle.yaml` -> `k get crd` 확인 -> 요구한 이름대로 ClusterRole/Role(+서브리소스, leases, events) 작성 -> `k scale deploy ... --replicas=1` -> `rollout status` -> CR 생성. (4~5분)
7. 마지막에 `k auth can-i`(되어야 하는 것과 안 되어야 하는 것), `k get <plural> -A`로 결과를 확인하고 답 파일을 `cat`으로 본다. 총 목표 6~8분.
