# B3. Create and manage Kubernetes clusters using kubeadm

## 이 항목에서 공부할 것
- [ ] `kubeadm init`용 설정 파일(`InitConfiguration` + `ClusterConfiguration` + `KubeletConfiguration`)을 쓰고 `kubeadm config validate`로 통과시킨다
- [ ] 필요한 이미지 목록을 `kubeadm config images list --config ...`로 뽑아 파일에 저장한다
- [ ] 예전 API 버전 설정 파일을 `kubeadm config migrate`로 변환하고 빠진 부분(KubeletConfiguration)을 직접 채운다
- [ ] `kubeadm init` 뒤 kubeconfig 3줄(`admin.conf` 복사)을 하고, CNI 매니페스트를 적용해 노드가 Ready, CoreDNS가 Running이 되는 것을 확인한다
- [ ] `kubeadm token list/create/delete`와 `--print-join-command`로 워커 join 명령을 만들고, CA 해시를 직접 계산할 수도 있다
- [ ] 컨트롤 플레인 노드 추가용 join 명령(`--control-plane --certificate-key`)이 어떤 단계로 만들어지는지 안다
- [ ] 이미 있는 kubeadm 클러스터의 `podSubnet` 등 생성 시 설정을 `kubeadm-config` ConfigMap에서 읽는다
- [ ] 노드 제거 절차(drain -> `kubeadm reset` -> `kubectl delete node`)를 안다

## 개념 설명

### kubeadm init
- 무엇: 컨트롤 플레인 첫 노드를 만드는 명령. 문서 "Init workflow" 순서: 사전 점검(preflight) -> 자체 서명 CA와 인증서 -> kubeconfig 파일들 -> API server/controller-manager/scheduler(와 etcd) static Pod 매니페스트를 `/etc/kubernetes/manifests`에 작성 -> 컨트롤 플레인 노드에 라벨/테인트 -> 부트스트랩 토큰 -> join용 ConfigMap과 RBAC -> CoreDNS와 kube-proxy 설치.
- 결과물은 컨트롤 플레인 노드의 `/etc/kubernetes` 아래에 있다 (시뮬레이터 컨트롤 플레인에서 확인): `admin.conf`, `controller-manager.conf`, `kubelet.conf`, `scheduler.conf`, `super-admin.conf`, `manifests/`, `pki/`.
- 자주 쓰는 옵션 (`kubeadm init --help`로 확인): `--apiserver-advertise-address`, `--pod-network-cidr`, `--service-cidr`(기본 `10.96.0.0/12`), `--control-plane-endpoint`, `--kubernetes-version`, `--node-name`, `--cri-socket`, `--upload-certs`, `--config`, `--dry-run`, `--ignore-preflight-errors`.
- 플래그 대신 `--config` 파일로도 같은 설정을 한다. 문서는 `--config`와 다른 플래그를 섞는 것이 일부 경우 허용되지 않는다고 한다. 한 방식만 쓰는 게 안전하다.
- `admin.conf`의 인증서는 `O=kubeadm:cluster-admins`(cluster-admin에 바인딩), `super-admin.conf`는 `O=system:masters`(RBAC를 우회하는 비상용)다 (노드에서 openssl로 확인).

### kubeadm 설정 파일 (kubeadm.k8s.io/v1beta4)
- 한 파일에 `---`로 문서를 여러 개 넣는다. 문서마다 역할이 다르다.
  - `InitConfiguration`: 이 노드에 관한 것. `localAPIEndpoint.advertiseAddress/bindPort`, `nodeRegistration.name/criSocket/taints`, 부트스트랩 토큰.
  - `ClusterConfiguration`: 클러스터 전체. `kubernetesVersion`, `clusterName`, `controlPlaneEndpoint`, `networking.podSubnet/serviceSubnet`, `apiServer.certSANs`, `etcd`.
  - `KubeletConfiguration` (apiVersion `kubelet.config.k8s.io/v1beta1`): kubelet 기본 설정. `cgroupDriver: systemd`가 대표적.
- `kubeadm config print init-defaults`로 뼈대를 뽑고, `--component-configs KubeletConfiguration`을 붙이면 kubelet 부분까지 나온다.
- 이미 만들어진 클러스터가 어떤 설정으로 만들어졌는지는 `kube-system`의 `kubeadm-config` ConfigMap에 있다 (아래 예시).
- `CRI socket`은 URL 스킴이 있어야 한다 (`unix:///run/containerd/containerd.sock`). 스킴이 없으면 `migrate/validate`가 경고를 내고 `unix`를 자동으로 붙인다.

### Pod network (CNI) 애드온
- `kubeadm init`만으로는 Pod 네트워크가 없다. 문서: 클러스터에는 Pod 네트워크를 하나만 설치할 수 있고, 설치했는지는 CoreDNS Pod가 Running인지로 확인한다. `kubeadm init` 문서는 DNS 서버(CoreDNS)가 배포되어도 CNI가 설치될 때까지 스케줄되지 않는다고 설명한다. 노드가 NotReady로 보이는 것은 q88/q89 문제 설명 기준이며 이 시뮬레이터에서는 CNI 없는 상태를 재현하지 않아 직접 보지 못했다(미확인).
- Pod CIDR는 호스트/서비스 네트워크와 겹치면 안 되고, `kubeadm init --pod-network-cidr`(또는 `podSubnet`)와 CNI 설정(예: Calico `CALICO_IPV4POOL_CIDR`, Tigera `Installation`의 `cidr`)이 일치해야 한다.
- 설치는 보통 `k apply -f <manifest>`. kubernetes.io의 addons 페이지는 CNI 프로젝트 목록과 외부 링크만 있다. 시험에서는 과제 안내/Quick Reference 링크의 매니페스트를 쓴다 (study-guide 3절).

### Bootstrap token과 join
- 워커는 `kubeadm join <endpoint>:6443 --token <t> --discovery-token-ca-cert-hash sha256:<hash>`로 합류한다. 토큰은 "들어와도 되는 노드"의 비밀번호, 해시는 "내가 붙는 API 서버가 진짜인지" 확인용 CA 지문이다.
- 토큰은 기본 24시간 후 만료된다 (`--ttl`). 토큰은 `kube-system`의 `bootstrap-token-<id>` Secret(type `bootstrap.kubernetes.io/token`)이다.
- 컨트롤 플레인 추가 join에는 `--control-plane --certificate-key <key>`가 더 필요하고, 인증서는 `kubeadm-certs` Secret에 올려 두며 2시간 뒤 삭제된다 (HA 문서). 자세한 HA 구성은 B5.

### 노드 제거와 초기화
- 문서 "Clean up": 컨트롤 플레인에서 `kubectl drain <node> --delete-emptydir-data --force --ignore-daemonsets`, 해당 노드에서 `kubeadm reset`, 그다음 `kubectl delete node <node>`. `kubeadm reset`은 iptables/IPVS 규칙을 정리하지 않는다.

## 예시

**상황 1: 새 클러스터용 `kubeadm init` 설정 파일을 쓰고 검증하고, 이미지 목록을 저장한다.**
```bash
cat > /opt/cka/init-config.yaml <<'EOF'
apiVersion: kubeadm.k8s.io/v1beta4
kind: InitConfiguration
localAPIEndpoint:
  advertiseAddress: 10.0.0.10
  bindPort: 6443
nodeRegistration:
  name: prod-cp1
  criSocket: unix:///run/containerd/containerd.sock
---
apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
kubernetesVersion: v1.34.0
clusterName: prod-eu
controlPlaneEndpoint: cp.prod.example.com:6443
networking:
  podSubnet: 10.200.0.0/16
  serviceSubnet: 10.96.0.0/16
apiServer:
  certSANs:
  - cp.prod.example.com
  - 10.0.0.10
---
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
cgroupDriver: systemd
EOF
kubeadm config validate --config /opt/cka/init-config.yaml
kubeadm config images list --config /opt/cka/init-config.yaml > /opt/cka/init-images.txt
```
확인과 기대 결과 (컨트롤 플레인 노드에서 실제 실행):
```bash
kubeadm config validate --config /opt/cka/init-config.yaml   # ok
cat /opt/cka/init-images.txt     # kube-apiserver / controller-manager / scheduler / kube-proxy :v1.34.0, coredns/coredns:v1.12.1, pause:3.10.1, etcd:3.6.4-0 (총 7줄)
```
필드 이름이 틀리면 strict decoding 오류가 난다: `podSubnet`을 `podSubNet`으로 바꾸면 `unknown field "networking.podSubNet"`, 종료 코드 1. 이 단계는 클러스터를 바꾸지 않는다. 실제 부트스트랩은 같은 파일로 `kubeadm init --config /opt/cka/init-config.yaml --upload-certs`.

**상황 2: 옛 설정 파일을 v1beta4로 바꾸고, Pod/Service 네트워크 겹침과 KubeletConfiguration 누락을 고친다.**
```bash
kubeadm config migrate --old-config broken-init.yaml --new-config fixed-init.yaml
printf -- '---\napiVersion: kubelet.config.k8s.io/v1beta1\nkind: KubeletConfiguration\ncgroupDriver: systemd\n' >> fixed-init.yaml
vim fixed-init.yaml          # podSubnet 값 수정 등
kubeadm config validate --config fixed-init.yaml
diff broken-init.yaml fixed-init.yaml
```
확인 (v1beta3 샘플 파일로 실제 실행): 출력 파일은 `apiVersion: kubeadm.k8s.io/v1beta4`가 되고, 스킴 없는 `criSocket: /run/containerd/containerd.sock`은 `unix:///run/containerd/containerd.sock`으로 자동 변환되며 경고가 한 줄 나온다. 입력에 있던 `KubeletConfiguration` 문서는 출력에서 사라졌고(그래서 `printf`로 다시 붙인다), `podSubnet: 10.96.0.0/16`과 `serviceSubnet: 10.96.0.0/12`처럼 겹치는 값도 `validate`는 `ok`로 통과시켰다. 겹침은 눈으로 직접 확인해야 한다.

**상황 3: 이미 떠 있는 kubeadm 클러스터가 어떤 CIDR로 만들어졌는지 읽는다 (CNI 설정 전에 자주 필요).**
```bash
k -n kube-system get cm kubeadm-config -o jsonpath='{.data.ClusterConfiguration}' | grep -E 'podSubnet|serviceSubnet|controlPlaneEndpoint|kubernetesVersion'
k get nodes -o custom-columns=NAME:.metadata.name,CIDR:.spec.podCIDR
```
시뮬레이터 결과: `podSubnet: 10.244.0.0/16`, `serviceSubnet: 10.96.0.0/16`, `controlPlaneEndpoint: k8s-control-plane:6443`, `kubernetesVersion: v1.34.0`. 노드별 CIDR는 `10.244.0.0/24`, `10.244.1.0/24`, `10.244.2.0/24`로 클러스터 `podSubnet`의 조각이다.

**상황 4: 컨트롤 플레인을 초기화하고 CNI를 올린다.** (미확인: 실제 `kubeadm init`/`join`은 클러스터를 바꾸므로 이 랩에서 실행하지 않았다. 옵션 이름은 `kubeadm init --help`로, 절차는 문서 v1.37 페이지로 확인했다.)
```bash
sudo kubeadm init --apiserver-advertise-address=10.0.0.10 --pod-network-cidr=10.244.0.0/16 --control-plane-endpoint=cp.example.com:6443
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config
k apply -f <과제에서 준 CNI 매니페스트>        # Calico라면 CIDR을 위 --pod-network-cidr와 맞출 것
k get nodes -w                                 # Ready가 될 때까지
k -n kube-system get pods -l k8s-app=kube-dns  # CoreDNS Running
```
CoreDNS 확인 명령의 라벨은 시뮬레이터에서 `coredns-...  1/1 Running` 두 개로 나왔다. root면 `export KUBECONFIG=/etc/kubernetes/admin.conf`도 된다 (문서).

**상황 5: 워커용 join 명령을 새로 만들고, 만료된 토큰 대신 쓰고, 해시를 직접 계산한다.**
```bash
kubeadm token list
kubeadm token create --ttl 2h --description "cka worker join" --print-join-command > /opt/cka/join-command.txt
kubeadm token delete abcdef.0123456789abcdef
cat /etc/kubernetes/pki/ca.crt | openssl x509 -pubkey | openssl rsa -pubin -outform der 2>/dev/null | openssl dgst -sha256 -hex | sed 's/^.* //'
```
확인과 기대 결과: 시뮬레이터에서 `kubeadm token create ... --print-join-command --dry-run`으로 실제 실행(`--dry-run`이라 토큰은 만들어지지 않고 `kubeadm token list`가 비어 있음)한 결과 마지막 줄은 `kubeadm join k8s-control-plane:6443 --token j7vdnj.tx0peodowbs4kwxd --discovery-token-ca-cert-hash sha256:60be...49fc` 형태였고, `sha256:` 뒤 값은 위 openssl 파이프의 출력(`60befda5...149fc`)과 같았다. 워커에서는 이 줄을 `sudo`로 실행한다 (실행은 미확인).

**상황 6: 컨트롤 플레인 노드 추가용 join 명령을 만든다.**
```bash
sudo kubeadm init phase upload-certs --upload-certs        # 마지막 줄이 certificate key (미확인: 클러스터를 바꾸므로 실행하지 않음)
kubeadm token create 0a1b2c.0123456789abcdef --ttl 45m --description "second control plane" --print-join-command --certificate-key <KEY>
```
두 번째 명령은 `--dry-run`과 임의의 64자리 key로 실행해 마지막 줄이 `kubeadm join k8s-control-plane:6443 --token 0a1b2c.0123456789abcdef --discovery-token-ca-cert-hash sha256:... --control-plane --certificate-key 000...0`으로 나오는 것을 확인했다. 이 줄을 새 컨트롤 플레인 노드에서 실행한다. `kubeadm init phase upload-certs --upload-certs --dry-run`은 이 클러스터에서 `failed to load kubeconfig ... dryrun/admin.conf` 오류가 났으므로 쓰지 않는다.

**상황 7: 워커 노드를 클러스터에서 제거한다.** (미확인: 문서 "Clean up" 절의 순서를 따른 것이며 이 랩에서 실행하지 않았다. 읽기 전용 점검만 했다.)
```bash
k drain <node> --delete-emptydir-data --force --ignore-daemonsets    # 컨트롤 플레인에서
sudo kubeadm reset                                                    # 해당 노드에서
k delete node <node>                                                  # 컨트롤 플레인에서
```

시뮬레이터 차이: kind 노드는 `kubeadm`이 이미 만든 노드 컨테이너라 `init`/`join`/`reset`을 실제로 돌릴 수 없고(q73/q74는 파일과 API 수준만 채점), 기본 CNI는 kindnet이다 (`ds/kindnet`). Calico 설치 연습은 ik8s가 필요하다 (q88/q89, 미테스트). 시뮬레이터는 v1.34.0이고 시험은 v1.37이라 `kubernetesVersion` 값이 다르다.

## 자주 틀리는 점
- 증상: `kubeadm config validate`가 `unknown field "networking.podSubNet"` -> 원인: 필드명 대소문자 오타 (strict decoding) -> 참조 페이지에서 정확한 이름(`podSubnet`)을 Ctrl+F로 확인한다.
- 증상: `validate`는 `ok`인데 Pod/Service CIDR가 겹친다 -> 원인: `validate`는 겹침을 잡지 않는다 (직접 확인) -> `10.96.0.0/16`이 `10.96.0.0/12`에 포함되는 식의 겹침은 눈으로 확인한다.
- 증상: `migrate`한 파일에서 kubelet 설정이 사라졌다 -> 원인: `migrate`가 `KubeletConfiguration` 문서를 버린다 (직접 확인) -> `cgroupDriver: systemd` 문서를 다시 붙인다. 원본은 건드리지 않는다.
- 증상: `criSocket`에 대한 `Usage of CRI endpoints without URL scheme is deprecated` 경고 -> 원인: `unix://` 스킴이 없다 -> `unix:///run/containerd/containerd.sock`.
- 증상: join 명령에 `--discovery-token-ca-cert-hash`가 없다 -> 원인: 토큰만 만들었다 -> `kubeadm token create --print-join-command`를 쓴다.
- 증상: 컨트롤 플레인 join이 인증서를 못 받는다 -> 원인: `--certificate-key` 누락이거나 업로드한 지 2시간이 지났다 (HA 문서) -> `kubeadm init phase upload-certs --upload-certs`를 다시 실행해 새 key를 쓴다.
- 증상: 같은 ID의 토큰을 만들려는데 실패한다 -> 원인: 이미 있다 (q75 해설) -> `kubeadm token list`로 먼저 보고 필요하면 `kubeadm token delete`.
- 증상: 노드가 NotReady, CoreDNS Pending -> 원인: CNI 미설치 (study-guide, 이 랩에서는 재현 못 함, 미확인) -> 과제가 준 매니페스트를 `k apply -f`. Calico면 `CALICO_IPV4POOL_CIDR`/`Installation.cidr`를 `podSubnet`과 맞춘다.
- 증상: Tigera operator 매니페스트가 `apply`에서 annotation 크기 오류 -> 원인: CRD가 커서 client-side apply 한도 초과 (q89 해설, 미확인) -> `k create -f` 또는 `k apply --server-side -f`.
- 증상: `kubectl`이 `http://localhost:8080 ... connection refused` -> 원인: kubeconfig가 없다 (init 후 설정을 안 함. `KUBECONFIG=/dev/null`로 같은 오류 재현 확인) -> `admin.conf`를 `$HOME/.kube/config`로 복사하거나 `export KUBECONFIG=/etc/kubernetes/admin.conf`.
- 증상: 며칠 전 토큰으로 join하려 한다 -> 원인: 토큰은 기본 24시간 후 만료된다 (문서) -> `kubeadm token create --print-join-command`로 새로 만든다.
- 증상: `kubeadm reset`했는데 iptables 규칙이 남았다 -> 원인: reset은 iptables/IPVS를 정리하지 않는다 (문서) -> 문서의 `iptables -F && ...` 줄을 수동 실행.

## 빠르게 푸는 순서
1. 문제를 읽고 어느 호스트(`ssh`), 어떤 파일 경로, 어떤 값(버전, CIDR, SAN, 노드 이름)이 필요한지 적는다. (30초)
2. 설정 파일 문제: `kubeadm config print init-defaults --component-configs KubeletConfiguration`으로 뼈대를 받아 필요한 필드만 남기거나, 참조 페이지의 v1beta4 예제를 복사한다. (2분)
3. `kubeadm config validate --config <file>`로 통과시키고 `kubeadm config images list --config <file>`로 이미지 목록을 파일에 저장한다. 원본 파일을 고치지 말라면 `migrate`로 새 파일을 만든다. (1분)
4. init 문제: 문서의 `kubeadm init <args>` 옵션과 kubeconfig 3줄을 그대로 사용하고, CNI 매니페스트는 과제 안내의 것을 `k apply -f`. 노드 Ready와 CoreDNS Running을 확인한다. (3~5분)
5. join 문제: `kubeadm token create --print-join-command`로 명령을 만들고 파일에 저장, 필요하면 `kubeadm token delete`. (1~2분)
6. 컨트롤 플레인 추가: `upload-certs`로 key를 받고 `--certificate-key`를 붙인 join 명령을 만든다. (2분)
7. 결과 파일을 `cat`으로 확인하고 `exit`로 base 호스트로 돌아온다. 총 목표 5~8분.
