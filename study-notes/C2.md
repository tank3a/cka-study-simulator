# C2. Define and enforce Network Policies

## 이 항목에서 공부할 것
- [ ] default-deny ingress 정책(`podSelector: {}` + `policyTypes: [Ingress]`)을 쓰고, 이후 모든 접속이 타임아웃인 것을 `wget -T2`로 확인한다
- [ ] `podSelector`로 같은 네임스페이스의 특정 Pod만 허용하고 `ports`로 TCP 포트를 하나로 제한한다
- [ ] 다른 네임스페이스의 Pod을 허용한다: `namespaceSelector`에 `kubernetes.io/metadata.name`(또는 `k label ns`로 붙인 라벨)을 쓴다
- [ ] 한 `from` 항목 안의 `namespaceSelector` + `podSelector`(AND)와 `-`가 둘인 경우(OR)를 구분하고, 후보 YAML 3개 중 가장 덜 허용하는 것을 `k describe netpol`로 판별한다 (q29)
- [ ] egress 정책을 쓰고 DNS(UDP와 TCP 53, kube-system의 `k8s-app=kube-dns`)를 반드시 같이 허용한다 (q30)
- [ ] 이미 있는 deny 정책 아래서 web->api, api->db 체인만 허용하는 정책을 추가·수정한다 (q45)
- [ ] `ipBlock`(`except` 포함)과 `endPort`(포트 범위) 문법을 문서에서 복사해 쓴다
- [ ] `policyTypes`를 생략했을 때의 기본값을 알고, 만든 뒤 `k get netpol -o yaml`로 실제 값을 확인한다

## 개념 설명

### NetworkPolicy가 하는 일 (isolation과 additive)
- 무엇인가: "이 Pod으로 들어오는(ingress) / 이 Pod에서 나가는(egress) 연결 중 무엇을 허용할지" 적는 네임스페이스 범위 리소스. 건물 출입 허용 명단과 비슷하다: 명단이 아예 없으면 누구나 드나들고, 한 번 명단이 생기면 명단에 있는 사람만 들어간다.
- 왜 필요한가: 기본값은 전부 허용이라 (확인함: 정책이 없을 때 다른 네임스페이스 Pod에도 닿음) 앞단 Pod만 DB에 닿게 하는 식의 제한을 하려면 정책이 필요하다.
- 핵심 동작: Pod은 방향마다 따로 "격리"된다. 어떤 정책이 그 Pod을 `podSelector`로 고르고 `policyTypes`에 `Ingress`가 있으면 그 Pod은 ingress 격리가 되고, 그때부터 허용된 연결만 들어온다. egress도 같다. 여러 정책의 허용은 합집합(additive)이고 거부 규칙은 없다 (문서 `The two sorts of pod isolation`). 응답 트래픽은 자동 허용된다.
- 예외 (문서, 이 랩에서 확인함): ingress 격리된 Pod에도 그 Pod이 있는 노드에서 오는 트래픽은 허용된다. default-deny 상태에서 Pod `web`은 타임아웃인데 같은 노드에서 `curl`하면 200이었다. kubelet 프로브가 계속 되는 이유다.
- 전제: 정책은 CNI가 집행한다. 집행하는 CNI가 아니면 만들어도 효과가 없다 (문서 `Prerequisites`). 이 랩은 kindnet이 집행한다 (`simulator/docs/KNOWN_LIMITS.md`, 이번에도 차단/허용이 실제로 동작함을 확인).
- 명령형 생성이 없다: `k create networkpolicy x`는 `error: Unexpected args: [networkpolicy x]` (확인함). 문서 YAML을 복사해 고친다.

### podSelector와 policyTypes
- `spec.podSelector`: 이 정책이 "보호/제한하는 대상 Pod". `{}`면 네임스페이스의 모든 Pod.
- `policyTypes`: `Ingress`, `Egress`, 또는 둘. 생략하면 `Ingress`는 항상 들어가고, `egress` 규칙이 하나라도 있으면 `Egress`도 들어간다. 확인함: `egress:`만 쓰고 `policyTypes`를 생략하자 저장된 값이 `["Ingress","Egress"]`, `ingress:`만 쓰면 `["Ingress"]`, 규칙 없이 `podSelector: {}`만 쓰면 `["Ingress"]`였다. 즉 egress 규칙만 쓴 정책이 의도치 않게 ingress도 막는다. 항상 `policyTypes`를 직접 쓴다.
- 문서의 `default-deny-all`은 `podSelector: {}` + `policyTypes: [Ingress, Egress]`이고 `--dry-run=server`를 통과했다 (확인함). 정책은 합집합이라 `allow-all-ingress`가 하나라도 있으면 다른 deny는 의미가 없어진다 (문서).
- `ingress: - {}` (빈 규칙)은 모든 ingress 허용 (문서 `Allow all ingress traffic`, 동작은 이 랩에서 시험 안 함 **(미확인)**). `ingress` 규칙 없이 `policyTypes: [Ingress]`면 모두 거부 (확인함).

### from / to 선택자: podSelector, namespaceSelector, ipBlock
- `podSelector` 단독: 정책과 같은 네임스페이스의 그 라벨 Pod만. 다른 네임스페이스는 막힌 채다 (확인함: 같은 라벨의 다른 네임스페이스 `web`은 타임아웃).
- `namespaceSelector` 단독: 그 라벨의 네임스페이스에 있는 모든 Pod. `namespaceSelector: {}`는 모든 네임스페이스의 모든 Pod이라 가장 넓다 (확인함: 다른 네임스페이스와 같은 네임스페이스의 `batch`가 모두 통과).
- 네임스페이스 이름으로 고르기: 컨트롤 플레인이 모든 네임스페이스에 붙여 주는 `kubernetes.io/metadata.name=<이름>` 라벨을 쓴다 (문서 `Targeting a Namespace by its name`). 임의 라벨(`env=prod`)을 쓰라는 문제는 `k get ns --show-labels`로 존재를 확인하고 없으면 `k label ns <ns> env=prod`로 붙인다 (확인함: 라벨을 붙인 네임스페이스만 통과, 정책과 같은 네임스페이스는 라벨이 없어 막힘).
- AND와 OR (문서 `Behavior of to and from selectors`, 이 랩에서 4개 클라이언트로 확인함):
  - 한 항목 안에 둘 다 쓰면 AND: "그 네임스페이스의 그 라벨 Pod". `from: [ {namespaceSelector: A, podSelector: B} ]`
  - `-`로 나눠 쓰면 OR: "그 네임스페이스의 모든 Pod 또는 정책 네임스페이스의 그 라벨 Pod". `from: [ {namespaceSelector: A}, {podSelector: B} ]`
- `ipBlock`: CIDR와 `except`. 문서는 클러스터 바깥 IP용이라 하고 Pod IP는 바뀌므로 비권장이다. 기술적으로는 동작한다 (확인함: `10.244.0.0/16 except <batch IP>/32`에서 batch만 차단).

### ports, endPort, protocol
- `ports: [{protocol: TCP, port: 80}]`: 목적지 포트 제한. 나머지 포트는 막힌다 (확인함: 80만 허용하면 같은 Pod의 8080은 타임아웃).
- 범위: `port: 8000`, `endPort: 9000` (숫자만, `endPort >= port`, Stable since v1.25, 문서 `Targeting a range of ports`). 확인함: 8000-9000을 허용하자 8080이 통과했고 `describe`에 `To Port Range: 8000-9000/TCP`로 나온다.
- `protocol` 기본 TCP, 값은 TCP/UDP/SCTP. DNS는 UDP 53과 TCP 53 둘 다 연다.

### egress와 DNS
- egress 격리 Pod은 이름 조회도 막는다. 증상은 "IP로는 되는데 이름은 `bad address`" (확인함). 대상 Service 이름을 쓰려면 DNS 서버(CoreDNS)로 가는 UDP/TCP 53을 허용해야 한다.
- 허용 대상은 `namespaceSelector: kubernetes.io/metadata.name=kube-system` AND `podSelector: k8s-app=kube-dns` (같은 `to` 항목 안). 이 규칙 하나로 DNS 조회가 성공했다 (확인함). 이 랩의 CoreDNS Pod 2개는 서로 다른 노드에 있다.
- Service 이름으로 접속해도 정책은 Pod 기준으로 판단한다: `http://db`(Service)를 Pod 선택자(`app=db`)로 허용해도 통과했다 (확인함).

## 예시

### 예시 1. default deny 후 앞단만 허용
상황: "ns `shop`에서 `app=db` Pod은 `role=frontend` Pod의 TCP 80만 받게 하라."
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: shop
spec:
  podSelector: {}
  policyTypes:
  - Ingress
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-frontend
  namespace: shop
spec:
  podSelector:
    matchLabels:
      app: db
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: frontend
    ports:
    - protocol: TCP
      port: 80
```
```bash
k apply -f np.yaml
k -n shop get netpol
k -n shop describe netpol db-allow-frontend | sed -n '/Spec:/,$p'
k -n shop exec web -- wget -qO- -T2 http://db          # 라벨 role=frontend 인 Pod: 성공
k -n shop exec batch -- wget -qO- -T2 http://db        # 다른 라벨: wget: download timed out
```
기대: `describe`에 `To Port: 80/TCP`, `From: PodSelector: role=frontend`, `Not affecting egress traffic` (확인함). 허용 Pod은 `<!DOCTYPE html>`, 차단 Pod은 2초 뒤 `wget: download timed out`. 문서는 정책을 CNI가 처리하는 데 시간이 걸릴 수 있다고 적는다 (`Pod lifecycle` 절). 이 랩에서는 3초 기다린 뒤 시험했다. 만들자마자 시험하면 거짓 성공이 날 수 있다.

### 예시 2. 후보 YAML 3개 중 가장 덜 허용하는 것 고르기 (q29 형태)
상황: "ns `shop-front`의 `role=frontend` Pod만 `shop-back`의 `api`(TCP 80)에 닿게 하는 후보 `np-a/b/c.yaml` 중 가장 덜 허용하는 하나만 적용하라. 파일 수정과 새 정책 작성은 금지."
```bash
cat /home/candidate/netpol/np-a.yaml /home/candidate/netpol/np-b.yaml /home/candidate/netpol/np-c.yaml
```
각 파일의 `from:` 아래 모양만 본다.
```yaml
# np-a: 모든 네임스페이스의 모든 Pod 허용 (가장 넓다)
- namespaceSelector: {}
# np-b: AND, shop-front 의 role=frontend 만 (정답)
- namespaceSelector:
    matchLabels: {kubernetes.io/metadata.name: shop-front}
  podSelector:
    matchLabels: {role: frontend}
# np-c: OR, shop-front 의 모든 Pod 또는 shop-back 의 role=frontend (np-b 보다 넓다)
- namespaceSelector:
    matchLabels: {kubernetes.io/metadata.name: shop-front}
- podSelector:
    matchLabels: {role: frontend}
```
```bash
k apply -f /home/candidate/netpol/np-b.yaml          # 고른 것 하나만
k -n shop-back describe netpol                        # From 구조를 다시 확인
k -n shop-front exec web -- wget -qO- -T2 http://api.shop-back     # 성공
k -n shop-front exec batch -- wget -qO- -T2 http://api.shop-back   # 타임아웃
```
위 세 모양을 이 랩의 4개 클라이언트(정책 네임스페이스/다른 네임스페이스 x frontend/batch)로 시험한 결과: np-a는 시험한 두 `batch`(다른 네임스페이스, 정책 네임스페이스)가 모두 통과, np-b(AND)는 다른 네임스페이스의 frontend 1개만 통과하고 나머지 3개 차단, np-c(OR)는 다른 네임스페이스의 frontend와 batch, 정책 네임스페이스의 frontend 3개 통과하고 정책 네임스페이스의 batch만 차단 (확인함, 네임스페이스 이름만 다르게 같은 구조). `describe`의 `From:` 아래에 `NamespaceSelector`와 `PodSelector`가 같은 블록에 있으면 AND, `----------`로 나뉘어 있으면 OR이다.

### 예시 3. egress + DNS (q30 형태)
상황: "ns `egress-lab`의 `app=client` Pod은 `egress-data` 네임스페이스의 `app=db` Pod TCP 80과 DNS(UDP/TCP 53)로만 나갈 수 있다. `ipBlock` 금지."
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-egress
  namespace: egress-lab
spec:
  podSelector:
    matchLabels:
      app: client
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: egress-data
      podSelector:
        matchLabels:
          app: db
    ports:
    - protocol: TCP
      port: 80
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```
```bash
k apply -f client-egress.yaml
k -n egress-lab exec client -- wget -qO- -T2 http://db.egress-data      # 성공
k -n egress-lab exec client -- wget -qO- -T2 http://cache.egress-data   # wget: download timed out
```
기대: 위 YAML을 네임스페이스 이름만 바꿔 (`notes-c2` / `notes-c2-other`) `--dry-run=server` 통과 후 적용했고, `db`는 성공, 같은 네임스페이스 `cache`는 타임아웃, 정책 네임스페이스 안의 `db`도 타임아웃(대상 네임스페이스가 AND 조건이라서)이었다 (확인함). DNS 규칙을 빼면 `wget: bad address 'db'`가 나고 Pod IP로는 접속된다 (확인함). TCP 53까지 여는 이유: 해설은 큰 응답이 TCP로 넘어갈 때 막히기 때문이라고 한다 **(미확인, 이 랩에서 재현 안 함)**.

### 예시 4. 체인만 허용하고 나머지는 차단 (q45 형태)
상황: "`deny-all-ingress`가 있다. web->api, api->db만(TCP 80) 열고 web->db와 다른 네임스페이스는 막은 채. 정책을 지우거나 ipBlock을 쓰지 말라."
```bash
k -n shop-np get pods --show-labels
k -n shop-np get netpol
k -n shop-np describe netpol allow-web-to-api        # PodSelector: app=api / From: app=webb  <- 오타 확인
k -n shop-np patch netpol allow-web-to-api --type=json -p='[{"op":"replace","path":"/spec/ingress/0/from/0/podSelector/matchLabels/app","value":"web"}]'
```
`api -> db`는 예시 1과 같은 모양을 `podSelector: app=db`, `from: podSelector app=api`, `port: 80`로 새로 만든다. 정책은 받는 쪽(`spec.podSelector`)에 붙고 `from`이 보내는 쪽이다. `from`에 `podSelector`만 쓰면 같은 네임스페이스로 한정되어 다른 네임스페이스는 계속 막힌다 (확인함). 확인:
```bash
k -n shop-np exec deploy/web -- wget -qO- -T2 http://<api Pod IP>     # 성공
k -n shop-np exec deploy/web -- wget -qO- -T2 http://<db Pod IP>      # 타임아웃
k -n np-other exec probe -- wget -qO- -T2 http://<api Pod IP>         # 타임아웃
```
`patch --type=json`의 경로는 `k get netpol -o yaml`로 인덱스를 보고 쓴다 (이 경로 모양으로 `app: webb` -> `web`을 고치는 patch를 이 랩에서 확인함). q45 시나리오 전체는 해설 기준이며 이 랩에서는 구조별로(`podSelector` 한정, 포트 제한, 오타 patch) 나눠 확인했다.

### 예시 5. 라벨로 네임스페이스 고르기, ipBlock, 포트 범위
```bash
k get ns --show-labels                              # kubernetes.io/metadata.name=... 는 자동
k label ns team-b env=prod                          # 문제가 요구한 라벨이 없을 때만
```
```yaml
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          env: prod
    - ipBlock:
        cidr: 10.244.0.0/16
        except:
        - 10.244.1.88/32
    ports:
    - protocol: TCP
      port: 80
    - protocol: TCP
      port: 8000
      endPort: 9000
```
`k explain networkpolicy.spec.ingress.from.ipBlock`, `k explain networkpolicy.spec --recursive`로 필드 이름을 바로 확인할 수 있다 (확인함). 위 합친 YAML은 `--dry-run=server`를 통과했고, `namespaceSelector: env=prod`, `ipBlock ... except`, `endPort`는 각각 따로 적용해 동작을 확인했다 (`namespaceSelector`와 `ipBlock`은 서로 다른 `-` 항목이므로 OR이다).

## 공식 문서에서 찾는 법
허용 사이트만 쓴다. 검색 결과 순위는 직접 확인하지 못했다 (미확인). 안 맞으면 URL을 주소창에 입력한다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| 기본 뼈대(ingress+egress+ipBlock) | `network policies` | https://kubernetes.io/docs/concepts/services-networking/network-policies/ | `test-network-policy` | `The NetworkPolicy resource` 절의 YAML(약 25줄). `ipBlock`, `namespaceSelector`, `podSelector`, `ports`, `egress`가 다 들어 있다. 필요 없는 줄을 지운다 |
| default deny / allow all | 같은 페이지 | 위와 같음 | `Default deny all ingress traffic` | 각 소제목 아래 짧은 YAML(9~10줄): ingress deny, allow all ingress, egress deny, allow all egress, `Default deny all ingress and all egress traffic` |
| AND / OR 구조 | 같은 페이지 | 위와 같음 | `Behavior of to and from selectors` | `user: alice` / `role: client` 예제 두 개(하나는 `-` 하나, 다른 하나는 `-` 둘). 이 절 아래 `namespaceSelector`, `podSelector` 설명 |
| 이름으로 네임스페이스 고르기 | 같은 페이지 | 위와 같음 | `Targeting a Namespace by its name` | 설명만 있음. `kubernetes.io/metadata.name` 라벨 문장 |
| 라벨로 여러 네임스페이스 | 같은 페이지 | 위와 같음 | `Targeting multiple namespaces by label` | `kubectl label namespace frontend namespace=frontend` 2줄과 이어지는 egress YAML |
| 포트 범위 | 같은 페이지 | 위와 같음 | `Targeting a range of ports` | `multi-port-egress` YAML(15줄). `endPort: 32768` |
| 따라 하며 시험 | `declare network policy` | https://kubernetes.io/docs/tasks/administer-cluster/declare-network-policy/ | `Limit access to the nginx service` | `access-nginx` 정책 YAML(10줄). 이어서 `wget --spider --timeout=1 nginx` 시험 명령 |

## 자주 틀리는 점
- 정책을 만들었는데 아무것도 안 막힌다 -> 정책 `metadata.namespace`가 대상 Pod의 네임스페이스와 다르거나(정책은 네임스페이스 범위, 문서 `spec ... in the given namespace`), `podSelector`가 Pod 라벨과 안 맞음 -> `k get pods --show-labels`와 `k describe netpol`의 `PodSelector`를 대조.
- AND인 줄 알고 썼는데 OR이다 -> `namespaceSelector`와 `podSelector` 사이에 `-`를 넣었다 -> 같은 `-` 항목 안에서 들여쓰기를 맞춘다 (확인함: OR 모양에서는 다른 네임스페이스의 `batch`까지 통과했고 AND 모양에서는 막혔다). `describe`로 확인.
- `podSelector`만 썼는데 다른 네임스페이스에서 안 된다 -> 정상. 같은 네임스페이스로 한정된다 (확인함) -> `namespaceSelector`를 AND로 추가.
- egress 정책 후 `bad address` -> DNS(UDP/TCP 53) 미허용 -> kube-system의 `k8s-app=kube-dns`로 가는 53을 추가한다 (확인함). 전부 열지(`egress: [{}]`, `0.0.0.0/0`) 않는다.
- `egress:`만 쓰고 `policyTypes`를 생략했더니 ingress까지 막혔다 -> 기본값 `["Ingress","Egress"]` (확인함) -> `policyTypes: [Egress]`를 직접 쓴다.
- 허용했는데 막힌다 -> 포트가 안 맞음(예: 컨테이너는 8080인데 `port: 80`) 또는 `from`이 보내는 쪽이 아니라 받는 쪽을 가리킴 -> 정책은 받는 쪽 `podSelector`에 붙고 `from`은 보내는 쪽 (확인함).
- 시험 중 `download timed out`을 DNS 문제로 오해 -> 타임아웃은 패킷 드롭(정책/경로), DNS 실패는 `bad address` -> 에러 문구로 구분 (A5).
- 정책을 삭제해서 문제를 풀었다 -> 문제가 "기존 정책 삭제 금지"라고 하면 감점 -> 허용 정책을 추가하거나 기존 정책의 오타만 고친다 (q45 제약).
- 시험에서 `describe`만 보고 안 시험함 -> 허용/차단을 둘 다 `wget -T2`로 확인한다. 차단 확인은 2초 기다린다.
- 시뮬레이터 차이: (1) 이 랩은 v1.34.0, 문서는 v1.37이다. (2) kindnet이 집행하므로 차단/허용이 실제로 동작한다. 시험 CNI의 지원 범위(`endPort` 등)는 **(미확인)**. 문서는 지원하지 않는 CNI에서는 `endPort`가 단일 `port`로만 적용된다고 적는다. (3) 이 랩의 검증은 모든 Pod을 `k8s-worker` 한 노드에 두고 했다. 다른 노드 간 집행은 시험하지 않았다 **(미확인)**. `k8s-worker2`의 Pod 네트워크 문제는 C1 참고.

## 빠르게 푸는 순서
1. context와 namespace를 확인하고, 정책이 붙을 쪽(받는 Pod 또는 egress를 제한할 Pod)과 허용할 상대(라벨, 네임스페이스, 포트)를 문제에서 표로 적는다 (1분).
2. `k get netpol -n <ns>`, `k get pods --show-labels`, `k get ns --show-labels`로 기존 정책과 라벨을 읽는다. 이미 있는 deny 정책은 지우지 않는다 (1분).
3. 문서의 `test-network-policy`나 default-deny YAML을 복사해 `name`, `namespace`, `podSelector`, `from`/`to`, `ports`만 고친다. 불필요한 `ipBlock`, `Egress`는 지운다 (2분).
4. `policyTypes`를 직접 확인한다. 같은 `-` 항목 안에 `namespaceSelector`+`podSelector`가 들어 있는지(AND) 본다 (0.5분).
5. `k apply -f` 후 `k describe netpol`로 `From`/`To` 구조와 `Policy Types`를 읽는다 (0.5분).
6. 허용되어야 할 경로와 막혀야 할 경로를 `k exec ... -- wget -qO- -T2 http://...`로 각각 하나 이상 시험한다. 반영 지연 때문에 첫 시험 전에 몇 초 기다린다 (1분).
7. 후보 YAML 중 고르는 문제는 `cat` 후 `from:` 구조만 비교해 하나만 `apply`한다. 파일을 수정하지 않는다. 전체 목표 약 6분.
