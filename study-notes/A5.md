# A5. Troubleshoot services and networking

## 이 항목에서 공부할 것
- [ ] "접속이 안 된다"를 에러 문구로 분류한다: `bad address`(DNS), `Connection refused`(엔드포인트/포트), `download timed out`(NetworkPolicy/노드 간 통신)
- [ ] Service -> EndpointSlice -> Pod 라벨 -> Pod 포트 순서로 따라가며 `k get svc,endpointslice`와 `k get pods --show-labels`로 selector 불일치를 찾는다
- [ ] `targetPort`가 틀린 경우(숫자와 이름 모두)를 `k patch svc --type=json`으로 고친다
- [ ] readiness 실패로 엔드포인트에서 빠진 Pod을 `k describe pod` Events로 찾고 Deployment를 고친다
- [ ] 클러스터 안 테스트 Pod으로 `wget`/`nslookup`을 쳐서 DNS 이름, Service IP, Pod IP 세 층을 따로 확인한다 (같은 네임스페이스 `web`, 다른 네임스페이스 `web.<ns>`)
- [ ] 엔드포인트가 있는데도 타임아웃이면 `k get netpol`/`k describe netpol`로 차단 정책을 찾는다
- [ ] kube-proxy와 CoreDNS가 살아 있는지 `k -n kube-system get pods`, `logs`로 확인한다
- [ ] 엔드포인트 IP 목록을 파일에 쓴다 (`-o jsonpath='{range ...}'`)

## 개념 설명

### Service가 Pod에 닿는 길 (진단 순서의 바탕)
- 무엇인가: 클라이언트 -> (이름 조회) DNS -> Service의 ClusterIP:port -> kube-proxy가 만든 규칙 -> EndpointSlice에 적힌 Pod IP:targetPort. 건물 대표번호(Service)로 전화하면 교환원(kube-proxy)이 담당자 직통(Pod)으로 연결해 주는 모양이다.
- 왜 필요한가: 어느 고리에서 끊겼는지 알아야 고칠 곳이 정해진다. 층을 건너뛰고 한 번에 보려 하면 헤맨다.
- 핵심 동작: 각 고리를 따로 시험한다. (1) 이름: `nslookup <svc>.<ns>.svc.cluster.local`. (2) Service IP: `wget <ClusterIP>:<port>`. (3) 엔드포인트: `k get endpointslice`. (4) Pod IP 직접: `wget <PodIP>:<containerPort>`. 앞 고리가 되고 다음이 안 되면 그 사이가 원인이다.
- 관계: Service는 selector로 Pod을 고르고(라벨), EndpointSlice 컨트롤러가 selector에 맞고 Ready인 Pod만 엔드포인트로 넣는다. NetworkPolicy(C2)는 이 모든 것 위에서 Pod 단에서 트래픽을 막는다.

### 에러 문구로 층 구분하기 (이 랩에서 전부 확인함, busybox `wget`)
- `wget: bad address 'web-ok'`: 이름 조회 실패. 다른 네임스페이스 Service를 짧은 이름으로 불렀거나(예: `web-ok`는 `notes-a5`에만 있음), DNS 서버에 못 닿았거나, 이름 오타다.
- `wget: can't connect to remote host (10.96.x.x): Connection refused`: 이름은 풀렸고 Service IP에는 닿았지만 받아 줄 곳이 없다. 엔드포인트가 비었거나(selector 오타, 전 Pod이 NotReady), `targetPort`에 아무도 listen하지 않는다. 둘 다 같은 문구라 `k get endpointslice`로 구분한다.
- `wget: download timed out`: 연결 시도에 응답이 없다. NetworkPolicy가 패킷을 버렸거나(엔드포인트는 멀쩡해도), 노드 간 Pod 네트워크가 끊겼다. 거부(refused)는 즉시 오고 타임아웃은 `-T` 시간을 다 기다린다.
- 응답이 오는데 내용이 이상하면 Service는 정상이고 앱 문제다 (`k logs`, A4).

### Endpoints / EndpointSlice 읽기
- `k get endpointslice -l kubernetes.io/service-name=<svc>`: ENDPOINTS 열이 Pod IP 목록이다. selector가 아무 Pod에도 안 맞으면 `<unset>`이고, named targetPort가 Pod의 포트 이름과 안 맞으면 PORTS가 `<unset>`이다 (둘 다 확인함).
- 함정: EndpointSlice의 ENDPOINTS 열은 Ready가 아닌 Pod의 IP도 보여 준다. readiness가 실패하는 Pod 2개를 가진 Service도 IP 목록이 나왔고, 각 항목의 `conditions.ready`가 `false`였다 (확인함). Ready 여부는 `-o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]} ready={.conditions.ready}{"\n"}{end}'`로 본다.
- `k get endpoints`는 아직 되지만 `Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice`를 찍는다 (확인함). 이 경우 Ready인 주소만 보여 주므로 not-ready Pod 때문에 비어 보이는 Service에서는 `<none>`이다. `k describe svc`의 `Endpoints:` 줄도 비어 있다 (확인함).
- `k get svc -o wide`의 SELECTOR 열로 Service가 고르는 라벨을 바로 본다.

### DNS 이름 규칙과 테스트 도구
- 같은 네임스페이스: `web`. 다른 네임스페이스: `web.<ns>` 또는 `web.<ns>.svc.cluster.local`. Pod의 `/etc/resolv.conf`는 `search <ns>.svc.cluster.local svc.cluster.local cluster.local`, `nameserver <kube-dns ClusterIP>`, `options ndots:5` (확인함).
- 테스트 이미지 주의: `busybox:1.37`의 `nslookup web-ok`는 짧은 이름에서 `NXDOMAIN`을 낸다 (`web-ok.cluster.local`만 찾아 감, 확인함). 같은 이름이 `wget`으로는 된다. 짧은 이름을 `nslookup`으로 시험하려면 `busybox:1.28`이나 문서가 쓰는 `registry.k8s.io/busybox:1.27.2`를 쓰거나, `nslookup web-ok.<ns>.svc.cluster.local`처럼 FQDN으로 친다 (셋 다 확인함). `dnsutils`(agnhost) 이미지는 문서에 있지만 이 랩에서 시험하지 않았다 **(미확인)**.
- 이미지를 시험장에서 새로 받을 수 있는지는 확인할 수 없다 **(미확인)**. 이미 떠 있는 Pod(`tester` 등)이 있으면 `k exec`를 쓴다.

### 노드 쪽 구성요소: kube-proxy와 CoreDNS
- kube-proxy: 각 노드에서 Service 규칙을 만든다. `k -n kube-system get pods -l k8s-app=kube-proxy`가 모두 Running이어야 한다. 이 랩의 모드는 `iptables`이고 `clusterCIDR: 10.244.0.0/16` (ConfigMap `kube-proxy`의 `config.conf`, 확인함). 노드에서 `iptables-save | grep <ns>/<svc>`로 `KUBE-SVC-...`와 `DNAT --to-destination <PodIP>:<port>` 규칙을 볼 수 있다 (확인함).
- CoreDNS: `k -n kube-system get pods -l k8s-app=kube-dns`, Service `kube-dns`(ClusterIP, 이 랩 `10.96.0.10`), `k -n kube-system get endpointslice -l kubernetes.io/service-name=kube-dns`로 3점 확인 (확인함). CoreDNS 설정 자체(Corefile)는 C6 항목이다.

## 예시

### 예시 1. 엔드포인트가 비었을 때: selector 오타 (q44, q28 형태)
상황: "Service `shop-api`가 응답하지 않는다. Deployment는 건드리지 말고 Service만 고쳐라."
```bash
k -n svc-lab get svc,endpointslice
k -n svc-lab get svc shop-api -o wide                # SELECTOR 열
k -n svc-lab get pods --show-labels                  # Pod 쪽 라벨과 비교
k -n svc-lab set selector svc/shop-api app=shop-api  # 오타 수정 (또는 k edit svc shop-api)
k -n svc-lab get endpointslice -l kubernetes.io/service-name=shop-api
```
기대: 수정 전 EndpointSlice의 ENDPOINTS가 `<unset>`, `wget`은 `Connection refused`. 수정 후 Pod IP 두 개가 나오고 `wget`이 nginx 페이지를 돌려준다 (이 랩의 `web-sel` Service로 확인함: selector `app=wep` -> `app=web`).

### 예시 2. 엔드포인트는 있는데 refused: targetPort가 틀림
상황: "`web-port`의 엔드포인트는 보이는데 `Connection refused`."
```bash
k -n svc-lab get endpointslice -l kubernetes.io/service-name=web-port    # PORTS 8080 <- 컨테이너는 80
k -n svc-lab get deploy web -o jsonpath='{.spec.template.spec.containers[0].ports}{"\n"}'
k -n svc-lab patch svc web-port --type=json -p='[{"op":"replace","path":"/spec/ports/0/targetPort","value":80}]'
```
기대: PORTS 열이 `80`으로 바뀌고 요청이 성공한다. 패치 직후 한두 초는 아직 refused일 수 있어 다시 쳐 본다 (확인함: 첫 시도는 refused, 몇 초 뒤 성공). `targetPort`를 이름으로 쓰는 Service는 Pod의 `ports[].name`과 글자까지 같아야 한다: Pod 포트 이름이 `http`인데 Service가 `web-http`면 ENDPOINTS는 IP가 있어도 PORTS가 `<unset>`이고 refused다. 값을 `"http"`(문자열)로 patch하면 고쳐진다 (확인함).

### 예시 3. Pod이 NotReady라서 엔드포인트에서 빠짐 (q48 형태)
상황: "NodePort `30048`이 열리지 않는다. 엔드포인트는 두 개여야 한다."
```bash
k -n svc-ready get pods                      # READY 0/1
k -n svc-ready describe pod -l app=portal | grep -i -m2 "readiness probe failed"
# 기대: Readiness probe failed: HTTP probe failed with statuscode: 404
k -n svc-ready patch deploy portal --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/"}]'
k -n svc-ready rollout status deploy/portal
k -n svc-ready get endpointslice -l kubernetes.io/service-name=portal -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]} ready={.conditions.ready}{"\n"}{end}'
```
기대: 두 줄 모두 `ready=true`. 롤아웃 직후 옛 Pod이 `ready=false`로 한 줄 더 보일 수 있다 (확인함). 엔드포인트가 안 생기면 Service의 `targetPort` 이름과 컨테이너 `ports[].name`도 대조한다 (q48의 두 번째 원인).

### 예시 4. 층별 테스트 (DNS -> Service IP -> Pod IP)
상황: "원인 층이 어디인지 모른다."
```bash
k -n svc-lab run tmp --rm -it --restart=Never --image=busybox:1.28 -- nslookup web-ok       # 1) 이름
k -n svc-lab exec tester -- wget -qO- -T3 http://web-ok                                       # 2) 이름으로 접속
k -n svc-lab exec tester -- wget -qO- -T3 http://$(k -n svc-lab get svc web-ok -o jsonpath='{.spec.clusterIP}')   # 2') Service IP
k -n svc-lab exec tester -- wget -qO- -T3 http://$(k -n svc-lab get pod -l app=web -o jsonpath='{.items[0].status.podIP}')   # 3) Pod IP
k -n svc-lab exec tester -- wget -qO- -T3 http://web-ok.other-ns                              # 4) 다른 네임스페이스는 접미사
```
기대: `nslookup`이 `web-ok.<ns>.svc.cluster.local`과 ClusterIP를 돌려준다. `wget`은 `<!DOCTYPE html>`. 1)이 실패하고 3)이 되면 DNS가 원인, 2')이 되고 2)만 안 되면 이름/네임스페이스, 3)만 되면 Service(엔드포인트/포트), 3)도 타임아웃이면 NetworkPolicy나 Pod 네트워크다. `ClusterIP`로 `ping`은 안 된다 (100% loss, 확인함. ClusterIP는 TCP/UDP 규칙만 있다). 접속 시험은 `wget`/`nc`로 한다.
테스트 Pod이 없고 만들기 싫으면 `k port-forward svc/web-ok 18093:80`을 `&`로 띄우고 `curl http://127.0.0.1:18093/`로 Service 하나가 200을 주는지 볼 수 있다 (확인함). 이 방법은 DNS와 NetworkPolicy 경로는 시험하지 않는다.
`-it`는 이 도구 환경에 터미널이 없어 `-i`만으로 같은 명령을 확인했다.

### 예시 5. 엔드포인트가 정상인데 타임아웃: NetworkPolicy
상황: "엔드포인트도 있고 Pod도 Ready인데 `download timed out`."
```bash
k -n svc-lab get netpol
k -n svc-lab describe netpol deny-web
```
기대 (확인함): 정책 하나가 `PodSelector: app=web`, `Allowing ingress traffic: <none> (Selected pods are isolated for ingress connectivity)`로 나온다. 이 상태에서 `wget`은 3초 뒤 `download timed out`이었고, `get endpointslice`는 정상이었다. 이 정책을 지우면 곧바로 응답이 돌아왔다. 고치는 방법은 지우기가 아니라 허용 규칙 추가인 경우가 많다 (C2, q45).

### 예시 6. 엔드포인트 IP를 파일에 쓰기 (q28 형태)
```bash
k -n svc-debug get endpointslice -l kubernetes.io/service-name=api -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{"\n"}{end}' > /home/candidate/api-endpoints.txt
cat /home/candidate/api-endpoints.txt
```
기대: Pod IP가 한 줄에 하나씩 (이 랩의 `web-ok` Service로 `10.244.1.57`, `10.244.1.60` 두 줄 확인함). 같은 값을 `k get pods -l app=api -o jsonpath='{range .items[*]}{.status.podIP}{"\n"}{end}'`로도 얻는다 (확인함). 이 파이프는 Ready가 아닌 Pod 주소도 포함하므로 문제가 "백킹 Pod"만 요구하면 Pod 목록이 맞는지 `ready=true`를 확인한다.

## 공식 문서에서 찾는 법
허용 사이트만 쓴다. 검색 결과 순위는 직접 확인하지 못했다 (미확인). 안 맞으면 URL을 주소창에 입력한다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| 진단 순서 전체 | `debug services` | https://kubernetes.io/docs/tasks/debug/debug-application/debug-service/ | `Does the Service exist?` | 페이지가 이 순서의 절로 되어 있다: DNS 이름 / IP / 정의 / EndpointSlice / Pod / kube-proxy. 각 절의 명령 블록을 순서대로 복사 |
| 엔드포인트 확인 명령 | 같은 페이지 | 위와 같음 | `Does the Service have any EndpointSlices?` | `kubectl get endpointslices -l kubernetes.io/service-name=hostnames` 한 줄과 selector 설명 |
| Service 정의 점검 항목 | 같은 페이지 | 위와 같음 | `Is the Service defined correctly?` | 점검 질문 목록(port, targetPort 숫자/문자열, 이름 포트, protocol). YAML은 `kubectl get service hostnames -o json` 출력 |
| 테스트 Pod 실행 | 같은 페이지 | 위와 같음 | `Running commands in a Pod` | `kubectl run -it --rm --restart=Never busybox --image=registry.k8s.io/busybox:1.27.2 sh` 한 줄 |
| NetworkPolicy가 막는지 | 같은 페이지 | 위와 같음 | `Any Network Policy Ingress rules` | 짧은 안내 문단뿐(YAML 없음). 자세한 정책은 C2 노트 |
| kube-proxy 점검 | 같은 페이지 | 위와 같음 | `Is the kube-proxy working?` | `iptables-save \| grep hostnames` 한 줄과 기대 출력(KUBE-SVC, KUBE-SEP 체인) |
| DNS 점검 | `debugging dns resolution` | https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/ | `Create a simple Pod to use as a test environment` | `dnsutils` Pod YAML(9줄). 이어서 `Check the local DNS configuration first`의 `cat /etc/resolv.conf` 명령, `Check if the DNS pod is running`의 `-l k8s-app=kube-dns` |
| 네임스페이스 오류 | 같은 페이지 | 위와 같음 | `Are you in the right namespace for the service?` | 설명만 있음 (짧은 이름은 같은 네임스페이스에서만 풀린다는 문장) |

## 자주 틀리는 점
- `wget: bad address` -> 이름 문제. 다른 네임스페이스의 Service를 짧은 이름으로 불렀다 (확인함) -> `<svc>.<ns>`. 또는 DNS 서버에 못 닿는다 (`k -n kube-system get pods -l k8s-app=kube-dns`, 테스트 Pod의 `cat /etc/resolv.conf`).
- 엔드포인트가 비었다 -> selector와 Pod 라벨 불일치(오타, `app` 대신 `run`), Pod이 다른 네임스페이스에 있음, 또는 Pod이 NotReady -> `k get pods --show-labels`, `k get svc -o wide`로 대조. 문제가 "Service만 고쳐라"면 Pod 라벨을 바꾸지 않는다.
- 엔드포인트가 있는데 refused -> `targetPort`가 틀리다. 숫자인지 이름인지 확인한다 (예시 2).
- `nslookup 짧은이름`이 `NXDOMAIN`인데 `wget 짧은이름`은 된다 -> `busybox:1.37`의 `nslookup` 특성 (확인함) -> FQDN으로 치거나 `busybox:1.28`을 쓴다. DNS가 고장났다고 오판하지 않는다.
- EndpointSlice에 IP가 보여서 안심했는데 응답 없음 -> not-ready Pod의 IP도 나열되기 때문 (확인함) -> `conditions.ready`나 `k get pods`의 READY 열을 본다.
- `k get endpoints` 사용 시 Warning 문구 -> v1.33+에서 deprecated (확인함) -> `endpointslice`를 쓴다. 출력은 같은 정보를 준다.
- 패치 직후 바로 시험해서 아직 refused -> 반영에 1~3초 걸린다 (확인함) -> 다시 시험한다.
- `ping <ClusterIP>`가 안 된다고 Service가 죽은 줄 안다 -> ClusterIP는 ICMP에 응답하지 않는다 (확인함) -> TCP 시험을 쓴다.
- 올바른 네임스페이스인지 확인하지 않고 `-n`을 빼먹는다 -> 모든 `k` 명령에 `-n <ns>`, 헷갈리면 `-A`.
- 시뮬레이터 차이: (1) 이 랩은 v1.34.0이고 문서는 v1.37이다. (2) CNI는 kindnet이고 NetworkPolicy를 강제한다 (`simulator/docs/KNOWN_LIMITS.md`). (3) 한때 `k8s-worker2`의 CNI 설정 대역이 노드 podCIDR와 어긋나 그 노드 Pod의 DNS/노드 간 통신이 실패한 적이 있다(랩 고장, 시험과 무관, 수정됨). 같은 증상이 다시 나오면 `kubectl --context k8s -n kube-system delete pod -l app=kindnet --field-selector spec.nodeName=k8s-worker2`로 kindnet을 재생성하거나 `bin/sim doctor`로 점검한다. (4) LoadBalancer와 Ingress 컨트롤러는 이 랩에 없다 (C3, C5).

## 빠르게 푸는 순서
1. context와 namespace를 확인하고 증상을 한 줄로 쓴다 (refused / timeout / bad address) (0.5분).
2. `k -n <ns> get svc -o wide,endpointslice`와 `k get pods --show-labels`를 연달아 쳐서 selector와 라벨, ENDPOINTS를 본다 (1분).
3. ENDPOINTS가 비면 selector 오타, `READY 0/1`이면 `k describe pod`의 Events(readiness)로 간다 (1분).
4. ENDPOINTS가 있으면 `targetPort`(숫자/이름)를 `k get svc -o yaml`과 컨테이너 `ports`로 대조한다 (1분).
5. 고친다: `k set selector`, `k patch svc --type=json`, `k edit`, Deployment 쪽이면 `k patch deploy`. Service만 고치라는 조건이 있으면 Deployment는 안 건드린다 (1분).
6. 테스트 Pod에서 `wget -T3`로 이름 -> Service -> Pod IP 순으로 확인한다. 타임아웃이면 `k get netpol` (1분).
7. 요구한 출력(엔드포인트 IP 파일 등)을 `jsonpath`로 쓰고 `cat`으로 확인한다 (0.5분). 전체 목표 약 6분.

## 연습 문제
**오늘 풀 문제** (study-guide 5절 Day 3: A5)
- `q28` — Service has no endpoints (selector + targetPort, EndpointSlice IPs to file): Service만 고치고 엔드포인트 IP를 파일에 쓴다
- `q44` — Service selector typo and wrong targetPort: 두 Service의 서로 다른 원인을 고친다
- `q45` — Ingress NetworkPolicy chain web-api-db: web->api, api->db만 열어 주는 정책 (C2와 겹침, 아래 C2 노트 참고)
- `q48` — NodePort without endpoints (readiness probe 404, named port): 원인 두 개를 모두 고쳐 NodePort 30048이 200

**재순회에 다시 나오는 문제**: `q44` (Day 11 세트), `q28`, `q48` (Day 12 세트), `q45` (Day 13 세트)

**추가 연습** (COVERAGE.md의 `NetworkPolicy blocking diagnosis` 행)
- `q47` — Egress policy blocks DNS: 이름은 안 풀리는데 IP는 되는 증상, kube-dns(53)만 허용 (C2와 겹침). q46(CoreDNS Corefile)과 같은 세트에 넣지 않는다
