# A4. Manage and evaluate container output streams

## 이 항목에서 공부할 것
- [ ] `k logs <pod> -c <container>`로 멀티 컨테이너 Pod의 컨테이너 하나만 골라 파일로 저장한다 (`> file`)
- [ ] 재시작한 컨테이너의 직전 인스턴스 로그를 `--previous`(`-p`)로 본다
- [ ] `--tail`, `--since`, `--timestamps`, `-f`, `-l <label>` (`--prefix`, `--all-containers`)로 로그 범위를 맞춘다
- [ ] `k logs deploy/<name>`, `job/<name>`처럼 상위 리소스 이름으로 로그를 보고, 여러 Pod 중 어느 것이 골라졌는지 확인한다
- [ ] `k describe pod`의 State / Last State / Reason / Exit Code / Events로 종료 원인(Error, OOMKilled 137, ImagePullBackOff)을 읽는다
- [ ] `k get events --sort-by=.lastTimestamp`와 `--field-selector type=Warning`(또는 `k events --types=Warning`)으로 이벤트를 시간순으로 뽑는다
- [ ] `k exec -c`, `k port-forward pod/<name>`, `k debug --target --profile=general`로 컨테이너 안이나 셸 없는 Pod을 들여다본다
- [ ] kubectl이 안 될 때 노드에서 `crictl logs`와 `/var/log/pods/...`로 로그를 읽는다

## 개념 설명

### 컨테이너 출력 스트림과 kubectl logs
- 무엇인가: 컨테이너 프로세스가 표준 출력(stdout)과 표준 에러(stderr)에 쓴 글자는 컨테이너 런타임이 노드의 파일로 받아 적고, kubelet이 그 파일을 API로 내준다. `kubectl logs`는 그 파일을 읽어 온다. 택배 상자(컨테이너)에서 나온 메모를 노드 창고(파일)에 쌓아 두고, 요청이 오면 창고지기(kubelet)가 꺼내 주는 모양이다.
- 왜 중요한가: "왜 죽었나", "무슨 요청이 들어왔나"의 1차 증거가 로그다. 파일에 쓰는 로그(`/var/log/app.log`)는 `kubectl logs`에 안 나오고 `k exec`로 읽어야 한다 (q109).
- 핵심 동작: stdout과 stderr는 기본적으로 한 줄기로 섞여 나온다. `kubectl logs ... 2>/dev/null`로 stderr만 걸러 낼 수 없다 (확인함: stderr로 쓴 `shipper ERROR` 줄이 그대로 나옴). 문서에는 `PodLogsQuerySplitStreams` 기능 게이트를 켜야 `kubectl get --raw ".../log?stream=Stderr"`로 나눠 볼 수 있다고 되어 있고 Alpha, 기본 꺼짐이다 (문서 `Container log streams`; 이 랩에서는 시험 안 함 **(미확인)**).
- 노드 쪽 모양: `/var/log/pods/<ns>_<pod>_<uid>/<container>/0.log` 파일이고 `/var/log/containers/`에 심볼릭 링크가 있다. 줄 형식은 `시각 stdout F 내용` (확인함). 회전은 kubelet 설정 `containerLogMaxSize`(기본 10Mi), `containerLogMaxFiles`(기본 5)이고, 컨테이너가 재시작되면 kubelet은 종료된 컨테이너 하나의 로그만 남긴다 (문서 `Log rotation`, `How nodes handle container logs`). 그래서 `--previous`는 "바로 직전 하나"만 준다. Pod이 지워지면 로그도 같이 사라진다.

### kubectl logs 옵션
- `-c <name>`: 컨테이너 지정. Pod에 컨테이너가 둘 이상이고 `-c`를 빼면 첫 컨테이너가 골라지고 stderr에 `Defaulted container "collector" out of: collector, shipper`가 나온다 (확인함). `> file`로 저장하면 이 안내 줄은 파일에 안 들어가지만, 틀린 컨테이너의 로그가 저장되므로 `-c`를 항상 쓴다.
- `-p` / `--previous`: 직전에 죽은 인스턴스. 한 번도 재시작 안 한 컨테이너에 쓰면 `previous terminated container "shipper" in pod "multi" not found` (확인함).
- `--tail=N`, `--since=10s`, `--since-time`, `--timestamps`, `--limit-bytes`, `-f`(계속 따라가기, 끝내려면 Ctrl+C).
- `-l app=x`: 라벨로 여러 Pod. 컨테이너가 둘 이상이면 `--all-containers`, 출처 표시는 `--prefix`(`[pod/이름/컨테이너] 줄`, 확인함). 기본 동시 요청 한도 `--max-log-requests=5`.
- `deploy/<name>`, `job/<name>`: 소유 Pod 하나를 골라 준다. Pod이 여럿이면 `Found 2 pods, using pod/web-66d47686b4-jwkl9`가 먼저 찍히고 그 Pod 하나만 보여 준다 (확인함). 전부 보려면 `--all-pods`(확인함) 또는 `-l`.
- 아직 시작 못 한 컨테이너: ImagePull 문제면 `container "web" in pod "badimage" is waiting to start: image can't be pulled`, init이 안 끝났으면 `PodInitializing` 오류로 로그가 없다 (둘 다 확인함). init 컨테이너 로그는 `-c <init 이름>`으로 본다 (확인함).

### 컨테이너 종료 상태 읽기 (describe, exit code, termination message)
- `k describe pod`의 컨테이너 칸: `State`(지금), `Last State`(직전 종료), `Reason`, `Exit Code`, `Restart Count`. 맨 아래 `Events`는 스케줄/이미지/프로브/BackOff 기록이다.
- Exit Code: 앱이 `exit 3`으로 끝나면 `Reason: Error`, `Exit Code: 3`. 메모리 한도를 넘어 죽으면 `Reason: OOMKilled`, `Exit Code: 137` (둘 다 확인함, 137 = 128 + 9(SIGKILL)).
- 시작 자체를 못 하면 `State: Waiting`에 `ImagePullBackOff`/`ErrImagePull`(없는 태그: `... docker.io/library/nginx:1.99-nonexistent: not found`), `CrashLoopBackOff`(죽고 재시작을 반복하며 간격이 늘어남), `RunContainerError`가 나온다. `RunContainerError`는 메모리 한도를 20~40Mi로 너무 낮게 줬을 때 `container init was OOM-killed (memory limit too low?)` 메시지로 본 적이 있다 (확인함).
- 종료 메시지: 컨테이너가 `/dev/termination-log`에 쓴 글이 `state.terminated.message`로 올라온다. `terminationMessagePolicy: FallbackToLogsOnError`를 주면 그 파일이 비어 있을 때 로그 마지막 부분(최대 2048바이트/80줄, 문서 기준)을 대신 쓴다 (둘 다 확인함).

### 이벤트(events)
- 무엇인가: 스케줄러, kubelet, 컨트롤러가 남기는 "일어난 일" 기록. 네임스페이스에 속한다 (`-n` 필요).
- 핵심 동작: `k get events`는 기본 정렬이 없다. `--sort-by=.lastTimestamp`는 오래된 것이 위, 최신이 맨 아래다 (확인함). `k events`는 시간순으로 정렬되고 `(x5 over 4m18s)`처럼 반복 횟수를 묶어 보여 준다 (확인함). Warning만: `--field-selector type=Warning` 또는 `k events --types=Warning`. 한 객체만: `--field-selector involvedObject.name=<pod>` 또는 `k events --for pod/<pod>` (둘 다 확인함).
- 관계: describe의 Events 칸은 같은 정보를 그 객체만 모아 보여 준다. Pending 원인(`FailedScheduling`)은 D5/E 쪽 문제와 겹친다.

### exec, port-forward, debug (출력이 안 나오는 컨테이너 들여다보기)
- `k exec <pod> -c <ctr> -- <명령>`: 컨테이너 안에서 실행. 파이프(`|`)는 내 터미널에서 실행되므로 컨테이너 안 파이프는 `-- sh -c '...'`. 셸이 없는 이미지(pause 등)는 `exec: "sh": executable file not found in $PATH` (확인함).
- `k port-forward pod/<name> 18080:80`: 로컬 포트:Pod 포트. `svc/<name>`은 Service 뒤 Pod 하나를 고르므로 특정 Pod을 보려면 `pod/<name>`을 쓴다 (둘 다 확인함). 포그라운드로 계속 돌므로 `&`로 보내고 끝나면 `kill %1`.
- `k debug <pod> -it --image=busybox:1.37 --target=<ctr> --profile=general -- sh`: 실행 중인 Pod에 임시(ephemeral) 컨테이너를 붙인다. `--target`이 있어야 대상 컨테이너의 프로세스 목록(`/proc/1/...`)이 보인다. `--profile`을 안 주면 `--profile=legacy is deprecated` 경고가 나오고 다른 UID 프로세스의 `/proc/1/environ`이 `Permission denied`다 (확인함). `general`이면 읽혔다 (확인함).
- `k debug node/<node> --image=busybox:1.37 --profile=sysadmin -it -- sh`: 현재 네임스페이스에 `node-debugger-<node>-xxxxx` Pod이 생기고 노드 파일시스템이 `/host`에 붙는다. `/host/var/log/pods`가 보였다 (확인함). 끝나면 그 Pod을 지운다.

## 예시

### 예시 1. 로그/이벤트/사용량을 파일에 모으기 (q49 형태)
상황: "ns `logs-lab`의 Pod `multi`(컨테이너 `collector`, `shipper`)와 계속 재시작하는 `crasher`에서 정보를 파일로."
```bash
mkdir -p /home/candidate/q49
k -n logs-lab logs multi -c shipper > /home/candidate/q49/shipper.log
k -n logs-lab logs crasher --previous > /home/candidate/q49/crasher-previous.log
k -n logs-lab get events --field-selector type=Warning --sort-by=.lastTimestamp > /home/candidate/q49/warnings.txt
k -n logs-lab top pod multi --containers > /home/candidate/q49/top.txt
head -3 /home/candidate/q49/*
```
기대: `shipper.log`에 `shipper out N`과 `shipper ERROR N`이 섞여 있고, `crasher-previous.log`에 `starting up`과 `fatal: license key missing`, `warnings.txt`에 `Back-off restarting failed container`(`BackOff`) 줄이 있다 (이 랩의 같은 모양 Pod으로 확인함). `top.txt`는 컨테이너마다 한 줄 (A3, metrics-server 필요).
`--previous`가 재시작 직후 `unable to retrieve container logs`로 실패하면 몇 초 뒤 다시 치라는 것은 q49 해설의 주의사항이며 이 랩에서 재현하지는 못했다 **(미확인)**. 어느 쪽이든 저장 후 파일이 비어 있지 않은지 `cat`으로 본다.

### 예시 2. CrashLoopBackOff / ImagePullBackOff 진단
상황: "배포 후 Pod이 안 뜬다. 원인을 찾아라."
```bash
k -n logs-lab get pods
# crasher    0/1  CrashLoopBackOff   4 (32s ago)
# badimage   0/1  ImagePullBackOff   0
k -n logs-lab describe pod crasher | sed -n '/Last State/,/Ready:/p'
# Last State: Terminated   Reason: Error   Exit Code: 3
k -n logs-lab logs crasher --previous        # fatal: license key missing  <- 앱이 직접 말해 준다
k -n logs-lab describe pod badimage | tail -8
# Failed to pull image "nginx:1.99-nonexistent": ... not found
k -n logs-lab set image pod/badimage web=nginx:1.27 2>&1 | head -1    # Pod 이미지는 바꿀 수 있다 (Deployment면 set image deploy/x web=nginx:1.27)
```
첫 명령 선택표: ImagePull은 `describe`(Events), CrashLoop은 `logs --previous`, 재시작이 반복되는데 로그가 깨끗하면 `describe`의 `Liveness probe failed`, OOM이면 `Last State`의 `OOMKilled`/137.

### 예시 3. OOMKilled와 종료 메시지 읽기
상황: "컨테이너가 계속 죽는다. 이유를 한 줄로 말하라."
```bash
k -n logs-lab get pod oomer -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{" "}{.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}'
# 기대: OOMKilled 137
k -n logs-lab get pod termmsg -o go-template='{{range .status.containerStatuses}}{{.name}}: {{.state.terminated.message}}{{end}}'
# 기대: app: disk full      (컨테이너가 /dev/termination-log 에 쓴 글)
```
OOMKilled는 로그에 아무 흔적이 없는 경우가 많아서 `describe`/`jsonpath`로 확인해야 한다. 고치려면 `k set resources deploy/<x> --limits=memory=...` (A3 참고).

### 예시 4. 이벤트 뽑기
상황: "ns의 Warning 이벤트를 시간순으로 파일에 저장하라."
```bash
k -n logs-lab get events --sort-by=.lastTimestamp | tail -5            # 최신이 맨 아래
k -n logs-lab get events --field-selector type=Warning --sort-by=.lastTimestamp
k -n logs-lab events --types=Warning                                    # 같은 내용, 정렬 기본, 반복 횟수 표시
k -n logs-lab events --for pod/crasher
```
기대: `Warning  Failed  pod/badimage  Error: ImagePullBackOff`, `Warning  BackOff  pod/crasher  Back-off restarting failed container app in pod crasher_...` 같은 줄 (확인함).

### 예시 5. exec, port-forward, debug (q109, q110 형태)
```bash
k -n exec-lab exec orders -c app -- printenv APP_REGION > /home/candidate/q109/region.txt
k -n exec-lab exec orders -c audit -- grep -c DENIED /var/log/audit/audit.log > /home/candidate/q109/denied-count.txt
k -n exec-lab exec orders -c audit -- wget -qO- http://127.0.0.1/ | head -5          # 같은 Pod은 localhost 공유
k -n pf-lab port-forward pod/report-v2 18080:80 &
sleep 2; curl -s http://127.0.0.1:18080/version > /home/candidate/q110/v2-version.txt; kill %1
k -n pf-lab debug sealed --image=busybox:1.37 --target=app --profile=general -q -i -- sh -c "tr '\0' '\n' </proc/1/environ | sed -n 's/^LICENSE_TIER=//p'"
```
기대: 마지막 명령이 환경변수 값(이 랩의 `sealed` Pod은 `gold`)을 출력한다. 같은 모양의 Pod으로 `exec ... sh`가 OCI 오류를 내는 것, `--profile` 없이는 Permission denied인 것, `-q -i` 비대화형이 값을 돌려주는 것을 모두 확인함. 대화형 `-it`는 이 도구 환경에 터미널이 없어 시험하지 못했다 **(미확인)**.

### 예시 6. API가 죽었을 때 노드에서 로그 읽기
상황: "kubectl이 응답하지 않는다. control-plane 컨테이너 로그를 봐야 한다."
```bash
ssh <node>
sudo -i
crictl ps -a --name kube-apiserver        # Exited 컨테이너도 보인다 (ATTEMPT 열이 재시작 횟수)
crictl logs --tail 20 <CONTAINER ID>
ls /var/log/pods/ | grep apiserver         # <ns>_<pod>_<uid> 디렉터리
tail -n 20 /var/log/pods/kube-system_kube-apiserver-*/kube-apiserver/*.log
```
이 랩에서는 호스트의 `docker exec`로 같은 읽기 명령(`crictl ps -a`, `crictl logs`, `/var/log/pods` 아래 `0.log`)이 Exited 컨테이너 포함 동작하는 것을 확인했다. kubelet 자체 로그는 `journalctl -u kubelet -e --no-pager` (A1).

## 자주 틀리는 점
- 멀티 컨테이너 Pod에서 `-c`를 빼고 저장했다 -> 첫 컨테이너 로그가 파일에 들어갔다 (stderr의 `Defaulted container` 안내만 신호) -> 항상 `-c`를 쓰고 `head`로 내용을 확인한다.
- `--previous` 대신 현재 로그를 봤다 -> 현재 컨테이너가 막 다시 시작된 상태라 직전 실행의 전체 기록을 못 본다 -> `--previous`. (이 랩의 `crasher`는 현재/이전 로그가 같은 두 줄이었다. 둘이 다른 앱에서는 `--previous`만 죽기 직전의 마지막 출력을 가진다.)
- `previous terminated container "x" ... not found` -> 재시작한 적이 없는 컨테이너 -> `--previous`를 빼거나, 컨테이너 이름이 맞는지 `describe`로 본다.
- ImagePullBackOff Pod에 `logs`를 쳤더니 `waiting to start: image can't be pulled` -> 컨테이너가 시작을 못 했으므로 로그가 없다 -> `describe`의 Events (`not found`면 태그/이름 오타).
- `stderr`만 따로 뽑으려 `2>/dev/null` -> 소용없다. `kubectl logs`는 두 스트림을 합쳐 준다 -> `grep ERROR`처럼 내용으로 거른다.
- 로그에 아무것도 없는데 컨테이너가 죽는다 -> OOMKilled는 앱 로그에 안 남는다 -> `describe`의 `Last State` / `Exit Code: 137`.
- `k get events`가 뒤죽박죽 -> 기본 정렬 없음 -> `--sort-by=.lastTimestamp` (최신이 맨 아래). 요구가 "오래된 순"이면 그대로, "최신 순"이면 `tac`이나 `tail`을 고려한다.
- `k logs deploy/web`이 Pod 하나만 보여 준다 -> 그렇게 동작한다 (`Found 2 pods, using pod/...`) -> 전부는 `--all-pods` 또는 `-l app=web --prefix`.
- `k logs -f`를 쳐 놓고 터미널이 멈춘 줄 안다 -> 계속 따라가는 명령이다 (확인함, 끝나지 않음) -> Ctrl+C. 시험에서는 `-f` 대신 `--tail`을 쓴다.
- 노드의 `kubectl debug node/...`가 Pod을 남겼다 -> 현재 네임스페이스에 `node-debugger-...` Pod이 생긴다 -> `k delete pod`로 정리한다. (이 랩에서 Completed 상태로 남은 것을 확인함)
- 시뮬레이터 차이: (1) 이 랩은 v1.34.0, 문서는 v1.37이다. (2) 노드 접근은 시험이 `ssh <node>`, 이 랩의 호스트 검증은 `docker exec`였다. 명령 자체(`crictl`, `/var/log/pods`)는 같다. (3) 한때 `k8s-worker2`의 CNI 설정 대역이 노드 podCIDR와 어긋나 그 노드 Pod의 DNS/노드 간 통신이 실패한 적이 있다(랩 고장, 시험과 무관, 수정됨). 같은 증상이 다시 나오면 `kubectl --context k8s -n kube-system delete pod -l app=kindnet --field-selector spec.nodeName=k8s-worker2`로 kindnet을 재생성하거나 `bin/sim doctor`로 점검한다.

## 빠르게 푸는 순서
1. 첫 줄의 context, namespace, 저장할 파일 경로를 확인하고 `mkdir -p`로 디렉터리를 만든다 (0.5분).
2. `k get pods -o wide`로 상태(Running/CrashLoopBackOff/ImagePullBackOff/Pending)와 컨테이너 개수(`2/2`)를 본다 (0.5분).
3. 상태별 첫 명령: 시작 못 함 -> `k describe pod`(Events), 죽고 재시작 -> `k logs --previous -c <ctr>` + `Last State`, Running인데 이상함 -> `k logs --tail=50 -c <ctr>` (1분).
4. 파일 저장은 `> 경로` 한 줄씩, 끝나면 `head`/`cat`으로 내용이 맞는지 확인한다 (1분).
5. 이벤트가 필요하면 `get events --field-selector type=Warning --sort-by=.lastTimestamp`를 그대로 친다 (0.5분).
6. 컨테이너 안 확인은 `k exec -c`, 셸이 없으면 `k debug --target --profile=general`, 특정 Pod 접속은 `port-forward pod/` (1.5분).
7. kubectl이 죽었으면 `ssh <node>` -> `sudo -i` -> `crictl ps -a` -> `crictl logs` (1분). 끝나면 `exit`로 base로 돌아온다. 전체 목표 약 6분.
