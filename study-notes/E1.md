# E1. Implement storage classes and dynamic volume provisioning

## 이 항목에서 공부할 것
- [ ] `k get sc`로 StorageClass 목록을 읽고 provisioner, default 여부, binding mode, 확장 가능 여부를 말한다
- [ ] 문서의 StorageClass YAML을 복사해 provisioner / reclaimPolicy / volumeBindingMode / allowVolumeExpansion을 요구대로 고쳐 만든다
- [ ] 새 StorageClass를 default로 만들지 않는다 (또는 `kubectl patch`로 default annotation을 켜고 끈다)
- [ ] `storageClassName`을 지정한 PVC와 Pod(Deployment)를 만들어 PV가 자동으로 생기는 것을 확인한다
- [ ] `WaitForFirstConsumer`에서 PVC가 Pending인 것이 정상임을 알고, Pod을 붙여 Bound로 만든다
- [ ] 동적으로 생긴 PV의 reclaim policy가 StorageClass 값을 따라가는 것을 `k get pv`로 확인한다
- [ ] `allowVolumeExpansion: true`인 클래스의 PVC를 `kubectl patch`로 키우고, `false`일 때 거부 메시지를 알아본다

## 개념 설명

### StorageClass
- 무엇인가: "어떤 종류의 저장소를, 어떤 방식으로 만들어 줄지"를 적어 둔 클러스터 범위(namespace 없음) 리소스. 식당 메뉴판이라고 생각하면 된다. 손님(PVC)은 메뉴 이름만 말하고, 주방(provisioner)이 요리(PV)를 만든다.
- 왜 필요한가: 관리자가 PV를 하나씩 손으로 만들지 않아도 PVC만 만들면 저장소가 생기게 하려고.
- 핵심 필드: `provisioner`(누가 만드나, 예: `rancher.io/local-path`), `reclaimPolicy`(PVC 삭제 후 PV 처리: `Delete` 기본 / `Retain`), `volumeBindingMode`(`Immediate` 기본 / `WaitForFirstConsumer`), `allowVolumeExpansion`(PVC 확장 허용), `parameters`(provisioner별 옵션), `mountOptions`.
- 관계: PVC의 `spec.storageClassName`이 이 클래스의 이름과 같으면 이 클래스의 provisioner가 PV를 만든다.
- `kubectl create storageclass`는 없다. 반드시 YAML로 만든다 (확인함).
- `provisioner`, `reclaimPolicy`, `volumeBindingMode`는 만든 뒤 수정할 수 없다. patch하면 `updates to reclaimPolicy are forbidden` / `field is immutable`이 나오므로 지우고 다시 만든다 (확인함). `allowVolumeExpansion`은 patch로 바꿀 수 있다.

### Dynamic provisioning (동적 프로비저닝)
- 무엇인가: PVC를 만들면 provisioner가 자동으로 PV를 만들어 붙여 주는 흐름. 순서는 PVC 생성 -> provisioner가 PV 생성 -> 둘이 Bound.
- 왜 필요한가: 정적 방식(E3)은 PV를 사람이 먼저 만들어야 해서 느리다.
- 핵심 동작: 만들어진 PV 이름은 `pvc-<uid>`, `claimRef`로 해당 PVC에 이미 묶여 있고, PV의 reclaim policy는 StorageClass의 `reclaimPolicy`를 복사한다.
- 관계: 정적 PV(E3)가 있어도 클래스 이름이 맞는 PV가 없으면 provisioner가 새로 만든다. 클래스 이름이 가리키는 StorageClass 객체가 없으면 만들 주체가 없어서 Pending이다.

### Default StorageClass
- 무엇인가: `storageclass.kubernetes.io/is-default-class: "true"` annotation이 붙은 클래스. `k get sc`에서 `(default)`로 보인다.
- 왜 필요한가: PVC에 `storageClassName`을 안 쓰면 admission이 default 클래스 이름을 자동으로 채워 넣는다.
- 핵심 동작: default가 둘 이상이면 가장 최근에 만든 것이 선택된다 (확인함: 새 default를 만든 직후 클래스 없는 PVC가 새 클래스로 채워졌다). default를 "바꾸려면" 기존 것을 `"false"`로 내리고 새 것을 `"true"`로 올린다.
- 주의: PVC에 `storageClassName: ""`(빈 문자열)을 명시하면 default를 쓰지 않고 "클래스 없는 PV"만 찾는다 (E3 참고).

### volumeBindingMode
- `Immediate`: PVC를 만들자마자 PV를 만들고 Bound. 어느 노드에서 쓸지 모르는 상태로 만든다.
- `WaitForFirstConsumer`: 그 PVC를 쓰는 Pod이 스케줄될 때까지 기다렸다가, Pod이 놓일 노드에 맞게 PV를 만든다. 그래서 Pod 없이 PVC만 만들면 Pending이고, Events에 `waiting for first consumer to be created before binding`이 보인다. 이것은 오류가 아니다.
- 이 클러스터의 `standard`(local-path)는 `WaitForFirstConsumer`다. local-path는 노드를 정해야 디렉터리를 만들 수 있어서다.

### reclaimPolicy / allowVolumeExpansion (클래스 쪽)
- `reclaimPolicy: Retain`이면 PVC를 지워도 PV가 `Released`로 남고 데이터도 남는다. `Delete`면 PV와 실제 저장소가 같이 지워진다.
- `allowVolumeExpansion: true`여야 바인딩된 PVC의 `spec.resources.requests.storage`를 키울 수 있다. 줄이는 것은 안 된다.

## 예시

### 예시 1. StorageClass 만들기 (default 아님, WaitForFirstConsumer, Retain, 확장 허용)
상황: "provisioner `rancher.io/local-path`로 `fast-local` 클래스를 만들고 default로 하지 말 것" (q02 형태).
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-local
provisioner: rancher.io/local-path
reclaimPolicy: Retain
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```
```bash
k apply -f sc.yaml
k get sc
# 기대: fast-local   rancher.io/local-path   Retain   WaitForFirstConsumer   true
#       standard (default) ...   Delete   WaitForFirstConsumer   false
# fast-local 옆에 (default)가 없어야 한다
```
default annotation(`is-default-class`)을 문서 예제에서 같이 복사했다면 `"false"`로 바꾸거나 줄을 지운다.

### 예시 2. PVC + Deployment로 동적 프로비저닝 확인
상황: "`web-pvc`(1Gi, RWO, `fast-local`)를 만들고 Deployment `web`이 `/data`에 마운트" (q02 형태).
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: web-pvc
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: fast-local
  resources:
    requests:
      storage: 1Gi
```
```bash
k apply -f pvc.yaml
k get pvc web-pvc
# 기대: STATUS Pending   (Events: waiting for first consumer to be created before binding)
k create deploy web --image=nginx:1.27 --dry-run=client -o yaml > web.yaml
# web.yaml 의 containers[0] 아래에 volumeMounts, spec.template.spec 아래에 volumes 를 추가 (아래)
k apply -f web.yaml && k rollout status deploy/web
k get pvc,pv
# 기대: web-pvc Bound, pvc-<uid> 1Gi RWO Retain Bound <ns>/web-pvc fast-local
```
```yaml
        volumeMounts:            # containers[0] 아래
        - {name: data, mountPath: /data}
      volumes:                   # template.spec 아래 (containers 와 같은 들여쓰기)
      - name: data
        persistentVolumeClaim:
          claimName: web-pvc
```
PV의 RECLAIM POLICY가 클래스의 `Retain`을 그대로 물려받았는지 본다. 이 PV는 PVC를 지우면 `Released`가 되고 디렉터리가 노드에 남는다.

### 예시 3. default StorageClass 바꾸기
상황: "`fast-local`을 default로 하고 기존 default는 해제" (문서의 patch 한 줄).
```bash
k patch storageclass standard -p '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"false"}}}'
k patch storageclass fast-local -p '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
k get sc
# 기대: fast-local (default) 하나만 표시
```
둘 다 `true`인 상태로 두면 default가 두 개가 되고 최신 것이 쓰인다. 반드시 기존 것을 먼저(또는 같이) 내린다. (이 시뮬레이터에서는 `standard`를 실제로 바꾸지 않고 `--dry-run=server`로 patch가 통과하는 것만 확인함. default 둘 공존/최신 우선 동작은 임시 클래스로 확인함.)

### 예시 4. PVC 확장
상황: "PVC `web-pvc`를 2Gi로" (q04, q51 형태).
```bash
k get sc fast-local -o jsonpath='{.allowVolumeExpansion}{"\n"}'     # true 여야 함
k patch pvc web-pvc -p '{"spec":{"resources":{"requests":{"storage":"2Gi"}}}}'
k get pvc web-pvc -o jsonpath='{.spec.resources.requests.storage}{"\n"}'
# 기대: 2Gi
```
클래스가 `false`면 `Forbidden: only dynamically provisioned pvc can be resized and the storageclass that provisions the pvc must support resize`로 거부된다 (확인함). 이때는 클래스에 `k patch sc <name> -p '{"allowVolumeExpansion":true}'`를 먼저 한다 (문제가 클래스 수정을 허용할 때만).

검색창 결과 순위는 시점마다 달라 직접 확인하지 못했다 (미확인). 결과가 안 맞으면 아래 URL을 주소창에 그대로 입력한다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| StorageClass YAML 뼈대 | `storage classes` | https://kubernetes.io/docs/concepts/storage/storage-classes/ | `StorageClass objects` | 맨 위 첫 YAML(`low-latency`, 14줄). `provisioner` / `reclaimPolicy` / `allowVolumeExpansion` / `volumeBindingMode`가 이미 다 들어 있다. `mountOptions`, `parameters`, `annotations`는 문제가 요구하지 않으면 지운다 |
| default 지정 / 해제 | `change default storage class` | https://kubernetes.io/docs/tasks/administer-cluster/change-default-storage-class/ | `kubectl patch storageclass` | `Mark the default StorageClass as non-default` 아래 patch 한 줄, `Mark a StorageClass as default` 아래 patch 한 줄 |
| binding mode 의미 | `volume binding mode` | 위 storage-classes 페이지 | `Volume binding mode` | 이 절 아래 20줄 Pod YAML. `nodeSelector: kubernetes.io/hostname: kube-01` 두 줄은 지우고 `claimName`만 바꿔 쓴다 |
| 동적 프로비저닝 PVC | `dynamic volume provisioning` | https://kubernetes.io/docs/concepts/storage/dynamic-provisioning/ | `Using Dynamic Provisioning` | 이 절의 `claim1` PVC YAML(11줄). `storageClassName`, `storage` 값만 바꾼다 |
| default 동작 원리 | `dynamic provisioning default` | 위 dynamic-provisioning 페이지 | `Defaulting Behavior` | YAML 없음(설명). "가장 최근 default가 쓰인다" 문장을 확인 |
| 정적용(no-provisioner) 클래스 | `storage class local` | 위 storage-classes 페이지 | `no-provisioner` | `Parameters` 아래 `Local` 절의 6줄 YAML |
| PVC 확장 | `expanding persistent volumes claims` | https://kubernetes.io/docs/concepts/storage/persistent-volumes/#expanding-persistent-volumes-claims | `allowVolumeExpansion` | 11줄 StorageClass YAML(확장 허용 필드 확인용). PVC는 YAML이 아니라 `edit`/`patch`로 `requests.storage`만 키운다 |

`change-default-storage-class` 페이지는 `official.md`의 목록에는 없지만 kubernetes.io/docs 안에 있고 2026-10-19에 HTTP 200으로 확인했다.

## 자주 틀리는 점
- PVC가 Pending이고 Events에 `waiting for first consumer to be created before binding` -> 클래스가 `WaitForFirstConsumer`라서 정상 -> Pod/Deployment를 만들어 PVC를 쓰게 한다. PVC를 지우고 다시 만들 필요 없다.
- PVC가 Pending이고 `storageclass.storage.k8s.io "xxx" not found` -> `storageClassName` 오타 또는 클래스 미생성 -> `k get sc`로 이름 확인. PVC의 `spec`은 (확장 제외) 수정이 안 되므로 `k delete pvc` 후 올바른 이름으로 다시 만든다.
- `kubectl create storageclass`(또는 `create pv`, `create pvc`)를 쳤다가 `error: Unexpected args: [storageclass x]` -> 그런 imperative 명령이 없다 -> 문서 YAML을 복사한다.
- `(default)`가 두 개 뜸 -> 새 클래스 YAML에 문서의 `is-default-class: "true"`가 남았거나, default를 옮기면서 기존 default를 안 내림 -> `k patch sc <old> -p ... "false"`.
- 클래스의 `reclaimPolicy`를 patch했는데 `Forbidden: updates to reclaimPolicy are forbidden` -> 클래스의 provisioner / reclaimPolicy / volumeBindingMode는 불변 -> 클래스를 지우고 다시 만든다 (이미 만들어진 PV는 영향 없음). 이미 있는 PV 하나의 정책만 바꾸려면 PV를 patch한다 (E2).
- PVC 확장이 `only dynamically provisioned pvc can be resized ...`로 거부 -> 클래스가 `allowVolumeExpansion: false` -> 문제가 허용하면 클래스를 patch, 아니면 다른 클래스의 PVC만 확장 (q51은 "한 클래스만 바꿔라"는 조건이 핵심).
- Retain 클래스로 만든 PV가 PVC 삭제 후 `Released`로 남아 다시 안 붙음 -> `claimRef`가 남아 있다 -> `k patch pv <pv> -p '{"spec":{"claimRef":null}}'` (확인함, `Available`로 돌아온다). 새 PVC가 같은 PV를 원하면 정적 바인딩(E3)으로 푼다.
- 시뮬레이터 차이: (1) 이 클러스터는 Kubernetes v1.34.0이고 시험 문서는 v1.37이다. (2) local-path에 `volumeBindingMode: Immediate`를 쓰면 `failed to provision volume ... configuration error, no node was specified`로 Pending이 된다 (확인함). 실제 시험의 provisioner에서는 다를 수 있다. (3) PVC를 키워도 파일시스템은 안 커지고 Events에 `waiting for an external controller to expand this PVC`만 남는다. API 값만 바뀌는지 본다.

## 빠르게 푸는 순서
1. 문제 첫 줄의 `kubectl config use-context ...`와 namespace를 확인한다 (0.5분).
2. `k get sc`로 기존 클래스 이름, provisioner, default 여부를 읽는다. 문제에 provisioner가 없으면 `k get sc standard -o yaml`의 값을 쓴다 (0.5분).
3. storage-classes 페이지 첫 YAML을 복사해 이름/provisioner/reclaimPolicy/bindingMode/expansion을 고친다. default 아님 조건이면 annotation 줄을 지운다 (1.5분).
4. `k apply -f` 후 `k get sc`로 열 값과 `(default)` 여부를 확인한다 (0.5분).
5. PVC는 dynamic-provisioning 페이지의 `claim1`을 복사해 `storageClassName`/크기/accessModes를 고친다 (1분).
6. Deployment는 `k create deploy ... --dry-run=client -o yaml`로 뼈대를 만들고 `volumes` + `volumeMounts`를 넣는다 (1.5분).
7. `k get pvc,pv,pod`로 Bound / Running을 확인하고, reclaim policy와 크기가 요구와 같은지 본다 (0.5분). 전체 목표 약 6분.
