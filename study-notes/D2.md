# D2. Use ConfigMaps and Secrets to configure applications

## 이 항목에서 공부할 것
- [ ] `k create cm`을 `--from-literal` / `--from-file` / `--from-env-file`로 만들고 키 이름이 어떻게 정해지는지 설명한다
- [ ] `k create secret generic`(`--from-literal`, `--from-file`), `tls`, `docker-registry` Secret을 만들고 값을 `base64 -d`로 확인한다
- [ ] Deployment/Pod의 환경변수에 `configMapKeyRef` / `secretKeyRef`로 키 하나를, `envFrom`으로 전체를 주입한다
- [ ] ConfigMap과 Secret을 볼륨으로 mount하고 `items`(일부 키 / 경로), `defaultMode`(파일 권한), `readOnly`를 지정한다
- [ ] `k set env deploy/<이름> --from=...`으로 환경변수 주입을 명령 한 줄로 한다
- [ ] 환경변수는 재시작해야 바뀌고 볼륨 파일은 잠시 뒤 자동으로 바뀐다는 차이를 보여 준다
- [ ] 참조 오류(`CreateContainerConfigError` / `ContainerCreating`)를 Events로 읽고 고친다

## 개념 설명

### ConfigMap
- 무엇인가: 설정 값을 Pod 밖에 키-값으로 적어 두는 namespace 리소스 (비밀이 아닌 값). 이미지를 다시 빌드하지 않고 설정을 바꾸려고 쓴다. 이미지는 요리 도구, ConfigMap은 레시피 메모.
- 핵심 필드: `data`(문자열), `binaryData`, `immutable`. 값에는 한 줄 값(`LOG_LEVEL: debug`)도, 파일 내용 전체(`app.properties: |` 여러 줄)도 들어간다.
- 만드는 법 (확인함): `--from-literal=KEY=VALUE`는 키가 KEY. `--from-file=app.properties`는 키가 파일 이름 `app.properties`, 내용이 값. `--from-file=cfg=app.properties`처럼 `키=경로`면 키를 직접 정한다. `--from-env-file=app.env`는 `KEY=VALUE` 줄마다 키가 하나씩 생긴다.
- `immutable: true`인 ConfigMap은 `data`를 patch하면 `field is immutable when immutable is set`로 거부된다 (확인함).

### Secret
- 무엇인가: ConfigMap과 같은 구조인데 비밀번호, 토큰, 인증서용. 값이 `data`에 base64로 저장된다. base64는 암호화가 아니라 인코딩이다 (누구나 `base64 -d`로 푼다).
- 핵심 필드: `type`(기본 `Opaque`, 인증서는 `kubernetes.io/tls`, 레지스트리 인증은 `kubernetes.io/dockerconfigjson`), `data`(base64 값), `stringData`(평문으로 쓰면 저장 때 `data`로 변환됨, 확인함).
- 만드는 법 (확인함): `k create secret generic NAME --from-literal=k=v`는 `Opaque`. `k create secret tls NAME --cert=... --key=...`는 `tls.crt`, `tls.key` 키를 가진 TLS 타입. `k create secret docker-registry NAME --docker-server=... --docker-username=... --docker-password=... --docker-email=...`.
- 이미지 pull용 Secret은 ServiceAccount의 `imagePullSecrets`에 달면 그 SA를 쓰는 Pod이 자동으로 쓴다: `k patch sa app-sa -p '{"imagePullSecrets":[{"name":"regcred"}]}'` (확인함).

### 환경변수로 주입 (env / envFrom)
- 키 하나: `env[].valueFrom.configMapKeyRef.{name,key}` 또는 `secretKeyRef.{name,key}`. 환경변수 이름(`env[].name`)은 키 이름과 달라도 된다 (예: Secret 키 `password` -> `DB_PASSWORD`).
- 전체: `envFrom[].configMapRef.name` / `secretRef.name`, `prefix`로 이름 앞에 붙일 글자를 줄 수 있다 (확인함: `prefix: APP_` -> `APP_LOG_LEVEL`). 환경변수 이름으로 쓸 수 없는 키(예: `app.properties`)는 조용히 빠지고 Pod은 정상 기동한다 (확인함).
- 명령 한 줄: `k set env deploy/api --from=configmap/api-config --keys=LOG_LEVEL`, `k set env deploy/api --from=secret/api-secret --keys=password --prefix=DB_` (확인함: `DB_PASSWORD`가 `password` 키를 가리킴. 키 이름이 대문자로 바뀌며 `Warning: key password transferred to PASSWORD`가 나오는 것은 정상).
- 참조가 틀리면 컨테이너가 시작되지 못해 `CreateContainerConfigError`가 된다 (아래 "자주 틀리는 점").

### 볼륨으로 mount
- `volumes[].configMap.name` 또는 `volumes[].secret.secretName`을 만들고 `volumeMounts`로 경로에 붙인다. 키가 파일 이름, 값이 파일 내용이다. 두 볼륨 모두 컨테이너 안에서 읽기 전용이다 (확인함).
- `items`: 일부 키만, 또는 다른 경로로 (`items: [{key: pass, path: creds/password, mode: 0600}]`, 확인함).
- `defaultMode`: 파일 권한. YAML에서는 반드시 앞에 0을 붙여 8진수로 쓴다. `defaultMode: 0400` -> 파일 mode 400, 그런데 `defaultMode: 400`(십진수)은 620이 된다 (둘 다 확인함). JSON으로 쓸 때만 십진수를 쓴다 (문서 Note).
- 디렉터리를 통째로 덮는다: `/usr/share/nginx/html`에 ConfigMap을 mount하면 원래 있던 `index.html`이 가려지고 ConfigMap 키만 보인다 (확인함). 파일 하나만 넣으려면 `subPath`를 쓴다.

### 변경이 반영되는 방식
- 환경변수는 컨테이너 시작 때 한 번 읽는다. ConfigMap을 바꿔도 실행 중인 Pod의 환경변수는 그대로다. 반영하려면 `k rollout restart deploy/<이름>` (확인함: 바꾼 뒤에도 `env=debug` 유지).
- 볼륨으로 mount한 파일은 kubelet이 주기적으로 갱신한다 (확인함: ConfigMap patch 후 약 47초 만에 파일 값이 바뀜). `subPath`로 mount한 파일은 갱신되지 않는다 (문서 Note).

## 예시

### 예시 1. 만들기 (q08 1, 2번)
상황: "ConfigMap `api-config`에 `LOG_LEVEL=debug`와 파일 `/home/candidate/app.properties`, Secret `api-secret`에 username/password".
```bash
k create cm api-config --from-literal=LOG_LEVEL=debug --from-file=app.properties=/home/candidate/app.properties
k create secret generic api-secret --from-literal=username=admin --from-literal=password=S3cr3tPass
k get cm api-config -o yaml
# 기대: data: LOG_LEVEL: debug / app.properties: | (파일 내용)
k get secret api-secret -o jsonpath='{.data.password}' | base64 -d; echo
# 기대: S3cr3tPass
k get secret api-secret -o jsonpath='{.type}{"\n"}'
# 기대: Opaque
```
`--from-file=/home/candidate/app.properties`(키 생략)도 키가 파일 이름 `app.properties`가 되어 같은 결과다. 키 이름을 문제가 지정하면 `키=경로` 형태를 쓴다.

### 예시 2. Deployment에 env와 볼륨을 한 번에 (q08 3번)
상황: "환경변수 두 개, `/etc/api`에 ConfigMap, `/etc/secrets`에 Secret(읽기 전용, mode 0400)".
```bash
k get deploy api -o yaml > api.yaml     # 또는 k edit deploy api
```
```yaml
      containers:
      - name: nginx
        image: nginx:1.27
        env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef: {name: api-config, key: LOG_LEVEL}
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: {name: api-secret, key: password}
        volumeMounts:
        - {name: config, mountPath: /etc/api}
        - {name: secrets, mountPath: /etc/secrets, readOnly: true}
      volumes:
      - name: config
        configMap: {name: api-config}
      - name: secrets
        secret: {secretName: api-secret, defaultMode: 0400}
```
```bash
k apply -f api.yaml && k rollout status deploy/api
k exec deploy/api -- sh -c 'echo $LOG_LEVEL $DB_PASSWORD; ls /etc/api; stat -L -c "%a %n" /etc/secrets/*'
# 기대: debug S3cr3tPass / LOG_LEVEL app.properties / 400 /etc/secrets/password, 400 /etc/secrets/username
```
`ls -l`에서는 파일이 `..data/...`로의 심볼릭 링크로 보이고 `-L`을 줘야 실제 권한이 나온다 (확인함). 이 Deployment 편집은 컨테이너 이름(`nginx`)과 이미지를 바꾸지 않는 것이 조건이다.

### 예시 3. 명령 한 줄로 환경변수만
상황: "환경변수만 요구하면 YAML 편집 없이".
```bash
k set env deploy/api --from=configmap/api-config --keys=LOG_LEVEL
k set env deploy/api --from=secret/api-secret --keys=password --prefix=DB_
k set env deploy/api --list
# 기대: # LOG_LEVEL from configmap api-config, key LOG_LEVEL
#       # DB_PASSWORD from secret api-secret, key password
```
`--keys`를 빼면 ConfigMap/Secret의 모든 키가 환경변수가 된다. 볼륨은 `set` 명령이 없으므로(`k set`에는 env, image, resources, selector, serviceaccount, subject만 있음, 확인함) YAML로 한다.

### 예시 4. Secret 여러 종류와 파일 mode (q60 형태)
상황: "TLS Secret, registry Secret(ServiceAccount에 연결), generic Secret, Pod에서 mode 0440 마운트 + 환경변수".
```bash
k create secret tls web-tls --cert=tls.crt --key=tls.key
k create secret docker-registry regcred --docker-server=registry.example.com --docker-username=ci-bot --docker-password='Pa55w0rd!' --docker-email=ci@example.com
k patch sa app-sa -p '{"imagePullSecrets":[{"name":"regcred"}]}'
k create secret generic api-token --from-literal=token=abc123
```
```yaml
apiVersion: v1
kind: Pod
metadata: {name: secure-app}
spec:
  serviceAccountName: app-sa
  containers:
  - name: app
    image: nginx:1.27
    env:
    - name: API_TOKEN
      valueFrom:
        secretKeyRef: {name: api-token, key: token}
    volumeMounts:
    - {name: tls, mountPath: /etc/tls, readOnly: true}
  volumes:
  - name: tls
    secret: {secretName: web-tls, defaultMode: 0440}
```
```bash
k apply -f secure-app.yaml && k wait --for=condition=Ready pod/secure-app
k exec secure-app -- sh -c 'stat -L -c "%a %n" /etc/tls/*; echo $API_TOKEN'
# 기대: 440 /etc/tls/tls.crt, 440 /etc/tls/tls.key / abc123
k get secret web-tls -o jsonpath='{.type}{"\n"}'
# 기대: kubernetes.io/tls   (regcred 는 kubernetes.io/dockerconfigjson)
```

### 예시 5. items / stringData / prefix
상황: "Secret의 키 하나만 다른 경로에, ConfigMap 전체를 접두사 붙여 환경변수로".
```yaml
apiVersion: v1
kind: Secret
metadata: {name: sd-secret}
stringData: {user: root, pass: hunter2}      # 평문으로 쓰면 저장될 때 base64 data 로 바뀐다
---
apiVersion: v1
kind: Pod
metadata: {name: items-pod}
spec:
  containers:
  - name: c
    image: busybox:1.37
    command: ["sleep","3600"]
    envFrom:
    - configMapRef: {name: env-cm}
      prefix: APP_
    volumeMounts:
    - {name: sec, mountPath: /etc/sec}
  volumes:
  - name: sec
    secret:
      secretName: sd-secret
      items:
      - {key: pass, path: creds/password, mode: 0600}
```
```bash
k exec items-pod -- sh -c 'env | grep ^APP_; stat -L -c "%a %n" /etc/sec/creds/password; ls /etc/sec'
# 기대: APP_<키>=... 줄들 / 600 /etc/sec/creds/password / creds   (user 파일은 없음: items 에 안 적은 키는 마운트되지 않음)
```

## 공식 문서에서 찾는 법
검색 결과 순위는 직접 확인하지 못했다 (미확인). 안 나오면 URL을 그대로 입력한다. Secret 개념 페이지에는 env / defaultMode 예제 YAML이 거의 없고 아래 task 페이지로 링크만 한다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| ConfigMap 만드는 명령 | `configure pod configmap` | https://kubernetes.io/docs/tasks/configure-pod-container/configure-pod-configmap/ | `kubectl create configmap <map-name>`, `--from-literal`, `--from-file` | `Create a ConfigMap using kubectl create configmap` 아래 명령들. 키 이름 지정은 `Define the key to use when creating a ConfigMap from a file` 절 |
| ConfigMap 키 하나 -> env | 같은 페이지 | 같은 페이지 | `Define a container environment variable with data from a single ConfigMap` | 그 절의 19줄 Pod YAML (`configMapKeyRef`) |
| ConfigMap 전체 -> env | 같은 페이지 | 같은 페이지 | `Configure all key-value pairs in a ConfigMap as container environment variables` | 그 절의 `envFrom` Pod YAML (13줄) |
| ConfigMap -> 볼륨 | 같은 페이지 | 같은 페이지 | `Populate a Volume with data stored in a ConfigMap` | 19줄 Pod YAML. 일부 키만은 바로 아래 `Add ConfigMap data to a specific path in the Volume`의 `items` 예시 |
| env + 볼륨을 한 Pod에 | `configmap` | https://kubernetes.io/docs/concepts/configuration/configmap/ | `game-demo` | `ConfigMaps and Pods` 절의 38줄 Pod YAML. `env`(`configMapKeyRef`)와 `volumes`(`items`)가 한 YAML에 모두 있다 |
| Secret을 명령으로 만들기 | `distribute credentials secure` | https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/ | `Create a Secret directly with kubectl` | `kubectl create secret generic test-secret --from-literal=...` 한 줄 |
| Secret -> 환경변수 | 같은 페이지 | 같은 페이지 | `Define a container environment variable with data from a single Secret` | 그 절의 14줄 Pod YAML (`secretKeyRef`) |
| Secret -> 볼륨 + 파일 권한 | 같은 페이지 | 같은 페이지 | `Set POSIX permissions for Secret keys` | 16줄 Pod YAML (`defaultMode: 0400`). 경로 지정은 바로 위 `Project Secret keys to specific file paths`(19줄) |
| tls / docker-registry Secret 명령 | `secret types` | https://kubernetes.io/docs/concepts/configuration/secret/ | `kubectl create secret tls`, `secret-tiger-docker` | `TLS Secrets` 절 명령 3줄, `Docker config Secrets` 절 `kubectl create secret docker-registry` 5줄 |
| Secret이 필수 / 옵션 참조 | 같은 페이지 | 위 secret 페이지 | `Optional Secrets` | `optional: true`가 있는 17줄 Pod YAML |

`distribute-credentials-secure` 페이지는 `official.md` 목록에는 없지만 Secret 개념 페이지가 링크하는 task 페이지이고 kubernetes.io/docs 안에 있으며 2026-10-19에 HTTP 200으로 확인했다.

## 자주 틀리는 점
- Pod이 `CreateContainerConfigError`, Events `Error: configmap "no-such-cm" not found` 또는 `couldn't find key NOPE in ConfigMap ns/name` (Secret은 `... in Secret ns/name`) -> `env` / `envFrom`이 없는 객체나 없는 키를 가리킴 (확인함) -> `k get cm,secret`와 `k get cm <이름> -o yaml`로 이름과 키를 맞춘다. 있어도 되고 없어도 되는 값이면 `optional: true`.
- Pod이 `ContainerCreating`에 머물고 Events `FailedMount ... secret "no-such-secret" not found` -> 볼륨으로 참조한 객체가 없음 (확인함, 환경변수 참조 오류와 상태 이름이 다르다) -> 객체를 만들면 kubelet이 재시도해 자동으로 시작된다.
- 환경변수 값이 안 바뀜 -> env는 시작 때 읽음 -> `k rollout restart deploy/<이름>`.
- Secret 파일 mode가 이상하다(620) -> `defaultMode: 400`처럼 0 없이 씀 -> `0400`. YAML에서 `0400`(8진수).
- `mountPath`로 잡은 디렉터리의 원래 파일이 사라짐 -> 볼륨이 디렉터리 전체를 가림 (확인함) -> `subPath`로 파일 하나만, 또는 다른 경로에 mount. `subPath` mount는 이후 ConfigMap 변경이 반영되지 않는다 (문서).
- `echo 'x' | base64`로 `data:`에 넣었더니 값 끝에 개행이 붙음 -> `echo 'x' | base64`는 `eAo=`, `echo -n 'x' | base64`는 `eA==`로 서로 다르다 (확인함). `echo -n`을 쓰거나 아예 `stringData`/`--from-literal`을 쓴다 (문서의 예시도 `echo -n`).
- `Pa55w0rd!` 같은 값의 `!`는 대화형 bash에서 히스토리 확장으로 해석될 수 있음 -> 작은따옴표로 감싼다 (예시 4처럼. 시험 터미널에서 실제 재현은 못 해 봄, 미확인).
- Deployment `api`를 고치면서 컨테이너 이름이나 이미지를 바꿔 버림 -> "이름과 이미지는 그대로" 조건 위반 -> 편집은 `env`, `volumeMounts`, `volumes`만 추가.
- ConfigMap을 만든 namespace와 Pod의 namespace가 다름 -> 같은 namespace의 객체만 참조 가능 -> `-n <ns>` 확인.
- 시뮬레이터 차이: 이 클러스터는 v1.34.0(시험은 v1.37). 파일 갱신 시간(약 1분)은 kubelet 설정에 따라 다를 수 있다.

## 빠르게 푸는 순서
1. context / namespace 확인, 대상 Deployment와 파일 경로, 키 이름 조건을 적는다 (0.5분).
2. 객체부터 만든다: `k create cm ...`, `k create secret generic ...` (또는 tls / docker-registry). `k get cm,secret`로 확인 (1분).
3. 환경변수만이면 `k set env ... --from=... --keys=... [--prefix=...]`, `k set env --list`로 확인 (1분).
4. 볼륨이 필요하면 `k get deploy <이름> -o yaml > d.yaml` 후 configmap 페이지의 `game-demo` YAML이나 위 예시 2를 보고 `env` / `volumeMounts` / `volumes`를 추가 (2분).
5. 파일 권한 요구는 `defaultMode: 0400` (0 포함), 읽기 전용 요구는 `volumeMounts[].readOnly: true` (0.5분).
6. `k apply -f d.yaml && k rollout status deploy/<이름>` (0.5분).
7. `k exec deploy/<이름> -- sh -c 'echo $VAR; ls <경로>; stat -L -c "%a %n" <파일>'`로 값과 권한 확인 (1분). 실패하면 `k describe pod`의 Events부터 본다. 전체 목표 6분.
