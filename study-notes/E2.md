# E2. Configure volume types, access modes and reclaim policies

## 이 항목에서 공부할 것
- [ ] Pod에 `emptyDir`(메모리 / sizeLimit), `hostPath`(type), `configMap` 볼륨을 `volumes` + `volumeMounts`로 연결한다
- [ ] 한 Pod의 두 컨테이너가 같은 `emptyDir`을 각각 mount해서 파일을 공유하게 만든다
- [ ] accessModes 네 가지(RWO / ROX / RWX / RWOP)의 뜻을 구분하고, PV 모드에 맞춰 PVC를 요청한다
- [ ] ROX PV를 selector로 골라 PVC를 바인딩하고, Pod에서 `readOnly: true`로 mount한다
- [ ] `kubectl patch pv`로 `persistentVolumeReclaimPolicy`를 `Retain` / `Delete`로 바꾸고 `k get pv`로 확인한다
- [ ] Retain PV가 `Released`가 되는 과정과 다시 쓰려면 `claimRef`를 비워야 하는 것을 안다
- [ ] `volumeMode: Block` PV/PVC를 바인딩하고 Pod에서는 `volumeDevices`로 쓰는 것을 안다

## 개념 설명

### volumes 와 volumeMounts
- 무엇인가: Pod의 `spec.volumes`에 "저장소 목록"을 이름과 함께 선언하고, 컨테이너의 `volumeMounts`에서 그 이름을 골라 "이 경로에 붙여라"라고 쓰는 두 단계 구조.
- 왜 필요한가: 컨테이너 파일시스템은 재시작하면 사라지고, 컨테이너끼리는 서로 안 보이기 때문.
- 핵심 필드: `volumes[].name`과 `volumeMounts[].name`이 같아야 한다. `mountPath`, `readOnly`, `subPath`. 컨테이너마다 따로 mount해야 한다 (한 컨테이너에 mount했다고 다른 컨테이너에 보이지 않는다).
- 관계: 볼륨 종류(emptyDir, hostPath, configMap, secret, persistentVolumeClaim)는 `volumes[]` 안의 키로 구분한다.

### emptyDir
- 무엇인가: Pod이 노드에 배정될 때 만들어지는 빈 디렉터리. Pod이 사라지면 같이 사라진다. 서랍 하나를 Pod 안 컨테이너들이 같이 쓰는 모습.
- 핵심 필드: `medium: Memory`(tmpfs, 메모리 사용), `sizeLimit`. sidecar 패턴에서 로그/파일 공유용으로 가장 많이 나온다.
- 확인함: `medium: Memory`로 만들면 컨테이너 안에서 `tmpfs ... /shared`로 보이고 크기 제한이 `sizeLimit`(64Mi)이다.

### hostPath
- 무엇인가: 노드의 파일/디렉터리를 Pod에 직접 붙인다. 노드마다 내용이 다르므로 운영에서는 피하지만 시험(PV, 로그 수집)에는 자주 나온다.
- 핵심 필드: `path`, `type`. `type`을 비우면 검사 없이 mount한다 (경로가 없으면 런타임이 디렉터리를 만든다. 확인함). `Directory`는 "이미 있어야 함"이라 없으면 Pod이 `ContainerCreating`에 걸린다 (확인함). `DirectoryOrCreate`는 없으면 만든다.
- 관계: PV의 `spec.hostPath`로도 쓴다 (E3).

### configMap / secret 볼륨
- 무엇인가: ConfigMap/Secret의 키를 파일로 보여 주는 볼륨 (자세한 설정은 D2). 컨테이너 안에서는 읽기 전용으로 붙는다 (확인함: `touch` -> `Read-only file system`).
- 핵심 필드: `configMap.name` / `secret.secretName`, `items`(일부 키만, 경로 변경), `defaultMode`.

### accessModes (PV / PVC 공통)
- 무엇인가: 볼륨을 누가 어떻게 붙일 수 있는지의 선언. PVC의 요청 모드를 PV가 "지원 목록에 포함"해야 바인딩된다.
- 네 가지: `ReadWriteOnce`(RWO, 노드 하나에서 읽기/쓰기. 같은 노드의 Pod 여러 개는 가능), `ReadOnlyMany`(ROX, 여러 노드에서 읽기 전용), `ReadWriteMany`(RWX, 여러 노드에서 읽기/쓰기), `ReadWriteOncePod`(RWOP, 클러스터 전체에서 Pod 하나만).
- 주의: 모드는 "바인딩 매칭 조건"이지 쓰기 방지 장치가 아니다 (문서 Note). ROX PV라도 mount가 자동으로 읽기 전용이 되지는 않으므로, "읽기 전용으로 마운트"하라면 `volumeMounts[].readOnly: true`를 직접 쓴다.
- 확인함: RWOP PVC를 쓰는 Pod 두 개 중 두 번째는 `Pending`이고 Events에 `PersistentVolumeClaim with ReadWriteOncePod access mode already in-use by another pod`가 나온다.
- 문서 표에 hostPath는 RWO만 있지만, 이 클러스터에서는 hostPath PV에 RWX/ROX/RWOP를 써도 API가 받아 바인딩된다 (표는 참고용).

### persistentVolumeReclaimPolicy (PV 쪽)
- 무엇인가: PVC가 지워진 뒤 PV를 어떻게 할지. `Retain`: PV와 데이터를 남기고 `Released` 상태가 된다. `Delete`: PV와 저장소를 지운다. `Recycle`은 deprecated.
- 어디에 있나: 정적 PV는 PV의 `spec.persistentVolumeReclaimPolicy`(기본 Retain), 동적 PV는 StorageClass의 `reclaimPolicy`를 복사해 온다 (E1).
- 관계: 이미 만들어진 PV의 정책은 `kubectl patch pv`로 바꿀 수 있다. `Released` PV는 `spec.claimRef`가 남아 있어서 다른 PVC가 못 붙는다. `claimRef`를 비우면 `Available`이 된다 (확인함).

### volumeMode: Filesystem / Block
- `Filesystem`(기본)은 디렉터리로 mount, `Block`은 포맷 안 된 디스크 장치로 컨테이너에 준다. Pod에서는 `volumeMounts`가 아니라 `volumeDevices`(`devicePath`)로 쓴다.
- PV와 PVC의 `volumeMode`가 같아야 바인딩된다. 미지정은 Filesystem과 같게 취급된다 (문서 매트릭스: Block vs Filesystem/미지정은 NO BIND).

## 예시

### 예시 1. emptyDir(메모리) + hostPath + configMap을 가진 두 컨테이너 Pod
상황: "writer와 reader가 `/shared`를 공유, writer만 `/hostlogs`, reader만 `/etc/conf`를 읽기 전용" (q05 A).
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: multi-vol
spec:
  containers:
  - name: writer
    image: busybox:1.37
    command: ["sh","-c","while true; do date >> /shared/out.log; sleep 5; done"]
    volumeMounts:
    - {name: shared, mountPath: /shared}
    - {name: hostlogs, mountPath: /hostlogs}
  - name: reader
    image: busybox:1.37
    command: ["sh","-c","tail -F /shared/out.log"]
    volumeMounts:
    - {name: shared, mountPath: /shared}
    - {name: conf, mountPath: /etc/conf, readOnly: true}
  volumes:
  - name: shared
    emptyDir: {medium: Memory, sizeLimit: 64Mi}
  - name: hostlogs
    hostPath: {path: /var/log/multi-vol, type: DirectoryOrCreate}
  - name: conf
    configMap: {name: app-conf}
```
```bash
k create cm app-conf --from-literal=mode=prod
k apply -f multi-vol.yaml
k get pod multi-vol
# 기대: READY 2/2  STATUS Running
k logs multi-vol -c reader --tail=2
# 기대: 날짜 줄이 찍힘 (writer가 쓴 /shared/out.log 를 reader가 읽음)
```

### 예시 2. PV 정책 바꾸기와 Released 되살리기
상황: "bound 상태인 `legacy-pv`를 지우지 말고 Retain으로" (q03 1번).
```bash
k get pv legacy-pv -o custom-columns=NAME:.metadata.name,RECLAIM:.spec.persistentVolumeReclaimPolicy
k patch pv legacy-pv -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
k get pv legacy-pv
# 기대: RECLAIM POLICY 열이 Retain, STATUS 는 그대로 Bound
```
PVC를 지우면 Retain PV는 `Released`로 남는다. 다시 쓰려면:
```bash
k patch pv legacy-pv -p '{"spec":{"claimRef":null}}'
k get pv legacy-pv
# 기대: STATUS Available, CLAIM 열이 비어 있음
```
필드 이름을 틀리면 (`persistentReclaimPolicy`) `Warning: unknown field "spec.persistentReclaimPolicy"` 와 `patched (no change)`가 나온다 (확인함). 반드시 `k get pv`로 바뀐 값을 다시 본다.

### 예시 3. ROX PV를 selector로 잡고 읽기 전용으로 mount
상황: "`tier=reports` 라벨의 PV를 클래스 없이 2Gi ROX로 claim하고 Pod에서 읽기 전용 mount" (q03 2, 3번).
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: reports-pvc
spec:
  accessModes: [ReadOnlyMany]
  storageClassName: ""
  resources:
    requests:
      storage: 2Gi
  selector:
    matchLabels:
      tier: reports
---
apiVersion: v1
kind: Pod
metadata:
  name: reports-reader
spec:
  containers:
  - name: c
    image: busybox:1.37
    command: ["sleep","3600"]
    volumeMounts:
    - {name: rep, mountPath: /reports, readOnly: true}
  volumes:
  - name: rep
    persistentVolumeClaim:
      claimName: reports-pvc
```
```bash
k apply -f reports.yaml
k get pvc reports-pvc
# 기대: Bound, ACCESS MODES ROX
k exec reports-reader -- touch /reports/x
# 기대: touch: /reports/x: Read-only file system
```
`storageClassName: ""`를 빼면 default 클래스가 채워져서 클래스 없는 PV와 안 붙는다 (확인함, E3 참고).

### 예시 4. Block 볼륨 바인딩
상황: "`volumeMode: Block` PV `raw-pv`와 PVC `raw-pvc`" (q05 B).
```yaml
apiVersion: v1
kind: PersistentVolume
metadata: {name: raw-pv}
spec:
  capacity: {storage: 2Gi}
  accessModes: [ReadWriteOnce]
  volumeMode: Block
  storageClassName: raw
  persistentVolumeReclaimPolicy: Retain
  hostPath: {path: /dev/raw-lab}
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: raw-pvc}
spec:
  accessModes: [ReadWriteOnce]
  volumeMode: Block
  storageClassName: raw
  resources:
    requests:
      storage: 1Gi
```
```bash
k get pvc raw-pvc
# 기대: Bound  (CAPACITY 는 PV 의 2Gi), STORAGECLASS raw
```
Pod에서는 `containers[].volumeDevices: [{name: data, devicePath: /dev/xvda}]` + `volumes[].persistentVolumeClaim.claimName: raw-pvc`로 쓴다. 이 YAML은 `--dry-run=server`로 통과를 확인했고 실제 기동은 해 보지 않았다 (미확인).

## 자주 틀리는 점
- Pod이 `ContainerCreating`에서 안 넘어가고 Events에 `hostPath type check failed: /xxx is not a directory` -> `hostPath.type: Directory`인데 노드에 경로가 없음 (확인함) -> `type`을 `DirectoryOrCreate`로 바꾸거나 type을 지운다.
- emptyDir에 쓴 파일이 다른 컨테이너에 안 보임 -> 그 컨테이너에는 `volumeMounts`를 안 달았음 -> 공유하는 컨테이너 모두에 같은 `name`으로 mount.
- ConfigMap mount 경로에 `touch`가 `Read-only file system` -> configMap/secret 볼륨은 읽기 전용 (정상). 쓰기가 필요하면 emptyDir를 따로 쓴다.
- patch 후 값이 안 바뀜 -> 필드명 오타 (`persistentVolumeReclaimPolicy`가 맞음). `patched (no change)`와 `unknown field` 경고를 읽는다.
- Retain PV를 쓰던 PVC를 지웠는데 새 PVC가 안 붙음 -> PV가 `Released`이고 `claimRef`가 남아 있음 -> `claimRef: null` patch.
- 정적 hostPath PV를 `Delete`로 두고 PVC를 지우면 PV가 `Failed`가 되고 Events에 `host_path deleter only supports /tmp/.+` (확인함, 경로가 `/tmp` 밖일 때). `/tmp` 밑이면 PV가 지워진다. 정적 PV는 보통 `Retain`으로 두는 이유.
- ROX 요청인데 PV가 RWO -> PVC가 Pending. PV의 accessModes가 PVC 요청 모드를 포함해야 한다.
- Block / Filesystem 불일치 -> Pending (문서 매트릭스). PVC의 `volumeMode`를 안 쓰면 Filesystem이다.
- PV `capacity`를 patch하면 bound 상태에서도 받아들여진다 (확인함). 문서는 PV를 직접 키우면 자동 확장이 막힐 수 있다고 경고하므로 확장은 PVC로 한다.
- 시뮬레이터 차이: 이 클러스터는 v1.34.0(시험은 v1.37). hostPath는 kind 노드(컨테이너) 안의 경로다. 문서 표와 달리 hostPath PV에 RWX/ROX가 받아들여진다. 문서는 RWOP를 CSI 전용으로 적었지만 hostPath PV에서도 스케줄러가 두 번째 Pod을 막았다.

## 빠르게 푸는 순서
1. context / namespace 확인, 문제에서 "삭제 금지", "PV 수정 금지" 같은 제약을 밑줄 친다 (0.5분).
2. `k get pv,pvc -A`와 `k get pv <이름> -o yaml`로 현재 모드, 정책, 라벨을 읽는다 (1분).
3. 정책 변경이면 `k patch pv ... -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'` 한 줄 (0.5분).
4. Pod 볼륨은 volumes 페이지(`Ctrl+F` `emptyDir configuration example`)에서 `volumes:` 블록만 복사하고, `volumeMounts`를 컨테이너마다 쓴다 (2분).
5. PVC는 `accessModes`, `storageClassName`(필요하면 `""`), `selector`, `volumeMode`를 PV와 나란히 맞춘다 (1.5분).
6. `k apply` 후 `k get pvc,pv,pod`로 Bound / Running을 확인하고 `k exec`로 마운트 결과(읽기 전용, 공유 파일)를 확인한다 (1분).
7. 정책 변경 문제는 마지막에 `k get pv -o custom-columns=NAME:.metadata.name,RECLAIM:.spec.persistentVolumeReclaimPolicy`로 다시 확인한다 (0.5분). 전체 목표 6~7분.
