# D4. Understand the primitives used to create robust, self-healing, application deployments

## 이 항목에서 공부할 것
- [ ] Pod를 지웠을 때 다시 살아나는 것(Deployment/ReplicaSet/DaemonSet/StatefulSet)과 안 살아나는 것(맨 Pod)을 `ownerReferences`로 구분한다
- [ ] `livenessProbe` / `readinessProbe` / `startupProbe`를 문서에서 복사해 붙이고, 실패 이벤트(`Liveness probe failed`, `Readiness probe failed`)로 어느 프로브가 문제인지 판별한다
- [ ] `restartPolicy`(`Always`/`OnFailure`/`Never`)가 Pod와 Job에서 어떻게 다른지 알고 맞게 고른다
- [ ] initContainer로 "의존 서비스가 뜰 때까지 대기"를 만들고(`Init:0/1` 상태 읽기), 네이티브 사이드카(`initContainers[].restartPolicy: Always`) + emptyDir 로그 수집 Pod를 YAML로 쓴다
- [ ] DaemonSet(노드마다 1개, 컨트롤 플레인 toleration, `updateStrategy`)을 만든다. `k create deploy --dry-run`에서 뼈대를 바꿔 쓴다
- [ ] StatefulSet + headless Service + `volumeClaimTemplates`를 만들고 `partition`으로 카나리 업데이트를 한다
- [ ] Job(`completions`/`parallelism`/`backoffLimit`/`ttlSecondsAfterFinished`)과 CronJob(`suspend`, `concurrencyPolicy`, `k create job --from=cronjob/...`)을 만든다
- [ ] PodDisruptionBudget을 만들고 `ALLOWED DISRUPTIONS`를 읽어, drain/eviction이 막히는 이유를 설명한다

## 개념 설명

### ReplicaSet (그리고 Deployment의 자가 치유)
- 무엇: 지정한 개수(`replicas`)의 Pod가 항상 떠 있게 유지하는 컨트롤러. Pod 하나가 죽으면 즉시 새로 만든다. 보통 직접 만들지 않고 **Deployment가 ReplicaSet을 만든다**(이름 `web-66d47686b4`의 해시가 그 증거).
- 왜: Pod는 노드가 죽거나 지워지면 그냥 사라진다. "N개 유지"라는 의지를 선언하면 컨트롤러가 현실을 맞춘다.
- 핵심 필드: `replicas`, `selector.matchLabels`(Pod 템플릿 라벨과 일치해야 함), `template`. Pod의 `metadata.ownerReferences[0].kind`가 `ReplicaSet`이면 컨트롤러가 관리하는 Pod다.
- 직접 확인: Deployment Pod 하나를 지우면 몇 초 안에 새 이름의 Pod가 생기지만, `k run`으로 만든 맨 Pod는 지우면 끝이다.
- 관계: 롤링 업데이트/롤백(D1)은 Deployment가 ReplicaSet을 갈아 끼우는 것이다. 개수 조절 자동화는 HPA(D3).

### Pod 수명주기와 restartPolicy
- 무엇: 컨테이너가 종료되면 kubelet이 `spec.restartPolicy`에 따라 재시작한다. 값: `Always`(기본), `OnFailure`, `Never`.
- 직접 확인 (`sh -c 'exit 1'`을 돌리는 Pod 3개): `Never`는 `Error`로 멈추고 RESTARTS 0, Pod phase `Failed`. `OnFailure`와 `Always`는 RESTARTS가 올라가고 곧 `CrashLoopBackOff`(재시작 간격이 점점 길어짐).
- 관계: Deployment/DaemonSet/StatefulSet의 Pod는 `Always`만 가능. Job/CronJob의 Pod는 `OnFailure` 또는 `Never`만 가능 (`Always`로 쓰면 서버가 거부: `valid values: "OnFailure", "Never"`).

### Probes (liveness / readiness / startup)
- 무엇: kubelet이 컨테이너 상태를 주기적으로 묻는 검사. 방법은 `httpGet`, `tcpSocket`, `exec`, `grpc`.
- 세 종류의 역할은 다르다.
  - `livenessProbe` 실패 -> 컨테이너를 **재시작**(이벤트 `Container ... failed liveness probe, will be restarted`).
  - `readinessProbe` 실패 -> 재시작은 안 하고 Pod를 **Service 대상에서 제외**(READY 0/1, EndpointSlice의 `ready: false`).
  - `startupProbe` 성공 전까지 liveness/readiness를 **미룬다**. 느리게 뜨는 앱이 시작 중에 죽임을 당하지 않게 하는 용도.
- 핵심 필드: `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds`, `successThreshold`, `failureThreshold`. startupProbe는 `failureThreshold x periodSeconds`가 앱의 최대 기동 시간이다.
- 비유: liveness는 "맥박이 없으면 심폐소생(재시작)", readiness는 "손님 받을 준비가 안 됐으면 문에 '준비중' 팻말(트래픽 차단)", startup은 "출근 전에는 근태 검사 보류".
- 관계: readiness 실패는 서비스 장애처럼 보인다(Endpoints 비어 있음). 그 진단은 A5.

### Init containers
- 무엇: 앱 컨테이너보다 **먼저, 순서대로, 끝까지 성공해야** 다음으로 넘어가는 컨테이너. 모두 성공해야 앱이 시작된다.
- 왜: DB/Service가 뜰 때까지 대기, 설정 파일 준비 같은 선행 작업.
- 상태 읽기: `Init:0/1`(첫 init 실행 중), `Init:CrashLoopBackOff`(init이 계속 실패). 로그는 `k logs <pod> -c <init이름>`.
- 주의 (직접 겪음): busybox의 `nslookup myservice`는 이름을 찾고도(`Name:`/`Address:` 출력) 검색 도메인 변형(`myservice.svc.cluster.local` 등)이 NXDOMAIN이면 종료 코드가 0이 아니어서 `until nslookup ...` 루프가 영원히 돈다. 문서 예제처럼 FQDN(`myservice.<ns>.svc.cluster.local`)으로 조회한다.

### Sidecar containers (네이티브 사이드카)
- 무엇: `initContainers` 안에 넣고 `restartPolicy: Always`를 준 컨테이너. init처럼 앱보다 먼저 시작하지만 **끝나길 기다리지 않고 앱과 함께 계속 실행**되고, Pod가 끝날 때 정리된다.
- 기존 방식(`containers`에 컨테이너 두 개)과 차이: 시작 순서가 보장되고, Job에서도 메인이 끝나면 Pod가 완료 처리된다. 기존 방식은 두 컨테이너 중 하나만 끝나면 Pod가 `NotReady`로 남는다(직접 확인: 메인이 5초 뒤 종료하는 2컨테이너 Pod가 `1/2 NotReady`).
- 로그 공유는 보통 `emptyDir` 볼륨을 **양쪽 컨테이너에 모두** 마운트한다.
- 확인: READY가 `2/2`, `initContainerStatuses`에 사이드카가 `ready=true started=true`.

### DaemonSet
- 무엇: 조건에 맞는 **노드마다 Pod 1개**를 보장(로그 수집기, 노드 에이전트, kube-proxy/CNI 같은 것).
- 핵심: 이 클러스터에서 처음엔 DESIRED 2(워커 2대)였다. 컨트롤 플레인 노드에는 `node-role.kubernetes.io/control-plane:NoSchedule` taint가 있어서 toleration을 넣어야 3이 된다. 특정 노드만 쓰려면 `nodeSelector`/`affinity`.
- `updateStrategy`: 기본 `RollingUpdate`(`maxUnavailable` 기본 1, `maxSurge` 0), 또는 `OnDelete`(Pod를 직접 지워야 새 템플릿 적용).
- `replicas` 필드가 없다. `selector`는 템플릿 라벨과 일치해야 한다.

### StatefulSet
- 무엇: Pod마다 **고정 이름(`db-0`, `db-1`)과 고정 저장소**가 필요한 앱용. 순서대로 만들고(0 -> 1) 역순으로 지운다(기본 `OrderedReady`).
- 필수 짝: **headless Service**(`clusterIP: None`)를 만들고 `spec.serviceName`에 그 이름을 적는다. 그러면 `db-0.db.<ns>.svc...` 같은 안정적 DNS 이름이 생긴다.
- `volumeClaimTemplates`: Pod마다 PVC(`data-db-0`, `data-db-1`)를 자동 생성. Pod를 지워도 같은 이름으로 돌아와 **같은 PVC**를 다시 붙인다 (직접 확인: `/data`에 쓴 파일이 Pod 삭제 후에도 남음).
- 업데이트: `updateStrategy.rollingUpdate.partition: N`이면 **ordinal이 N 이상인 Pod만** 새 템플릿으로 바뀐다(카나리). 직접 확인: partition 1에서 이미지 변경 -> `db-1`만 1.26, `db-0`은 1.27 유지.
- `persistentVolumeClaimRetentionPolicy`: `whenDeleted`/`whenScaled`에 `Retain`(기본)/`Delete`. 직접 확인: `whenScaled: Retain`이면 replicas를 줄여도 PVC가 남고, `whenDeleted: Delete`이면 StatefulSet을 지울 때 PVC도 사라졌다.
- 관계: 저장소 부분은 E1/E3(StorageClass, PVC). 이 클러스터의 기본 SC `standard`는 `WaitForFirstConsumer`.

### Job / CronJob
- Job: "끝까지 한 번 실행"하는 Pod를 만든다. `completions`(성공해야 하는 횟수), `parallelism`(동시 실행 수), `backoffLimit`(실패 재시도 한도, 넘으면 Job `Failed`/`BackoffLimitExceeded`), `activeDeadlineSeconds`(전체 제한 시간), `ttlSecondsAfterFinished`(끝난 뒤 자동 삭제). Pod `restartPolicy`는 `Never`/`OnFailure`.
- CronJob: 일정(`schedule`, cron 형식)마다 Job을 만든다. `suspend: true`로 일시 중지, `concurrencyPolicy`(`Allow`/`Forbid`/`Replace`), `successfulJobsHistoryLimit`/`failedJobsHistoryLimit`, `startingDeadlineSeconds`.
- 직접 확인: `k create cronjob`의 기본 Pod `restartPolicy`는 `OnFailure`, 기본 `concurrencyPolicy: Allow`, 성공 기록 3개. `k create job manual --from=cronjob/hello`로 즉시 1회 실행할 수 있다.

### PodDisruptionBudget (PDB)
- 무엇: 노드 drain, 업그레이드 같은 **자발적 중단(eviction)** 중에도 최소 몇 개 Pod는 살아 있게 하는 안전장치. 갑작스런 장애(비자발적)는 막지 못한다.
- 핵심: `selector`(대상 Pod 라벨) + `minAvailable` 또는 `maxUnavailable` 중 **하나만**. `k get pdb`의 `ALLOWED DISRUPTIONS`가 0이면 지금은 어떤 Pod도 evict할 수 없다.
- 직접 확인 (replicas 3, `minAvailable: 2`): ALLOWED 1 -> 첫 eviction은 성공(201), 곧바로 둘째는 `TooManyRequests: Cannot evict pod as it would violate the pod's disruption budget`, ALLOWED가 0으로 내려감. `maxUnavailable: 0`이면 처음부터 ALLOWED 0이라 전부 거부.
- 관계: `kubectl drain`은 이 eviction API를 쓰므로 PDB가 막으면 drain이 진행되지 않는다(문서 설명. 이 노트에서는 노드를 건드리지 않아 drain 자체는 실행하지 않았다). 롤링 업데이트와는 별개다.

## 예시

**상황 1: Deployment Pod는 살아나고 맨 Pod는 안 살아나는 것을 확인.**
```bash
k create deploy web --image=nginx:1.27 --replicas=3
k run bare --image=nginx:1.27
k delete pod bare --wait=false; k delete $(k get pod -l app=web -o name | head -1) --wait=false
k get pods     # web 3개 유지(새 이름 1개), bare는 없음
k get pod -l app=web -o jsonpath='{.items[0].metadata.ownerReferences[0].kind}{"\n"}'   # ReplicaSet
```

**상황 2: readiness가 항상 실패하는 Pod, liveness가 항상 실패하는 Pod를 만들고 차이를 본다 (404 경로).**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: probe-ready
  labels: {app: probe-ready}
spec:
  containers:
  - name: nginx
    image: nginx:1.27
    ports:
    - containerPort: 80
    readinessProbe:
      httpGet: {path: /nope, port: 80}
      periodSeconds: 3
---
apiVersion: v1
kind: Pod
metadata:
  name: probe-live
spec:
  containers:
  - name: nginx
    image: nginx:1.27
    livenessProbe:
      httpGet: {path: /nope, port: 80}
      initialDelaySeconds: 2
      periodSeconds: 3
      failureThreshold: 2
```
```bash
k get pod probe-ready probe-live
k describe pod probe-ready | grep -A8 ^Events
```
기대 결과: `probe-ready 0/1 Running 0`(재시작 없음, 이벤트 `Readiness probe failed: HTTP probe failed with statuscode: 404`), `probe-live`는 RESTARTS가 계속 올라가 `CrashLoopBackOff`(이벤트 `Liveness probe failed ... 404`, `Container nginx failed liveness probe, will be restarted`). readiness Pod를 Service로 묶으면 `k get endpoints`가 비고 EndpointSlice에는 주소가 있으나 `conditions: {"ready":false}`.

**상황 3: startupProbe로 15초 걸리는 기동을 보호한다.**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: probe-startup
spec:
  containers:
  - name: app
    image: busybox:1.37
    command: ["sh", "-c", "sleep 15; touch /tmp/ok; sleep 3600"]
    startupProbe:
      exec: {command: ["cat", "/tmp/ok"]}
      periodSeconds: 2
      failureThreshold: 15      # 최대 30초까지 기다림
    livenessProbe:
      exec: {command: ["cat", "/tmp/ok"]}
      periodSeconds: 2
      failureThreshold: 1
```
기대 결과: 40초 뒤 `1/1 Running`, RESTARTS 0. (startupProbe를 빼면 liveness가 먼저 실패해 재시작한다고 문서가 설명한다. 이 부분은 빼고 돌려 보지 않았다 (미확인).)

**상황 4: init 컨테이너가 Service가 생길 때까지 대기, 네이티브 사이드카가 로그를 따라간다.**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: init-demo
spec:
  initContainers:
  - name: wait-svc
    image: busybox:1.37
    command: ['sh', '-c', 'until nslookup myservice.notes-d4.svc.cluster.local; do echo waiting; sleep 2; done']
  containers:
  - name: app
    image: nginx:1.27
---
apiVersion: v1
kind: Pod
metadata:
  name: native-sidecar
spec:
  volumes:
  - name: logs
    emptyDir: {}
  initContainers:
  - name: log-shipper
    image: busybox:1.37
    restartPolicy: Always          # 이 한 줄이 사이드카로 만든다
    command: ['sh', '-c', 'touch /var/log/app.log; tail -F /var/log/app.log']
    volumeMounts:
    - name: logs
      mountPath: /var/log
  containers:
  - name: app
    image: busybox:1.37
    command: ['sh', '-c', 'while true; do date >> /var/log/app.log; sleep 2; done']
    volumeMounts:
    - name: logs
      mountPath: /var/log
```
```bash
k get pod init-demo native-sidecar          # init-demo 0/1 Init:0/1, native-sidecar 2/2 Running
k logs native-sidecar -c log-shipper --tail=2
k create svc clusterip myservice --tcp=80:80    # (네임스페이스는 YAML의 notes-d4를 본인 것으로)
k get pod init-demo                          # 몇 초 뒤 1/1 Running
```

**상황 5: DaemonSet 뼈대 만들기 + 컨트롤 플레인에도 띄우기.**
```bash
k create deploy agent --image=busybox:1.37 --dry-run=client -o yaml > ds.yaml
# kind: Deployment -> DaemonSet 로 바꾸고 replicas, strategy: {}, status: {} 줄을 지운다
vim ds.yaml
```
`spec.template.spec`에 `command: ["sleep","3600"]`과 아래를 추가:
```yaml
      tolerations:
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
```
```bash
k apply -f ds.yaml; k rollout status ds/agent; k get ds agent
```
기대 결과: toleration 전 `DESIRED 2`, 후 `DESIRED 3`. 확인한 업데이트 전략: `{"rollingUpdate":{"maxSurge":0,"maxUnavailable":1},"type":"RollingUpdate"}`. 이 뼈대 변환(kind만 바꾸고 3줄 삭제)은 `--dry-run=server`로 통과를 확인했다.

**상황 6: StatefulSet + headless Service, 카나리 업데이트.**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  clusterIP: None
  selector: {app: db}
  ports:
  - {port: 80, name: web}
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db
  replicas: 2
  selector:
    matchLabels: {app: db}
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Delete
    whenScaled: Retain
  template:
    metadata:
      labels: {app: db}
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        volumeMounts:
        - {name: data, mountPath: /data}
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 100Mi
```
```bash
k rollout status sts/db; k get pod,pvc          # db-0, db-1, data-db-0, data-db-1 (Bound)
k patch sts db --type=merge -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":1}}}}'
k set image sts/db nginx=nginx:1.26
k get pods -l app=db -o 'custom-columns=NAME:.metadata.name,IMAGE:.spec.containers[0].image'
```
기대 결과: `db-0 nginx:1.27`, `db-1 nginx:1.26`. (`Warning: spec.SessionAffinity is ignored for headless services`는 무시해도 된다.)

**상황 7: Job, 실패 Job, CronJob 수동 실행.**
```bash
k create job fail --image=busybox:1.37 --dry-run=client -o yaml -- sh -c 'exit 1' > job.yaml   # spec 아래에 backoffLimit: 1 추가
k apply -f job.yaml; k get job fail             # 약 30초 뒤 STATUS Failed, 0/1
k get job fail -o jsonpath='{.status.conditions[*].reason}{"\n"}'     # BackoffLimitExceeded
k create cronjob hello --image=busybox:1.37 --schedule='*/1 * * * *' -- sh -c 'date; echo hello'
k create job manual-run --from=cronjob/hello; k logs job/manual-run
k patch cj hello -p '{"spec":{"suspend":true,"concurrencyPolicy":"Forbid"}}'; k get cj hello
```
`completions: 3`, `parallelism: 2`, `backoffLimit: 2`, `activeDeadlineSeconds: 120`, `ttlSecondsAfterFinished: 60`을 `spec`에 넣은 Job은 15초 만에 `Complete 3/3`이 됐다 (Pod는 `restartPolicy: Never`).

**상황 8: PDB 만들고 eviction이 막히는지 본다.**
```bash
k create pdb web-pdb --selector=app=web --min-available=2
k get pdb web-pdb                 # MIN AVAILABLE 2, ALLOWED DISRUPTIONS 1 (replicas 3일 때)
P=$(k get pod -l app=web -o name | head -1 | cut -d/ -f2)
printf '{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"%s","namespace":"<ns>"}}' $P | k create --raw /api/v1/namespaces/<ns>/pods/$P/eviction -f -
```
첫 번째는 `"status":"Success","code":201`, 연달아 다른 Pod에 하면 `Error from server (TooManyRequests): Cannot evict pod as it would violate the pod's disruption budget.` PDB를 `--max-unavailable=0`으로 만들면 처음부터 같은 거부.

## 자주 틀리는 점
- 증상: Pod가 `0/1 Running`인데 재시작이 없고 Service Endpoints가 빈다 -> readinessProbe 실패 (`describe`의 `Readiness probe failed`) -> 프로브 `path`/`port`를 앱에 맞게 고친다.
- 증상: RESTARTS가 계속 올라가고 `CrashLoopBackOff`인데 앱 로그는 정상 -> livenessProbe가 너무 일찍/엄격하게 실패 (`Liveness probe failed`) -> `initialDelaySeconds`/`failureThreshold`를 늘리거나 `startupProbe`를 쓴다.
- 증상: init 컨테이너가 `Init:0/1`에서 안 끝남. 로그에는 이름을 찾았다고 나옴 -> busybox `nslookup <짧은이름>`의 종료 코드 문제 -> FQDN으로 조회 (직접 겪음).
- 증상: Job을 `restartPolicy: Always`로 쓰니 거부됨 -> Job/CronJob은 `OnFailure`/`Never`만 허용 (확인함).
- 증상: Job이 `Failed 0/1`, 이벤트 `BackoffLimitExceeded` -> 컨테이너가 계속 실패해 `backoffLimit`(기본 6, 이 노트에서는 1로 설정) 초과 -> `k logs job/<name>`으로 원인을 먼저 본다.
- 증상: DaemonSet이 컨트롤 플레인에는 안 뜬다 -> `NoSchedule` taint -> toleration 추가 (확인함: DESIRED 2 -> 3).
- 증상: StatefulSet이 만들어졌는데 Pod가 안 뜸/DNS가 없음 -> headless Service가 없거나 `serviceName`이 다르다. 이 Service는 `clusterIP: None`이어야 한다.
- 증상: `partition`을 줬는데 아무것도 안 바뀐 것 같다 -> ordinal이 partition 미만인 Pod는 일부러 안 바뀐다. 전체 적용은 `partition: 0`.
- 증상: 사이드카를 `containers`에 넣었더니 메인이 끝난 뒤 Pod가 `NotReady`로 남음 -> 네이티브 사이드카(`initContainers` + `restartPolicy: Always`)로 옮긴다. 네이티브 사이드카를 쓰는 Job에서 사이드카가 SIGTERM을 무시(`sleep` 셸)하면 Job 완료까지 기본 종료 대기 30초가 더 걸렸다 (Job은 결국 `Complete`).
- 증상: `drain`이 멈춤/`Cannot evict pod ... disruption budget` -> PDB의 `ALLOWED DISRUPTIONS`가 0 (`k get pdb -A`) -> replicas를 늘려 여유를 만들거나 PDB 값을 완화.
- 증상: `minAvailable`과 `maxUnavailable`을 둘 다 씀 -> 하나만 쓴다 (문서 `Specifying a PodDisruptionBudget`의 두 블록이 각각 하나씩 사용).
- 시뮬레이터 차이 (2026-10-19 관측): 클러스터 v1.34.0(시험 v1.37). 한때 `k8s-worker2`의 CNI 설정 대역이 노드 podCIDR와 어긋나 그 노드 Pod의 DNS/노드 간 통신이 실패한 적이 있다(랩 고장, 시험과 무관, 수정됨). 같은 증상이 다시 나오면 `kubectl --context k8s -n kube-system delete pod -l app=kindnet --field-selector spec.nodeName=k8s-worker2`로 kindnet을 재생성하거나 `bin/sim doctor`로 점검한다.

## 빠르게 푸는 순서
1. (30초) 컨텍스트/네임스페이스 확인. 문제가 "새로 만들기"인지 "고치기"인지, **지우지 말라/이름 유지** 같은 조건을 읽는다.
2. (1분) 뼈대: Deployment/Job/CronJob/PDB는 `k create ... --dry-run=client -o yaml > x.yaml`. DaemonSet은 Deployment 뼈대에서 `kind`를 바꾸고 3줄 삭제. StatefulSet/프로브/사이드카는 문서 블록을 복사한다.
3. (2분) 문서 블록을 붙이고 이름, 이미지, 라벨 3곳(`selector.matchLabels` = `template.labels`)을 맞춘다. StatefulSet은 headless Service와 `serviceName`을 같이 챙긴다.
4. (30초) `k apply -f x.yaml --dry-run=server`로 필드 오타를 먼저 걸러낸 뒤 `k apply -f x.yaml`.
5. (30초) 상태 확인: `k get pod -w`로 READY/STATUS, 프로브는 `k describe pod`의 Events, StatefulSet은 `k get pod,pvc`, PDB는 `k get pdb`의 ALLOWED.
6. (1분) 안 뜨면 이벤트부터: `Init:` 접두는 init 로그(`-c`), `0/1 Running`은 readiness, 재시작 증가는 liveness/종료 코드(`k logs --previous`).
7. (총 5~7분 목표) 마지막으로 요구 조건(이름, 개수, `partition` 값, `suspend`)을 `-o yaml | grep`으로 대조.
