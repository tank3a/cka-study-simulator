# B1. Manage role based access control (RBAC)

## 이 항목에서 공부할 것
- [ ] `k create role` / `k create rolebinding`으로 네임스페이스 권한을 만들고, 규칙이 둘 이상이면 YAML로 마무리한다
- [ ] ServiceAccount를 만들어 기존 Deployment에 `k set serviceaccount`로 붙인다 (Deployment를 지우지 않는다)
- [ ] ClusterRole + RoleBinding(한 네임스페이스만)과 ClusterRole + ClusterRoleBinding(클러스터 전체)을 구분해서 만든다
- [ ] 그룹(`--group`), 사용자(`--user`), non-resource URL(`/metrics`)에 권한을 준다
- [ ] `k auth can-i <verb> <resource> -n <ns> --as=system:serviceaccount:<ns>:<sa>`로 yes/no를 확인하고 `--list`로 전체 권한을 본다
- [ ] 과한 ClusterRoleBinding을 찾아(`k get clusterrolebinding -o wide`) 지우고 최소 권한으로 다시 준다
- [ ] 잘못 만든 binding의 `roleRef`는 못 고친다는 걸 알고 삭제 후 재생성한다
- [ ] CSR로 사용자 인증서를 발급·승인하고, 인증서가 박힌(embed) kubeconfig를 직접 만든다

## 개념 설명

### Role / ClusterRole
- 무엇: "무엇을 해도 되는가"를 적은 허용 목록. 거부 규칙은 없고 허용만 더한다.
- 왜: 사람/Pod가 API를 부를 때 기본은 전부 금지이기 때문에, 필요한 만큼만 열어 주는 도구가 필요하다.
- 핵심 필드: `rules[].apiGroups`(코어 그룹은 `""`), `resources`, `verbs`, 선택적으로 `resourceNames`, `nonResourceURLs`.
- Role은 한 네임스페이스 안의 리소스만, ClusterRole은 (1) 노드·PV 같은 클러스터 범위 리소스, (2) `/metrics` 같은 non-resource URL, (3) 여러 네임스페이스에 재사용할 권한 정의에 쓴다.
- 서브리소스는 슬래시로 따로 적는다: `pods/log`. `pods`만 적으면 로그는 열리지 않는다.
- 비유: Role은 "회의실 A 열쇠 목록", ClusterRole은 "건물 전체에서 쓸 수 있는 열쇠 목록의 견본".

### RoleBinding / ClusterRoleBinding
- 무엇: 위 목록(role)을 사람(subject)에게 붙이는 연결. subject는 `User`, `Group`, `ServiceAccount`.
- 범위는 "binding의 종류"가 결정한다 (표). 실수가 가장 많은 부분이다.

| 만들 것 | 가리키는 role | 효과 범위 |
|---|---|---|
| RoleBinding | Role | binding이 있는 네임스페이스 |
| RoleBinding | ClusterRole | binding이 있는 네임스페이스 한 곳만 (권한 정의는 재사용) |
| ClusterRoleBinding | ClusterRole | 모든 네임스페이스 + 클러스터 범위 리소스 |

- `roleRef`(어떤 role을 가리키는지)는 만든 뒤 수정할 수 없다. 바꾸려면 지우고 다시 만든다.
- 가리키는 role이 아직 없어도 binding은 만들어진다 (오타를 알려주지 않는다).

### ServiceAccount
- 무엇: Pod가 API를 부를 때 쓰는 계정. 네임스페이스에 속한다. 사용자 이름은 `system:serviceaccount:<ns>:<name>`.
- Pod에 `spec.serviceAccountName`이 없으면 그 네임스페이스의 `default` 계정을 쓴다.
- 최근 버전에서는 SA를 만들어도 토큰 Secret이 자동으로 생기지 않는다 (직접 확인: `k get secret`이 비어 있음). 토큰이 필요하면 `k create token <sa>`.
- binding의 subject에서는 `namespace`가 필수다. 다른 네임스페이스의 같은 이름 SA는 다른 계정이다.

### User / Group (인증서 기반)
- Kubernetes에는 User 오브젝트가 없다. 클라이언트 인증서의 CN이 사용자 이름, O가 그룹 이름이 된다 (`k auth whoami`로 확인 가능).
- 새 사용자는 "키 생성 -> CSR 생성 -> CertificateSigningRequest 오브젝트 -> approve -> 인증서 추출 -> kubeconfig에 embed" 순서다.
- 인증서가 있어도 RoleBinding이 없으면 아무것도 못 한다. 인증은 "누구냐", RBAC는 "무엇을 해도 되냐".

### k auth can-i
- 현재 사용자(또는 `--as` 로 흉내 낸 사용자)가 특정 동작을 할 수 있는지 서버에 물어 `yes`/`no`로 답한다.
- `--as`, `--as-group`, `-n`, `--subresource`, `--list`를 쓴다. `-n`을 빼면 현재 컨텍스트의 기본 네임스페이스(보통 default)를 검사한다.

## 예시

**상황 1: 네임스페이스 `dev`에 SA `ci-deployer`를 만들고, deployments 변경 + pods 조회 + pods/log 읽기만 허용한 뒤 기존 Deployment `pipeline`에 붙인다.**
```bash
k create ns dev
k -n dev create sa ci-deployer
k -n dev create deploy pipeline --image=nginx:1.27      # 시험에서는 이미 있음
cat <<'EOF' | k apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deploy-manager
  namespace: dev
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get","list","watch","create","update","patch"]
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get","list"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get"]
EOF
k -n dev create rolebinding ci-deployer-binding --role=deploy-manager --serviceaccount=dev:ci-deployer
k -n dev set serviceaccount deploy/pipeline ci-deployer
```
확인:
```bash
SA=system:serviceaccount:dev:ci-deployer
k auth can-i list pods -n dev --as=$SA                   # yes
k auth can-i get pods/log -n dev --as=$SA                # yes
k auth can-i delete deployments -n dev --as=$SA          # no
k auth can-i get secrets -n dev --as=$SA                 # no
k auth can-i list pods -n default --as=$SA               # no (다른 네임스페이스)
k -n dev get pods -o custom-columns=NAME:.metadata.name,SA:.spec.serviceAccountName   # 새 Pod는 ci-deployer
```
`k create role ... --verb=get,list --resource=pods,pods/log`처럼 한 줄로 만들면 두 리소스가 같은 verb를 공유한다. verb가 다른 규칙이 섞이면 위처럼 YAML로 쓰거나 `--dry-run=client -o yaml`로 뼈대를 뽑아 규칙을 이어 붙인다. (`--resource=deployments`만 써도 apiGroups가 `apps`로 채워지는 것을 확인했다.)

**상황 2: 그룹에게 클러스터 전체 조회, SA에게는 한 네임스페이스에서만 수정, 사용자에게 `/metrics` 읽기를 준다.**
```bash
k create clusterrole ns-lister --verb=get,list,watch --resource=namespaces
k create clusterrolebinding ns-lister --clusterrole=ns-lister --group=ops-audit

k create clusterrole cm-editor --verb=get,list,watch,update,patch --resource=configmaps
k -n dev create rolebinding cm-editor --clusterrole=cm-editor --serviceaccount=dev:ci-deployer   # RoleBinding이 ClusterRole을 참조

k create clusterrole metrics-reader --verb=get --non-resource-url=/metrics
k create clusterrolebinding metrics-reader --clusterrole=metrics-reader --user=monitor
```
확인:
```bash
k auth can-i list namespaces --as=anyone --as-group=ops-audit                          # yes
k auth can-i update configmaps -n dev --as=system:serviceaccount:dev:ci-deployer        # yes
k auth can-i update configmaps -n default --as=system:serviceaccount:dev:ci-deployer    # no
k auth can-i get /metrics --as=monitor                                                  # yes
```

**상황 3: SA `reporter`(네임스페이스 `audit`)가 가진 ClusterRoleBinding을 찾아 지우고 최소 권한만 다시 준다.**
```bash
k get clusterrolebinding -o wide | grep -E 'NAME|audit/reporter'    # SERVICEACCOUNTS 열이 "<ns>/<name>"
k get clusterrolebinding -o wide | grep audit/reporter | awk '{print $1}' | sort > /tmp/bindings.txt   # 이름만 파일로
k delete clusterrolebinding $(cat /tmp/bindings.txt)
k -n audit create role reporter-read --verb=get,list,watch --resource=pods,services
k -n audit create rolebinding reporter-read --role=reporter-read --serviceaccount=audit:reporter
k create clusterrole reporter-nodes --verb=get,list --resource=nodes
k create clusterrolebinding reporter-nodes --clusterrole=reporter-nodes --serviceaccount=audit:reporter
```
확인:
```bash
k auth can-i list nodes --as=system:serviceaccount:audit:reporter                  # yes
k auth can-i get secrets -n audit --as=system:serviceaccount:audit:reporter         # no
k auth can-i --list -n audit --as=system:serviceaccount:audit:reporter | head       # 실제 가진 권한 표
```
RoleBinding 쪽도 훑으려면 `k get rolebinding -A -o wide`. 노드는 클러스터 범위 리소스라 Role이 아니라 ClusterRole + ClusterRoleBinding이 필요하다. `jq`는 [TIPS]의 호스트 도구 목록(kubectl, yq, curl, wget, man)에 없어서 위처럼 `-o wide`와 grep으로 푸는 편이 안전하다 (jq 설치 여부는 미확인).

**상황 4: 새 개발자 `dana`의 인증서를 발급하고(하루짜리), `dev`에서 읽기만 허용하고, 그 인증서로 쓰는 kubeconfig를 만든다.**
```bash
openssl genrsa -out dana.key 2048
openssl req -new -key dana.key -subj "/CN=dana/O=devs" -out dana.csr
cat <<EOF | k apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: dana
spec:
  request: $(cat dana.csr | base64 | tr -d "\n")
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages:
  - client auth
EOF
k certificate approve dana
k get csr dana -o jsonpath='{.status.certificate}' | base64 -d > dana.crt
k -n dev create rolebinding dana-view --clusterrole=view --user=dana

# 현재 kubeconfig에서 서버 주소와 CA를 그대로 가져와 새 파일에 embed
SERVER=$(k config view --minify --raw -o jsonpath='{.clusters[0].cluster.server}')
k config view --minify --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > ca.crt
U=dana.kubeconfig
k config set-cluster mycluster --server="$SERVER" --certificate-authority=ca.crt --embed-certs=true --kubeconfig=$U
k config set-credentials dana --client-certificate=dana.crt --client-key=dana.key --embed-certs=true --kubeconfig=$U
k config set-context dana@mycluster --cluster=mycluster --user=dana --namespace=dev --kubeconfig=$U
k config use-context dana@mycluster --kubeconfig=$U
```
확인:
```bash
k get csr dana                                   # CONDITION이 Approved,Issued
openssl x509 -in dana.crt -noout -subject -dates # subject=O = devs, CN = dana (OpenSSL 3 표기) / notAfter가 하루 뒤
k --kubeconfig=$U auth whoami                    # Username dana, Groups [devs system:authenticated]
k --kubeconfig=$U get pods                       # dev의 Pod 목록
k --kubeconfig=$U auth can-i delete pods         # no
k --kubeconfig=$U get pods -n default            # Forbidden: User "dana" cannot list resource "pods" ... namespace "default"
```
(k는 `kubectl` 별칭이다. 위 명령들은 같은 형태로 `notes-b1` 네임스페이스와 임시 이름의 CSR/ClusterRole로 실제 실행해 확인했고, 끝난 뒤 모두 지웠다.)

시뮬레이터 차이: 시뮬레이터 서버는 v1.34.0이고 시험은 v1.37이다. RBAC 동작 차이는 보지 못했지만 버전 차이는 있다. 시험 호스트에서는 `base64 -w0`도 되지만, 위의 `base64 | tr -d "\n"`가 공식 문서와 같은 형태라 어디서나 된다.

## 공식 문서에서 찾는 법
허용 사이트만 쓴다. 검색창 결과 순위는 직접 확인하지 못했다(미확인). 안 나오면 아래 URL 경로를 주소창에 직접 쓴다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| Role YAML 뼈대 | `RBAC authorization` | https://kubernetes.io/docs/reference/access-authn-authz/rbac/ | `Role example` | `access/simple-role.yaml` 블록 (pod-reader) |
| RoleBinding / ClusterRoleBinding YAML | 위와 같음 | 위와 같음 | `RoleBinding examples`, `ClusterRoleBinding example` | `simple-rolebinding-with-role.yaml` 등 subjects/roleRef 블록 |
| imperative 명령 모음 | 위와 같음 | 위와 같음 | `Command-line utilities` 뒤 `kubectl create role` | 페이지의 `kubectl create role/clusterrole/rolebinding/clusterrolebinding` 예제 줄 |
| `pods/log` 같은 서브리소스 | 위와 같음 | 위와 같음 | `Referring to resources` | `pod-and-pod-logs-reader` Role 블록 |
| non-resource URL(`/healthz`, `/metrics`) | 위와 같음 | 위와 같음 | `nonResourceURLs` | `nonResourceURLs: ["/healthz", "/healthz/*"]` 규칙 |
| can-i 사용법, SA를 `--as`로 흉내 | `authorization can-i` | https://kubernetes.io/docs/reference/access-authn-authz/authorization/ (※) | `Checking API access` | `kubectl auth can-i list pods --namespace target --as system:serviceaccount:dev:dev-sa` |
| SA와 토큰 | `service accounts admin` | https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/ | `kubectl create token` | `kubectl create token my-sa ...` 줄 |
| CSR 발급 전 과정 | `certificate issue client csr` | https://kubernetes.io/docs/tasks/tls/certificate-issue-client-csr/ (※) | `Create a Kubernetes CertificateSigningRequest` | `kind: CertificateSigningRequest` YAML 블록 (signerName, expirationSeconds, usages) |
| approve / 인증서 추출 | 위와 같음 | 위와 같음 | `Approve the CertificateSigningRequest`, `Get the certificate` | `kubectl certificate approve ...`, `jsonpath='{.status.certificate}'` 줄 |
| kubeconfig에 사용자 추가 | 위와 같음 | 위와 같음 | `Configure the certificate into kubeconfig` | `set-credentials ... --embed-certs=true`, `set-context` 줄 |
| set-cluster 형태 확인 | `configure access multiple clusters` | https://kubernetes.io/docs/tasks/access-application-cluster/configure-access-multiple-clusters/ (※) | `Define clusters, users, and contexts` | `kubectl config ... set-cluster` 줄 |

(※) `official.md`/`study-guide.md` 목록에는 없는 kubernetes.io/docs 페이지다. 2026-10-19에 curl로 HTTP 200을 확인했다.
RBAC 페이지의 YAML 예제는 "Role and ClusterRole" 절의 `Role example`/`ClusterRole example`, "RoleBinding and ClusterRoleBinding" 절의 `RoleBinding examples`/`ClusterRoleBinding example`에 있다. 같은 문서의 `Referring to subjects` 절에는 `system:serviceaccount:`(단수)와 `system:serviceaccounts:`(복수) 접두사 설명이 있다.

## 자주 틀리는 점
- 증상: `error: serviceaccount must be <namespace>:<name>` -> 원인: `--serviceaccount=ci-deployer`처럼 이름만 줬다 -> `--serviceaccount=dev:ci-deployer`.
- 증상: 분명히 권한을 줬는데 `can-i`가 `no` -> 원인: `-n`을 빼서 default 네임스페이스를 검사했거나, `--as`를 `system:serviceaccount:<ns>:<name>` 형식으로 쓰지 않았다 -> `-n`과 `--as` 형식을 먼저 확인한다.
- 증상: "한 네임스페이스에서만"인데 다른 네임스페이스에서도 된다 -> 원인: ClusterRoleBinding을 썼다 (ClusterRoleBinding + `view`로 default, kube-system 모두 `yes`가 나오는 것을 확인) -> 지우고 RoleBinding으로 다시 만든다 (ClusterRole은 그대로 참조 가능).
- 증상: `The Role ... is invalid: ... namespaced rules cannot apply to non-resource URLs` -> 원인: `/metrics` 같은 non-resource URL을 Role에 넣었다 -> ClusterRole + ClusterRoleBinding.
- 증상: `cannot change roleRef` -> 원인: 기존 binding의 role을 patch/edit로 바꾸려 했다 -> `k delete rolebinding ...` 후 다시 만든다.
- 증상: `Warning: 'gett' is not a standard resource verb`인데 Role이 만들어졌다 -> 원인: verb 오타는 경고만 하고 통과한다 -> 만든 뒤 `can-i`로 반드시 확인한다. 존재하지 않는 리소스(`podz`)는 `the server doesn't have a resource type`으로 막힌다.
- 증상: `pods/log`를 읽지 못한다 -> 원인: `resources`에 `pods`만 적었다 -> `pods/log`를 별도 항목으로 추가한다.
- 증상: 이름이 같은 SA를 잘못 건드렸다 (예: `audit/reporter` 와 `other/reporter`) -> 원인: 바인딩 목록에서 네임스페이스를 보지 않았다 -> `k get clusterrolebinding -o wide`의 `SERVICEACCOUNTS` 열 `<ns>/<name>`를 끝까지 본다. 문제에 "다른 팀 것은 건드리지 말 것"이 있으면 특히 주의.
- 증상: SA를 바꿨는데 Pod가 여전히 `default` -> 원인: Pod는 생성 시점의 SA를 쓴다 -> `k set serviceaccount deploy/x sa`는 롤아웃을 일으키므로 `k rollout status` 후 새 Pod에서 확인한다 (한동안 이전 Pod가 같이 보일 수 있다).
- 증상: CSR을 approve했는데 `dana.crt`가 비어 있다 -> 원인: `signerName`/`usages`가 틀려 발급이 안 됐거나 approve 전에 추출했다 -> `k get csr`에서 `Approved,Issued`인지 본다.
- 증상: 다른 곳에서 쓰는 kubeconfig가 동작하지 않는다 -> 원인: `--embed-certs=true`를 빼서 파일 경로만 저장됐다 (`k config view`가 `DATA+OMITTED`로 보이는 것은 정상, 데이터가 들어 있다는 뜻) -> 다시 만든다. 현재 kubeconfig에서 CA를 뽑을 때는 `--minify --raw` 둘 다 필요하다.

## 빠르게 푸는 순서
1. 문제의 컨텍스트/네임스페이스/요구 이름(Role, Binding, SA)을 메모한다. "와일드카드 금지", "다른 네임스페이스 금지" 같은 금지 조건을 먼저 찾는다. (30초)
2. SA가 필요하면 `k create sa`. 리소스가 `apps` 소속인지 헷갈리면 `k api-resources | grep <이름>`으로 그룹 확인. (30초)
3. 규칙이 하나면 `k create role/clusterrole ...`, 둘 이상이면 문서의 `Role example`을 복사해 YAML로 쓴다. (1~2분)
4. `k create rolebinding/clusterrolebinding`에서 범위를 결정한다: 한 네임스페이스면 RoleBinding, 전체면 ClusterRoleBinding. SA는 `ns:name`. (30초)
5. 기존 Deployment에 붙이는 문제면 `k set serviceaccount deploy/x <sa>`, 새 Pod가 뜰 때까지 `k rollout status`. (30초)
6. `k auth can-i`로 "되어야 하는 것"과 "안 되어야 하는 것"을 둘 다 확인하고, 답 파일을 요구하면 출력만 정확히 리다이렉트한다. (1분)
7. 감사형 문제는 `k get clusterrolebinding -o wide | grep <ns>/<sa>`로 찾고 지우기 전에 이름을 파일에 먼저 저장한다. (1분)
8. 인증서/kubeconfig 문제는 `certificate-issue-client-csr` 페이지를 열어 CSR YAML만 복사한다. 목표 총 5~6분.
