# A1. Troubleshoot clusters and nodes

## 이 항목에서 공부할 것
- [ ] `k get nodes`, `k describe node <n>`에서 `Ready` 상태, Conditions(`MemoryPressure`/`DiskPressure`/`PIDPressure`), Taints, Lease를 읽고 "노드 문제인지 아닌지"를 1분 안에 판단한다
- [ ] `ssh <노드>` -> `sudo -i` 후 `systemctl status kubelet`, `systemctl is-enabled kubelet`, `journalctl -u kubelet -n 50 --no-pager`로 kubelet이 죽은 이유(정지/비활성/설정 오류)를 찾는다
- [ ] kubelet 설정 위치(`systemctl cat kubelet` -> drop-in -> `/var/lib/kubelet/config.yaml`, `kubeadm-flags.env`, `/etc/kubernetes/kubelet.conf`)를 따라가 잘못된 경로/오타를 고친다
- [ ] 고친 뒤 `systemctl daemon-reload`(unit/drop-in을 바꿨을 때), `systemctl restart kubelet`, `systemctl enable --now kubelet` 중 무엇이 필요한지 구분하고, 다시 `journalctl`로 두 번째 오류가 없는지 확인한다
- [ ] 컨테이너 런타임 상태를 `systemctl status containerd`, `crictl ps -a`, `crictl pods`, `crictl logs <id>`로 확인한다 (`crictl`의 endpoint 지정 방법 포함)
- [ ] 로그/상태를 `exit`로 `base`로 돌아온 뒤 `k get nodes`에서 `Ready`가 되는지 확인한다 (잘못된 노드에 남아 있지 않기)
- [ ] ssh가 막힌 상황의 대안으로 `k debug node/<n>`을 쓸 수 있다

## 개념 설명

### Node 객체와 Ready 상태
- 무엇: 노드마다 있는 API 객체. kubelet이 주기적으로 상태를 보고하고, 그 결과가 `k describe node`의 Conditions에 나온다.
- 핵심 필드: `Ready`(True/False/Unknown), `MemoryPressure`, `DiskPressure`, `PIDPressure`. `Unknown`은 "kubelet이 보고를 안 한다"는 뜻이라 보통 kubelet이 죽었거나 API 서버에 못 닿는 경우다.
- 하트비트 두 가지 (문서): 노드 `.status` 업데이트와 `kube-node-lease` 네임스페이스의 노드 Lease. 이 클러스터에서 `k get lease -n kube-node-lease`에 노드 3개의 Lease가 있다 (확인함).
- NotReady 이후 (문서): 노드 컨트롤러가 `Ready`를 `Unknown`으로 바꾸고 `node.kubernetes.io/unreachable` taint를 붙이며(NoSchedule, NoExecute), 기본 5분 뒤 그 노드의 Pod를 evict한다. 그래서 "새 Pod가 그 노드에 안 뜬다"는 증상도 결국 노드 문제다.
- 관계: Pod가 Pending/Terminating에서 안 움직일 때 원인이 노드 쪽이면 A1, 컨트롤 플레인이면 A2, Service면 A5.

### kubelet (노드의 에이전트)
- 무엇: 각 노드에서 systemd 서비스로 도는 프로세스. API 서버와 통신해 Pod를 실제로 띄우고, 노드 상태를 보고하고, static Pod 매니페스트 디렉터리를 감시한다.
- 왜 중요한가: kubelet이 죽으면 노드가 `NotReady`가 된다. 시험에서 가장 흔한 노드 문제다.
- 파일 위치는 `systemctl cat kubelet`으로 따라간다 (확인함, 이 랩의 kubeadm 구조):

| 무엇 | 경로 (이 랩에서 확인) |
|---|---|
| unit 파일 | `systemctl cat kubelet`의 첫 줄 주석에 실제 경로가 나온다 (이 랩: `/etc/systemd/system/kubelet.service`) |
| drop-in | `/etc/systemd/system/kubelet.service.d/10-kubeadm.conf` (여기서 아래 세 파일을 가리킨다) |
| 설정 파일 | `/var/lib/kubelet/config.yaml` (`--config=`) |
| 추가 플래그 | `/var/lib/kubelet/kubeadm-flags.env` (`KUBELET_KUBEADM_ARGS`), 마지막 수단 `/etc/default/kubelet` |
| API 서버 접속 정보 | `/etc/kubernetes/kubelet.conf` (`--kubeconfig=`) |
| 클라이언트 CA | `/etc/kubernetes/pki/ca.crt` (config.yaml의 `authentication.x509.clientCAFile`) |
| static Pod 디렉터리 | `/etc/kubernetes/manifests` (config.yaml의 `staticPodPath`) |
| 런타임 소켓 | `/run/containerd/containerd.sock` (config.yaml의 `containerRuntimeEndpoint`) |

- 이 랩에서 config.yaml의 주요 키: `cgroupDriver: systemd`, `clusterDNS`, `staticPodPath`, `containerRuntimeEndpoint`, `authentication.x509.clientCAFile`. 이 중 경로를 가리키는 키(`clientCAFile`, `containerRuntimeEndpoint`, `staticPodPath`)가 오타 단골이다.
- 실행 중인 kubelet의 실제 설정은 `k get --raw "/api/v1/nodes/<n>/proxy/configz"`로도 볼 수 있다 (확인함; 문서의 `kubectl proxy` + curl 방식과 같은 API).
- 시뮬레이터 차이: kind 노드는 컨테이너라 unit 경로(`/etc/systemd/system/...`)와 `kubelet.service`의 `ConditionPathExists=/var/lib/kubelet/config.yaml` 같은 kind 전용 줄이 있다. 시험 노드는 일반 VM이다.

### 컨테이너 런타임 (containerd) 와 crictl
- 무엇: kubelet이 실제 컨테이너를 만들 때 쓰는 런타임. 이 랩과 시험 모두 containerd(소켓 `/run/containerd/containerd.sock`). `systemctl status containerd`로 상태를 본다.
- `crictl`: 런타임에 직접 묻는 CLI. `k`가 안 될 때(API 서버가 죽었을 때)도 노드에서 된다. 자주 쓰는 것: `crictl ps -a`(종료된 것 포함), `crictl pods`, `crictl logs <id>`, `crictl images`, `crictl inspect <id>`, `crictl stats`.
- endpoint 지정 (문서): `--runtime-endpoint` 플래그, `CONTAINER_RUNTIME_ENDPOINT` 환경변수, `/etc/crictl.yaml` 중 하나. 이 랩의 `/etc/crictl.yaml`은 `runtime-endpoint: unix:///run/containerd/containerd.sock`. 소켓 철자를 틀리면 `level=fatal msg="validate service connection: validate CRI v1 runtime API for endpoint ..."`가 나온다 (확인함).
- `crictl ps -a`의 `ATTEMPT` 열이 재시작 횟수, `STATE`가 `Exited`인 이전 컨테이너도 남아 있어 직전 실패 로그를 볼 수 있다.

### 진단 도구 모음
- `systemctl status <svc>`: 활성 상태, 최근 로그 몇 줄. `is-active`/`is-enabled`는 한 단어 결과.
- `journalctl -u kubelet -n 50 --no-pager`(최근 50줄), `-f`(실시간), `-p err`(오류만), `--since "-1 min"`. 첫 번째 오류가 보통 원인이다.
- kubelet 자체 상태: 노드에서 `curl -s localhost:10248/healthz`가 `ok` (확인함). 이 랩에서 kubelet은 10250(API)과 10248(healthz)을 연다.
- 자원: `df -h /`, `free -m`. `DiskPressure`/`MemoryPressure` Condition이 True면 먼저 본다.
- 노드에 못 들어갈 때: `k debug node/<n> --image=busybox:1.37 -- sleep 120`은 그 노드에 디버그 Pod를 만들고 호스트 루트를 `/host`에 마운트한다 (확인함: `/host/etc/kubernetes`, `/host/var/lib/kubelet/config.yaml`을 읽을 수 있었다. 이 Pod는 hostPID/hostNetwork가 켜지고, 끝나면 직접 `k delete pod`). systemctl/journalctl은 쓸 수 없다. 시험은 `ssh`가 기본이다.

## 예시
(노드 안 명령은 `ssh <노드>` 후 `sudo -i`에서 실행. 이 노트는 노드를 고장내지 않았으므로 "읽기 전용 점검"은 실제로 실행해 확인했고, "복구 절차"는 시뮬레이터 해설(q37, q38)을 따른 것이라 실행해 확인하지 못했다.)

**상황 1: 어느 노드가 문제인지 찾고 원인을 좁힌다 (읽기 전용, 실행 확인).**
```bash
k get nodes
k describe node k8s-worker | sed -n '/^Taints/p;/^Unschedulable/p;/Conditions:/,/Addresses:/p'
k get lease -n kube-node-lease
```
정상일 때 기대 결과: 모든 노드 `Ready`, `Taints: <none>`(컨트롤 플레인은 `node-role.kubernetes.io/control-plane:NoSchedule`), Conditions의 `Ready True KubeletReady kubelet is posting ready status`, 세 Pressure는 `False`. 문제 노드는 `Ready`가 `Unknown`이고 Taints에 `node.kubernetes.io/unreachable`가 붙는다 (문서 예제).

**상황 2: 노드에 들어가 kubelet과 런타임을 확인한다 (읽기 전용, 실행 확인).**
```bash
ssh k8s-node1          # 시험: ssh <문제에 적힌 노드>
sudo -i
systemctl is-active kubelet containerd        # active / active
systemctl is-enabled kubelet                  # enabled  (재부팅 후에도 올라오는지)
journalctl -u kubelet -n 5 --no-pager
journalctl -u kubelet -p err --no-pager -n 3  # 오류만
curl -s localhost:10248/healthz; echo         # ok
crictl ps | head -5
df -h / | tail -1; free -m | head -2
exit                                          # base로 복귀, 필수
```
정상일 때 `journalctl -p err`는 `-- No entries --`. 실제로는 부팅 직후 API 서버가 아직 안 떴을 때 이런 줄이 기록돼 있었다: `"Unable to register node with API server" err="Post \"https://k8s-control-plane:6443/api/v1/nodes\": dial tcp 172.18.0.3:6443: connect: connection refused"`. 이 문구는 **kubelet 문제가 아니라 API 서버에 못 닿는다**는 뜻이라 컨트롤 플레인(A2)을 본다.

**상황 3: kubelet 설정 경로를 따라간다 (읽기 전용, 실행 확인).**
```bash
systemctl cat kubelet | grep -E 'ExecStart|EnvironmentFile|Environment='
cat /var/lib/kubelet/kubeadm-flags.env
grep -nE 'clientCAFile|containerRuntimeEndpoint|staticPodPath|cgroupDriver' /var/lib/kubelet/config.yaml
ls /etc/kubernetes/pki/ca.crt /run/containerd/containerd.sock     # 설정이 가리키는 파일이 실제 있는지
```
기대 결과 (이 랩): `clientCAFile: /etc/kubernetes/pki/ca.crt`, `containerRuntimeEndpoint: unix:///run/containerd/containerd.sock`, `staticPodPath: /etc/kubernetes/manifests`, 두 `ls`가 파일을 보여 준다. 설정이 가리키는 경로에 `ls`가 `No such file`이면 그것이 원인이다.

**상황 4: kubelet이 정지/비활성인 경우의 복구 절차 (q37 해설 기준) (미확인).**
```bash
systemctl status kubelet                 # inactive (dead), disabled 이면 사람이 stop/disable 한 것
systemctl enable --now kubelet           # enable = 재부팅 후에도 유지, --now = 즉시 시작
systemctl is-active kubelet; systemctl is-enabled kubelet
exit; k get nodes                        # 30~60초 안에 Ready
```
`systemctl start`만 하면 재부팅 후 다시 죽는다. 문제에 "재부팅 후에도"가 있으면 `enable`이 정답의 핵심이다.

**상황 5: kubelet이 계속 재시작/실패하는 경우 (q38 해설 기준) (미확인).**
```bash
systemctl status kubelet                     # activating (auto-restart) 이 반복되면 설정 오류
journalctl -u kubelet -n 50 --no-pager       # 맨 처음 나오는 오류를 읽는다
grep -n clientCAFile /var/lib/kubelet/config.yaml; ls /etc/kubernetes/pki/ca.crt
sed -i 's#ca-bundle.crt#ca.crt#' /var/lib/kubelet/config.yaml    # 예: clientCAFile 경로 수정
systemctl restart kubelet; journalctl -u kubelet -n 30 --no-pager   # 다음 오류가 있는지 다시 확인
```
q38은 오류가 둘이다: `clientCAFile` 경로, 그리고 `containerRuntimeEndpoint`의 소켓 철자(`containerd.sck`). 하나 고치고 끝내지 말고 고친 뒤 로그를 다시 본다. unit/drop-in/EnvironmentFile을 바꿨다면 `systemctl daemon-reload`도 한다.

**상황 6: 디버그 Pod로 노드 파일을 읽는다 (읽기 전용, 실행 확인).**
```bash
k debug node/k8s-worker --image=busybox:1.37 -- sleep 120      # "Creating debugging pod node-debugger-k8s-worker-xxxxx ..."
k exec node-debugger-k8s-worker-xxxxx -- ls /host/etc/kubernetes     # kubelet.conf manifests pki
k delete pod node-debugger-k8s-worker-xxxxx
```
`--profile=legacy is deprecated` 경고가 나온다. 문서의 `-it --image=ubuntu` 형태는 대화형 셸용.

## 자주 틀리는 점
아래 증상 문구 중 `journalctl` 오류 원문은 시뮬레이터 해설(q37, q38)과 문서 기준이며, 이 노트에서는 노드를 고장내지 않아 재현하지 못했다 (미확인). 단, 표시한 "확인함" 항목은 실제로 실행했다.
- 증상: `k get nodes`에 `NotReady`, `Ready=Unknown` -> kubelet이 보고를 못 한다(정지/비활성/설정 오류/API 서버 접속 불가) -> 노드에서 `systemctl status kubelet` -> `inactive`면 `enable --now`, `activating (auto-restart)`면 `journalctl`의 첫 오류.
- 증상: `systemctl start kubelet`으로 올렸는데 재부팅하면 다시 `NotReady` -> `enable`을 안 했다 -> `systemctl enable --now kubelet`. 확인은 `systemctl is-enabled kubelet`.
- 증상: 오류 하나 고쳤는데도 kubelet이 계속 안 뜬다 -> 오류가 여러 개다(q38: CA 경로 + 런타임 소켓 철자) -> `restart` 후마다 `journalctl -u kubelet -n 30`을 다시 읽는다.
- 증상: kubelet 로그에 `dial tcp <컨트롤플레인IP>:6443: connect: connection refused` -> 노드 쪽 문제가 아니라 API 서버가 안 떠 있다 (확인함: 부팅 직후 실제 로그) -> 컨트롤 플레인 노드에서 A2 절차.
- 증상: `crictl ps`가 `validate service connection ... endpoint` 오류 -> 소켓 경로 오타 또는 endpoint 미지정 -> `/etc/crictl.yaml`을 확인하거나 `crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps` (확인함).
- 증상: 고치고 `exit` 안 하고 다음 문제로 넘어가 엉뚱한 노드에서 명령 실행 -> 프롬프트의 호스트 이름을 보는 습관, 노드 작업이 끝나면 `exit` 두 번(root -> 사용자 -> base) 필요할 수 있다.
- 증상: 새 Pod가 어느 노드에도 안 뜨는데 노드는 `Ready` -> 노드 문제가 아니다 -> `k describe pod`의 `FailedScheduling` 사유(D5)나 `Taints`를 본다.
- 증상: `Ready`인데 `DiskPressure=True` -> 노드 디스크 부족으로 eviction 중 -> 노드에서 `df -h`, 큰 로그/이미지 정리(`crictl images`, `crictl rmi`는 신중히). 이 랩에서는 재현하지 않았다 (미확인).
- 시뮬레이터 차이: 클러스터 v1.34.0(시험 v1.37). 노드가 Docker 컨테이너라 `reboot`이 의미 없고, kubelet unit 경로/`ConditionPathExists`가 kind 전용이다. 시험에서 `kubectl`은 ssh한 노드에 있고 base에는 없다 ([TIPS]).

## 빠르게 푸는 순서
1. (30초) `k get nodes`로 NotReady 노드 이름 확인. 문제가 "이름을 파일에 저장"하라고 하면 먼저 저장(`k get nodes --no-headers | awk '$2!="Ready"{print $1}' > <경로>`).
2. (30초) `k describe node <n>`: Conditions의 `Ready` 이유/메시지와 Taints, 최근 Events.
3. (30초) `ssh <n>` -> `sudo -i`. 프롬프트가 해당 노드인지 확인.
4. (1분) `systemctl status kubelet`(+`is-enabled`) -> `journalctl -u kubelet -n 50 --no-pager`로 첫 오류 확인. 런타임 의심이면 `systemctl status containerd`, `crictl ps -a`.
5. (1~2분) 원인별 수정: 정지 -> `enable --now`; 설정 경로 오타 -> `config.yaml`의 `grep` + `ls`로 실제 경로 대조 후 수정 -> `restart`.
6. (1분) `journalctl -u kubelet -n 30`로 새 오류 없는지 재확인, `systemctl is-active kubelet`.
7. (30초) `exit`로 base 복귀 후 `k get nodes`에서 `Ready` 확인(30~60초 소요). 요구 파일/조건 대조. (총 5~6분 목표)

## 연습 문제
- **오늘 풀 문제** (study-guide.md 5절 Day 2):
  - `q37` — Worker NotReady, kubelet stopped/disabled (easy): 노드 이름을 파일에 저장하고 `enable --now`로 복구, 재부팅에도 유지.
  - `q38` — kubelet will not start (bad clientCAFile + runtime endpoint typo) (hard): 설정 오류 두 개를 로그로 찾아 고친다.
  - `q43` — Pending: requests, nodeSelector+taint, missing StorageClass: 노드는 정상인데 Pod가 안 뜨는 "노드 문제가 아닌" 경우를 구분한다 (계획표가 A1에 배정; COVERAGE.md는 A4로 분류).
- **추가 연습** (COVERAGE.md의 A1 개념 기준):
  - `q39` — kube-apiserver down (etcd CA path, secure-port) (hard): kubelet/crictl로 control plane 컨테이너 로그를 보는 연습. A2와 공유. q37, q40과 같은 세트에 넣지 않는다.
  - `q41` — Static pod manifest in wrong dir + bad image: kubelet 설정의 `staticPodPath`와 `crictl`. A2와 공유.
  - `q49` — Collect logs (-c, --previous), Warning events, top --containers, crictl container ID: `crictl`로 컨테이너 ID 찾기. A4와 공유.
- 주의: q38은 `k8s-worker2` kubelet을 망가뜨리고(INDEX.md 공유 상태 14번), q39는 q37/q40과 충돌한다.
