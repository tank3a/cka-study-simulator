# B7. Understand extension interfaces (CNI, CSI, CRI, etc.)

## 이 항목에서 공부할 것
- [ ] kubelet이 쓰는 CRI 소켓과 런타임 이름을 찾는다 (`/var/lib/kubelet/config.yaml`의 `containerRuntimeEndpoint`, `/etc/crictl.yaml`, `crictl version`)
- [ ] 노드의 CNI 설정 파일 이름과 플러그인 바이너리 디렉터리를 찾는다 (`/etc/cni/net.d`, `/opt/cni/bin`)
- [ ] 노드의 `podCIDR`와 클러스터 `podSubnet`(kubeadm-config)을 읽는다
- [ ] 기본 StorageClass의 provisioner를 읽고, `k get csidrivers` / `k get csinodes`로 "CSI 드라이버가 실제로 설치됐는지" 판단한다
- [ ] `CSIDriver`와 CSI provisioner를 쓰는 `StorageClass`를 만들고, 드라이버 Pod가 없을 때 PVC가 왜 Pending인지 설명한다
- [ ] `RuntimeClass`(handler, overhead, scheduling)를 만들고 Pod/Deployment의 `runtimeClassName`에 연결한다
- [ ] handler 이름이 노드의 containerd 설정(`containerd.runtimes.<이름>`)과 맞는지 확인하고, 틀렸을 때의 증상을 알아본다
- [ ] CNI 매니페스트(Calico 등)의 Pod CIDR 값을 클러스터 `podSubnet`에 맞게 고쳐 적용하는 절차를 안다

## 개념 설명

### 확장 인터페이스란
- 무엇: Kubernetes 본체는 컨테이너 실행, Pod 네트워크, 볼륨을 **직접 구현하지 않고** 표준 인터페이스만 정해 두고 구현체를 갈아 끼우게 한다. 세 가지가 시험 범위다 (이름 뒤의 "etc."는 그 밖의 확장점이고, 이 노트에서는 다루지 않는다).
- 한눈에 보기:

| 인터페이스 | 누가 누구를 부르나 | 설정/위치 (kubeadm 노드) | kubectl로 보이는 것 |
|---|---|---|---|
| CRI (런타임) | kubelet -> containerd(gRPC 소켓) | kubelet config의 `containerRuntimeEndpoint`, `/etc/containerd/config.toml` | `k get nodes -o wide`의 CONTAINER-RUNTIME, `RuntimeClass` |
| CNI (네트워크) | containerd가 Pod 생성 때 플러그인 실행 | `/etc/cni/net.d/*.conf(list)`, 바이너리 `/opt/cni/bin` | 노드 `spec.podCIDR`, kube-system의 CNI DaemonSet |
| CSI (스토리지) | kubelet/외부 sidecar -> 드라이버 Pod(gRPC) | 드라이버 Deployment/DaemonSet | `CSIDriver`, `CSINode`, `StorageClass.provisioner`, PV의 `csi:` |

- 비유: 콘센트 규격. 규격(인터페이스)만 같으면 어떤 가전(구현체)도 꽂을 수 있다.

### CRI와 RuntimeClass
- 무엇: kubelet은 CRI라는 gRPC API로 컨테이너 런타임(containerd, CRI-O)과 대화한다. 주소는 kubelet 설정 `containerRuntimeEndpoint`(예: `unix:///run/containerd/containerd.sock`)다. `crictl`은 같은 소켓으로 말하는 디버깅 도구다.
- `RuntimeClass`(클러스터 범위, `node.k8s.io/v1`)는 "이 Pod은 이름 붙은 런타임 설정으로 실행"을 고르는 오브젝트다. 핵심 필드:
  - `handler`: 노드의 containerd 설정 `[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.<handler>]`의 `<handler>`와 **글자 그대로** 같아야 한다.
  - `overhead.podFixed`: 샌드박스 자체가 먹는 고정 CPU/메모리. admission이 Pod의 `spec.overhead`로 복사해 스케줄링/쿼터 계산에 더한다.
  - `scheduling.nodeSelector`: 이 클래스를 쓰는 Pod의 nodeSelector에 합쳐져 해당 노드로만 간다.
- Pod에서는 `spec.runtimeClassName: <이름>`. 지정하지 않으면 기본 런타임.
- 관계: RuntimeClass는 CRI 위의 "선택 스위치"다. 시뮬레이터의 containerd에는 `runc`(기본)와 `test-handler` 핸들러가 있다 (`/etc/containerd/config.toml`).

### CNI와 Pod CIDR
- 무엇: Pod가 만들어질 때 containerd가 `/etc/cni/net.d`의 설정 파일을 읽고 `/opt/cni/bin`의 플러그인 바이너리를 실행해 Pod에 IP와 인터페이스를 준다. 설정은 노드 로컬 파일이고, 보통 CNI DaemonSet(Calico, Cilium, Flannel, kindnet)이 설치해 둔다.
- `podCIDR`: kube-controller-manager가 노드마다 `spec.podCIDR`(예 `10.244.1.0/24`)을 할당한다. 전체 범위는 `kubeadm init`의 `--pod-network-cidr`/`networking.podSubnet`이고 `kubeadm-config`에 남는다. CNI 플러그인이 쓰는 IP 풀은 이 범위 안이어야 한다 (그래서 Calico 매니페스트의 CIDR을 `podSubnet`에 맞춘다).
- CNI가 없으면 노드가 Ready가 되지 않는다 (일반 지식, 시뮬레이터에서는 재현하지 않음: 미확인). 문서 표현은 "CNI 플러그인이 쿠버네티스 네트워크 모델을 구현하는 데 필요하다".
- 관계: NetworkPolicy는 CNI가 지원해야 동작한다 (C2). CoreDNS와 Pod 연결(C1/C6)은 CNI 위에서 돈다.

### CSI와 CSIDriver / CSINode / StorageClass
- 무엇: CSI 드라이버는 보통 (1) controller 쪽 Deployment(external-provisioner 등 sidecar 포함)와 (2) 노드마다 도는 DaemonSet(node plugin)으로 설치되는 **Pod**들이다. 드라이버 이름(예 `ebs.csi.aws.com`)이 StorageClass의 `provisioner`가 된다.
- `CSIDriver`(클러스터 범위, `storage.k8s.io/v1`): 드라이버의 성격을 선언한다. `attachRequired`(attach 단계 필요 여부), `podInfoOnMount`(마운트 때 Pod 정보 전달), `volumeLifecycleModes`(`Persistent`, `Ephemeral`). `CSINode`는 노드별로 **실제로 등록된** 드라이버 목록으로, 드라이버 Pod가 떠야 채워진다.
- 동작 순서: PVC -> StorageClass의 provisioner(=드라이버)가 PV를 만든다 -> kubelet이 node plugin으로 마운트.
- 판단 요령: `k get csidrivers`가 비어 있고 `CSINode`의 DRIVERS가 0이면 CSI 드라이버가 없다. 기본 StorageClass의 provisioner가 CSIDriver 목록에 없으면(시뮬레이터의 `rancher.io/local-path`) 그것은 CSI가 아닌 external provisioner다.
- 관계: 볼륨/PV/PVC/StorageClass 자체는 E1~E3 항목이다. 여기서는 "그 아래의 드라이버 규격"을 묻는다.

## 예시

**상황 1: 워커 노드의 CRI/CNI 사실과 클러스터 CSI 사실을 읽어 `key=value`로 정리한다 (q26 형식).**
```bash
k get node k8s-worker -o jsonpath='{.spec.podCIDR}{"\n"}'
k get nodes -o wide                                      # CONTAINER-RUNTIME 열: containerd://...
k get sc                                                 # (default) 표시가 있는 클래스
k get sc standard -o jsonpath='{.provisioner}{"\n"}'     # 기본 클래스 이름은 위에서 읽은 값
k get csidrivers; k get csinodes                         # 드라이버 등록 여부
k -n kube-system get cm kubeadm-config -o jsonpath='{.data.ClusterConfiguration}' | grep podSubnet

ssh k8s-node1                                            # 시뮬레이터에서 k8s-worker로 가는 별칭
sudo -i
crictl version                                           # RuntimeName: containerd
grep containerRuntimeEndpoint /var/lib/kubelet/config.yaml
cat /etc/crictl.yaml                                     # runtime-endpoint: unix:///run/containerd/containerd.sock
ls /etc/cni/net.d ; ls /opt/cni/bin
crictl info | grep -B1 '"type": "NetworkReady"'          # "status": true
exit; exit
```
기대 결과 (시뮬레이터): podCIDR `10.244.1.0/24`(노드마다 다름), `containerd://2.1.3`, 기본 클래스 `standard` / provisioner `rancher.io/local-path`, `csidrivers`는 `No resources found`, `csinodes`의 DRIVERS는 모두 `0`, `podSubnet: 10.244.0.0/16`, `RuntimeName: containerd`, `unix:///run/containerd/containerd.sock`, CNI 설정 파일 `10-kindnet.conflist`, 바이너리 디렉터리 `/opt/cni/bin` (host-local, loopback, portmap, ptp). 노드에 들어가지 않고 kubelet 설정만 보려면 `k get --raw "/api/v1/nodes/k8s-worker/proxy/configz" | grep -o '"containerRuntimeEndpoint":"[^"]*"'`가 같은 값을 준다. `crictl info`에는 `"confDir": "/etc/cni/net.d"`, `"binDirs": ["/opt/cni/bin"]`도 나온다.

**상황 2: RuntimeClass를 만들고 Pod에 연결한다 (overhead와 노드 선택 포함).**
```bash
cat <<'EOF' | k apply -f -
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: runc-small
handler: runc
overhead:
  podFixed:
    cpu: 50m
    memory: 16Mi
scheduling:
  nodeSelector:
    kubernetes.io/hostname: k8s-worker
EOF
k -n demo run rc-demo --image=busybox:1.37 --dry-run=client -o yaml \
  --overrides='{"spec":{"runtimeClassName":"runc-small"}}' -- sleep 3600 | k apply -f -
```
확인:
```bash
k -n demo get pod rc-demo -o wide                                              # Running, NODE k8s-worker
k -n demo get pod rc-demo -o jsonpath='{.spec.runtimeClassName} {.spec.overhead}{"\n"}'   # runc-small {"cpu":"50m","memory":"16Mi"}
k get runtimeclass                                                             # runc-small   runc
```
RuntimeClass를 먼저 만들지 않고 Pod를 만들면 즉시 `Forbidden: pod rejected: RuntimeClass "nope" not found`가 나온다. handler 이름이 노드 설정에 없으면 (예: `handler: gvisor`) Pod는 만들어지지만 `ContainerCreating`에 멈추고 `k describe pod`의 Events에 `FailedCreatePodSandBox ... no runtime for "gvisor" is configured`가 뜬다. 노드의 핸들러 목록은 `sudo grep -E 'containerd.runtimes' /etc/containerd/config.toml`로 읽는다 (읽기만 한다). 이 예시는 `notes-b7` 네임스페이스에서 실제로 실행했다.

**상황 3: CSIDriver와 CSI provisioner를 쓰는 StorageClass, 그 위의 PVC를 만들고 Pending 이유를 확인한다.**
```bash
cat <<'EOF' | k apply -f -
apiVersion: storage.k8s.io/v1
kind: CSIDriver
metadata:
  name: demo.csi.example.com
spec:
  attachRequired: false
  podInfoOnMount: true
  volumeLifecycleModes:
  - Persistent
  - Ephemeral
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: csi-demo
provisioner: demo.csi.example.com
reclaimPolicy: Retain
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
parameters:
  type: fast
EOF
cat <<'EOF' | k -n demo apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: csi-demo
  resources:
    requests:
      storage: 1Gi
EOF
```
확인:
```bash
k get csidrivers                  # demo.csi.example.com  false(ATTACHREQUIRED)  true(PODINFOONMOUNT)  Persistent,Ephemeral
k get sc csi-demo                 # PROVISIONER demo.csi.example.com, Retain, WaitForFirstConsumer, 기본 클래스 아님
k get csinodes                    # DRIVERS 0 (드라이버 Pod가 없으니 등록 안 됨)
k -n demo get pvc data            # Pending
k -n demo describe pvc data | tail -3     # waiting for first consumer to be created before binding
```
이 PVC를 쓰는 Pod를 만들면 PVC 이벤트가 `Waiting for a volume to be created either by the external provisioner 'demo.csi.example.com' or manually ...`로 바뀌고, Pod는 `Pending`, NODE `<none>`, **Pod 자신의 Events는 비어 있다** (PVC 쪽 이벤트를 봐야 이유가 나온다). 정상이며 드라이버 Pod를 설치하기 전까지 Bound가 되지 않는다. `k explain csidriver.spec`로 필드 설명을 볼 수 있다. 정리: `k delete sc csi-demo; k delete csidriver demo.csi.example.com`.

**상황 4: CNI 매니페스트(Calico)의 IP 풀을 클러스터 `podSubnet`으로 바꾸어 적용한다.**
```bash
k -n kube-system get cm kubeadm-config -o jsonpath='{.data.ClusterConfiguration}' | grep podSubnet     # podSubnet: 10.244.0.0/16
cp calico.yaml calico-custom.yaml                                  # 원본은 수정하지 않는다
grep -n CALICO_IPV4POOL_CIDR calico-custom.yaml                    # 주석 처리된 두 줄: "# - name: ..." / "#   value: "192.168.0.0/16""
sed -i -e 's|^\( *\)# - name: CALICO_IPV4POOL_CIDR|\1- name: CALICO_IPV4POOL_CIDR|' \
       -e 's|^\( *\)#   value: "192.168.0.0/16"|\1  value: "10.244.0.0/16"|' calico-custom.yaml
diff calico.yaml calico-custom.yaml                                # 2줄만 바뀌어야 한다
k apply -f calico-custom.yaml
k get nodes -w                                                     # Ready가 될 때까지
```
(미확인: 실제 설치와 노드 Ready 전환은 실행하지 않았다. 시뮬레이터 `k8s`는 kindnet이 깔려 있고 Calico 설치는 별도 `ik8s` 클러스터가 필요하다. 검증한 것은 시뮬레이터가 제공하는 `calico.yaml`(v3.33.0)에 위 `sed`를 GNU sed 4.9로 적용했을 때 정확히 2줄만 바뀌고, `kubectl apply --dry-run=client`가 모든 리소스를 `created (dry run)`으로 받아들이는 것까지다. 시험에서는 문제가 주는 매니페스트 URL/파일의 해당 줄을 vim으로 직접 고쳐도 된다.)

시뮬레이터 차이: 서버는 v1.34.0이고 시험은 v1.37. 시뮬레이터 CNI는 kindnet(`10-kindnet.conflist`)이라 Calico/Cilium과 파일 이름이 다르고, 노드 디렉터리 `/etc/cni/net.d`는 root 전용이라 `sudo`가 필요하다. 이 kind 노드에는 kubeadm의 `cri-socket` 노드 어노테이션이 없어서 (`kubeadm.alpha.kubernetes.io/cri-socket`이 비어 있음) 소켓은 kubelet 설정/`crictl` 설정에서 읽어야 한다. 기본 StorageClass `standard`는 CSI 드라이버가 아니라 local-path provisioner다. containerd에는 `runc` 외에 `test-handler`도 있다. 실제 gVisor/Kata 같은 샌드박스 런타임은 없다.

허용 사이트만 쓴다. 검색 결과 순위는 직접 확인하지 못했다(미확인). 안 나오면 URL 경로를 주소창에 직접 쓴다.

| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| CRI가 무엇이고 소켓 옵션은 어디서 | `Container Runtime Interface` | https://kubernetes.io/docs/concepts/containers/cri/ | `container-runtime-endpoint` | (코드 블록 없음) 설명 문장 |
| RuntimeClass YAML (handler) | `RuntimeClass` | https://kubernetes.io/docs/concepts/containers/runtime-class/ (※) | `RuntimeClass is a non-namespaced resource` | `kind: RuntimeClass`, `handler:` 블록 + Pod의 `runtimeClassName` 블록 |
| containerd 핸들러 이름 규칙 | 위와 같음 | 위와 같음 | `containerd` (`CRI Configuration` 절) | `[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.${HANDLER_NAME}]` |
| RuntimeClass overhead / scheduling | 위와 같음 | 위와 같음 | `Pod Overhead`, `Scheduling` | `overhead: podFixed:`, `scheduling: nodeSelector:` 설명/예제 |
| CNI 플러그인 요구사항 | `network plugins` | https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/ | `Installation`, `Network Plugin Requirements`, `Loopback CNI` | (필요 시) cni-conf-dir `portMappings` JSON 예시 |
| CNI 애드온 목록 (Calico, Cilium, Flannel 등) | `installing addons` | https://kubernetes.io/docs/concepts/cluster-administration/addons/ | `Networking and Network Policy` | (이름 목록. 설치 매니페스트는 각 프로젝트 문서이고 시험에서는 문제의 링크/파일을 쓴다) |
| CSI 볼륨 소스, 드라이버 필드 | `volumes csi` | https://kubernetes.io/docs/concepts/storage/volumes/#csi | `csi`, `volumeHandle`, `driver` | `csi:` PV 필드 설명 |
| StorageClass의 provisioner | `storage classes` | https://kubernetes.io/docs/concepts/storage/storage-classes/ | `Provisioner`, `Default StorageClass` | `provisioner:` 줄이 있는 StorageClass 예제 |
| CSIDriver / CSINode 필드 | (페이지 대신 터미널) | `k explain csidriver.spec`, `k explain csinode.spec` | - | 필드 이름 확인용 |

(※) `official.md`/`study-guide.md` 목록에 없는 kubernetes.io/docs 페이지다. 2026-10-19에 curl로 HTTP 200과 YAML 블록(`RuntimeClass`, `runtimeClassName`, containerd `runtimes` 줄)을 확인했다.
cri 페이지에는 RuntimeClass YAML이 없다. RuntimeClass 문제는 위 (※) 페이지에서 푼다. `CSIDriver` 오브젝트의 YAML 예제는 volumes/storage-classes 페이지에 없는 것을 확인했다 (`CSIDriver`라는 단어가 없음). 필드는 `k explain csidriver.spec`로 확인한다.

## 자주 틀리는 점
- 증상: `cri_socket` 답을 `k get node -o jsonpath='{...cri-socket}'`로 찾았는데 빈 값 -> 원인: kubeadm이 붙이는 `kubeadm.alpha.kubernetes.io/cri-socket` 어노테이션이 이 환경에는 없다 -> 노드의 `/var/lib/kubelet/config.yaml`(`containerRuntimeEndpoint`)이나 `/etc/crictl.yaml`에서 읽는다 (`configz`도 가능).
- 증상: `cni_config_file` 답에 경로 전체를 씀 -> 원인: 문제는 "파일 이름"을 요구했다 -> `ls /etc/cni/net.d`의 이름만 (`10-kindnet.conflist`). containerd는 설정 파일을 하나만 쓴다 (`crictl info`의 `maxConfNum: 1`).
- 증상: `cni_bin_dir`을 `/etc/cni/net.d`로 답함 -> 원인: 설정 디렉터리와 바이너리 디렉터리를 혼동 -> 설정은 `/etc/cni/net.d`, 플러그인 실행 파일은 `/opt/cni/bin`.
- 증상: 기본 StorageClass를 "CSI 드라이버"로 답함 -> 원인: `rancher.io/local-path`는 CSIDriver로 등록돼 있지 않다 (`k get csidrivers`가 비어 있음) -> 드라이버 여부는 `csidrivers`/`csinodes`로 판단한다.
- 증상: `provisioner`를 틀린 이름으로 만든 StorageClass의 PVC가 계속 Pending -> 원인: 그 이름의 드라이버가 없다 -> `k describe pvc`의 이벤트(`Waiting for a volume to be created either by the external provisioner ...`)에 드라이버 이름이 나오므로 철자를 대조한다.
- 증상: CSI PVC를 쓰는 Pod가 Pending인데 `k describe pod` Events가 비어 있다 -> 원인: 스케줄러가 PVC 바인딩을 기다리는 중이다 -> `k describe pvc`의 Events와 PVC의 `volume.kubernetes.io/selected-node` 어노테이션을 본다.
- 증상: RuntimeClass Pod가 `ContainerCreating`에서 안 넘어감, `no runtime for "x" is configured` -> 원인: `handler`가 노드 containerd 설정에 없다 -> 노드에서 `grep containerd.runtimes /etc/containerd/config.toml`로 이름을 읽어 정확히 쓴다 (containerd 설정은 바꾸지 않는다).
- 증상: `pod rejected: RuntimeClass "x" not found` -> 원인: RuntimeClass(클러스터 범위)를 먼저 만들지 않았거나 이름 오타 -> `k get runtimeclass`.
- 증상: RuntimeClass에 `-n demo`를 붙여 만들려 함 -> 원인: 클러스터 범위 리소스 (`non-namespaced resource`, 문서 YAML 주석) -> 네임스페이스는 Pod 쪽에만.
- 증상: Calico 적용 후에도 Pod IP가 이상하거나 노드가 Ready가 아님 -> 원인: IP 풀 CIDR이 `podSubnet`과 다르다 (또는 `CALICO_IPV4POOL_CIDR` 주석을 풀지 않았다) -> `grep -n CALICO_IPV4POOL_CIDR`로 두 줄이 주석 해제됐는지, `kubeadm-config`의 `podSubnet`과 같은지 확인 (미확인: 실제 설치에서의 증상은 재현하지 않음).
- 증상: 큰 CNI 매니페스트의 `kubectl apply`가 `metadata.annotations: Too long`으로 실패 -> `k create -f` 또는 `k apply --server-side -f` (q89 힌트 출처, 직접 재현하지 않음: 미확인).

## 빠르게 푸는 순서
1. 문제의 컨텍스트와 호스트(어느 노드의 값을 묻는지)를 확인하고, 출력 파일/형식(`key=value`)과 "노드 설정 변경 금지"를 적는다. (30초)
2. kubectl로 읽을 수 있는 것을 먼저 모두 읽는다: `podCIDR`, `get sc`, `get csidrivers`, `get csinodes`, `kubeadm-config`의 `podSubnet`. (1분)
3. 노드에서만 보이는 것을 한 번의 ssh 세션에 모은다: `crictl version`, `grep containerRuntimeEndpoint /var/lib/kubelet/config.yaml`, `ls /etc/cni/net.d /opt/cni/bin`, (필요 시) `grep containerd.runtimes /etc/containerd/config.toml`. `exit`로 base 복귀. (2분)
4. 답 파일을 한 번에 `cat > file <<'EOF'`로 쓰고 `cat`으로 확인한다. 읽은 값을 그대로 쓴다. (1분)
5. RuntimeClass가 필요하면 runtime-class 페이지의 YAML을 복사해 `name`/`handler`(노드에서 확인한 이름)만 바꾸고 `overhead`/`scheduling`을 추가한다. Pod는 `k run --dry-run=client -o yaml --overrides=...` 또는 Deployment에 `k patch`로 `runtimeClassName`. (2분)
6. CSI 객체는 `k explain csidriver.spec`로 필드명을 확인하고 YAML로 만든다. PVC가 Pending인 것은 정상인지(드라이버 없음) `describe`로 확인한다. (2분)
7. CNI 매니페스트는 CIDR 두 줄만 고치고 `diff`로 변경 범위를 확인한 뒤 적용한다. 총 목표 6~8분.

추가 연습:
