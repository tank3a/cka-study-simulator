# D1. Understand application deployments and how to perform rolling update and rollbacks

## 이 항목에서 공부할 것
- [ ] `k create deploy ... --replicas --port`로 Deployment를 만들고 `--dry-run=client -o yaml`로 YAML 뼈대를 뽑는다
- [ ] `k set image deploy/<이름> <컨테이너>=<이미지>`로 업데이트하고 `k rollout status`로 끝날 때까지 기다린다 (`--timeout`, 종료 코드 포함)
- [ ] `k rollout history`와 `--revision=N`으로 revision 목록과 내용을 읽고, `kubernetes.io/change-cause` annotation으로 CHANGE-CAUSE를 남긴다
- [ ] 멈춘 rollout을 `k rollout undo`(직전) 또는 `--to-revision=N`(특정 revision)으로 되돌리고 이미지 값으로 확인한다
- [ ] `strategy.rollingUpdate`의 `maxSurge` / `maxUnavailable`을 `kubectl patch` 또는 YAML로 바꾸고 둘 다 0이면 안 되는 규칙을 안다
- [ ] `k scale`, `k rollout restart`, `k rollout pause/resume`을 쓰고, 어떤 변경이 새 revision을 만드는지 구분한다
- [ ] `k get rs`로 revision과 ReplicaSet이 1:1로 대응하는 것을 읽는다
- [ ] Deployment의 `selector`는 만든 뒤 못 바꾸므로 지우고 다시 만들어야 하는 상황을 알아본다

## 개념 설명

### Deployment 와 ReplicaSet
- 무엇인가: Deployment는 "Pod을 원하는 개수로, 원하는 버전으로 유지"하는 관리자다. 실제 Pod 개수는 그 밑의 ReplicaSet(RS)이 맞춘다. 반장(Deployment)이 조(RS)를 만들고, 조원(Pod)을 세는 것은 조장(RS)이다.
- 왜 필요한가: 이미지를 바꾸면 새 RS를 만들어 Pod을 조금씩 옮기고, 옛 RS는 개수 0으로 남겨 둔다. 옛 RS가 남아 있어서 롤백이 가능하다.
- 핵심 동작: Pod 템플릿(`spec.template`)이 바뀔 때만 새 RS(=새 revision)가 생긴다. `k scale`이나 strategy만 바꾸는 patch는 revision을 만들지 않는다 (확인함).
- 컨테이너 이름: `k create deploy web --image=nginx:1.27`은 컨테이너 이름을 이미지 이름에서 따와 `nginx`로 만든다 (확인함). `set image`는 이 이름을 쓴다.
- `spec.selector`는 만든 뒤 수정 불가다 (`field is immutable`, 확인함). 템플릿의 label은 selector와 계속 맞아야 한다.

### Rolling update 와 maxSurge / maxUnavailable
- 무엇인가: 새 버전 Pod을 먼저 조금 띄우고 옛 Pod을 조금 내리는 일을 반복해 서비스 중단 없이 교체하는 방식 (기본 전략 `RollingUpdate`). 대안은 `Recreate`(전부 내리고 전부 띄움).
- `maxSurge`: 원하는 개수보다 "더" 만들 수 있는 Pod 수 (올림). `maxUnavailable`: 업데이트 중 사용 불가여도 되는 Pod 수 (내림). 정수 또는 퍼센트. 둘 다 기본 25%.
- 규칙: 둘 다 0이면 안 된다 (확인함: `maxUnavailable: Invalid value: 0: may not be 0 when maxSurge is 0`). `Recreate`일 때 `rollingUpdate`를 같이 쓰면 거부된다 (확인함: `may not be specified when strategy type is 'Recreate'`).
- 확인: `k describe deploy <이름>`의 `RollingUpdateStrategy: 0 max unavailable, 2 max surge`.

### Revision, rollout history, change-cause
- revision은 RS에 붙은 번호(`deployment.kubernetes.io/revision`)다. `k rollout history deploy/<이름>`이 번호와 CHANGE-CAUSE를 보여 주고 `--revision=N`은 그 revision의 Pod 템플릿(이미지 등)을 보여 준다.
- CHANGE-CAUSE는 Deployment의 `kubernetes.io/change-cause` annotation 값이다. `--record`는 deprecated이므로 `k annotate`로 직접 쓴다.
- 오래된 RS는 `revisionHistoryLimit`개(기본 10, 확인함)까지만 남는다. `progressDeadlineSeconds` 기본은 600초 (확인함).

### Rollback (undo)
- `k rollout undo deploy/<이름>`은 직전 revision의 템플릿으로 되돌리고, `--to-revision=N`은 N번 템플릿으로 되돌린다. 되돌아간 템플릿은 새 revision 번호를 받고, 원래 번호는 history에서 사라진다 (확인함: 2번으로 undo -> history가 1, 3, 4로 바뀜. 1번으로 undo -> 새 번호 5).
- 롤백되는 것은 Pod 템플릿뿐이다. replicas, strategy는 그대로다 (문서 Note).
- 깨진 rollout이 멈춰 있어도 옛 Pod은 계속 서비스한다: 이미지가 틀리면 `READY 3/3  UP-TO-DATE 1  AVAILABLE 3`처럼 새 Pod 1개만 `ErrImagePull`/`ImagePullBackOff`에 걸려 있다 (확인함).

### pause / resume / restart / scale
- `rollout pause`: 템플릿을 여러 번 바꿔도 rollout을 시작하지 않는다 (확인함: 새 RS가 안 생김). `resume`하면 한 번에 반영(새 revision 하나).
- `rollout restart`: 템플릿에 재시작 표식을 넣어 Pod을 전부 롤링 교체한다. 새 revision이 생긴다 (확인함).
- `k scale deploy/<이름> --replicas=5`: revision 없이 개수만 바꾼다.

## 예시

### 예시 1. 만들고, 업데이트하고, 기록 보기
상황: "`web` 3개를 nginx:1.27로 띄우고 alpine으로 올린다".
```bash
k create deploy web --image=nginx:1.27 --replicas=3 --port=80
k rollout status deploy/web
k set image deploy/web nginx=nginx:1.27-alpine
k rollout status deploy/web
k rollout history deploy/web
# 기대: 마지막에 deployment "web" successfully rolled out
#       REVISION  CHANGE-CAUSE
#       1         <none>
#       2         <none>
k get rs
# 기대: RS 2개, 하나는 3/3, 옛 것은 0/0/0
```
컨테이너 이름을 모르면 `k get deploy web -o jsonpath='{.spec.template.spec.containers[*].name}'`. 전부 바꾸려면 `k set image deploy/web '*=nginx:1.27-alpine'`도 된다 (확인함).

### 예시 2. 멈춘 rollout 되돌리기 (q07 1번)
상황: "방금 업데이트한 rollout이 멈췄다. 마지막 정상 revision으로".
```bash
k set image deploy/web nginx=nginx:1.27-doesnotexist       # 일부러 깨뜨리기(연습용)
k rollout status deploy/web --timeout=20s; echo "exit=$?"
# 기대: Waiting for deployment "web" rollout to finish: 1 out of 3 new replicas have been updated...
#       error: timed out waiting for the condition / exit=1
k get deploy web                                           # UP-TO-DATE 1, AVAILABLE 3 (옛 Pod 유지)
k rollout undo deploy/web
k rollout status deploy/web
k get deploy web -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
# 기대: nginx:1.27-alpine (정상이던 직전 이미지)
```
`rollout status`는 기본으로 끝나지 않고 계속 기다리므로 연습할 때는 `--timeout`을 쓰고, 시험에서는 Ctrl+C로 빠져나온다.

### 예시 3. 전략 바꾸기 (q07 2번)
상황: "RollingUpdate, maxSurge 2, maxUnavailable 0".
```bash
k patch deploy web -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":2,"maxUnavailable":0}}}}'
k get deploy web -o jsonpath='{.spec.strategy}{"\n"}'
# 기대: {"rollingUpdate":{"maxSurge":2,"maxUnavailable":0},"type":"RollingUpdate"}
k rollout history deploy/web | tail -2        # revision 이 늘지 않았는지 확인
```
처음부터 YAML이면 문서 `Rolling Update Deployment`의 Hybrid 예시처럼 `spec.strategy`를 `selector`와 같은 들여쓰기 레벨에 둔다.
```yaml
spec:
  replicas: 4
  selector:
    matchLabels: {app: web}
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2
      maxUnavailable: 0
  template: {...}
```

### 예시 4. change-cause 남기고 업데이트, history 저장 (q07 3, 4번)
상황: "annotation `upgrade to alpine`을 기록하며 이미지를 올리고 history를 파일로 저장".
```bash
k annotate deploy/web kubernetes.io/change-cause="upgrade to alpine" --overwrite
k set image deploy/web nginx=nginx:1.27-alpine
k rollout status deploy/web
k rollout history deploy/web > /home/candidate/web-history.txt     # 경로는 문제에서 준 것
cat /home/candidate/web-history.txt
# 기대: 마지막 REVISION 줄의 CHANGE-CAUSE 가 upgrade to alpine
```
확인한 순서 효과: `set image` 뒤에 `annotate`해도 새 revision의 CHANGE-CAUSE가 채워진다. `annotate`를 먼저 하면 아직 현재인 직전 revision의 CHANGE-CAUSE도 같은 값으로 덮어써진다 (둘 다 확인함). 그러니 직전 기록을 보존해야 하면 `set image` 다음에 `annotate`하고, 문제 문장이 "업데이트 전에"라고 하면 그 순서대로 해도 현재 revision에는 기록된다.

### 예시 5. 특정 revision으로 롤백 (q52 형태)
상황: "CHANGE-CAUSE가 `v2-stable`인 revision으로 롤백하고 cause를 `rollback to v2-stable`로".
```bash
k rollout history deploy/shop > /home/candidate/history-before.txt   # 문제가 요구한 "변경 전 저장"
k rollout history deploy/shop                                        # v2-stable 의 REVISION 번호 N 찾기
k rollout history deploy/shop --revision=N                           # 이미지가 맞는지 확인
k rollout undo deploy/shop --to-revision=N
k annotate deploy/shop kubernetes.io/change-cause="rollback to v2-stable" --overwrite
k rollout status deploy/shop
k rollout history deploy/shop | tail -3
# 기대: 마지막 revision 의 CHANGE-CAUSE 가 rollback to v2-stable, N번은 더 이상 목록에 없음
```
undo로 만들어진 새 revision은 되돌린 대상 revision의 CHANGE-CAUSE를 그대로 가져온다 (확인함: `<none>`이던 1번으로 undo하자 새 revision도 `<none>`). 그래서 문제가 새 문구를 요구하면 undo 뒤에 `annotate --overwrite`를 한다.

### 예시 6. 자주 쓰는 한 줄
```bash
k scale deploy/web --replicas=5          # revision 생기지 않음
k rollout restart deploy/web             # 새 revision 생김
k rollout pause deploy/web; k set image deploy/web nginx=nginx:1.27; k rollout resume deploy/web
```

## 자주 틀리는 점
- `k set image`가 `error: unable to find container named "xxx"` -> 컨테이너 이름이 이미지 이름과 다름 (`k create deploy`는 이미지 이름에서 따옴) -> `k get deploy <이름> -o jsonpath='{.spec.template.spec.containers[*].name}'` 또는 `'*=이미지'`.
- `k rollout status`가 안 끝남 -> 새 Pod이 안 뜨는 중(이미지 오타 등) -> Ctrl+C 후 `k get pod`, `k describe pod`로 원인 확인, 이전 상태로 가려면 `k rollout undo`. 연습 때는 `--timeout=20s`를 붙이면 실패 시 종료 코드 1이 나온다 (확인함).
- `rollout undo`를 했더니 revision 번호가 달라짐 -> 되돌린 템플릿이 새 번호를 받음 (정상) -> 번호로 지시하는 문제는 `history`를 매번 다시 읽는다. 없는 번호는 `error: unable to find specified revision 99 in history` (확인함).
- CHANGE-CAUSE가 `<none>` -> annotation을 안 씀 -> `k annotate deploy/<이름> kubernetes.io/change-cause="..." --overwrite`. 업데이트 전후 어느 쪽이든 현재 revision에는 기록되지만, 먼저 하면 직전 revision의 문구도 덮어쓴다 (확인함).
- `k patch`로 strategy를 바꿨는데 history가 안 늘어남 -> 정상: 템플릿이 안 바뀌면 revision이 안 생긴다. 새 rollout이 필요하면 이미지/템플릿을 바꾸거나 `rollout restart`.
- `may not be 0 when maxSurge is 0` -> maxSurge와 maxUnavailable을 둘 다 0으로 씀 -> 하나는 1 이상.
- `strategy: Recreate`로 바꾸는 patch가 `rollingUpdate: Forbidden` -> 남아 있는 `rollingUpdate` 블록 때문 -> `--type=json`으로 `/spec/strategy/rollingUpdate`를 remove하면서 type을 replace (확인함).
- `selector`를 patch했더니 `field is immutable` -> selector는 불변 -> Deployment를 지우고 새 selector로 다시 만든다 (`k delete deploy ...; k apply -f ...` 또는 `k replace --force -f <파일>`. 후자는 한 번에 지우고 다시 만든다, 확인함). 템플릿의 label만 바꾸는 patch는 되고 Pod이 새로 만들어진다 (확인함).
- `rollout pause` 중에 `set image`를 했는데 아무 일도 안 일어남 -> pause 상태에서는 rollout이 시작되지 않음 -> `k rollout resume deploy/<이름>`.
- 시뮬레이터 차이: 이 클러스터는 v1.34.0(시험은 v1.37). 이미지는 인터넷에서 pull해야 하므로 처음 보는 태그는 느릴 수 있다. 존재하지 않는 태그는 `ErrImagePull` 후 `ImagePullBackOff`로 바뀐다.

## 빠르게 푸는 순서
1. context / namespace 확인, 대상 Deployment 이름과 요구(롤백 / 전략 / 이미지 / 기록 파일)를 번호 매겨 적는다 (0.5분).
2. `k get deploy,rs -n <ns>`와 `k rollout history deploy/<이름>`으로 현재 revision과 이미지를 본다 (0.5분).
3. 롤백이면 `k rollout undo`(직전) 또는 history에서 번호를 찾아 `--to-revision=N`. `k rollout status`로 완료 확인 (1분).
4. 전략 변경은 `k patch ... strategy` 한 줄 (둘 다 0이 아닌지 확인) 후 `k get deploy -o jsonpath='{.spec.strategy}'` (0.5분).
5. 이미지 업데이트는 컨테이너 이름을 확인하고 `k set image`, 이어서 `k annotate ... change-cause` (1분).
6. `k rollout status`가 끝나면 `k get deploy`로 READY / UP-TO-DATE / AVAILABLE이 모두 목표 replicas인지 본다 (0.5분).
7. 파일 저장 요구는 `k rollout history ... > 경로` 후 `cat`으로 내용 확인 (0.5분). 전체 목표 약 5~6분.
