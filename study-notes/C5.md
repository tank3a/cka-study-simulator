# C5. Know how to use Ingress controllers and Ingress resources

## 이 항목에서 공부할 것
- [ ] `k create ingress NAME --class=... --rule="host/path*=svc:port[,tls=secret]"`로 Ingress 뼈대를 만든다 (`*`가 붙으면 Prefix, 없으면 Exact)
- [ ] YAML에서 필수 필드(`pathType`, `backend.service.name`, `backend.service.port.number|name`, 슬래시로 시작하는 `path`)를 틀리지 않고 쓴다
- [ ] 한 호스트의 여러 경로(fanout), 호스트별 규칙(name-based), 와일드카드 호스트(`*.example.com`), `defaultBackend`를 작성한다
- [ ] TLS를 붙인다: `k create secret tls` + `spec.tls[].hosts/secretName`
- [ ] IngressClass를 만들고 `controller`, 기본 클래스 어노테이션(`ingressclass.kubernetes.io/is-default-class`)의 의미를 안다
- [ ] 예전 어노테이션(`kubernetes.io/ingress.class`)을 `spec.ingressClassName`으로 바꾼다
- [ ] `k describe ingress`의 Rules/Backends로 backend Service와 Pod IP가 연결됐는지 확인한다
- [ ] "Ingress 리소스만으로는 아무 일도 일어나지 않는다. 컨트롤러가 있어야 한다"를 설명하고, 컨트롤러가 없을 때 무엇이 보이는지 안다

## 개념 설명

### Ingress 리소스
클러스터 밖에서 들어오는 HTTP/HTTPS 요청을 host와 path로 나눠 클러스터 안 Service로 보내는 규칙 모음입니다(건물 안내 데스크의 "방문객 안내표"). 규칙은 `spec.rules[]`(host + `http.paths[]`)이고, 각 path에 `pathType`과 `backend`가 필수입니다.
- `pathType`: `Exact`(정확히 일치, 대소문자 구분), `Prefix`(`/` 단위로 앞부분 일치. `/aaa/bbb`는 `/aaa/bbb/ccc`에 맞고 `/aaa/bbbxyz`에는 안 맞음), `ImplementationSpecific`(컨트롤러에 맡김).
- 여러 path가 맞으면 가장 긴 path, 같으면 Exact가 우선입니다(문서 "Multiple matches").
- `spec.defaultBackend`: 어떤 규칙에도 안 맞는 요청의 목적지. `rules`가 없으면 모든 트래픽이 여기로.
- host에 `*.example.com` 같은 와일드카드를 쓸 수 있습니다. `*`만 쓰면 거부됩니다(검증).
- Ingress API는 동결(frozen)되었고 쿠버네티스 프로젝트는 Gateway 사용을 권장합니다(Ingress Controllers 문서의 안내문). 새 기능은 Gateway API(C4)에 추가됩니다.

### Ingress 컨트롤러
Ingress 리소스를 실제로 읽어서 로드밸런서/프록시를 설정하는 프로그램(ingress-nginx, HAProxy, Traefik, 클라우드 컨트롤러 등)입니다. 컨트롤러가 없으면 Ingress는 API에 저장될 뿐 ADDRESS가 비고 트래픽도 처리되지 않습니다. 문서의 Prerequisites: "You must have an Ingress controller to satisfy an Ingress. Only creating an Ingress resource has no effect."

### IngressClass
"이 Ingress는 어느 컨트롤러가 처리하나"를 가리키는 클러스터 범위 리소스입니다. `spec.controller`는 컨트롤러가 정한 식별 문자열이고(예: `k8s.io/ingress-nginx`), Ingress의 `spec.ingressClassName`이 IngressClass 이름을 가리킵니다.
- 기본 클래스: IngressClass에 어노테이션 `ingressclass.kubernetes.io/is-default-class: "true"`를 달면 `ingressClassName`이 없는 새 Ingress에 그 클래스가 자동 지정됩니다. 기본 클래스가 둘 이상이면 `ingressClassName` 없는 Ingress 생성이 admission에서 거부됩니다 (미확인: 문서 기준, 직접 실행 안 함. 기본 IngressClass를 만들면 공용 클러스터에 영향을 주기 때문).
- 옛 방식 `metadata.annotations["kubernetes.io/ingress.class"]`는 deprecated입니다(검증: 적용 시 `Warning: annotation "kubernetes.io/ingress.class" is deprecated, please use 'spec.ingressClassName' instead`).
- `ingressClassName`에 적은 이름의 IngressClass가 존재하지 않아도 Ingress 생성은 성공합니다(검증). 그냥 아무 컨트롤러도 처리하지 않을 뿐입니다.

### TLS
`spec.tls[].hosts`와 `secretName`(타입 `kubernetes.io/tls` Secret)을 적으면 컨트롤러가 그 호스트의 HTTPS를 종료합니다. Secret에는 `tls.crt`, `tls.key` 키가 있어야 하고(`k create secret tls`가 만들어 줌), 문서 예제는 Secret과 Ingress를 같은 네임스페이스에 둡니다. `tls`의 `hosts`는 `rules`의 host와 명시적으로 같아야 합니다(문서 Note: 기본 규칙에는 TLS가 적용되지 않음).

### 다른 리소스와의 관계
Ingress → (IngressClass) → 컨트롤러가 Ingress의 backend Service를 보고 그 Service의 EndpointSlice(C3)에서 Pod IP를 읽어 프록시합니다. 그래서 Service 포트/selector가 틀리면 Ingress도 안 됩니다.

## 예시
(네임스페이스 `lab`, Service `green`, `blue`(80)는 예시입니다.)

**시뮬레이터 차이 (먼저 읽기)**: 이 시뮬레이터에는 Ingress 컨트롤러가 설치돼 있지 않고 IngressClass도 0개입니다(`k get ingressclass` → `No resources found`). 그래서 Ingress를 만들어도 ADDRESS는 비어 있고 Events도 없으며 HTTP 응답은 확인할 수 없습니다. API 검증과 `describe`의 backend 연결 확인까지만 가능합니다. 실제 시험에 컨트롤러가 있는지는 (미확인)입니다.

상황 1: host `site.example.com`, `/green`→green:80, `/blue`→blue:80 (둘 다 Prefix), TLS Secret `site-tls`, class `nginx` (q34 형태).
```bash
k -n lab create ingress site --class=nginx \
  --rule="site.example.com/green*=green:80,tls=site-tls" \
  --rule="site.example.com/blue*=blue:80" --dry-run=client -o yaml > site.yaml
vim site.yaml        # tls.hosts에 site.example.com, secretName: site-tls 확인
k -n lab apply -f site.yaml
k -n lab get ingress site
k -n lab describe ingress site
```
기대 결과(검증):
```
NAME   CLASS   HOSTS              ADDRESS   PORTS     AGE
site   nginx   site.example.com             80, 443   0s
...
TLS:
  site-tls terminates site.example.com
Rules:
  Host              Path  Backends
  site.example.com
                    /green   green:80 (10.244.x.x:80)
                    /blue    blue:80 (10.244.x.x:80)
```
- `--rule`의 path 끝 `*`는 `pathType: Prefix`, 없으면 `Exact`입니다. 생성 후 YAML에서 `pathType`을 꼭 확인하세요.
- `,tls=site-tls`는 첫 `--rule`에만 붙이면 됩니다(같은 호스트). `,tls`만 쓰면 secretName 없이 hosts만 생깁니다.
- Backends의 괄호 안 IP는 Service의 Endpoints입니다. Service 이름이 틀리면 `nosuch:80 (<error: services "nosuch" not found>)`, Service는 있는데 Pod가 안 붙으면 `noep:80 ()`처럼 빈 괄호로 보입니다(둘 다 검증). 후자는 C3 방식으로 Service를 점검하세요.

같은 내용을 YAML로:
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: site
spec:
  ingressClassName: nginx
  tls:
  - hosts: [site.example.com]
    secretName: site-tls
  rules:
  - host: site.example.com
    http:
      paths:
      - {path: /green, pathType: Prefix, backend: {service: {name: green, port: {number: 80}}}}
      - {path: /blue,  pathType: Prefix, backend: {service: {name: blue,  port: {number: 80}}}}
```
```bash
k -n lab create secret tls site-tls --cert=tls.crt --key=tls.key      # Secret이 없을 때만
```

상황 2: 기본 backend + 와일드카드 호스트 + Exact 경로 (q100 형태). 서버 검증 통과.
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: wild
spec:
  ingressClassName: nginx
  defaultBackend:
    service: {name: green, port: {number: 80}}
  rules:
  - host: "*.example.com"
    http:
      paths:
      - {path: /exact, pathType: Exact, backend: {service: {name: blue, port: {number: 80}}}}
```
`k create ingress d --default-backend=green:80 --dry-run=client -o yaml`도 `spec.defaultBackend`를 만들어 줍니다(검증). 포트를 이름으로 쓰려면 `port: {name: http}`(서버 검증 통과).

상황 3: IngressClass 만들기 / 기본 클래스 지정 (q101, q102 형태). 서버 dry-run으로만 검증했습니다.
```yaml
apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: internal
  annotations:
    ingressclass.kubernetes.io/is-default-class: "true"   # 기본 클래스로 만들 때만
spec:
  controller: k8s.io/ingress-nginx
```
```bash
k get ingressclass                                   # 클러스터 범위라 -n 불필요
k explain ingressclass.spec                          # controller, parameters
```
상황 4: 예전 어노테이션을 새 필드로.
```bash
k -n lab get ingress old -o yaml | grep -n 'ingress.class'     # metadata.annotations 에 있음
k -n lab edit ingress old       # annotations 줄 삭제, spec.ingressClassName: nginx 추가
```
상황 5: 흔한 검증 에러 (서버가 돌려주는 문구).
```bash
# pathType 빠짐
The Ingress "nopt" is invalid: spec.rules[0].http.paths[0].pathType: Required value: pathType must be specified
# path가 슬래시로 시작하지 않음
spec.rules[0].http.paths[0].path: Invalid value: "green": must be an absolute path
# 옛 v1beta1 필드 (serviceName/servicePort)
strict decoding error: unknown field "spec.rules[0].http.paths[0].backend.serviceName", unknown field "...servicePort"
```

## 공식 문서에서 찾는 법
| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| 최소 Ingress YAML | `ingress` | https://kubernetes.io/docs/concepts/services-networking/ingress/ | `The Ingress resource` | 바로 아래 `service/networking/minimal-ingress.yaml` |
| 여러 경로(fanout) | `ingress simple fanout` | 같은 페이지 | `Simple fanout` | `simple-fanout-example.yaml` |
| 호스트별 규칙 | `ingress name based virtual hosting` | 같은 페이지 | `Name based virtual hosting` | `name-virtual-host-ingress.yaml` (호스트 없는 규칙 예제는 `name-virtual-host-ingress-no-third-host.yaml`) |
| TLS | `ingress tls` | 같은 페이지 | `tls-example-ingress.yaml` (또는 `secretName`) | 앞의 Secret YAML + `tls:` 가 들어간 Ingress YAML |
| 와일드카드 호스트 | `ingress hostname wildcards` | 같은 페이지 | `Hostname wildcards` | `ingress-wildcard-host.yaml` |
| defaultBackend / Resource backend | `ingress default backend` | 같은 페이지 | `DefaultBackend` | 설명문 위주. 필드는 `k explain ingress.spec.defaultBackend` |
| pathType 규칙표 | 같은 페이지 | 같은 페이지 | `Path types` | Prefix/Exact 매칭 예 표 (복사할 YAML 아님) |
| IngressClass / 기본 클래스 | `ingress class` | 같은 페이지 | `Default IngressClass` (일반 IngressClass는 `Ingress class`) | `default-ingressclass.yaml`, `external-lb.yaml` |
| 컨트롤러 종류와 안내 | `ingress controllers` | https://kubernetes.io/docs/concepts/services-networking/ingress-controllers/ | `Ingress controllers` | YAML 없음. 상단 Note(Gateway 권장, Ingress API 동결) 확인 |
| kubectl 한 줄 생성 | (터미널) `k create ingress -h` | 해당 없음 | 해당 없음 | 도움말 Examples (`--rule="foo.com/path*=svc:8080"`, `--default-backend`) |

## 자주 틀리는 점
- 증상: `pathType: Required value` → 원인: v1에서는 `pathType`이 필수 → 각 path에 `Prefix|Exact|ImplementationSpecific`.
- 증상: `unknown field ... serviceName` → 원인: 오래된 예제(extensions/v1beta1)를 복사함 → `backend.service.name` / `backend.service.port.number`로.
- 증상: `k create ingress ... --rule="host/path=svc:80"`로 만들었더니 의도와 다른 매칭 → 원인: `*` 없으면 Exact → 의도가 Prefix면 `path*`.
- 증상: `k create ingress`로 TLS를 만들었는데 `tls` 블록에 secretName이 없음 → 원인: `,tls`만 쓰고 `=secret`을 빼먹음 → `,tls=site-tls`.
- 증상: ADDRESS가 비어 있음 → 원인: 컨트롤러 없음(이 시뮬레이터) 또는 컨트롤러가 아직 처리 전 → 시뮬레이터에서는 정상. 실제 환경에서는 `k get pods -A | grep -i ingress`, `k get ingressclass`로 컨트롤러 확인.
- 증상: `spec.ingressClassName`을 오타내도 에러가 없음 → 원인: 클래스 존재 여부를 admission이 검사하지 않음(검증) → `k get ingressclass`로 이름을 대조.
- 증상: 기본 IngressClass가 둘이라 새 Ingress가 거부됨 → 원인: 기본 클래스는 하나만 허용 (미확인: 문서 기준) → 어노테이션이 있는 IngressClass를 하나만 남김.
- 증상: Ingress `describe`의 Backends에 Pod IP가 안 보임 → 원인: backend Service의 selector/포트 문제 → C3 노트로.
- 증상: TLS가 적용되지 않음 → 원인: `tls.hosts`가 `rules`의 host와 다르거나, Secret에 `tls.crt`/`tls.key`가 없음(문서 Note) → hosts를 rules의 host와 똑같이, Secret은 `k create secret tls`로 생성.
- 문제가 "Ingress를 Gateway API로 옮겨라"이면 C4 노트의 대응표를 사용하고, 새 HTTPRoute가 Accepted인 것을 확인한 다음 Ingress를 삭제합니다.

## 빠르게 푸는 순서
1. (30초) 문제의 네임스페이스, Ingress 이름, `ingressClassName`, host, 각 path와 pathType, backend Service:포트, TLS Secret 이름을 적는다. "Do not modify the Services"류 제약 확인.
2. (30초) `k -n NS get svc,ingress`로 Service 이름/포트와 IngressClass를 확인 (`k get ingressclass`).
3. (1분) `k create ingress ... --rule=... --class=... --dry-run=client -o yaml > ing.yaml`.
4. (1분) `vim ing.yaml`: `pathType`(Prefix/Exact), `tls.hosts`, `secretName`을 문제와 대조해 고친다. 필드가 기억나지 않으면 문서 `The Ingress resource`의 `minimal-ingress.yaml`과 `tls-example-ingress.yaml`을 참고.
5. (30초) `k apply -f ing.yaml`, 에러 문구를 그대로 읽고 수정.
6. (1분) `k describe ingress NAME`에서 Rules의 Backends에 Pod IP가 보이는지, TLS 줄이 맞는지 확인.
7. (선택) 컨트롤러가 있는 환경이면 `curl -H 'Host: ...' http://<주소>/path`. 이 시뮬레이터에서는 생략.
목표: 4~5분.
