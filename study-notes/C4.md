# C4. Use the Gateway API to manage Ingress traffic

## 이 항목에서 공부할 것
- [ ] `k get gc,gtw,httproute -A`로 GatewayClass / Gateway / HTTPRoute 현황과 Accepted, Programmed 상태를 읽는다
- [ ] Gateway를 만든다 (`gatewayClassName`, listener의 name / port / protocol / hostname / allowedRoutes)
- [ ] HTTPRoute를 만든다: `parentRefs`, `hostnames`, `rules[].matches`(path, headers), `backendRefs`
- [ ] HTTPS listener에 TLS Secret을 연결한다 (`tls.mode: Terminate`, `certificateRefs`). 문서 위치를 외워 둘 것
- [ ] HTTP → HTTPS 리다이렉트 HTTPRoute를 `sectionName`으로 http listener에만 붙인다 (`RequestRedirect`)
- [ ] 기존 Ingress를 읽고 같은 host/path/backend를 HTTPRoute로 옮긴 뒤 Ingress를 삭제한다
- [ ] `k describe httproute|gateway`의 Conditions(Accepted, ResolvedRefs, Programmed)로 실패 원인을 읽는다
- [ ] 가중치(`weight`)로 트래픽을 나누고, 다른 네임스페이스 라우트(`allowedRoutes`)가 막히는 이유를 안다

## 개념 설명

### GatewayClass
"어떤 컨트롤러가 처리하는가"를 가리키는 클러스터 범위 리소스(Ingress의 IngressClass에 해당). 인프라 담당자가 만듭니다. `spec.controllerName`이 컨트롤러와 연결됩니다. 시뮬레이터에는 `nginx`(컨트롤러 `gateway.nginx.org/nginx-gateway-controller`, NGINX Gateway Fabric)가 있고 `k get gc`에서 ACCEPTED가 True입니다.

### Gateway
"어느 포트로 어떤 프로토콜 트래픽을 받을지" 정하는 입구(건물 출입문). 핵심 필드는 `gatewayClassName`과 `listeners[]`입니다.
- listener: `name`, `port`, `protocol`(HTTP, HTTPS ...), 선택 `hostname`, HTTPS면 `tls`, 어떤 네임스페이스의 Route를 받을지 정하는 `allowedRoutes.namespaces.from`(기본 Same).
- `tls.mode: Terminate`이면 Gateway가 TLS를 풀고, `certificateRefs`가 kubernetes.io/tls Secret을 가리킵니다(Secret은 기본적으로 Gateway와 같은 네임스페이스).
- 시뮬레이터(NGF)는 Gateway를 만들면 `<gateway 이름>-nginx`라는 Deployment와 NodePort Service(데이터 플레인)를 자동으로 만듭니다. `k get gtw`의 ADDRESS는 그 Service의 ClusterIP입니다.

### HTTPRoute
"입구로 들어온 요청을 어느 Service로 보낼지" 정하는 규칙(안내 데스크). Ingress의 `rules`에 해당합니다.
- `parentRefs`: 붙을 Gateway(`name`, 필요하면 `namespace`, 특정 listener만 고르는 `sectionName`).
- `hostnames`: 처리할 Host 헤더 목록.
- `rules[]`: `matches`(path `PathPrefix|Exact`, headers, 메서드, 쿼리), `filters`(`RequestRedirect`, `URLRewrite`, `RequestHeaderModifier`), `backendRefs`(`name`, `port`, 선택 `weight`).
- 여러 규칙이 맞으면 더 구체적인 match(헤더까지 포함된 것, 긴 path)가 우선입니다. 규칙의 작성 순서가 아니라 구체성이 먼저입니다(검증: 헤더 없는 `/` 규칙과 헤더가 있는 `/` 규칙을 둘 다 두어도 헤더 있는 쪽이 이김).
- `matches`를 생략한 규칙은 모든 요청에 맞는 기본 규칙입니다.

### 상태(Conditions)
컨트롤러가 리소스의 `status`에 결과를 적어 줍니다. HTTPRoute는 `status.parents[].conditions`에서 Accepted(Gateway/listener에 붙을 수 있나), ResolvedRefs(backend Service와 포트를 찾았나), Gateway/listener는 Accepted, Programmed, ResolvedRefs, Conflicted입니다. 안 될 때는 항상 `k describe`의 Status부터 봅니다.

### ReferenceGrant
다른 네임스페이스의 Service/Secret을 참조하려면 대상 네임스페이스에 ReferenceGrant가 있어야 합니다. 없으면 `RefNotPermitted`.

### Ingress에서 옮길 때의 대응표
| Ingress | Gateway API |
|---|---|
| `ingressClassName` | Gateway의 `gatewayClassName`, HTTPRoute의 `parentRefs` |
| `rules[].host` | HTTPRoute `hostnames` |
| `pathType: Prefix` / `Exact` | `path.type: PathPrefix` / `Exact` |
| `backend.service.name`, `port.number` | `backendRefs[].name`, `port` |
| `tls[].secretName` | Gateway HTTPS listener의 `tls.certificateRefs[].name` |

## 예시
(네임스페이스 `lab`은 예시 이름입니다. 아래 YAML은 모두 서버 검증(`--dry-run=server`)과 실제 적용으로 확인했습니다.)

상황 1: 현황 보기.
```bash
k get gc,gtw -A
k get httproute -A
```
기대 결과: `gatewayclass.gateway.networking.k8s.io/nginx  gateway.nginx.org/nginx-gateway-controller  True`, Gateway는 `CLASS nginx  ADDRESS 10.96.x.x  PROGRAMMED True`. (짧은 이름 `gc`, `gtw`는 확인됨, HTTPRoute에는 짧은 이름이 없음)

상황 2: Gateway `web-gw`(HTTP 80)가 이미 있다. `app.example.com`의 `/v1`은 app-v1, `/v2`는 app-v2, 나머지는 app-v1, 단 헤더 `X-Env: canary`는 app-v2로 보낸다 (q31 형태).
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: app-route
spec:
  parentRefs:
  - name: web-gw
  hostnames:
  - app.example.com
  rules:
  - matches:
    - path: {type: PathPrefix, value: /v1}
    backendRefs:
    - {name: app-v1, port: 80}
  - matches:
    - path: {type: PathPrefix, value: /v2}
    backendRefs:
    - {name: app-v2, port: 80}
  - matches:
    - path: {type: PathPrefix, value: /}
      headers:
      - {type: Exact, name: X-Env, value: canary}
    backendRefs:
    - {name: app-v2, port: 80}
  - matches:
    - path: {type: PathPrefix, value: /}
    backendRefs:
    - {name: app-v1, port: 80}
```
```bash
k -n lab apply -f app-route.yaml
k -n lab get httproute app-route -o jsonpath='{range .status.parents[*].conditions[*]}{.type}={.status} {end}{"\n"}'   # Accepted=True ResolvedRefs=True
k -n lab get svc web-gw-nginx                                   # 데이터 플레인 Service, PORT(S) 80:3xxxx/TCP
curl -s -H 'Host: app.example.com' http://<노드IP>:<nodePort>/v1               # v1
curl -s -H 'Host: app.example.com' -H 'X-Env: canary' http://<노드IP>:<nodePort>/other   # v2
```
검증 결과: `/v1`→v1, `/v2`→v2, `/other`→v1, 헤더 canary + `/other`→v2, 헤더 canary + `/v1`→v1(path 규칙이 우선), Host가 다르면 404.

상황 3: HTTPS(TLS 종료) + HTTP→HTTPS 리다이렉트 (q32 형태). Secret `shop-tls`와 Service `shop`(80)이 이미 있다.
```bash
# Secret이 없을 때만 (자체 서명)
openssl req -x509 -newkey rsa:2048 -nodes -days 365 -subj "/CN=shop.example.com" -addext "subjectAltName=DNS:shop.example.com" -keyout tls.key -out tls.crt
k -n lab create secret tls shop-tls --cert=tls.crt --key=tls.key
```
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gw
spec:
  gatewayClassName: nginx
  listeners:
  - name: https
    port: 443
    protocol: HTTPS
    hostname: shop.example.com
    tls:
      mode: Terminate
      certificateRefs:
      - {kind: Secret, name: shop-tls}
    allowedRoutes: {namespaces: {from: Same}}
  - name: http
    port: 80
    protocol: HTTP
    hostname: shop.example.com
    allowedRoutes: {namespaces: {from: Same}}
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: shop-route}
spec:
  parentRefs:
  - {name: shop-gw, sectionName: https}
  hostnames: [shop.example.com]
  rules:
  - backendRefs:
    - {name: shop, port: 80}
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: shop-redirect}
spec:
  parentRefs:
  - {name: shop-gw, sectionName: http}
  hostnames: [shop.example.com]
  rules:
  - filters:
    - type: RequestRedirect
      requestRedirect:
        scheme: https
        statusCode: 301
```
```bash
k -n lab get gtw,httproute
k -n lab get gtw shop-gw -o jsonpath='{range .status.listeners[*]}{.name}{" attached="}{.attachedRoutes}{" "}{range .conditions[*]}{.type}={.status} {end}{"\n"}{end}'
curl -s -o /dev/null -D - -H 'Host: shop.example.com' 'http://<노드IP>:<http nodePort>/abc?x=1'      # 301, Location: https://shop.example.com/abc?x=1
curl -sk --resolve shop.example.com:<https nodePort>:<노드IP> https://shop.example.com:<https nodePort>/      # <title>Welcome to nginx!</title>
```
기대 결과: 두 listener 모두 `attached=1 Programmed=True Accepted=True ResolvedRefs=True Conflicted=False`. `sectionName`을 빼면 두 Route가 두 listener 모두에 붙으려 해서 의도와 달라집니다.

상황 4: Ingress `legacy`(blog.example.com: `/` Prefix→blog, `/docs` Prefix→docs, `/health` Exact→docs)를 HTTPRoute로 옮기고 Ingress를 지운다 (q33 형태).
```bash
k -n lab get ingress legacy -o yaml          # host, path, pathType, backend 확인
```
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: legacy-route
spec:
  parentRefs:
  - name: main-gw
  hostnames: [blog.example.com]
  rules:
  - matches: [{path: {type: PathPrefix, value: /}}]
    backendRefs: [{name: blog, port: 80}]
  - matches: [{path: {type: PathPrefix, value: /docs}}]
    backendRefs: [{name: docs, port: 80}]
  - matches: [{path: {type: Exact, value: /health}}]
    backendRefs: [{name: docs, port: 80}]
```
```bash
k -n lab apply -f legacy-route.yaml
k -n lab describe httproute legacy-route | grep -A2 -E 'Type: +(Accepted|ResolvedRefs)'    # Status: True
k -n lab delete ingress legacy               # 새 라우트가 동작하는 것을 확인한 뒤 삭제
```
검증 결과: `/`→blog, `/docs`, `/docs/x`, `/health`→docs, `/health/x`→blog(Exact라 안 맞음).

상황 5 (선택): 가중치 분할. `backendRefs`에 `weight`를 비율로 줍니다.
```yaml
  rules:
  - backendRefs:
    - {name: app-v1, port: 80, weight: 80}
    - {name: app-v2, port: 80, weight: 20}
```
20번 요청에서 v1 18회, v2 2회 정도로 나뉘었습니다(비율 분할이라 정확한 숫자는 매번 다름).

**시뮬레이터 차이**: GatewayClass `nginx`는 NGINX Gateway Fabric이고, Ingress 컨트롤러는 설치돼 있지 않습니다. Gateway 생성 후 데이터 플레인 Pod가 Ready가 될 때까지 20~30초가 걸렸습니다. 시뮬레이터 터미널에서는 ClusterIP에 닿지 않고 `노드IP:NodePort`로 테스트합니다. 검증 시점에 k8s-worker2에 뜬 Pod는 클러스터 DNS에 접근하지 못해 데이터 플레인이 Ready가 되지 않았습니다(k8s-worker에서만 정상). Gateway가 계속 `PROGRAMMED False/Unknown`이고 `web-gw-nginx` Pod가 `0/1`이면 `k get pod -o wide`로 노드를 확인하세요. 시험의 Gateway 컨트롤러 종류는 (미확인)입니다.

## 자주 틀리는 점
상태 메시지는 NGF에서 실제로 확인한 문구입니다.
- 증상: HTTPRoute가 `ResolvedRefs=False reason=BackendNotFound`, 메시지 `No matching port for Service app-v1 and port 8080`, 요청은 500 → 원인: `backendRefs.port`가 Service의 `port`와 다름 → 고침: `k get svc`의 PORT(S) 값으로(targetPort가 아님).
- 증상: `ResolvedRefs=False`, 메시지 `Not found: "nope"` → 원인: backend Service 이름 오타 또는 네임스페이스 다름 → 이름 수정.
- 증상: `Accepted=False reason=NoMatchingListenerHostname` → 원인: Route의 `hostnames`가 listener `hostname`과 맞지 않음 → hostnames를 listener에 맞추거나 listener hostname 제거.
- 증상: `Accepted=False reason=NoMatchingParent`, `The Listener is not found for this parent ref` → 원인: `sectionName`이 listener 이름과 다름(예: HTTP-only Gateway에 `sectionName: https`) → `k get gtw NAME -o yaml`에서 listener 이름 확인.
- 증상: HTTPRoute의 `status`가 비어 있음(parents 없음) → 원인: `parentRefs.name`이 존재하지 않는 Gateway → Gateway 이름 확인.
- 증상: 다른 네임스페이스의 Route가 `Accepted=False reason=NotAllowedByListeners` → 원인: listener의 `allowedRoutes`가 기본값(Same) → `from: All` 또는 `from: Selector` + 네임스페이스 라벨. backend가 다른 네임스페이스면 `RefNotPermitted`(ReferenceGrant 필요).
- 증상: Gateway listener `Accepted=False reason=InvalidCertificateRef`, `Secret ... does not exist` → 원인: `certificateRefs`의 Secret 이름 오타/없음/네임스페이스 다름 → `k get secret`으로 확인, 타입은 `kubernetes.io/tls`.
- 증상: HTTPS listener `Accepted=False reason=UnsupportedValue`, `tls must be defined for HTTPS listener` → 원인: `protocol: HTTPS`인데 `tls` 블록 없음.
- 증상: 오타난 `gatewayClassName`(예: nginxx)의 Gateway가 `PROGRAMMED Unknown`, ADDRESS 없음, 메시지 `Waiting for controller` → 원인: 처리할 컨트롤러가 없음. API는 거부하지 않으므로 `k get gc`로 이름 확인.
- 증상: 헤더 규칙이 안 먹는 것처럼 보임 → 원인: 헤더 이름 대소문자/`type: Exact` 값 불일치. 반대로 path가 더 구체적인 규칙은 헤더 규칙보다 먼저 맞습니다(검증).
- 증상: Ingress를 지웠는데 서비스가 죽음 → 원인: HTTPRoute가 Accepted/ResolvedRefs True인지 확인하기 전에 삭제 → 순서는 "Route 확인 후 Ingress 삭제".
- Gateway TLS 예제는 찾기 어렵다는 후기가 많습니다. gateway-api.sigs.k8s.io `guides/user-guides/tls/`에서 `certificateRefs`를 Ctrl+F 하는 경로를 손에 익히세요.

## 빠르게 푸는 순서
1. (30초) 문제의 Gateway 이름/네임스페이스, hostname, 경로, backend Service와 **포트 숫자** 적기. `k get gc,gtw,httproute -A`.
2. (30초) `k -n NS get gtw NAME -o yaml`에서 listener 이름과 hostname 확인 (`sectionName`에 쓸 값).
3. (1분) 문서 `http-routing`에서 첫 HTTPRoute YAML 복사, `parentRefs`, `hostnames`, `rules`를 문제대로 수정.
4. (TLS면 +2분) `guides/user-guides/tls/`에서 `certificateRefs` 스니펫을 Gateway listener에 붙이고, 리다이렉트는 `http-redirect-rewrite`의 `http-filter-redirect` 복사.
5. (30초) `k apply -f`, 바로 `k describe httproute NAME`의 Status에서 Accepted, ResolvedRefs 둘 다 True인지 확인.
6. (1분) 가능하면 `curl -H 'Host: ...' http://노드IP:NodePort/경로`로 응답 확인. 안 되면 conditions 메시지부터 읽기.
7. (Ingress 마이그레이션이면) 기존 Ingress의 host/path/pathType/backend 포트를 표로 옮긴 뒤 Route가 True인 것을 보고 마지막에 Ingress 삭제.
목표: Route 하나 5~6분, TLS/리다이렉트 포함 10~12분.

- **추가 연습**:
  - `q98` — gateway-allowed-routes-namespaces: Shared Gateway with allowedRoutes namespace selector, label team namespace, cross-namespace HTTPRoute, GatewayClass controllerName (Gateway 컨트롤러 필요, 어려움)
  - `q99` — ingress-to-gateway-tls-exact: Migrate a TLS Ingress with Exact+Prefix paths to Gateway (HTTPS) + HTTPRoute, delete Ingress
  - `q33` — ingress-to-gateway-migrate: Migrate an Ingress to an HTTPRoute, delete the Ingress (계획표에서는 C5 칸에 배정되어 있어 C5 노트의 오늘 문제이기도 함)
