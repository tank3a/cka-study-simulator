# C3. Use ClusterIP, NodePort, LoadBalancer service types and endpoints

## 이 항목에서 공부할 것
- [ ] `k expose deploy`로 ClusterIP Service를 만들고 `--port`(Service 포트)와 `--target-port`(컨테이너 포트)를 구분해서 지정한다
- [ ] NodePort Service를 만들고 `nodePort`를 30000-32767 안의 값으로 고정한다 (`k expose`에는 `--node-port`가 없으므로 YAML에 직접 넣는다)
- [ ] `k create svc nodeport|clusterip|loadbalancer|externalname`으로 뼈대를 만들고 `k set selector svc`로 selector를 고친다
- [ ] LoadBalancer Service를 만들고 EXTERNAL-IP가 `<pending>`이어도 spec과 자동 할당된 nodePort를 확인한다
- [ ] `k get endpointslice -l kubernetes.io/service-name=NAME`으로 Service가 Pod에 실제로 연결됐는지 본다
- [ ] Endpoints가 비는 세 가지 원인(selector 불일치, Pod NotReady, 잘못된 targetPort)을 구분한다
- [ ] 멀티 포트 Service(포트마다 `name` 필수)와 이름 있는 targetPort(`targetPort: http`)를 쓴다
- [ ] headless(`clusterIP: None`)와 ExternalName Service를 만들고 DNS 결과가 어떻게 다른지 안다

## 개념 설명

### Service (공통)
Pod IP는 Pod가 재생성될 때마다 바뀝니다. Service는 "라벨이 맞는 Pod 묶음"에 붙는 고정 주소(가상 IP)와 DNS 이름입니다. 전화 대표번호처럼 번호는 그대로 두고 뒤에서 받는 사람(Pod)만 바뀝니다.
- `spec.selector`: 대상 Pod를 고르는 라벨. 여기가 틀리면 연결 대상이 0개가 됩니다.
- `spec.ports[].port`: Service가 받는 포트. `targetPort`: Pod(컨테이너)가 실제로 듣는 포트(숫자 또는 containerPort의 이름). 생략하면 `port`와 같은 값.
- `spec.type`: 노출 범위. 기본값 ClusterIP.
- Service는 selector가 맞는 Pod를 컨트롤러가 찾아 EndpointSlice에 적어 두고, 노드의 kube-proxy가 그 목록으로 트래픽을 나눠 보냅니다.

### ClusterIP
클러스터 안에서만 접근되는 가상 IP(기본 타입). Pod끼리 통신, 다른 타입의 기반이 됩니다. 접근: `<svc>`(같은 네임스페이스), `<svc>.<ns>`, `<svc>.<ns>.svc.cluster.local`(DNS 이름 규칙은 C6 노트).

### NodePort
ClusterIP에 더해 **모든 노드**의 같은 포트(기본 30000-32767)가 열려 `<노드IP>:<nodePort>`로 들어오면 Service로 전달됩니다. `nodePort`를 생략하면 자동 할당, 지정하면 그 값(범위 밖이거나 이미 사용 중이면 생성 실패).

### LoadBalancer
NodePort에 더해 클라우드의 외부 로드밸런서를 요청하는 타입. 클라우드 컨트롤러가 없으면 EXTERNAL-IP는 계속 `<pending>`이지만 nodePort는 NodePort와 똑같이 할당됩니다. 시험에서는 보통 "타입을 LoadBalancer로 만들고 spec 값(포트, externalTrafficPolicy 등)을 맞춰라" 형태.

### Endpoints / EndpointSlice
Service가 가리키는 실제 Pod IP:port 목록. 요즘은 EndpointSlice(`discovery.k8s.io/v1`)가 기본이고 `Endpoints` API는 deprecated라 `k get ep`를 치면 경고가 나옵니다(동작은 함).
- EndpointSlice는 라벨 `kubernetes.io/service-name=<Service 이름>`으로 찾습니다.
- 각 항목의 `conditions.ready`가 false인 Pod(readinessProbe 실패)는 트래픽을 받지 못합니다(`k describe ep`에서는 NotReadyAddresses).
- selector가 없는 Service는 직접 EndpointSlice를 만들어 연결합니다(문서 "Services without selectors").

### Headless / ExternalName
- Headless(`clusterIP: None`): 가상 IP 없이 DNS가 Pod IP들을 직접 돌려줍니다. StatefulSet의 Pod별 DNS(`pod-0.svc.ns...`)에 쓰입니다.
- ExternalName: selector 없이 DNS CNAME만 돌려주는 별칭(`spec.externalName`). 프록시/Endpoints는 없습니다.

## 예시
(네임스페이스 `lab`과 Deployment `web`은 예시 이름입니다. Pod 라벨은 `app=web`.)

상황 1: Deployment `web`을 NodePort 80 → 컨테이너 80, nodePort 30080으로 노출하고, 클러스터 내부용 ClusterIP 8080 → 80도 만든다.
```bash
k -n lab get deploy web --show-labels                      # 라벨 확인: app=web
k -n lab expose deploy web --name=web-svc --type=NodePort --port=80 --target-port=80 --dry-run=client -o yaml > web-svc.yaml
vim web-svc.yaml                                           # ports[0]에 nodePort: 30080 추가
k -n lab apply -f web-svc.yaml
k -n lab expose deploy web --name=web-internal --port=8080 --target-port=80
```
```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: NodePort
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
    nodePort: 30080
```
```bash
k -n lab get svc web-svc web-internal -o wide
k -n lab get endpointslice -l kubernetes.io/service-name=web-svc
```
기대 결과: `web-svc  NodePort  10.96.x.x  <none>  80:30080/TCP  ... app=web`, `web-internal  ClusterIP  ... 8080/TCP`, EndpointSlice의 ENDPOINTS에 Pod IP 3개. `k expose`는 Deployment의 selector를 그대로 가져옵니다(검증: `app=web`).

상황 2: `k create svc`로 빠르게 만들고 selector를 고친다 (`--node-port` 지원).
```bash
k -n lab create svc nodeport web-np --tcp=80:80 --node-port=30310
k -n lab get endpointslice -l kubernetes.io/service-name=web-np      # ENDPOINTS <unset>: selector가 app=web-np로 잡혔기 때문
k -n lab set selector svc web-np app=web
k -n lab get endpointslice -l kubernetes.io/service-name=web-np      # Pod IP 3개
```
`k create svc`는 selector를 항상 `app=<Service 이름>`으로 만들고, 포트 이름을 `80-80`처럼 자동으로 붙입니다.

상황 3: LoadBalancer, headless, ExternalName.
```bash
k -n lab create svc loadbalancer web-lb --tcp=80:80 && k -n lab set selector svc web-lb app=web
k -n lab get svc web-lb          # EXTERNAL-IP <pending>, PORT(S) 80:31484/TCP (nodePort는 자동 할당)
k -n lab create svc clusterip web-headless --clusterip=None --tcp=80:80 && k -n lab set selector svc web-headless app=web
k -n lab get svc web-headless    # CLUSTER-IP None
```
```yaml
apiVersion: v1
kind: Service
metadata:
  name: ext
spec:
  type: ExternalName
  externalName: my.database.example.com
```
확인(Pod 안에서): `nslookup web-headless.lab.svc.cluster.local`은 Pod IP 3개, `nslookup -type=CNAME ext.lab.svc.cluster.local`은 `canonical name = ...`을 돌려줍니다.

상황 4: 멀티 포트 + 이름 있는 targetPort, 세션 고정, externalTrafficPolicy.
```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  ports:
  - {name: web, port: 8080, targetPort: http}   # Pod의 containerPort 이름이 http
  - {name: alt, port: 9090, targetPort: 80}
```
```bash
k -n lab patch svc web-svc -p '{"spec":{"sessionAffinity":"ClientIP","sessionAffinityConfig":{"clientIP":{"timeoutSeconds":600}},"externalTrafficPolicy":"Local"}}'
k -n lab get svc web-svc -o jsonpath='{.spec.sessionAffinity} {.spec.externalTrafficPolicy}{"\n"}'   # ClientIP Local
```
상황 5: 접근 테스트.
```bash
k get nodes -o wide                                   # INTERNAL-IP 확인
curl -s http://<노드IP>:30080 | grep -o '<title>.*</title>'     # <title>Welcome to nginx!</title>
k -n lab run tmp --rm -i --restart=Never --image=busybox:1.37 -- wget -qO- -T3 http://web-internal:8080
```
**시뮬레이터 차이**: (1) LoadBalancer는 EXTERNAL-IP가 계속 `<pending>`입니다. (2) 시뮬레이터 터미널에서 ClusterIP는 닿지 않고 `노드IP:nodePort`만 닿습니다(검증: 200 / ClusterIP는 연결 실패). (3) 서버는 v1.34.0, 시험은 v1.37이라 `kubectl explain` 출력이 조금 다를 수 있습니다. (4) 한때 `k8s-worker2`의 CNI 설정 대역이 노드 podCIDR와 어긋나 그 노드 Pod의 DNS/노드 간 통신이 실패한 적이 있다(랩 고장, 시험과 무관, 수정됨). 같은 증상이 다시 나오면 `kubectl --context k8s -n kube-system delete pod -l app=kindnet --field-selector spec.nodeName=k8s-worker2`로 kindnet을 재생성하거나 `bin/sim doctor`로 점검한다.

## 공식 문서에서 찾는 법
| 하고 싶은 일 | 사이트 검색창에 칠 검색어 | 문서 URL | 페이지에서 Ctrl+F로 찾을 단어 | 복사할 블록 |
|---|---|---|---|---|
| Service 기본 YAML(selector, port, targetPort) | `service` | https://kubernetes.io/docs/concepts/services-networking/service/ | `Defining a Service` | 바로 아래 첫 YAML (`my-service`, selector `app.kubernetes.io/name: MyApp`, port 80, targetPort 9376) |
| NodePort 포트 고정 | `service nodeport` | 같은 페이지 | `Choosing your own port` (또는 `nodePort: 30007`) | `type: NodePort` 절의 YAML (`nodePort: 30007`) |
| LoadBalancer 타입 | `service loadbalancer` | 같은 페이지 | `type: LoadBalancer` | 첫 YAML (`type: LoadBalancer`; `status.loadBalancer`는 컨트롤러가 채우므로 빼도 됨) |
| 멀티 포트(이름 필수) | `service multi-port` | 같은 페이지 | `Multi-port Services` | `name: http` / `name: https` 두 포트 YAML |
| ExternalName | `service externalname` | 같은 페이지 | `type: ExternalName` | `externalName: my.database.example.com` YAML |
| Headless | `headless service` | 같은 페이지 | `Headless Services` | 별도 YAML 없음, `spec.clusterIP: None` 한 줄만 추가 |
| 세션 고정 / 트래픽 정책 | `service session affinity` | 같은 페이지 | `Session stickiness`, `Traffic policies` | 설명문만 있음, 필드명 `sessionAffinity`, `externalTrafficPolicy`는 `k explain svc.spec`로도 확인 |
| EndpointSlice 구조와 라벨 | `endpointslices` | https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/ | `kubernetes.io/service-name` | 첫 EndpointSlice YAML (`example-abc`) |
| 연결이 안 될 때 점검 순서 | `debug service` | https://kubernetes.io/docs/tasks/debug/debug-application/debug-service/ | `Does the Service have any EndpointSlices?` | 그 절의 `kubectl get endpointslices -l kubernetes.io/service-name=...` 류 명령 |
| expose 후 확인 명령 예제 | `connecting applications with services` | https://kubernetes.io/docs/tutorials/services/connect-applications-service/ | `Creating a Service` | `kubectl expose deployment/my-nginx`, `kubectl get endpointslices -l kubernetes.io/service-name=my-nginx` |

## 자주 틀리는 점
- 증상: `k create svc`로 만들었는데 접속이 안 되고 ENDPOINTS가 `<unset>` → 원인: selector가 자동으로 `app=<Service 이름>`이 됨 → 고침: `k get pods --show-labels`로 실제 라벨 확인 후 `k set selector svc NAME app=web`. (`k expose deploy`는 Deployment selector를 자동으로 가져와서 이 문제가 없음)
- 증상: `k expose --node-port=30080`이 `unknown flag` → 원인: expose에는 해당 플래그가 없음 → 고침: `--dry-run=client -o yaml`로 뼈대를 만들어 `nodePort` 추가, 또는 `k create svc nodeport --node-port=`.
- 증상: `provided port is not in the valid range. The range of valid ports is 30000-32767` / `provided port is already allocated` → 원인: 범위 밖이거나 다른 Service가 사용 중 → 고침: 다른 값을 쓰거나 `k get svc -A | grep 30080`으로 충돌 Service 확인.
- 증상: Endpoints는 있는데 `Connection refused` → 원인: `targetPort`가 컨테이너가 듣는 포트와 다름(검증: 8081로 만들면 EndpointSlice PORTS가 8081) → 고침: `targetPort`를 containerPort로.
- 증상: ENDPOINTS가 비어 있고 접속하면 즉시 `Connection refused` → 원인: Pod가 NotReady(readinessProbe 실패)이거나 selector 불일치 → 고침: `k get pods --show-labels`, `k describe pod`의 `Readiness probe failed`, EndpointSlice의 `ready: false` 확인.
- 증상: `spec.ports[0].name: Required value` → 원인: 포트가 2개 이상인데 `name`이 없음 → 고침: 모든 포트에 소문자 이름.
- 증상: `k get ep`에서 `Warning: v1 Endpoints is deprecated` → 원인: 정상 경고 → `k get endpointslice`를 쓰면 경고 없음.
- 증상: 방금 만든 NodePort가 `Connection refused` → 원인: kube-proxy 규칙 반영 지연(검증: 생성 직후 거부, 약 5초 뒤 200) → 고침: 몇 초 뒤 재시도.
- 증상: busybox `nslookup web.lab`이 NXDOMAIN → 원인: busybox 1.37의 nslookup은 점이 있는 이름에 search 도메인을 붙이지 않음(`wget http://web.lab`은 성공, 검증됨) → 고침: FQDN(`web.lab.svc.cluster.local`) 사용 (C6 노트 참고).
- 증상: LoadBalancer의 EXTERNAL-IP가 `<pending>` → 원인: LB 구현이 없는 클러스터에서는 정상 → spec만 확인.
- "Deployment/Pod는 수정하지 말 것" 같은 제약을 놓치지 말기: q27은 Deployment `web`과 Pod `tester`를 수정하지 말라고 합니다. selector가 안 맞을 때 Pod 라벨을 바꾸지 말고 Service 쪽을 고치세요.

## 빠르게 푸는 순서
1. (30초) 문제의 네임스페이스, Service 이름, 타입, port/targetPort/nodePort 숫자를 적는다.
2. (30초) `k -n NS get deploy NAME --show-labels` 또는 `k get pods --show-labels`로 selector로 쓸 라벨 확인.
3. (1분) `k expose deploy NAME --name=... --type=... --port=... --target-port=... --dry-run=client -o yaml > svc.yaml`.
4. (1분) nodePort/멀티 포트처럼 플래그로 안 되는 필드는 YAML을 열어 추가 (`vim`), 막히면 문서 `Choosing your own port`의 YAML 참고.
5. (30초) `k apply -f svc.yaml`, 에러 메시지(범위/중복/이름 필수)를 그대로 읽고 수정.
6. (1분) `k get svc -o wide`, `k get endpointslice -l kubernetes.io/service-name=NAME`으로 ENDPOINTS 개수가 Pod 수와 같은지 확인.
7. (1분) `curl 노드IP:nodePort` 또는 `k run tmp --rm -i --restart=Never --image=busybox:1.37 -- wget -qO- -T3 http://NAME:PORT`로 실제 응답 확인.
목표: 쉬운 문제는 5분 이내.
