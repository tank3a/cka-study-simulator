# D3. Configure workload autoscaling

## 이 항목에서 공부할 것
- [ ] `k autoscale deploy <이름> --min=N --max=M --cpu=50%`로 HPA를 만들고, `k get hpa`의 TARGETS가 숫자(예: `cpu: 0%/50%`)인지 확인한다
- [ ] TARGETS가 `<unknown>`이면 `k describe hpa`의 Conditions 메시지를 읽고, requests가 없는 경우 `k set resources`로 고친다
- [ ] `--dry-run=client -o yaml`로 HPA 뼈대를 뽑고, 문서의 `behavior` 블록(`stabilizationWindowSeconds`, `policies`)을 붙여 autoscaling/v2 YAML을 완성한다
- [ ] 메트릭을 둘 이상(cpu + memory) 또는 `ContainerResource`(특정 컨테이너만)로 지정한다
- [ ] 부하를 주고 `k get hpa -w`로 replicas가 늘고, 부하를 끊으면 줄어드는 것을 확인한다
- [ ] `Utilization`(요청 대비 %)과 `AverageValue`(절대값)의 차이를 알고, `--cpu=50`과 `--cpu=50%`가 다른 객체를 만든다는 것을 안다
- [ ] VerticalPodAutoscaler YAML(`targetRef`, `updatePolicy.updateMode`, `resourcePolicy`)을 문서에서 복사해 작성한다 (`Off`는 따옴표)

## 개념 설명

### HorizontalPodAutoscaler (HPA)
- 무엇: Deployment/StatefulSet/ReplicaSet의 `replicas`를 메트릭에 따라 자동으로 늘리고 줄이는 객체. kube-controller-manager 안의 컨트롤러가 기본 15초마다 한 번씩 계산한다 (문서: `--horizontal-pod-autoscaler-sync-period` 기본 15초).
- 왜: 트래픽이 몰릴 때 사람이 `k scale`을 치지 않아도 Pod 수가 맞춰져야 하기 때문.
- 핵심 필드 (`autoscaling/v2`):
  - `scaleTargetRef`: 누구를 조절할지 (`apiVersion`, `kind`, `name`). 네임스페이스 필드는 없고, **HPA와 같은 네임스페이스**의 대상만 가리킨다.
  - `minReplicas` / `maxReplicas`: 하한/상한. `minReplicas` 기본값 1.
  - `metrics[]`: 무엇을 기준으로 할지 (아래 "메트릭 종류").
  - `behavior`: 올리고 내리는 속도 제한 (아래).
- 계산식 (문서): `desiredReplicas = ceil(currentReplicas x 현재값 / 목표값)`. 비율이 1.0에 가까우면(기본 오차 10%) 아무것도 안 한다. 예: 목표 50%인데 현재 200%면 replicas가 4배가 되려 하고, `maxReplicas`에서 잘린다.
- 관계: HPA는 Deployment의 `spec.replicas`를 직접 덮어쓴다. 그래서 문서는 HPA를 쓸 때 매니페스트에서 `spec.replicas`를 빼라고 권한다 (`kubectl apply` 할 때마다 그 값으로 되돌려지기 때문).
- 비유: 에어컨 온도 조절기. 설정 온도(목표 50%)와 현재 온도(평균 CPU)를 비교해서 바람 세기(Pod 수)를 바꾼다.

### 메트릭 파이프라인: metrics-server와 `resources.requests`
- HPA의 CPU/메모리 값은 metrics-server(`metrics.k8s.io` API)에서 온다. `k top pod`이 되면 파이프라인은 정상이다.
- `Utilization`은 "**requests 대비** 사용량 %"이다. 그래서 컨테이너에 `resources.requests.cpu`가 없으면 분모가 없어서 계산할 수 없다. 이것이 시험에서 가장 흔한 함정이다 (q09의 핵심).
- 새 Pod는 metrics-server가 첫 수집을 할 때까지 약 1분은 값이 비어 있다. 이때의 `<unknown>`은 정상이고, requests 문제와는 메시지로 구분한다 (아래 "자주 틀리는 점").

### 메트릭 종류
| `type` | 의미 | 목표 필드 |
|---|---|---|
| `Resource` | Pod 전체의 cpu/memory | `Utilization`(requests 대비 %) 또는 `AverageValue`(예: `500m`, `200Mi`) |
| `ContainerResource` | Pod 안 **한 컨테이너**의 cpu/memory (사이드카 제외하고 싶을 때) | 위와 같고 `container: <이름>` 추가 |
| `Pods` / `Object` / `External` | 사용자 정의/외부 메트릭 (별도 어댑터 필요) | 문서 예제를 복사. 이 클러스터에서는 어댑터가 없어 실행해 보지 않았다 (미확인) |
- 메트릭이 여러 개면 각각 계산한 replicas 중 **가장 큰 값**을 쓴다 (문서: "Scaling on multiple metrics").

### behavior (스케일 속도 제한)
- `scaleUp` / `scaleDown` 각각에 `stabilizationWindowSeconds`, `policies[]`(`type: Pods|Percent`, `value`, `periodSeconds`), `selectPolicy`(`Max` 기본, `Min`, `Disabled`)를 둔다.
- 기본값 (문서): 내릴 때는 안정화 창 300초(그동안의 최고 추천값 사용) + 15초에 100%까지 허용, 올릴 때는 창 0초 + 15초에 100% 또는 4 Pod 중 큰 값. 그래서 부하가 사라져도 **기본 5분은** 안 줄어든다.
- 일부만 적어도 된다. 적은 값만 기본값 위에 덮어쓴다.
- 정책이 여러 개면 기본은 "가장 많이 바꿔 주는 정책"이 이긴다 (`selectPolicy: Max`).
- `tolerance`(오차 허용 %)는 문서(v1.37)에서 안정 기능이다. 이 시뮬레이터(v1.34)에서는 알파 기능 게이트가 필요하다고 `k explain`에 나온다 (시뮬레이터 차이).

### VerticalPodAutoscaler (VPA)
- 무엇: Pod 개수가 아니라 **각 Pod의 requests/limits**를 사용 기록에 맞춰 조정하는 객체. 코어 API가 아니라 **CRD이고 따로 설치해야** 한다 (문서). `apiVersion: autoscaling.k8s.io/v1`.
- 구성 요소 (문서): recommender(추천값 계산, `.status.recommendation`에 저장), updater(Pod를 evict하거나 제자리 수정), admission webhook(새 Pod에 추천값 주입).
- `spec.updatePolicy.updateMode`: `Off`(추천만 기록), `Initial`(Pod 생성 시에만 적용), `Recreate`(evict 후 재생성), `InPlaceOrRecreate`, `InPlace`, `Auto`(deprecated, `Recreate`와 같음).
- `spec.resourcePolicy.containerPolicies[]`: `containerName`, `minAllowed`, `maxAllowed`, `controlledResources`, `controlledValues`.
- 시뮬레이터: VPA CRD는 q61/q62가 만든 **스키마 없는 껍데기**(`x-kubernetes-preserve-unknown-fields`)라 필드 오타도 통과하고, recommender가 없어 `.status.recommendation`이 채워지지 않는다 (low fidelity).

## 예시

**상황 1: Deployment `web`에 HPA를 만든다 (min 2, max 5, CPU 50%). Pod에 requests가 아직 없다.**
```bash
k create deploy web --image=nginx:1.27 --replicas=2      # 시험에서는 이미 있음
k autoscale deploy web --min=2 --max=5 --cpu=50%
k get hpa
```
기대 결과 (requests가 없을 때):
```
NAME   REFERENCE        TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
web    Deployment/web   cpu: <unknown>/50%   2         5         0          0s
```
`k describe hpa web`의 Conditions: `ScalingActive False FailedGetResourceMetric ... missing request for cpu in container nginx of Pod web-...`.

**상황 2: 위 `<unknown>`을 고친다 (requests 추가 -> 롤아웃).**
```bash
k set resources deploy web --requests=cpu=100m,memory=64Mi
k rollout status deploy web
k get hpa                      # 약 1분 뒤
```
기대 결과: `web   Deployment/web   cpu: 0%/50%   2   5   2`. Conditions는 `ScalingActive True ValidMetricFound`. 처음 몇 분 `AbleToScale ... ScaleDownStabilized`는 정상 메시지다.

**상황 3: 뼈대를 뽑아 YAML로 `behavior`를 넣는다 (내릴 때 60초 안정화, 30초에 1 Pod씩; 올릴 때 30초에 2 Pod씩).**
```bash
k autoscale deploy burn --min=1 --max=4 --cpu=50% --dry-run=client -o yaml > hpa.yaml   # 뼈대 (맨 아래 status 줄은 있어도 된다)
vim hpa.yaml     # spec 아래에 behavior 추가
k apply -f hpa.yaml
```
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: burn
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: burn
  minReplicas: 1
  maxReplicas: 4
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60
      policies:
      - type: Pods
        value: 1
        periodSeconds: 30
    scaleUp:
      policies:
      - type: Pods
        value: 2
        periodSeconds: 30
```
실제로 CPU를 태우는 Deployment(requests 100m, limits 200m)에 걸어 본 결과: HPA 생성 약 40초 뒤 `cpu: 201%/50%`, 60초 뒤 REPLICAS 1 -> 3(30초에 2 Pod 제한), 80초 뒤 4(maxReplicas). 부하를 끊자 약 40초 뒤 4 -> 3, 이후 30초마다 하나씩 2 -> 1. `k describe hpa burn`의 Events에 `SuccessfulRescale ... above target` / `All metrics below target`이 남는다. 확인은 `k get hpa burn -w`.

**상황 4: 메모리도 함께, 그리고 `nginx` 컨테이너만 CPU 기준으로.**
```yaml
  metrics:
  - type: ContainerResource
    containerResource:
      name: cpu
      container: nginx
      target:
        type: Utilization
        averageUtilization: 60
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 200Mi
```
`k apply --dry-run=server`로 검증했다 (필드 이름 통과). 한 줄로 쓰고 싶으면 `k autoscale deploy web --min=2 --max=6 --cpu=60% --memory=70%` (cpu, memory 두 `Resource` 메트릭이 생김).

**상황 5: VPA를 추천 전용(Off)으로, 컨테이너별 하한/상한을 둔다.**
```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  updatePolicy:
    updateMode: "Off"          # 따옴표 필수
  resourcePolicy:
    containerPolicies:
    - containerName: "*"
      minAllowed: {cpu: 50m, memory: 64Mi}
      maxAllowed: {cpu: "1", memory: 1Gi}
```
```bash
k apply -f vpa.yaml
k get vpa web-vpa -o jsonpath='{.spec.updatePolicy}{"\n"}'     # {"updateMode":"Off"} 이어야 한다
```
시뮬레이터에서는 CRD 껍데기라 `k apply`만 통과를 확인했다. 실제 추천값(`.status.recommendation`)은 확인하지 못했다 (미확인).

## 자주 틀리는 점
- `TARGETS`가 `cpu: <unknown>/50%`, REPLICAS가 0 또는 안 변함 -> `k describe hpa`의 Conditions에 `missing request for cpu in container <이름> of Pod ...` -> Pod 템플릿에 `resources.requests.cpu`가 없다 -> `k set resources deploy <d> --requests=cpu=100m` 후 롤아웃 (확인함).
- 같은 `<unknown>`인데 Events에 `no metrics returned from resource metrics API` / `did not receive metrics for targeted pods` -> 만든 직후 또는 Pod가 방금 떠서 아직 수집 전 -> 1분쯤 기다린다. 계속되면 `k top pod`이 되는지, `k get apiservices | grep metrics`가 `True`인지 본다 (이 둘이 안 되면 A3 항목).
- `k autoscale ... --cpu=50`이라고 쳤더니 목표가 `50m` 절대값 -> `%`를 빼면 `AverageValue: 50m`이 된다 (`--dry-run=client -o yaml`로 확인함). 퍼센트는 `--cpu=50%`.
- `--cpu-percent=50`은 kubectl v1.34.1에서 "deprecated" 경고가 나오지만 동작한다. v1.37에서 제거됐는지는 확인하지 못했다 (미확인). `--cpu=50%`만 쓴다.
- HPA를 만들었는데 `REFERENCE`가 `Deployment/nope`, REPLICAS 0 -> `scaleTargetRef.name` 오타 또는 다른 네임스페이스에 만들었다 (HPA는 같은 네임스페이스만 가리킨다). `-n`을 확인한다.
- 부하를 껐는데 5분 동안 Pod가 안 줄어든다 -> `scaleDown` 기본 안정화 창 300초. 문제가 "빨리 줄여라/60초 후에 줄여라"면 `behavior.scaleDown.stabilizationWindowSeconds`를 지정한다.
- `kubectl apply -f deploy.yaml`을 다시 하면 replicas가 원래 값으로 돌아간다 -> HPA가 있으면 매니페스트에서 `spec.replicas`를 뺀다 (문서 권고, 직접 재현하지는 않았다).
- VPA YAML에서 `updateMode: Off`가 `false`로 저장된다 -> YAML이 `Off`를 불리언으로 읽는다. 따옴표 `"Off"` (확인함: `{"updateMode":false}`). 진짜 VPA CRD라면 타입 오류로 거부될 수 있다.
- 시뮬레이터 차이: 클러스터는 v1.34.0(시험 문서는 v1.37). metrics-server는 `--kubelet-insecure-tls`로 돌고, VPA는 컨트롤러 없는 껍데기 CRD다. `behavior.tolerance`는 v1.34에서 알파 게이트가 필요하다.

## 빠르게 푸는 순서
1. (30초) 문제의 Deployment 이름, 네임스페이스, 컨텍스트 확인. `k get deploy -n <ns> <d> -o yaml | grep -A6 resources`로 requests 유무부터 본다.
2. (30초) requests가 없으면 `k set resources deploy <d> -n <ns> --requests=cpu=100m` (문제가 값을 정했으면 그 값). 롤아웃이 한 번 일어난다.
3. (30초) 단순 요구면 `k autoscale deploy <d> -n <ns> --min=A --max=B --cpu=N%` 한 줄로 끝. 이름을 지정하라면 `--name=<hpa이름>`.
4. (2분) `behavior`, memory, ContainerResource가 있으면 `--dry-run=client -o yaml > hpa.yaml`로 뼈대를 만들고 문서의 `behavior:` 블록을 붙여 `k apply -f`.
5. (30초) `k get hpa -n <ns>`에서 TARGETS가 숫자인지 확인. `<unknown>`이면 1분 기다린 뒤 `k describe hpa`.
6. (30초) 요구한 필드를 `k get hpa <h> -n <ns> -o yaml | grep -A12 behavior`처럼 다시 확인. (총 약 5분)
7. VPA 문제는 문서 `Update modes` 예제를 복사해 `targetRef`/`updateMode`/`containerPolicies`만 바꾸고 `"Off"` 따옴표를 확인한다.

## 연습 문제
- **오늘 풀 문제** (study-guide.md 5절 Day 4):
  - `q09` — HPA with behavior (missing requests trap): requests가 없어서 `<unknown>`인 Deployment에 HPA(min 2, max 8, CPU 60%, 안정화 30초)를 만든다.
- **추가 연습**:
  - `q14` — topologySpreadConstraints + rollout strategy + HPA (hard, 가중치 7): HPA를 다른 스케줄링 요구와 함께 푼다.
  - `q61` — VPA in recommendation-only mode with bounds (low fidelity): 껍데기 CRD에 `Off` 모드 VPA 작성.
  - `q62` — Repair a VPA: target, Initial mode, per-container policy (hard, low fidelity).
- 주의: q09, q14는 metrics-server가 필요하고, q105/q106(metrics-server를 건드림)과 같은 세트에 넣지 않는다 (INDEX.md 충돌 목록).
